#### <a id="d-01"></a>🟠 D-01. Неверная сумма в PUT: два разных message в ответе 400

**Требования:** [R-24](#r-24 "При неверных данных настройка прежняя, ответ 400") (При неверных данных настройка прежняя, ответ 400), [R-39](#r-39 "Код 400 — параметры запроса заполнены неверно") (Код 400 — параметры запроса заполнены неверно) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, архитектор

- Часть B › Логика работы метода, строка 127: «вернуть HTTP 400 с result ERROR и message «Проверьте сумму»
- Часть B › Статусы, строка 169: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 400. Unsuccessful — Bad request, строка 185: «{"result":"ERROR","message":"Некорректный запрос"}»

**Проблема.** Логика метода (строка 127) требует для неверной суммы или enabled message «Проверьте сумму», а перечень статусов и пример 400 (строка 169, строка 185) дают «Некорректный запрос». Условие, при котором применяется «Некорректный запрос», не названо.  
**Сценарий.** PUT с enabled=1 и amount=999: по строке 127 клиент получает «Проверьте сумму», по строке 185 — «Некорректный запрос».  
**Последствия.** Разные тексты под полем на экране, тесты и клиент расходятся при приёмке.  
**Что исправить.** Оставить в примере 400 общий случай только для ошибок структуры запроса (например, не JSON) с явным условием, а для неверных amount и enabled закрепить «Проверьте сумму»; привести строка 169 и строка 185 в соответствие с строки 127.

#### <a id="d-02"></a>🟠 D-02. Ссылка на исходную операцию клиринга не входит в хранимые данные

**Требования:** [R-06 / Ф-2](#r-06 "Правила учёта расходов месяца по типам операций") (Правила учёта расходов месяца по типам операций), [R-09](#r-09 "Взаимодействие процессинга, сервиса расходов, настроек и push") (Взаимодействие процессинга, сервиса расходов…), [R-12](#r-12 "Перечень хранимых данных и единицы сумм") (Перечень хранимых данных и единицы сумм) · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** неполнота · **Блокирует:** разработку и тестирование · **Нашли:** риски

- Часть A › Функциональные требования, строка 41: «расходы месяца исходной покупки изменяются на разницу»
- Часть A › Sequence Diagram, строка 46: «ссылку на исходную операцию для отмены, клиринга и возврата»
- Часть A › Требования к данным, строка 53: «идентификатор исходной операции для отмены и возврата»

**Проблема.** Событие клиринга несёт ссылку на исходную операцию (строка 46), а правило Ф-2 требует изменить расходы месяца исходной покупки, но в данных (строка 53) идентификатор исходной операции хранится только для отмены и возврата.  
**Сценарий.** Авторизация 4 000 ₸ одобрена 31 января в 23:58, клиринг на 4 200 ₸ пришёл 1 февраля: без хранимой связи разницу 200 ₸ нельзя отнести к январю.  
**Последствия.** Неверные расходы месяца, лишний или пропущенный push, спор при приёмке.  
**Что исправить.** Записать в строке 53: «идентификатор исходной операции для отмены, клиринга и возврата».  
**Было → стало.** Строка 53: «идентификатор исходной операции для отмены и возврата» → «Хранить идентификатор исходной операции для отмены, клиринга и возврата, а также сумму и месяц исходной операции.»  
**Вопрос владельцу.** Что делать с клирингом, для которого исходная авторизация в хранилище не найдена? → [Q-01](#q-01)

**Обоснование.** Критичных дефектов нет, но существенных шесть, поэтому разработку и тестирование можно начинать только с условиями. Первым делом нужно устранить [D-01](#d-01) (два разных message для ошибки 400 при неверной сумме: строка 127 и строка 185). После этого определить amount при несохранённой настройке ([D-04](#d-04)) и в ответе PUT при enabled = 0 ([D-05](#d-05)).

**Что исправить в первую очередь**

1. 🟠 [D-01](#d-01) Неверная сумма в PUT: два разных message в ответе 400. Что сделать: оставить в примере 400 общий случай только для ошибок структуры запроса (например, не JSON) с явным условием, а для неверных amount и enabled закрепить «Проверьте сумму»; привести строка 169 и строка 185 в соответствие с строки 127.
2. 🟠 [D-02](#d-02) Ссылка на исходную операцию клиринга не входит в хранимые данные. Что сделать: записать в строке 53: «идентификатор исходной операции для отмены, клиринга и возврата».
3. 🟠 [D-03](#d-03) Последние четыре цифры карты для push нигде не хранятся и не передаются. Что сделать: указать источник последних четырёх цифр, добавить атрибут в данные и описать контракт вызова к настройкам с этим полем.
4. 🟠 [D-04](#d-04) Не задан amount в GET для карты без сохранённого порога. Что сделать: определить значение amount (или отсутствие поля) при несохранённой настройке: <уточнить: значение amount при несохранённой настройке>.
5. 🟠 [D-05](#d-05) Ответ PUT при enabled = 0 без amount не определён. Что сделать: задать значение amount в ответе для этой ветки.
6. 🟠 [D-06](#d-06) Недоставленные события и срок ключей дедупликации не покрыты данными. Что сделать: добавить в раздел данных статус доставки события, ключ дедупликации со сроком 35 дней и правило обработки недоставленных.

**<a id="q-01"></a>Q-01** Клиринг без найденной исходной авторизации · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)  
Как учитывать клиринг, если исходная авторизация покупки в хранилище не найдена (например, события потеряны или клиринг пришёл позже срока хранения)?  
Где: строка 46 «ссылку на исходную операцию для отмены, клиринга и возврата»; строка 41 «Возврат по покупке, которой нет в хранилище, не меняет расходы.»

- **A** Клиринг без найденной авторизации расходы не меняет, событие фиксируется как ошибка для разбора
- **B** Клиринг без найденной авторизации учитывается как новая покупка на всю сумму клиринга в месяце даты клиринга (UTC+5)
- **C** Клиринг без найденной авторизации учитывается только если сумма клиринга больше нуля, в месяце даты клиринга (UTC+5); иначе не меняет расходы

Зачем: Без правила две команды по-разному обработают клиринг с неизвестной авторизацией: одна проигнорирует, другая добавит в расходы. Это меняет счётчик и момент отправки push, а тест такого сценария написать нельзя.

**<a id="q-02"></a>Q-02** Источник последних четырёх цифр карты для push · ⛔ блокирует · кому: Архитектор · к [D-03](#d-03)  
Какая система является источником последних четырёх цифр карты для текста push и в каком вызове и поле они передаются сервису расходов?  
Где: строка 46 «получить порог карты и последние четыре цифры карты»; строка 53 «Хранить идентификатор карты, месяц, идентификатор операции, тип операции»

- **A** Сервис настроек хранит последние четыре цифры карты и отдаёт их в ответе на вызов сервиса расходов вместе с порогом
- **B** Процессинг передаёт последние четыре цифры карты в каждом событии, сервис расходов их не хранит
- **C** Сервис расходов запрашивает последние четыре цифры у карточного процессинга при отправке push отдельным вызовом

Зачем: Без источника и контракта нельзя собрать текст «Расходы по карте *1234 …»: разработчики не знают, откуда брать цифры и что хранить, а тест текста push написать нельзя.

**<a id="q-03"></a>Q-03** Значение порога, если он ни разу не сохранялся · не блокирует · кому: Архитектор · к [D-04](#d-04), [D-05](#d-05)  
Что возвращают метод чтения настроек и метод сохранения порога в поле amount, если порог по карте ещё ни разу не сохранён (новая карта, либо сохранение с enabled = 0 без amount)?  
Где: строка 238 «Если порог не сохранён: <уточнить: значение amount при несохранённой настройке>»; строка 125 «при enabled = 0 параметр amount необязателен и не проверяется, сохранённый порог не…»

- **A** Поле amount в ответе отсутствует, на экране поле «Порог, ₸» пустое
- **B** Поле amount равно null, на экране поле «Порог, ₸» пустое
- **C** Поле amount равно 1 000 (минимальный порог), на экране показывается 1 000

Зачем: Без решения фронтенд и бэкенд по-разному трактуют ответ для новой карты (0, null, отсутствие поля), нельзя написать тест первого открытия экрана и ответ сохранения с enabled = 0.

**<a id="q-04"></a>Q-04** Судьба недоставленных событий и хранение статуса · не блокирует · кому: Архитектор · к [D-06](#d-06)  
Что происходит с событием, помеченным недоставленным после исчерпания повторов, и где хранится эта пометка вместе со сроком ключей дедупликации?  
Где: строка 50 «после этого событие помечается недоставленным»; строка 57 «ключи хранятся 35 дней»

- **A** Событие хранится со статусом «недоставлено», повторная отправка выполняется автоматически каждые 5 минут до 24 часов, затем событие фиксируется для ручного разбора
- **B** Событие хранится со статусом «недоставлено» 35 дней вместе с ключом дедупликации и только фиксируется для мониторинга, без повторной отправки
- **C** Событие хранится со статусом «недоставлено», повторная отправка запускается вручную оператором в течение 35 дней

Зачем: Без правила клиент может не получить push по достигнутому порогу, а в данных нет места для статуса; тест на недоступность сервиса уведомлений нельзя написать.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
