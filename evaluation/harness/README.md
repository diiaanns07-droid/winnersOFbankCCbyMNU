# Счётчик качества (`evaluation/harness`, протокол bcc-eval v1)

Модуль №16. Он считает TP, FP, FN, дубли и ложные тревоги на чистых документах по эталону
и предсказаниям продукта и сравнивает режимы `rules_only` и `rules_plus_llm`.
Счётчик не обращается к LLM. Зависимости: стандартная библиотека Python 3.11+;
для PDF/DOCX в генераторе — reportlab, python-docx, pdfplumber.

```bash
python -m evaluation.harness --gold labels.jsonl --pred predictions.jsonl --out metrics.json
```

## Одна команда для закрытого корпуса

```bash
python -m evaluation.harness run --gold CLOSED/labels.jsonl --docs CLOSED/docs --mode rules_only --out out/closed
```

Команда сопоставляет файлы из `--docs` с кейсами по SHA-256 (`source_sha256` эталона), запускает
`python -m bcc_review` на каждом файле и считает результат. Манифест строится сам, правки кода не нужны.
Нужен checkout `bcc/integration` с установленным пакетом (`pip install -e .`).

Результаты в `out/closed/` (все машиночитаемые):

| Файл | Что внутри |
| :--- | :--- |
| `metrics.json` | TP/FP/FN, precision/recall/F1 (null при пустом знаменателе), по типам, кейсам и форматам; пропуски измерения; режим; `harness_sha256`, `policy_version` |
| `matrix.jsonl` | фактическая матрица: строка на каждый TP (`label_id` ↔ `defect_id`), DUP (`kept_defect_id`), FP (`reasons`, `disputed_with`), FN (`near_miss_defect_ids`) |
| `adjudication.jsonl` | лист разбора по всем FP: поле `decision` заполняет человек |
| `summary.txt` | сводка: кейсы, пропуски, режим, правило типов, версия счётчика |
| `predictions.jsonl`, `manifest.json`, `run_config.json`, `reports/` | вход подсчёта и отчёты продукта; `reports/index.json` связывает короткие каталоги с `render_id` |

* Файл без пары в эталоне указан в выводе как лишний.
* Кейс без файла попадает в пропуски измерения.
* Готовые предсказания считаются той же логикой:
  `python -m evaluation.harness --gold … --pred … [--manifest …] --out-dir DIR`.
* Каталоги отчётов называются 12 hex от `render_id`, а не самим `render_id`. С артефактами движка
  относительный путь не длиннее 80 символов, а длинные пути на Windows давали WinError 206.

| Подкоманда | Что делает |
| :--- | :--- |
| *(без подкоманды)* | подсчёт: `--gold --pred --out [--manifest] [--adjudication] [--adjudication-out] [--type-match hierarchy\|exact] [--render-format md\|pdf\|docx] [--mode] [--status]` |
| `run` | прогон продукта по манифесту: `--manifest --mode rules_only\|rules_plus_llm\|mock --out DIR [--format] [--provider] [--cache off\|on] [--cases] [--gold]` |
| `adapt` | `report.json` продукта (контракт v1) → `predictions.jsonl` |
| `adapt-labels` | плоские метки (`defect_id, type, criterion, severity, quote, line/locator, related_quote, explanation`) → эталон с `anchors` |
| `compare` | таблица режимов: `--metrics rules_only=A/metrics.json --metrics rules_plus_llm=B/metrics.json --out compare.md` |
| `selfcheck` | контрольная арифметика: ручной ответ (`controls/*/expected.json`) против счётчика, все перестановки строк, повтор формата |
| `python -m evaluation.harness.audit` | состав прогонов до подсчёта: пары по ID и SHA, пропуски, повторы, режим, покрытие LLM (раздел ниже) |
| `--version` | версия счётчика, версия политики и `harness_sha256` (хеш `*.py` и `taxonomy.toml`) |
| `fingerprint`, `leakcheck` | проверка, что закрытые ответы не попали в открытый dev-набор (по хешам) |

Коды выхода: 0 — успешно, 2 — ошибка формата входа (сообщение называет файл, строку и поле),
3 — `compare`: режимы несопоставимы, 1 — `leakcheck`: найдена утечка.

## Форматы

**Эталон** (`labels.jsonl`, одна строка на дефект или на кейс). Обязательные поля, общие с GPT Pro:
`case_id, family, source_sha256, issue_type, anchors, expected_outcome`.

```json
{"label_id": "cashback.unit_change.cap_in_tiyn#1", "case_id": "cashback.unit_change.cap_in_tiyn",
 "family": "cashback", "source_sha256": "<SHA-256 размеченного файла>", "issue_type": "unit_mismatch",
 "anchors": [{"role": "a", "quote": "Сумма кэшбэка за месяц не превышает 10 000 тиынов.", "locator": "md:L27"},
             {"role": "b", "quote": "Провести покупку «Такси» на 4 000 ₸ | Кэшбэк месяца 10 000 ₸"}],
 "anchor_policy": "all", "expected_outcome": "present", "severity": "major",
 "criterion": "ISO29148-5.2.5:unambiguous", "scenario": "…", "explanation": "…", "visibility": "public"}
```

* `expected_outcome`: `present` — дефект, который нужно найти; `clean` — кейс без дефектов
  (`issue_type: null`, `anchors: []`), любая находка на нём — ложная тревога; `absent` —
  контрольное место (роль опоры `control`): находка здесь отмечается как `control_hit`.
* `anchor_policy`: `all` — находка должна процитировать все опоры (противоречия: обе стороны,
  как требует контракт v1 для конфликтов); `any` — достаточно одной (пропуск обещанного элемента).
* Опора — дословный видимый текст документа без Markdown-разметки. `locator` — справочный:
  сравнение идёт по тексту, поэтому одна разметка подходит для MD, PDF и DOCX.
* Каждый размеченный кейс полностью описан эталоном: строка `clean` или строки `present`.

**Предсказания** (`predictions.jsonl`): строки `record: "finding"` и `record: "run"`.
`adapt` и `run` строят их из `report.json`; можно подать и вручную в плоской форме.

```json
{"record": "finding", "source_sha256": "…", "mode": "rules_plus_llm", "defect_id": "F-003",
 "issue_type": "contradiction", "kind": "conflict", "severity": "major", "status": "confirmed",
 "anchors": [{"quote": "…", "locator": "line_end=27,line_start=27"}, {"quote": "…"}]}
{"record": "run", "source_sha256": "…", "mode": "rules_plus_llm", "status": "complete",
 "physical_calls": 9, "cache_hits": 0, "tokens_in": 41000, "tokens_out": 5200, "duration_s": 74.2}
```

Предсказание привязывается к кейсу по `render_id`, по `source_sha256` через манифест
(SHA-256 файла MD, PDF или DOCX), по `source_sha256` эталона или по явному `case_id`.
Если строки `run` есть, кейс без строки `run` или с `status: failed` считается **пропуском
измерения**, а не нулём находок. Пропуски перечислены в `missing_measurements`.

**Адаптер Report → предсказания** (контракт v1, `contracts/v1.json`): `Finding.evidence[].quote`
(при отсутствии — `block.text[start:end]`), `witness.evidence_a/b`, при пустых evidence — `hints`;
`Finding.kind` → `issue_type` по `taxonomy.toml`. `conflict` отображается в родителя `contradiction`:
продукт не различает подтипы event/status/unit/boundary, совпадение будет уровня `parent`.
Неизвестный `kind` даёт `other`, попадает в `unmapped_kinds` и не может стать TP без разбора.
Из `run` берутся `calls.physical`, `calls.cache_hits`, `tokens.input/output`, `duration_s`,
`mode`, `status`; `document.format: markdown` → формат представления `md`.

## Правила подсчёта

1. **Пара допустима**, если совпадают `case_id`, совместим вид дефекта (`exact`; `parent` при
   `--type-match hierarchy`, по умолчанию) и цитаты находки покрывают опоры по `anchor_policy`.
2. **Один к одному**: из допустимых пар строится паросочетание максимальной мощности (алгоритм
   Куна). Групповая находка с опорами трёх дефектов закрывает один; остальные остаются FN с
   пометкой `claimed_by_group`. Порядок обработки: по убыванию оценки, при равной оценке — по
   `pred_key` (хеш файла, режима, `defect_id`, типа и цитат), метки — по `label_id`. Поэтому
   результат, включая выбор «TP или дубль» и порядок списков, не зависит от порядка строк.
3. **Дубль** — находка, допустимая только для уже закрытых дефектов. Дубли показываются отдельно,
   не входят ни в TP, ни в FP основной precision; `precision_strict` считает их FP.
   Из двух находок на один дефект TP получает точный тип, родительский тип уходит в дубли.
4. **На разбор** (`pending`): пограничный синоним типа (`borderline` в `taxonomy.toml`) или
   покрытие части опор. До решения это FP. Решения подаются `--adjudication decisions.jsonl`:
   `{"pred_key", "decision": "match"|"false_alarm"|"new_real_defect"|"duplicate", "label_id"}`.
   `new_real_defect` исключается из FP и TP и попадает в `new_real_defects`. Лист разбора по всем FP
   пишет `--adjudication-out`; `--review-seed S --review-sample N` даёт воспроизводимую выборку.
5. **Пустые знаменатели**: precision = TP/(TP+FP), `null` при TP+FP = 0; recall = TP/(TP+FN),
   `null` при TP+FN = 0; F1 = 2TP/(2TP+FP+FN), `null` при нуле. Пустой документ и полностью
   чистый документ без находок дают `null` по всем трём, а не 0 или 1.
6. **Форматы.** Независимый кейс — `case_id`. Основные метрики считаются по одному представлению
   (`primary_render` манифеста, обычно MD, или `--render-format`). PDF и DOCX идут в `per_format`
   и `format_consistency` как проверка парсера и экспорта, а не как новые победы.
7. **Строки run.** Одинаковые строки одного представления схлопываются. Из разных строк берётся
   худший статус (`failed` < `partial` < `complete`), с предупреждением. До 0.1.1 бралась первая
   по порядку строка.
8. **Чистые документы.** `clean_controls` — ложные тревоги на кейсах `clean`. Для мутантов
   `fp_background` отмечает ложную находку, которая есть и на чистой базе того же семейства.

### Правило неоднозначного сопоставления

1. **Допустимость.** Находка закрывает дефект, только если тип совместим и цитаты покрывают все
   обязательные опоры (`all`) или одну из них (`any`).
   * Цитата, общая для двух дефектов, сама по себе не закрывает ни один. Такая находка — FP на разборе:
     `disputed_with` перечисляет оба дефекта.
   * Дефект без другой находки — FN; кандидаты перечислены в `near_miss_defect_ids`.
2. **Несколько допустимых дефектов.** Строится паросочетание максимальной мощности: сначала
   закрывается как можно больше дефектов.
3. **Равенство вариантов.** Решает оценка: `exact` выше `parent`, затем доля покрытия. При равной оценке
   выбирается меньший `pred_key`, метки упорядочены по `label_id`. Порядок строк во входе роли не играет.
4. **Дубль.** Ещё одна допустимая находка на уже закрытый дефект — DUP с `kept_defect_id`.
5. **Похожие цитаты.** Если на краю общего отрезка расходятся число, отрицание или единица, опора
   не покрыта: «меньше 30» в «не меньше 30» не совпадает с «больше 1 и меньше 30».

Проверено на открытом корпусе: `evaluation/dev/controls`, ручной ответ — `expected.json`, раздел
selfcheck «открытый корпус».

### Устойчивость (0.1.1)

Контроль `controls/robustness` — граф с двумя эталонными противоречиями A и B:
* X допустима к A и B на уровне parent;
* Y и её явный дубль Z допустимы только к A;
* W цитирует одну сторону A;
* V даёт тревогу на чистом контроле.

Ручной ответ записан в `expected.json` до запуска. `python -m evaluation.harness selfcheck` сверяет его
со счётчиком в режимах `hierarchy` и `exact`. Затем проверяет все 120 перестановок находок, 24 перестановки
эталона и повтор той же выдачи для DOCX того же `case_id`.

На 0.1.0 счётные метрики уже были инвариантны. Но при равных оценках от порядка строк зависело,
кто TP, а кто дубль: Y или Z, по 60 из 120 перестановок. От порядка зависел и порядок списка FP.
В 0.1.1 изменены только выбор при равных оценках, порядок списков, правило конфликтующих
строк run и вывод сводки. Пороги и правила политики `bcc-eval-policy/1` не менялись. Открытый прогон,
пересчитанный кодом 0.1.0 и 0.1.1, даёт совпадающие метрики.

### Почему непрерывный отрезок токенов (сравнение на малом примере)

Самый рискованный выбор — когда цитата находки «покрывает» опору эталона. Пять способов
проверены на 12 парах, включая надмножество-абзац, фрагмент, разметку, разрыв строки PDF,
пересказ LLM, соседнее предложение, отличие в числе и перемешанные ячейки PDF:

| Способ | Верно |
| :--- | ---: |
| вхождение подстроки после нормализации | 10/12 |
| мешок токенов, доля опоры ≥ 0.6 | 9/12 |
| символьный LCS ≥ 0.6 | 9/12 |
| **непрерывный общий отрезок токенов** | **11/12** |
| общая подпоследовательность токенов | 9/12 |

Символьные способы и мешок токенов путают «1 000 ₸» с «10 000 ₸» и строки приёмки,
отличающиеся одним числом. Итоговое правило (`normalize.coverage`):
* непрерывный общий отрезок ≥ 0.6 токенов опоры;
* или фрагмент опоры ≥ 4 токенов и ≥ 0.3 её длины (≥ 3 токенов, если в нём есть число или единица);
* или фрагмент ≥ 3 токенов, который встречается в документе кейса ровно один раз
  (по контракту v1 продукт цитирует дословный фрагмент блока).

Если на краю общего отрезка с одной из сторон стоит число, отрицание или единица измерения
(«тенге»/«тиынах», «UTC+5»/«UTC»), покрытия нет. Перемешанные ячейки PDF не засчитываются
автоматически и уходят на разбор как частичное покрытие. Таблица случаев зафиксирована
в `tests/p16/test_normalize.py`.

## Проверка состава до подсчёта (`evaluation/harness/audit`, bcc-eval-audit/1)

Запускается до `compare` и до любых F1. Читает только файлы каталогов прогона: `run_config.json`,
`predictions.jsonl`, `reports/**/report.json`, `reports/index.json`, `reports/*/stderr.txt` и манифест.
Продукт, сеть и код подсчёта (`score`, `matching`) не вызываются. Пакет лежит вне корня счётчика, поэтому
`harness_sha256` от него не меняется (`7b54d224…` до и после).

```bash
python -m evaluation.harness.audit --gold CLOSED/labels.jsonl \
  --run rules_only=out/closed/ro --run rules_plus_llm=out/closed/llm \
  --expect-agent-commit 2821989 --out out/closed/audit
```

Понимает обе раскладки раннера: 0.1.0 (сборка 2821989: `reports/<case_id>__<fmt>/`) и 0.1.2
(`reports/<12 hex>/` + `index.json`). Понимает и составной каталог, где `predictions.jsonl` объединён
из подкаталогов с собственными `run_config.json`, как в `open_run`. Скопированный каталог тоже читается:
`report_path` сопоставляется по хвосту пути.

Пара — `case_id` эталона во всех прогонах, в основном представлении.

| Код | Вид | Когда |
| :--- | :--- | :--- |
| `sha_mismatch` | нарушение | `report.run.source_sha256` ≠ SHA файла по манифесту (без манифеста — `source_sha256` эталона), или SHA различается между прогонами. Так выглядит файл, изменённый под тем же именем: раннер 0.1.0 пишет в строку run SHA из манифеста, и подсчёт молча сопоставит отчёт с эталоном прежнего файла |
| `repeat` | нарушение | на кейс больше одной строки run или одного `report.json`; подсчёт объединил бы находки всех запусков |
| `missing_report` | нарушение | в части прогонов нет `report.json`, `run.status=failed` или нет строки run. Для чистого кейса отмечено отдельно: его ложные тревоги выпадут, precision завысится. Если строка run осталась `complete`, а файла нет, подсчёт посчитает кейс измеренным |
| `mode_mismatch` | нарушение | `report.run.mode` ≠ запрошенному; `rules_only` с `calls.physical > 0`; `rules_plus_llm` без единого этапа с вызовом модели в статусе ok/cached |
| `config_mismatch` | нарушение | различаются манифест, кэш, версия счётчика, `agent_commit`/`agent_version` продукта (или не равен `--expect-agent-commit`), основной формат кейса. `case_id = *`: затронуты все пары |
| `unknown` | неизвестно | в отчёте нет `run.source_sha256`/`document.id`, `run.mode`, `run.status` (для `rules_only` ещё `run.calls.physical`, для `rules_plus_llm` — `run.calls.physical` и `run.stages`), отчёт не читается или запрошенный режим неизвестен |
| `missing_all` | справочно | кейс не измерен ни в одном прогоне: выпадает из обоих наборов одинаково (на открытом корпусе — `edge.empty`) |
| `partial` | справочно, допустимо | `rules_plus_llm`, модель ответила хотя бы на одном этапе, но отчёт `partial` или в `stderr.txt` есть ошибки адаптера, которых нет в `run.calls.failed` («скрытый partial») |

Фактическое покрытие LLM на отчёт:
* этапы `run.stages` с `calls > 0` и их статус;
* физические вызовы;
* ошибки адаптера из `stderr.txt` (строки `anthropic {…"status": "error"…}`). В сборке 2821989 неуспешные
  вызовы адаптера команды не попадают ни в `run.calls`, ни в `run.stages`, ни в `trace.jsonl`.

Результаты в `--out`: `composition.md` (вердикт, матрица «нарушение → case_id → причина», покрытие LLM, пары
по ID и SHA), `composition.json`, `matrix.jsonl`, `admissible_case_ids.txt`.
Коды выхода: 0 — все пары допустимы; 3 — есть нарушения; 4 — нарушений нет, но есть неизвестные; 2 — ошибка входа.

Существующий `compare` (`comparable()`) сверяет эталон, манифест, кэш, формат, правило типов и число
размеченных кейсов. Всё перечисленное в таблице выше он не видит: на открытом стенде во всех 8 сценариях
он ответил «сопоставимо: да» (`evaluation/dev/results/composition_open_stand.json`).

## Режимы продукта

`run` вызывает `python -m bcc_review INPUT OUTPUT.md` по контракту v1 и сравнивает режимы
на одинаковых манифесте, формате и настройке кэша. Всё это записано в `run_config.json` и в
каждой строке `run`; `compare` отказывается сравнивать несопоставимые прогоны.

* `rules_only` → `--offline-lint`. Дочерний процесс запускается в **сетевой песочнице**:
  ключи провайдеров (`*_API_KEY`, `ANTHROPIC_*`, `GEMINI_*`, `GOOGLE_*`, `OPENAI_*`, токены)
  удалены из окружения, `HTTP(S)_PROXY` указывает на закрытый порт `127.0.0.1:9`. Реальный запрос
  к LLM не может уйти. Дополнительно проверяется `run.calls.physical == 0` и `run.mode == rules_only`;
  иначе в строке `run` появляется `violations`.
* `rules_plus_llm` → `--provider anthropic|gemini`; `mock` → `--provider mock` (подставной транспорт
  движка; сеть закрыта той же песочницей, что и в `rules_only`).
* `metrics.json → runs.transport` и `runs.implementations` показывают, что реально отработало:
  режим, провайдер и модель, а также реализация каждого слота движка из `Report.run.modules`
  (`team:…` или `fallback:…`).
* `--cache off` (по умолчанию) передаёт `--no-cache`, чтобы физические вызовы были настоящими.
* Длительность — время процесса по часам счётчика; вызовы и токены — из `report.json`.
  Не сообщённое значение в таблице показано как «—» с причиной, а не как 0.
