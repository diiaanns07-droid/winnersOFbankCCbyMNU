# Независимая оценка агента BCC · IE-1.0

Версия от 26 ноября 2026 года. Получатели — №16 (сопоставление и счётчик), Max (версия продукта), №18 (исполнение). До первого просмотра ответов на новом наборе фиксируем этот текст, публичный расчёт и план выборки. Хранитель составляет эталон с помощью ИИ отдельно от разработки. Результат предыдущего публичного dev-прогона был известен. Закрытые ответы агента при составлении эталона недоступны. Участие человека удостоверяется отдельной подписью и временем.

## Что считаем

Единица — одна исправимая причина в одной содержательной редакции. Семья объединяет документы одного сюжета. Контрольные и изменённые версии внутри семьи зависимы. Больший вес за повторное представление в PDF или DOCX исключён. Основная единица запуска — одна версия MD. Для вариативности выводим итоги по семействам. Генерализацию на реальные банковские ТЗ этот дизайн не измеряет.

1. Конфликт устанавливают по объекту, состоянию, субъекту, моменту и прочим существенным предусловиям. Один и тот же вход должен требовать двух несовместимых последствий. Для совпадения нужны обе источниковые опоры. Одинаковое число при разных состояниях само по себе совместимо. Для пропуска нужны процитированное обещание и граница исчерпывающего перечня. Для вывода по смыслу проверяем просмотр этого перечня.
2. Допустим парафраз заголовка или объяснения с сохранением числа, единицы, отрицания, условия и исхода. Дословный текст опоры открывается в исходнике по позиции. Координаты Unicode с нуля, правая граница исключена. Перенос строки/разметка допустимы при механическом сравнении. Исполнитель №16 использует coverage, версию таксономии hierarchy и максимальное паросочетание один к одному. Политика all требует все опоры. В отдельном аудите подтверждённая находка должна содержать точные позиции, а конфликт — двухсторонний смысловой свидетель. Статус needs_review и ошибка проверки цитаты показываются отдельно. Для основной цифры доказательных находок допускаем только confirmed с проверенными опорами.
3. Одна находка покрывает одну причину. Один дефект в трёх разделах имеет один defect_id с несколькими опорами. Повторная подходящая находка — дубль D. Групповая запись, которая описывает два разных исправления, закрывает максимум одну причину. Неподтверждённые предупреждения отражаем в дополнительном механическом расчёте по всем статусам и в операционной нагрузке на чистых.
4. Первичный механический результат №16 сохраняется неизменяемым. Независимый ИИ отдельно проверяет кандидатов TP на смысл, неподтверждённые цитаты и спорные пары на разборе. При недоказанной привязке соответствующий подтверждённый сигнал остаётся FP, дефект остаётся FN. Для нового реального дефекта сохраняем исходные числа, обоснование, обе версии разметки и отдельный пересчёт с теми же предсказаниями. Изменение применяют симметрично ко всем затронутым редакциям и режимам. Человеческую колонку заполняет только фактический рецензент.
5. Precision = TP/(TP+FP), recall = TP/(TP+FN), F1 = 2TP/(2TP+FP+FN). Строгая precision включает D в знаменатель. Полнота критичных = обнаруженные критичные причины / все критичные по исходному эталону. Пустой знаменатель записываем null. На чистом ТЗ отдельно считаем число неподтверждённых эталоном замечаний и долю чистых ТЗ хотя бы с одной тревогой. Прогон failed или отсутствующий отчёт исключаем из условных метрик и явно включаем в знаменатель запланированных запусков. Для неполных результатов указываем статус.
6. Технический успех запуска — чистый рабочий каталог продукта, тот же SHA, команда вернула 0, записала MD/JSON, источник и координаты прошли verify, выполнен фактически запрошенный режим. В rules_only ожидается partial из-за отключённых семантических этапов. Дополнительно считаем полное семантическое выполнение (complete без пропущенных этапов). Для живого успеха нужны ответ провайдера, фактическая модель, положительное число вызовов и ноль попаданий в кэш. Попытка без ответа не подтверждает работу модели. Незапущенный режим всюду имеет null.
7. Вопрос к засеянной причине считается полезным при одновременном выполнении трёх условий. Можно открыть конкретное место, варианты действительно ведут к двум разрешённым бизнесом исходам, и ответ меняет конкретный текст или ожидаемый тест. Считаем покрытие ожидаемых вопросов и отдельно долю удачных среди просмотренных карточек. Для причин без карточки покрытие равно нулю. Для основного замера вопросов проверяем все карточки шести заранее выбранных документов, по одному на страту. Сопоставление по смыслу выполняет независимый ИИ. Результаты человека остаются null до проверки человеком.
8. Для A→B сверяем устранённую, сохранённую и новую причины по содержанию и опорам. На перенумерации ожидается сохранение идентичности обеих причин. При физическом удалении страницы конфликт становится непроверяемым. Ложное закрытие — явно «исправлено» при оставшейся причине или исчезновении доказательства. Различаем исчезновение карточки и доказанное исправление. Отдельно сообщаем долю верных переходов от всех ожидаемых и условную долю от переходов, для которых агент вообще выдал исходную карточку.
9. Для проверки развилок на первом конфликте первой семьи выписываем обе согласованные редакции и тесты до запуска. При наличии карточки применяем оба ответа к одному исходному SHA через штатный интерфейс и повторно проверяем полученные редакции. При отсутствии подходящей карточки запускаем агент на обеих эталонных редакциях, фиксируя отдельно доступность интерфейса и согласованность текстов.

## План до запуска

Четыре независимые банковские семьи × шесть редакций. В каждой семье есть чистая база, совместимая обратная пара, конфликт, пропуск, редакция с двумя причинами и следующая редакция. Два дополнительных продольных контроля проверяют перенумерацию и исчезновение страницы. Обе бизнес-развилки — вне основного знаменателя. Повторный формат имеет тот же case_id.

Бюджетная парная панель — по одному документу из каждой из шести страт. До испытания зафиксированы i01, i08, i15, i22, i05, i06. Все четыре семьи представлены. Сравнение режимов допускается на одинаковых входах, версии, формате и настройках кэша. Для шести документов также отдельно сообщаем офлайн-результат. Для каждого случая фиксируем первую попытку, сохраняем технические сбои и присваиваем повтору новый run_id. Предложение владельцу — до 12 учтённых вызовов на документ, до 180 секунд, 30 секунд на обращение, ноль повторов движка, кэш выключен. Резервный HTTP-адаптер релиза может повторно отправить схему один раз на один учтённый вызов. Таким образом, верхняя граница 72 учтённых вызова, до 144 HTTP-посылок на шесть документов. Согласование квоты принадлежит №18.

Выборка разбора ложных тревог — первые восемь по возрастанию SHA-256 строки IE-1|case_id|finding_id плюс все кандидаты TP, пограничные совпадения и обратные пары. Проверяем все семантические FN по посадочным причинам. Храним по отдельности первичный счётчик, второй разбор ИИ, человеческие суждения и незаполненные поля. Отсутствие опубликованной метрики живой модели означает отсутствие измерения.

## Передача №16 до запуска

Формат и проверяемый пример находятся в FORMAT.md и example/. Источники эталона и его версии фиксируются SHA-256. В открытом Git до заморозки доступны протокол и учебный пример. Закрытые документы, ключи и исходные ответы хранятся раздельно. Корпус никогда не передаётся модели вместе с эталоном. Для публичных артефактов публикуем агрегаты и обезличенные ссылки по case_id. Прямой доступ к исходным файлам выдаёт хранитель.

Нулевые знаменатели и явный учёт дублей следуют опубликованному примеру оценки. Банковские причины сопоставляются по двум сторонам текста и сценарию. [Референс счётчика](https://github.com/foxfordkz-cyber/qazaq-loc-qa/blob/fa5be81531f7c4880fcd68aa337f7f658bad132d/src/evaluation.mjs)
