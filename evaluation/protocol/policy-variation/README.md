# Независимая проверка разных банковских политик · PV-1

Фиксируется до первого ответа агента по этому набору. За метод и эталон отвечает независимый ИИ-проверяющий. Команда продукта не видит входов и ответов до фиксации SHA. Первичный релиз в контракте Max — `f91d3b6f485e883d316c94fc5e032f1a8d6c2553`. Механический счётчик №16 закреплён за `a79a47d887bf5265c946019c004ca8d3e4f2b988`. Предыдущий открытый результат и испытание IE-1.0 этому проверяющему известны. Здесь иные сюжеты, формулировки и заранее записанные исходы.

## План

Четыре вымышленные услуги банка. В каждой рассматриваются две допустимые политики, для каждой создаются чистая спецификация и редакция с одной нарушенной причиной. Итого 16 содержательных документов, 8 заложенных дефектов и 8 чистых контролей. Фактический порядок разделов в основном представлении сбалансирован. У каждого документа есть ещё два физических представления. В первом меняются местами разделы A и B с неизменным текстом. Во втором меняются только формулировки на заранее проверенные эквиваленты, а исходный порядок сохраняется. У всех трёх форм один case_id. Исходники MD используются для исключения влияния другого парсера. Первичные метрики считаются только по первому представлению. Четыре семьи остаются единицей разнообразия.

Каждая политика принимается как действующее правило конкретного входа. Обе противоположные бизнес-политики допустимы. Смысл задают актор, состояние, момент события, условия и наблюдаемый исход. Ни порядок разделов, ни обычная банковская практика не делают один раздел приоритетным. Банковские дни отличаются от календарных, включённая граница отличается от исключённой. Для пропуска область поиска ограничивает явно исчерпывающий список полей. Для непроверяемого требования учитывается весь документ, включая определения и тесты. Политика, пояснения, допустимые альтернативные формулировки, недопустимые интерпретации и ожидаемый тест хранятся в закрытом эталоне каждой редакции.

## Критерии и счёт

* **Critical.** Один и тот же разрешённый сценарий даёт взаимоисключающее фактическое движение или удержание денег. В наборе две такие причины.
* **Major.** Разные дни обработки или недоступный обещанный реквизит мешают реализовать и принять операцию. Отсутствие проверяемой верхней границы по обязательному сроку оставляет приёмочный тест без результата. В наборе шесть таких причин.
* **Minor.** Локальная редакционная проблема сохраняет исход и приёмочное решение. Обоснованные новые причины записываются отдельно с обоснованием. Поправка эталона получает свою версию, применяется ко всем применимым представлениям и режимам. Первичные числа сохраняются.

1. Первичная единица — одна заложенная причина в одном case_id. В знаменатель предсказаний попадают уникальные confirmed-замечания, включая confirmed с неподтверждённым основанием как FP. Отдельно показываются все статусы и любые тревоги на чистом входе.
2. Сначала проверяются SHA входа и продукта, режим и код verify. Для каждой цитаты независимо сопоставляются block_id, Unicode-смещения и буквальный срез, а затем строки именно того входного файла, к которому относится отчёт. Проверка источника и оценка делового вывода имеют отдельные поля.
3. Для совпадения требуются совместимый тип по hierarchy №16, необходимые опоры, та же причина и условия с несовместимым исходом, недостающей частью контракта или непроверяемым сроком. Пересказ заголовка допустим. Разные роли или предусловия, а также только одна сторона конфликта не устанавливают совпадения. Потеря важных слов при нормализации требует разбора. У пропуска проверяются обещание и граница полного перечня. У непроверяемости достаточно прямой опоры на единственный неопределённый срок, подтверждённой просмотром всего документа.
4. Счётчик строит паросочетание один к одному. Подходящие повторы закрытой причины учитываются в D. Основная precision = TP/(TP+FP), строгая = TP/(TP+FP+D), recall = TP/(TP+FN). Нулевой знаменатель даёт null. Частичное совпадение до принятого решения остаётся FP и оставляет метку FN. Степень тяжести TP сравнивается отдельно. Ручной пример с дублем опубликован в [калибровке](../../results/public-calibration.json).
5. Независимый проверяющий пересматривает смысл каждого кандидата TP и пограничного совпадения. Для промахов документируется конкретное невыполненное условие. Допустимый дословный короткий фрагмент из той же строки, который механический счётчик отклонил, может получить отдельный семантический TP только при однозначной привязке к размеченному месту, верной причине и выполненном контракте опор. Первичный вывод №16 сохраняется рядом с решением. Дубли считаются последовательно и в смысловом разборе. Самооценки агента не используются как эталон. Проверку человеком отмечают только при наличии рецензента.
6. Офлайн-команда вызывает релиз без кэша и без сети. Отсутствующий отчёт, failed либо несовпадение режима фиксируются как пропуск измерения. Partial допустим для rules_only. Для модели считаются только фактически исполненные прогоны с именем модели из ответа и положительным числом обращений. На несопоставимых входах эффекта модели не оцениваем.

Для возможного живого прогона заранее выделены восемь ID в отдельном манифесте. В каждой семье по одному чистому и одному дефектному документу, представлены обе политики. Владелец получает только анонимизированные входные MD и манифест при согласованном бюджете. Ключа и подтверждения квоты в этой сессии нет.

## Запрос Max и №16

Max, для другого кандидата передай только полный SHA, точную команду и автоматически полученные отчёты по согласованным входам. Боевой прогон по кейсу организаторов остаётся у тебя. Для №16 оставляем действующий [формат JSONL](../FORMAT.md). Корпус и результаты другого SHA требуют отдельной строки результатов.
