#### <a id="d-02"></a>🔴 D-02. Критерий приёмки №2 относит покупку к февралю, Ф-2 — к месяцу совершения

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 по Алматы: по Ф-2 растёт январский счётчик, по приёмке — февральский.

**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик вырос на 4 000 ₸», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Январский счётчик вырос на 4 000 ₸, февральский не изменился.»

#### <a id="d-03"></a>🔴 D-03. Ф-3 (один push в месяц) противоречит Ф-4 (push независимо от истории)

#### <a id="d-06"></a>🟠 D-06. Метод `saveLimit` изменяет данные через GET с параметрами в URL

- Часть B › Общие параметры, строка 103: «Сохранение порога»
- Часть B › Общие параметры, строка 104: «REST type | GET»
- Часть B › Общие параметры, строка 108: «/alerts/saveLimit»
- Часть B › Общие параметры, строка 109: «--data 'cardId=demo-42&amount=50000&enabled=1»
- Часть B › Request body, строка 147: «Content-Type: application/json»

**Проблема.** `saveLimit` меняет настройку, но тип запроса GET (строка 104), идентификатор карты и значения идут в строке запроса (строка 109) и оседают в журналах. Также указан Content-Type: application/json при отсутствии тела (строки 147–148).

**Сценарий.** Команда разработки или эксплуатации ищет значение (адрес, ссылку, параметр) и не находит его.  
**Последствия.** Работа останавливается на уточнении; в промышленную среду нечего настраивать.  
**Как исправить.** Указать значения или явно написать «не применяется» с причиной.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 108: «Prod: —» → «Prod: <уточнить: значение>; Swagger: <уточнить: значение>»  
*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требование [R-16](#r-16 "Общие параметры метода сохранения порога") · нашли: правило «заглушки и шаблон»*

#### <a id="d-17"></a>🟠 D-17. При ERROR «прежнее состояние» вернуть нечем: amount и enabled только при успехе

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»

**Проблема.** Шаг 5 (строка 121) требует вернуть прежнее состояние, но amount возвращается «При успехе» (строка 156), в теле ERROR только result и message.  
**Сценарий.** Действует порог 50000, клиент шлёт amount=500: ответ не содержит текущего значения.  
**Последствия.** Разработчики сервера и клиента по-разному поймут, что значит «вернуть прежнее состояние».  
**Как исправить.** Определить: либо состояние не меняется и не возвращается, либо amount и enabled входят в тело ошибки.  
**Было → стало.** Строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt» → «При отказе настройка не меняется; тело ошибки: {"message":"Проверьте сумму"}; поля amount и enabled в ответ не включаются.»  
**Вопрос владельцу.** Нужно ли возвращать прежние amount и enabled в ответе при отказе? → [Q-04](#q-04) (варианты ответа)

#### <a id="d-18"></a>🟠 D-18. Типы amount и enabled в запросе (integer) и в ответе (string) различаются

- Часть B › Query-параметры, строка 143: «amount | integer»
- Часть B › Query-параметры, строка 144: «enabled | integer»
- Часть B › Ответ, строка 156: «amount | string»
- Часть B › Ответ, строка 157: «enabled | string»

**Проблема.** amount и enabled в запросе — integer (строки 143–144), в ответе — string (строки 156–157), в примере "50000".  
**Сценарий.** Клиент отправляет amount как integer и получает обратно значение типа string; строгий разбор ответа или сравнение отправленного и сохранённого значения не проходит.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 143: «amount | integer» → «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Порог в тенге, обязательный"), [R-28](#r-28 "Признак включения 0/1, обязательный"), [R-32](#r-32 "Порог в тенге при успехе"), [R-33](#r-33 "Признак включения «0» или «1»") · нашли: правило «контракт API»*

#### <a id="d-19"></a>🟠 D-19. Перечень кодов успеха и ошибок противоречив и открыт

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»
- Часть B › 403. Unsuccessful — Forbidden, строка 188: «403. Unsuccessful — Forbidden»

**Проблема.** Строка 151: успех — 200 или 201, но 201 не описан, а 200 подписан «Created» (строка 165). Ошибки перечислены как «400, 401 и далее» — список открыт.

**Как исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный» → «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
