#### <a id="d-01"></a>🔴 D-01. Сумма вне диапазона: код 400 и код 200 с ERROR одновременно

- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Строка 163 задаёт код 400 для неверных параметров, а пример строки 171 для суммы вне диапазона даёт HTTP 200 с result ERROR. По строке 151 код 200 — успешный.  
**Сценарий.** amount=500 при диапазоне 1 000–1 000 000: по строке 163 ответ 400, по строке 171 ответ 200 с ERROR; приложение, смотрящее на код 200, покажет «сохранено».  
**Последствия.** Клиент покажет успех при отказе сохранения порога; тесты по коду и по телу дают разные результаты.  
**Как исправить.** Для ошибки ввода суммы оставить только код 400 с телом message; пример строки 171 перенести под код 400; код 200 — только для успешного сохранения.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «400. Ошибка ввода суммы: {"message":"Проверьте сумму"}»  
**Вопрос владельцу.** Что верно: «ответ 400» (как в «Статус 400») или «ответ с кодом 200 и result ERROR» (как в «Ответ: result»)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — код 400 с телом {"message":"Некорректный запрос"}; B — код 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; C — код 400 с телом {"result":"ERROR","message":"Проверьте сумму"}  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Порог в тенге, обязательный"), [R-30](#r-30 "Правило успешного и неуспешного ответа по коду"), [R-31](#r-31 "Исход сохранения: OK или ERROR"), [R-36](#r-36 "Код 400 — неверные параметры запроса") · нашли: архитектор, проверка набора, правило «контракт API»*

#### <a id="d-02"></a>🔴 D-02. Чтение порога и суммы за месяц не описано ни одной операцией

- Часть A › Дизайн процесса UI, строка 29: «поле «Порог, ₸»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки»
- Часть B › Общие параметры, строки 103 и 108: «Сохранение порога. Функциональные требования: чтение порога» · «Dev: /alerts/saveLimit»

**Проблема.** Строки 52 и 29 обещают чтение настроек и показ суммы за месяц, строка 103 упоминает «чтение порога», но в части B есть только `saveLimit`, который заменяет настройку и не возвращает текущих значений без записи.  
**Сценарий.** Клиент открывает экран «Уведомления»: приложению нечем получить сохранённый порог, переключатель и сумму за месяц без перезаписи настройки.  
**Последствия.** Экран не заполняется сохранённым порогом; клиент вводит порог заново, реализация и тесты чтения не имеют описания.  
**Как исправить.** Описать метод чтения порога: путь, параметры, ответ и статусы.  
**Предлагаемая формулировка.** «Метод чтения порога карты: GET `/alerts/getLimit`, параметр `cardId`, ответ {"result":"OK","amount":"<порог>","enabled":"<0|1>"}, статусы 401, 403/404, 500.»  
**Вопрос владельцу.** Чтение порога — отдельная операция или `/alerts/saveLimit` должен возвращать текущие значения без записи? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — отдельный GET-метод чтения по `cardId` (с проверкой сессии и принадлежности карты)…; B — чтение выполняется тем же методом сохранения без параметров amount и enabled

#### <a id="d-03"></a>🔴 D-03. Критерий приёмки 2 и Ф-2 относят одну покупку к разным месяцам

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу по дате совершения, а критерий приёмки (строка 64) для покупки 31 января 23:58, проведённой 1 февраля, ожидает рост февральского счётчика. Какое событие определяет месяц, не сказано.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸, проведена 1 февраля в 00:03 по Алматы: по Ф-2 январский счётчик +4 000 ₸, по строке 64 февральский +4 000 ₸.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸, февральский не меняется», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸, февральский не меняется», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Предлагаемая формулировка.** «Январский счётчик вырос на 4 000 ₸; февральский счётчик не изменился (месяц по дате совершения 31 января, Ф-2).»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик +4 000 ₸, февральский не меняется» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — по дате совершения покупки в Алматы; B — по дате проведения покупки в Алматы

*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-11](#r-11 "Состав хранимых данных по карте и расходам"), [R-12](#r-12 "Чтение и сохранение настроек через REST API") · нашли: риски*

#### <a id="d-15"></a>🟠 D-15. Повтор события: неясно, повторится ли push

**Где:** Часть A › Требования к интеграции, строка 52: «Повторная доставка одного события процессинга сохраняет исходный итог»

**Проблема.** Строка 52 «сохраняет исходный итог» не говорит, отправляется ли push повторно при повторной доставке события.  
**Сценарий.** Покупка 1 500 ₸ при 48 500 ₸ доставлена дважды: клиент получает один push или два.  
**Последствия.** Разработчик и тестировщик расходятся в том, нужна ли защита от повторного push, и клиент может получить два уведомления за один месяц.  
**Как исправить.** Заменить формулировку на явное описание поведения для суммы и для push при повторной доставке.  
**Было → стало.** Строка 52: «Повторная доставка одного события процессинга сохраняет исходный итог» → «Повторная доставка одного события процессинга не меняет накопленную сумму и не отправляет повторный push.»  
**Вопрос владельцу.** При повторной доставке одного события push отправляется повторно или нет?  
*Существенный, блокирует разработку · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требование [R-12](#r-12 "Чтение и сохранение настроек через REST API") · нашли: аналитик*

#### <a id="d-16"></a>🟠 D-16. Адрес продуктивного вызова и Swagger не заполнены

#### <a id="d-18"></a>🟠 D-18. Тип amount и enabled в запросе и ответе различается

#### <a id="d-19"></a>🟠 D-19. Перечень кодов ответа: 201 не описан, 200 подписан Created

**<a id="q-07"></a>Q-07** Единицы сумм и правило сравнения с порогом · можно ответить позже · кому: Аналитик · к [D-07](#d-07)

Где: Часть A › Требования к данным, строка 49: «сумму покупки в тиынах»; критерий приёмки №1, строка 63: «Расходы 48 500 ₸, порог 50 000 ₸»

- **A** Все суммы сравниваются в тенге: сумма покупки переводится из тиынов делением на 100 с округлением вниз до целых тенге
- **B** Все суммы хранятся в тиынах; порог переводится в тиыны умножением на 100 перед сравнением

Зачем: Без правила пересчёта покупка на дробную сумму тенге может дать разный итог и разное срабатывание порога на границе.

**<a id="q-08"></a>Q-08** Код ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-21](#d-21)  
Какой код получает держатель, запросивший настройку чужой карты: 403 или 404? В общем описании кодов сказано про 403 для запрещённого ресурса, а в правиле для чужой карты — 404, как для несуществующей.  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен.»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты.»

- **A** Для чужой и отсутствующей карты возвращать 404 с телом {"message":"Карта не найдена"}; код 403 для карты не используется
- **B** Для чужой карты возвращать 403 с телом {"message":"Доступ запрещён"}; для отсутствующей карты возвращать 404 с телом {"message":"Карта не найдена"}

Зачем: Разные ответы на чужую карту позволяют по коду узнать, существует ли карта другого клиента, и тест на эту ветку может ожидать 403 или 404 без однозначного правила.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
