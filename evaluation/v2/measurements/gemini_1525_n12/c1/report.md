#### <a id="d-01"></a>🔴 D-01. Не определено ключевое событие учёта расходов: авторизация или проведение

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель документа обещает уведомление «в момент покупки» (строка 23), а Ф-2 учитывает только «проведённые покупки» (строка 38), поступающие с задержкой 1–3 дня.  
**Сценарий.** Клиент совершает покупку 10 мая, лимит превышен. По цели push должен уйти 10 мая, но по Ф-2 проведение приходит 12 мая, из-за чего push отправляется с задержкой в 2 дня.  
**Последствия.** Разработка и тестирование не смогут выбрать источник событий (авторизация или клиринг), а банк рискует не выполнить главную цель доработки и получить жалобы клиентов из-за задержки уведомления.  
**Как исправить.** Определить единое ключевое событие карточной операции для расчёта расходов и привести цель и требование Ф-2 к общему знаменателю.  
**Было → стало.** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят авторизованные покупки по карте. Пересчёт сумм и отправка push-уведомления выполняются в течение минуты после получения события авторизации.»  
**Вопрос владельцу.** Какое событие карточной операции запускает пересчёт расходов и отправку push: авторизация в момент покупки или финансовое проведение (клиринг)? → [Q-01](#q-01) (варианты ответа)

#### <a id="d-07"></a>🟠 D-07. Противоречие правила лимита push и отправки при смене порога

**Проблема.** Параметры amount и enabled в запросе имеют тип integer (строка 143, строка 144), а в ответе и примере описаны как string (строка 156, строка 157, строка 167).  
**Сценарий.** Мобильное приложение передаёт amount как число и получает в ответе строку, что вызывает ошибку строгого парсинга JSON.  
**Последствия.** Сбои десериализации ответа API в мобильном приложении.  
**Как исправить.** Унифицировать типы полей: использовать тип integer для amount и enabled как в запросе, так и в ответе.  
**Предлагаемая формулировка.** «amount | integer | Порог в тенге; enabled | integer | Признак включения (0 или 1).»  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Параметр amount, обязательный порог в тенге"), [R-28](#r-28 "Параметр enabled, обязательный признак включения"), [R-32](#r-32 "Параметр ответа amount, порог в тенге при успехе"), [R-33](#r-33 "Параметр ответа enabled, признак включения") · нашли: архитектор, правило «контракт API»*

#### <a id="d-16"></a>🟠 D-16. Код 201 отсутствует в статусах, а заголовок 200 подписан Created

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»

**Проблема.** Правило строки 151 упоминает код 201, которого нет в списке статусов, а заголовок кода 200 ошибочно наименован «200. Successful — Created» (строка 165).  
**Сценарий.** Автотесты контракта API падают из-за расхождения между наименованием статуса Created и HTTP-кодом 200 OK.  
**Последствия.** Клиент обработает ответ как неизвестную ошибку; спор при приёмке о правильном коде; автотесты контракта нельзя написать однозначно.  
**Как исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»  
**Вопрос владельцу.** Какой HTTP-код ответа и наименование статуса должен возвращать сервис при успешном сохранении и при попытке доступа к чужой карте? → [Q-03](#q-03) (варианты ответа)  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-30](#r-30 "Правило определения успешности ответа по коду HTTP"), [R-35](#r-35 "Код 200 при успешном выполнении метода") · нашли: правило «контракт API»*

#### <a id="d-17"></a>🟠 D-17. Открытый перечень кодов ответа с формулировкой «и далее»

**Где:** Часть B › Ответ, строка 151: «Если результат 400, 401 и далее — неуспешный»

**Проблема.** Правило кодов ответа содержит незавершённый список: «Если результат 400, 401 и далее — неуспешный» (строка 151).  
**Сценарий.** При возникновении кода 422 или 502 разработка и автотесты не имеют однозначного правила обработки неизвестных кодов.  
**Последствия.** Реализация и тесты расходятся на непоименованных значениях; спор при приёмке.  
**Как исправить.** Заменить открытый перечень полным списком значений или правилом, по которому значение однозначно относится к перечню.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 151: «Если результат 400, 401 и далее — неуспешный» → «Если результат 400, 401 и <уточнить: полный перечень>»  
*Существенный, блокирует разработку · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требование [R-30](#r-30 "Правило определения успешности ответа по коду HTTP") · нашли: правило «размытые слова»*

#### <a id="d-18"></a>🟠 D-18. Отсутствие обязательного поля result в примерах ошибок 4xx/5xx

- Часть B › Ответ, строка 155: «result | string | OK / ERROR»
- Часть B › 400. Unsuccessful — Bad request, строка 180: «{"message":"Некорректный запрос"}»
- Часть B › 401. Unsuccessful — Unauthorized, строка 185: «{"message":"Требуется вход"}»
- Часть B › 403. Unsuccessful — Forbidden, строка 192: «{"message":"Карта не найдена"}»

**Проблема.** Таблица ответа (строка 155) указывает поле result как обязательное, но в примерах ответов 400, 401, 403 и 500 (строки 180–197) это поле отсутствует.  
**Сценарий.** При ошибке 401 клиент пытается прочитать поле result из ответа, получает `null` и завершает работу с исключением.  
**Последствия.** Разные реализации обработки ошибок у клиента и сервера; тесты контракта на ошибки не написать.  
**Как исправить.** Либо добавить result во все тела ошибок, либо указать в таблице ответа, при каких кодах поле result присутствует.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «result | <уточнить: тип> | Обязательно во всех ответах | Признак результата»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-31](#r-31 "Параметр ответа result, исход сохранения"), [R-41](#r-41 "Код 400 Bad request и пример тела ответа"), [R-42](#r-42 "Код 401 Unauthorized и пример тела ответа"), [R-43](#r-43 "Код 403 Forbidden и обработка 404 для чужой карты"), [R-44](#r-44 "Код 500 Internal server error и пример тела ответа") · нашли: правило «контракт API»*

#### <a id="d-19"></a>🟠 D-19. Несогласованность кодов ответа 403 и 404 при доступе к чужой карте

- Часть B › 200. Successful — Created, строки 165 и 175: «200. Successful — Created» · «403. Ответ в случае, если на указанный ресурс доступ запрещен»
- Часть B › 403. Unsuccessful — Forbidden, строки 188 и 189: «403. Unsuccessful — Forbidden» · «Для чужой карты возвращается 404, как и для отсутствующей карты»

**Проблема.** Раздел строки 175 задаёт код 403 для запрета доступа к ресурсу, а описание строки 189 указывает возврат 404 для чужой карты, отсутствующего в общем перечне статусов.  
**Сценарий.** Клиент передаёт в запросе ID чужой карты. Сервер возвращает 404 вместо 403, что приводит к некорректной обработке в клиенте.  
**Последствия.** Некорректная обработка ошибок в клиентском приложении из-за неоднозначности статус-кода.  
**Как исправить.** Зафиксировать использование единого кода 404 при доступе к чужой карте.  
**Было → стало.** Строка 165: «200. Successful — Created» → «200. Successful — OK. 404. Unsuccessful — Not Found: {"message":"Карта не найдена"}»  
**Вопрос владельцу.** Что верно: «сервер возвращает ответ с кодом 403 Forbidden» (как в «Статус 403») или «сервер возвращает ответ с кодом 404 Not Found» (как в «Статус 404»)?  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-39](#r-39 "Код 403 при запрете доступа к ресурсу"), [R-43](#r-43 "Код 403 Forbidden и обработка 404 для чужой карты") · нашли: архитектор, проверка набора, правило «контракт API»*

- **A** Использовать метод POST `/alerts/saveLimit` с передачей JSON в теле запроса, возвращать HTTP 200 OK при успехе и HTTP 400 Bad Request при неверной сумме.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
