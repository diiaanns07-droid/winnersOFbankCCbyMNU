### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Месяц покупки: Ф-2 относит по дате совершения, критерий приёмки и BPMN — по проведению

**Требования:** [R-06 / Ф-2](#r-06), [R-14](#r-14), [R-04](#r-04) · **Критерий:** Корректность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** аналитик, тестировщик, риски

- Часть A › BPMN схема процесса, строка 34: «Проведение покупки»
- Часть A › Функциональные требования, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- Часть A › Критерии приемки, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу по дате совершения, а учёт и критерий приёмки (строка 64) относят покупку 31 января к февралю по дате проведения; BPMN (строка 34) начинает с проведения.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸ проведена 1 февраля в 00:03. По Ф-2 сумма идёт в январь, по критерию приёмки (строка 64) — в февраль. Порог может сработать в одном месяце и не сработать в другом.  
**Последствия.** Разработка выбирает одну дату, тест по критерию или по Ф-2 не проходит; клиент получает push в неверном месяце, счётчики расходятся.  
**Что исправить.** Выбрать одну дату и записать её в Ф-2 и в критерии приёмки (строка 64) одинаково: «Месяц определяется по дате <уточнить: совершения или проведения> покупки в часовом поясе UTC+<уточнить смещение>».  
**Было → стало.** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Покупка относится к месяцу по дате её проведения процессингом в часовом поясе <уточнить: смещение UTC+N>. В расходы входят только проведённые покупки.»  
**Вопрос владельцу.** Какое событие определяет месяц покупки: проведение или совершение держателем, и какой часовой пояс UTC+N применять? → [Q-01](#q-01)

#### <a id="d-02"></a>🔴 D-02. Операция чтения настроек и суммы за месяц не описана; единственный метод только сохраняет

**Требования:** [R-03](#r-03), [R-12](#r-12), [R-16](#r-16) · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** отсутствует элемент · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, проверка набора, правило «promises.read_operation», тестировщик

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»
- Часть B › Общие параметры, строка 103: «Сохранение порога. Функциональные требования: чтение порога»
- Часть B › Логика работы метода, строка 120: «4. Заменить настройку и вернуть результат сохранения»
- Часть B › Query-параметры, строка 144: «enabled | integer | 1 знак | Да | 0 или 1 | Признак включения | enabled»

**Проблема.** Документ обещает чтение настроек (строка 52, строка 103) и показ суммы за месяц на экране (строка 29), но единственный адрес `/alerts/saveLimit` (строка 108) заменяет настройку и требует amount и enabled (строка 120, строки 142–144). Метода чтения порога и накопленной суммы нет.  
**Сценарий.** Клиент открывает «Карты → Расходы → Уведомления» по карте demo-42. Приложению нечем получить текущий порог, признак и сумму за месяц без записи настройки.  
**Последствия.** Экран нельзя заполнить данными сервера; реализация и приёмка экрана и чтения невозможны.  
**Что исправить.** Добавить в REST API описание метода чтения настроек: адрес, метод, параметры (`cardId`), ответ с полями result, amount, enabled и суммой за месяц, либо явно указать <уточнить: какой отдельный документ описывает чтение>.  
**Было → стало.** Строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить» → «Чтение: GET <уточнить: путь чтения>, вход `cardId`; ответ 200: amount (порог, тенге), enabled, сумма за месяц (тенге); ошибки по общей таблице кодов.»

#### <a id="d-03"></a>🔴 D-03. Ф-3 (один push в месяц) и Ф-4 (push при достижении после смены порога) дают разное число push

**Требования:** [R-07 / Ф-3](#r-07), [R-08 / Ф-4](#r-08), [R-24](#r-24) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, тестировщик, риски, аналитик

- Часть A › Функциональные требования, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Часть A › Функциональные требования, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»
- Часть B › Особые правила, строка 125: «Повторное сохранение заменяет действующую настройку»

**Проблема.** Ф-3 (строка 39) ограничивает один push за календарный месяц, Ф-4 (строка 40) требует push при следующем достижении порога «независимо от истории предыдущей настройки». Не сказано, распространяется ли месячный лимит на случай после смены порога.  
**Сценарий.** В марте порог 50 000 ₸, push отправлен при 50 000 ₸. Порог повышен до 100 000 ₸ (накоплено 50 000 ₸). Покупка доводит расходы до 100 000 ₸. По Ф-3 второго push нет; по Ф-4 push есть.  
**Последствия.** Клиент получает два push за месяц или ни одного при достижении нового порога; тест по Ф-4 нельзя принять однозначно.  
**Что исправить.** Согласовать Ф-3 и Ф-4: «Push за календарный месяц не более одного, в том числе после смены порога» либо «<уточнить: исключение из лимита при смене порога>».  
**Вопрос владельцу.** Может ли клиент получить второй push за месяц, если он поднял порог после уже отправленного push и расходы снова достигли нового порога? → [Q-03](#q-03)

#### <a id="d-04"></a>🔴 D-04. Сумма вне диапазона: по статусам 400, по логике и примеру — 200 с result ERROR

**Требования:** [R-19](#r-19), [R-21](#r-21), [R-30](#r-30), [R-35](#r-35), [R-36](#r-36), [R-37](#r-37) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** тестировщик, архитектор, проверка набора, правило «api.success_with_error»

- Часть B › Логика работы метода, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»
- Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Для суммы вне диапазона перечень статусов (строка 163) даёт 400, а шаг 5 логики (строка 121) и пример (строка 171) — HTTP 200 с result ERROR; строка 151 считает 200 успешным, строка 165 подписывает 200 как Created.  
**Сценарий.** Запрос amount=999, enabled=1 с валидной сессией: по строке 163 — 400, по строке 171 — 200 с {"result":"ERROR","message":"Проверьте сумму"}. По строке 151 второй ответ считается успешным.  
**Последствия.** Клиент покажет успешное сохранение при отказе сервера или разработчики реализуют разные ответы; приёмка не может зафиксировать отказ по сумме.  
**Что исправить.** Выбрать один код для неверной суммы, например 400, и заменить строка 121, строка 171 и пример ответа на него; отразить в строке 151 и строка 163 одинаково.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «При amount вне 1 000–1 000 000 или не целом значении метод возвращает HTTP 400 и тело {"result":"ERROR","message":"<уточнить: текст ошибки>"}; пример со статусом 200 и ERROR исключить.»  
**Вопрос владельцу.** Какой HTTP-код должен возвращаться при отклонении суммы: 400 или 200 с result ERROR? → [Q-04](#q-04)

#### <a id="d-05"></a>🟠 D-05. Чужая карта: по статусам 403, по разделу 404 с телом «Карта не найдена»

**Требования:** [R-38](#r-38), [R-40](#r-40) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, тестировщик, архитектор, правило «api.status_404»

- Часть B › Статусы, строка 162: «200. Ответ в случае успешного выполнения метода»
- Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»
- Часть B › 403. Unsuccessful — Forbidden, строка 188: «403. Unsuccessful — Forbidden»
- Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты»

**Проблема.** Для чужой карты статус 403 описан в строке 175, а строка 189 возвращает 404; 404 в перечне статусов (строки 162–176) не описан, хотя в разделе ответа 403 он указан.  
**Сценарий.** Сессия клиента A, `cardId` указывает на карту клиента B. По строке 175 — 403, по строке 189 — 404 с {"message":"Карта не найдена"}.  
**Последствия.** Тест на отказ доступа не может зафиксировать код; клиент получает разные ответы; утечка факта существования карты зависит от выбранного кода.  
**Что исправить.** Выбрать один код для чужой и отсутствующей карты (например 404) и добавить его в перечень статусов; в строке 175 уточнить, что 403 не используется для чужой карты.

#### <a id="d-06"></a>🟠 D-06. Метод, изменяющий порог, объявлен как GET; параметры в адресе; Content-Type при пустом теле

**Требования:** [R-12](#r-12), [R-16](#r-16), [R-29](#r-29) · **Критерий:** Корректность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · **Вид:** контракт API · **Блокирует:** разработку · **Нашли:** правило «api.get_mutation.saveLimit», архитектор, риски, правило «api.content_type_without_body»

- Часть B › Общие параметры, строка 103: «Сохранение порога»
- Часть B › Общие параметры, строка 104: «REST type | GET»
- Часть B › Общие параметры, строка 108: «/alerts/saveLimit»
- Часть B › Общие параметры, строка 109: «curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN»
- Часть B › Request body, строка 147: «Content-Type: application/json»

**Проблема.** `saveLimit` (строка 103, строка 108) заменяет настройку, но тип запроса GET (строка 104); параметры `cardId`, amount, enabled передаются в строке адреса (строка 109); строка 147 задаёт Content-Type при «Тело не используется» (строка 148).  
**Сценарий.** Ссылка с amount=1000000&enabled=0 открыта в браузере или подгружена кэшем прокси: настройка меняется без действий клиента; значения оседают в журналах.  
**Последствия.** Порог меняется без ведома клиента; утечка идентификатора карты и суммы в журналах; шлюз с политикой «GET только на чтение» отклонит метод.  
**Что исправить.** Заменить на POST с параметрами в теле (application/json), либо <уточнить: иной метод>; убрать Content-Type из запроса без тела или описать тело.  
**Было → стало.** Строка 147: «Content-Type: application/json» → «REST type: <уточнить: PUT или POST>. Параметры передаются в теле запроса (application/json).»

#### <a id="d-07"></a>🟠 D-07. Сумма покупки в тиынах, порог в тенге: правило пересчёта и сравнения не описано

**Требования:** [R-11](#r-11), [R-05 / Ф-1](#r-05) · **Критерий:** Однозначность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · **Вид:** расхождение единиц · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, аналитик, архитектор, правило «units.currency_mix»

- Часть A › Функциональные требования, строка 37: «задаёт целый порог от 1 000 до 1 000 000 ₸ включительно»
- Часть A › Требования к данным, строка 49: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге»
- Часть A › Критерии приемки, строка 63: «Итог 50 000 ₸ и один push»

**Проблема.** строка 49 хранит сумму покупки в тиынах, строка 37 задаёт порог в тенге; правило приведения единиц и сравнения суммы с порогом не описано.

**<a id="q-01"></a>Q-01** Момент отнесения покупки к месяцу и push · ⛔ блокирует · кому: Владелец продукта · к [D-01](#d-01), [D-08](#d-08)

Где: строка 38 «Месяц определяется по дате совершения покупки в Алматы»; строка 64 «Провести 1 февраля в 00:03 по Алматы»; строка 23 «в момент покупки»

- **A** Месяц и push определяются по дате и времени совершения (авторизации) покупки в Алматы; push отправляется сразу после авторизации, даже если проведение произошло позже.
- **B** Месяц и push определяются по дате и времени проведения покупки в Алматы; push отправляется после проведения, цель формулируется как узнать о достижении порога при проведении.
- **C** Месяц определяется по дате совершения в Алматы, push отправляется по проведению; покупка 31 января, проведённая 1 февраля, относится к январю.

Зачем: Ф-2 относит покупку к месяцу по дате совершения, критерий приёмки относит ту же покупку 31 января к февралю по проведению, BPMN начинает с проведения. Разработка и тест дадут разный месяц для одного входа, а push может прийти в одном месяце и не прийти в другом.

**<a id="q-02"></a>Q-02** Чтение настроек и суммы за месяц · ⛔ блокирует · кому: Архитектор · к [D-02](#d-02)  
Каким методом приложение получает текущий порог, признак включения и сумму за месяц, если единственный описанный метод только сохраняет настройку?  
Где: строка 52 «Приложение читает и сохраняет настройки через дочерний документ»; строка 103 «Функциональные требования: чтение порога»; строка 29 «сумма за месяц и кнопка «Сохранить»»

- **A** В REST API добавляется метод чтения настроек: GET с параметром `cardId`; ответ содержит result, amount, enabled и сумму за месяц в тенге; ошибки — как у метода сохранения.
- **B** Экран не показывает текущий порог и сумму за месяц: из раздела UI убирается сумма за месяц, приложение показывает только поле ввода и кнопку «Сохранить».

Зачем: Без метода чтения приложение при открытии экрана не знает текущий порог и не может показать сумму за месяц. Разработка и тест экрана «Карты → Расходы → Уведомления» не имеют входа и выхода для чтения.

**<a id="q-03"></a>Q-03** Повторный push в месяце после смены порога · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03), [D-12](#d-12)  
Может ли по карте уйти второй push за календарный месяц, если клиент сменил порог или включил уведомление, и должен ли push уйти сразу при сохранении порога, если накопленная сумма уже не ниже него?  
Где: строка 39 «На карту приходится максимум один такой push за календарный месяц»; строка 40 «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **A** Не более одного push за календарный месяц по карте, в том числе после смены порога и включения. Если push за месяц уже отправлен, новый не отправляется. Если push не отправлен и после сохранения сумма не ниже порога, push отправляется сразу.
- **B** После смены порога разрешён один дополнительный push при достижении нового порога, всего не более двух в месяц. При сохранении порога, который накопленная сумма уже превышает, push не отправляется до следующего перехода.
- **C** Лимит один push в месяц не действует после смены порога: при сохранении порога, не выше накопленной суммы, push отправляется сразу; при каждом новом переходе через порог push отправляется без ограничения по числу за месяц.

Зачем: Для одного и того же входа (смена порога после отправленного push) Ф-3 даёт ноль push, Ф-4 даёт один. Тестировщик и разработчик расходятся в том, сколько push и когда отправлять по сохранению порога.

**<a id="q-04"></a>Q-04** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-04](#d-04)  
Какой HTTP-код и тело ответа возвращается при сумме порога вне диапазона 1 000–1 000 000 ₸ или не целом значении?  
Где: строка 163 «400. Ответ в случае, если параметры запроса заполнены неверно»; строка 121 «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; строка 171 «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму"}; шаг 5 логики и пример ответа приводятся к статусу 400; успех остаётся 200.
- **B** HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; статус 400 используется только для структурно неверного запроса, например без `cardId` или enabled.
- **C** HTTP 400 для любых неверных параметров, включая отсутствие `cardId`, с телом {"message":"Некорректный запрос"}; поле result в этом случае не возвращается.

Зачем: Для суммы 999 ₸ при валидной сессии тест ожидает либо 400, либо 200 с ERROR. Клиентское приложение по-разному обрабатывает эти ответы: одно видит сбой запроса, другое — успешный ответ с ошибкой в теле.

**<a id="q-05"></a>Q-05** Код ответа для чужой карты · ⛔ блокирует · кому: ИБ · к [D-05](#d-05)  
Какой код возвращается при запросе по карте, принадлежащей другому клиенту, и должен ли он отличаться от ответа для несуществующей карты?  
Где: строка 175 «403. Ответ в случае, если на указанный ресурс доступ запрещен»; строка 189 «Для чужой карты возвращается 404, как и для отсутствующей карты»

- **A** Чужая и отсутствующая карта: HTTP 404 с телом {"message":"Карта не найдена"}; 403 в этом методе не используется; 404 добавляется в перечень статусов.
- **B** Чужая карта: HTTP 403 с телом {"message":"Доступ запрещён"}; отсутствующая карта: HTTP 404 с телом {"message":"Карта не найдена"}.
- **C** Чужая и отсутствующая карта: HTTP 403 с телом {"message":"Доступ запрещён"}; 404 в этом методе не используется.

Зачем: Для сессии клиента A с `cardId` карты клиента B тест ожидает 403 по перечню статусов и 404 по разделу ответа. Вариант 403 или 404 по-разному раскрывает существование карты в системе, что является вопросом ИБ.

**<a id="q-06"></a>Q-06** Кто и при каком статусе карты задаёт порог · не блокирует · кому: Владелец продукта · к [D-13](#d-13), [D-15](#d-15)  
Кто вправе задать порог: держатель любой карты KZT, включая дополнительную, или только владелец счёта? И что происходит с настройкой, если карта заблокирована или не в KZT?  
Где: строка 37 «Держатель активной карты KZT задаёт целый порог»; строка 105 «Bearer, сессия владельца карты»; строка 118 «Проверить принадлежность карты клиенту»

- **A** Держатель любой активной карты KZT, в том числе дополнительной, задаёт порог и видит сумму за месяц. Сохранение для заблокированной карты или карты не в KZT отклоняется ответом 400 с ERROR, настройка не меняется.
- **B** Только владелец счёта задаёт порог; держателю дополнительной карты отказ с кодом 404 как для чужой карты. Сохранение для заблокированной карты или карты не в KZT отклоняется ответом 400 с ERROR, настройка не меняется.
- **C** Держатель и владелец счёта задают порог для своих карт, последнее сохранение перезаписывает предыдущее. При блокировке карты настройка сохраняется, push по ней не отправляется.

Зачем: Ф-1 и API по-разному называют субъекта: держатель против владельца сессии. Для дополнительной карты тест не знает, кому вернуть отказ, а для заблокированной карты метод сохраняет порог и возвращает OK, при этом push продолжает уходить.

**<a id="q-07"></a>Q-07** Учёт покупок в иностранной валюте · не блокирует · кому: Владелец продукта · к [D-14](#d-14)  
Входят ли покупки в иностранной валюте в счётчик расходов, и если да, по какому курсу и на какую дату пересчитывается их сумма в тенге?  
Где: строка 38 «В расходы входят проведённые покупки»; строка 49 «сумму покупки в тиынах»

- **A** В расходы входят покупки в любой валюте; сумма переводится в тенге по курсу процессинга на дату проведения покупки.
- **B** В расходы входят покупки в любой валюте; сумма переводится в тенге по курсу процессинга на дату совершения покупки.
- **C** В расходы входят только покупки в KZT; покупки в иностранной валюте не учитываются.

Зачем: Покупка на 10 долларов США при одном и том же пороге даёт разный итог в зависимости от даты курса; тестовые данные для проверки счётчика не определены, и приёмка не может подтвердить итог.

**<a id="q-08"></a>Q-08** Содержимое push: сумма покупки или итог · не блокирует · кому: Владелец продукта · к [D-18](#d-18)  
Какую сумму видит клиент в push при достижении порога: сумму покупки, которая перевела расходы через порог, или накопленную сумму за месяц?  
Где: строка 43 «передать последние четыре цифры карты и сумму при достижении порога»; строка 63 «Итог 50 000 ₸ и один push»

- **A** Сумму покупки, которая перевела накопленную сумму через порог; накопленная сумма в push не передаётся.
- **B** Накопленную сумму за месяц на момент достижения порога; сумма покупки в push не передаётся.
- **C** Сумму покупки и накопленную сумму за месяц в одном push.

Зачем: Для покупки 1 500 ₸ при накоплении 48 500 ₸ и пороге 50 000 ₸ push либо содержит 1 500 ₸, либо 50 000 ₸. Текст push и его тест не могут быть написаны до ответа.

**<a id="q-09"></a>Q-09** Состав события процессинга для возврата и push · не блокирует · кому: Архитектор · к [D-16](#d-16), [D-19](#d-19)  
Какие поля передаёт процессинг в событии операции: тип операции, идентификатор исходной покупки для возврата, последние четыре цифры карты? Откуда сервис расходов берёт их, если процессинг не передаёт?  
Где: строка 38 «Возврат уменьшает расходы месяца исходной покупки»; строка 49 «Хранить идентификатор карты, месяц, идентификатор операции»; строка 43 «Процессинг → сервис расходов: проведена покупка»

- **A** Событие содержит тип операции, идентификатор исходной покупки для возврата и последние четыре цифры карты.
- **B** Событие содержит тип операции и идентификатор исходной покупки; последние четыре цифры сервис расходов берёт из справочника карт по `cardId`.
- **C** Событие содержит тип операции и последние четыре цифры карты; возврат уменьшает счётчик месяца возврата без привязки к исходной покупке.

Зачем: Без типа операции нельзя исключить переводы и наличные, без ссылки на покупку нельзя уменьшить месяц исходной покупки, без четырёх цифр нельзя передать их в push. Хранилище и тест возврата не имеют состава входа.

**<a id="q-10"></a>Q-10** Признак повторной доставки события · не блокирует · кому: Архитектор · к [D-20](#d-20)  
Как распознаётся повторная доставка одного события покупки и должен ли повтор повторно отправлять push, если первая отправка не состоялась?  
Где: строка 52 «Повторная доставка одного события процессинга сохраняет исходный итог»; строка 49 «идентификатор операции»

- **A** Повтор распознаётся по идентификатору операции; повтор не меняет счётчик; push повторно отправляется, только если первая попытка push завершилась ошибкой.
- **B** Повтор распознаётся по идентификатору операции; повтор не меняет счётчик и не отправляет push повторно, даже если первая отправка не состоялась.
- **C** Повтор распознаётся по сочетанию карты, суммы и даты; повтор не меняет счётчик и не отправляет push повторно.

Зачем: Если две реальные покупки по 1 500 ₸ в один день распознаются как повтор, вторая не попадёт в счётчик. Если повтор не распознан, push уйдёт дважды. Тест повторной доставки не может задать ожидаемый итог.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Критерии.** Отдельное требование (ISO/IEC/IEEE 29148:2018 п. 5.2.5, 5.2.7): необходимость, уместность (что, а не как), однозначность, полнота требования, единичность, осуществимость, проверяемость, корректность, соответствие шаблону, язык требований. Набор (29148 п. 5.2.6, IEEE 830-1998 п. 4.3): согласованность, полнота набора, осуществимость набора, понятность, возможность валидации, ранжирование по важности, модифицируемость, прослеживаемость. Плюс ИБ и операционные риски по чек-листу банка.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
