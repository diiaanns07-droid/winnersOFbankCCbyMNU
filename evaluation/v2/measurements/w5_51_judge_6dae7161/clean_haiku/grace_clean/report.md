**<a id="q-01"></a>Q-01** Возврат покупки и порог полного погашения · можно ответить позже · кому: Владелец продукта · к [D-11](#d-11)  
Сравнивается ли внесённая клиентом сумма для проверки полного погашения с суммой на дату выписки или с суммой, уменьшенной возвратами покупок, отражёнными до 25-го числа? Правило про полное погашение и правило про возврат дают разный результат для одного и того же клиента.  
Где: Ф-3, строка 38: «Если клиент внёс сумму для погашения полностью до окончания платёжного периода…»; Ф-5, строка 40: «Возврат покупки, отражённый до окончания платёжного периода, тоже уменьшает оставшуюся…»

- **A** Порог полного погашения равен сумме для погашения на дату выписки. Возврат покупки, отражённый до 25-го включительно, не меняет порог, но уменьшает задолженность, на которую начисляются проценты при неполном погашении.
- **B** Порог полного погашения равен сумме на дату выписки за вычетом возвратов покупок расчётного периода, отражённых до 25-го включительно. Если клиент внёс этот остаток до 25-го включительно, проценты по покупкам не начисляются.

Зачем: Без выбора два разработчика по-разному реализуют проверку полного погашения при возврате, и тесты на эту ситуацию нельзя написать однозначно.

Где: Часть A › Общие сведения, строка 18: «Мобильный банк, кредитный модуль, карточный процессинг, сервис уведомлений»; Часть A › Архитектура решения, строка 25: «Мобильное приложение → API кредитных карт → кредитный модуль»

- **A** Карточный процессинг после зачисления платежа отправляет в кредитный модуль событие с суммой, датой зачисления и идентификатором карты; в архитектуре и sequence-диаграмме добавляется процессинг с этим событием.
- **B** Кредитный модуль при каждом запросе сведений о льготном периоде синхронно запрашивает у карточного процессинга платежи за текущий период с отметкой времени зачисления.

Зачем: Без выбора не ясно, откуда берутся платежи для расчёта остатка и как учитывается условие «не позднее чем за 5 минут до запроса», поэтому интеграцию нельзя реализовать и проверить.

**<a id="q-04"></a>Q-04** Назначение кнопки «Пополнить» · можно ответить позже · кому: Владелец продукта · к [D-07](#d-07)  
Что делает кнопка «Пополнить» в блоке льготного периода: какой сценарий и какой метод API она запускает? В документе кнопка есть на экране, а в части API описаны только получение сведений и включение напоминания.  
Где: Часть A › Дизайн процесса UI, строка 28: «кнопка «Пополнить» и переключатель «Напоминать о платеже»»; Часть B, строка 98: «Описаны два метода: получение сведений о льготном периоде (метод 1) и включение или…»

- **A** Кнопка открывает пополнение на сумму для погашения; для этого в части API добавляется отдельный метод пополнения платежа по карте с описанием запроса, ответа и кодов.
- **B** В этой версии кнопка «Пополнить» не выводится; блок показывает только дату, сумму, дни и переключатель.

Зачем: Разработчики мобильного приложения не могут связать кнопку с методом и не могут написать тест на переход, а при реализации будет либо мёртвая кнопка, либо вызов несуществующего метода.

**<a id="q-05"></a>Q-05** Источник покупок для прогноза процентов и общей задолженности · можно ответить позже · кому: Архитектор · к [D-19](#d-19)  
Каким вызовом кредитного модуля метод получения сведений получает покупки текущего расчётного периода с датами отражения и общую задолженность на дату запроса? Шаг с выпиской и платежами этих данных не содержит.  
Где: Логика работы метода, п. 3, строка 120: «Получить из кредитного модуля последнюю выписку и платежи после даты выписки»; Особые правила, п. 2, строка 127: «прогноз процентов считается на всю задолженность по покупкам расчётного периода с даты…»; Часть B › Ответ, строка 159: «Общая задолженность по карте на дату запроса, тиыны»

- **A** Кредитный модуль отдаёт по карте список покупок текущего расчётного периода с датами отражения и текущую общую задолженность; метод получения сведений запрашивает их на шаге 3 и по ним считает прогноз процентов и `totalDebt`.
- **B** Кредитный модуль отдаёт готовые суммы: прогноз процентов при частичном погашении и общую задолженность на дату запроса; метод получения сведений передаёт их в ответе без расчёта.

Зачем: Без источника данных невозможно посчитать `interestForecast` и `totalDebt`, а значит ни один тест на эти поля нельзя написать.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
