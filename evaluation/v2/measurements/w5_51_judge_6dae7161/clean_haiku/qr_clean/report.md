### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🟠 D-01. Маршрут перевода по QR: схема последовательности минует сервис QR-кодов

- Часть A › Архитектура решения, строка 25: «Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод»
- Часть A › Sequence Diagram, строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду»
- Часть B › Схема, строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов»

**Проблема.** Строки 25 и 136 направляют перевод через сервис QR-кодов, а строка 45 ведёт приложение отправителя напрямую в сервис переводов. Проверки срока и оплаты QR (строка 124, строка 126) при прямом вызове могут быть пропущены.  
**Сценарий.** QR с суммой 5 000 ₸ создан в 10:00, перевод отправлен в 10:20: по строке 124 ответ 410, но по строке 45 перевод уходит в сервис переводов без проверки срока.  
**Последствия.** Разработчики интеграции реализуют разные маршруты, и проверка срока и статуса QR-кода может быть пропущена.  
**Как исправить.** Привести Sequence Diagram в соответствие с архитектурой: перевод идёт через сервис QR-кодов.  
**Было → стало.** Строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду» → «Приложение отправителя → сервис QR-кодов: выполнить перевод по QR-коду. Сервис QR-кодов → сервис переводов: провести перевод.»  
**Вопрос владельцу.** Перевод по QR-коду выполняется через сервис QR-кодов (A) или приложение вызывает сервис переводов напрямую (B)? → [Q-01](#q-01) (варианты ответа)  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-02](#r-02 "Маршрут вызовов между приложениями и сервисами"), [R-11](#r-11 "Последовательность вызовов между системами"), [R-31](#r-31 "Схема вызова метода перевода по QR-коду") · нашли: аналитик, архитектор, проверка набора*

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
