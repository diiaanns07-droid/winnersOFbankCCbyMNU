### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Не определено, какое событие процессинга считается «проведена»

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель обещает push «в момент покупки» (строка 23), в расходы входят «проведённые» покупки (строка 38), событие «проведена покупка» (строка 43) не определено: авторизация или клиринг. Срок «в течение минуты» (строка 46) считается от неясного события.  
**Сценарий.** Покупка 1 500 ₸ авторизована сегодня, клиринг через 2 дня. При событии «авторизация» push уходит сразу, при «клиринге» — через 2 дня и возможно с другой суммой.  
**Последствия.** Разработка выбирает событие наугад, тестирование не может проверить обещание «в момент покупки»; клиент получает push с опозданием либо по сумме, которая потом изменится.  
**Как исправить.** Зафиксировать, какое событие процессинга (авторизация или клиринг) входит в расходы, как учитывается разница сумм и отмена авторизации, и согласовать с этим цель и срок в одну минуту.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки, по которым получено событие <уточнить: авторизация или клиринг>; при отмене авторизации или ином размере суммы расходы пересчитываются <уточнить: как>.»  
**Вопрос владельцу.** Расходы учитываются по авторизации (push сразу) или по клирингу (push через 1–3 дня)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — максимум один push на карту в календарный месяц (Алматы) при любых сменах порога; B — после каждой смены порога на значение выше накопленных расходов допускается новый push…; C — push отправляется при каждом переходе от суммы ниже порога к сумме не ниже порога…  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Уведомить клиента о достижении бюджета при покупке"), [R-06 / Ф-2](#r-06 "Правила учёта расходов и определения месяца"), [R-09](#r-09 "Последовательность обмена процессинга, расходов, настроек и push"), [R-10](#r-10 "Передача push на отправку в течение минуты") · нашли: риски, аналитик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Ф-3 и Ф-4 по-разному решают повторный push за месяц

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки»

#### <a id="d-04"></a>🔴 D-04. Критерий приёмки №2 противоречит правилу Ф-2 о месяце

**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03: по Ф-2 растёт январь, по критерию — февраль.

Где: Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR.»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно.»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** Код 400 с телом «Некорректный запрос»; настройка не меняется; прежнее состояние не возвращается, ветка ERROR в блоке 200 удаляется.
- **B** Код 200 с result ERROR, message «Проверьте сумму» и полями прежних amount и enabled; код 400 только для отсутствующих или нечисловых параметров.

Зачем: Клиент и сервер по-разному разберут ответ на недопустимую сумму, тест ожидаемого кода не напишешь.

**<a id="q-06"></a>Q-06** Тип HTTP-метода сохранения порога · можно ответить позже · кому: Архитектор · к [D-06](#d-06)  
Каким HTTP-методом сохранять порог, если сейчас изменяющий метод объявлен как GET с параметрами в адресе?  
Где: Часть B › Общие параметры, строка 104: «REST type | GET»; Часть B › Request body, строка 148: «Тело не используется.»

- **A** POST с параметрами в теле запроса в формате JSON; параметры из строки адреса убираются.
- **B** PUT с параметрами в теле запроса в формате JSON, повторное сохранение идемпотентно.

Зачем: GET с изменением состояния кэшируется, повторяется прокси и пишет параметры в журналы.

**<a id="q-07"></a>Q-07** Единица суммы и пересчёт тиын в тенге · можно ответить позже · кому: Архитектор · к [D-07](#d-07)  
В каких единицах хранить и сравнивать расходы и порог, как округлять тиыны?  
Где: Часть A › Требования к данным, строка 49: «сумму покупки в тиынах» · «порог в тенге»

- **A** Расходы хранятся в тиынах, порог переводится в тиыны (×100), сравнение в тиынах без округления.
- **B** Расходы хранятся в тиынах и округляются вниз до целых тенге перед сравнением с порогом.

Зачем: Без правила на сумме с тиынами, например 49 999,50 ₸ при пороге 50 000, результат сравнения будет разным.

**<a id="q-08"></a>Q-08** Код ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-18](#d-18)  
Какой код возвращать, если карта принадлежит другому клиенту: 403 или 404, как для несуществующей карты?  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен.»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты.»

- **A** 404 «Карта не найдена» и для чужой, и для отсутствующей карты (не раскрывать существование); 403 для этого случая не используется.
- **B** 403 «Forbidden» для чужой карты, 404 только для несуществующей карты.

Зачем: Два места дают разный код на один вход; выбор влияет на раскрытие существования чужих карт.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
