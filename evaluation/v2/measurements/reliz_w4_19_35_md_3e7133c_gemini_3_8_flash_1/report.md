#### <a id="d-01"></a>🔴 D-01. Отсутствует метод REST API для чтения настроек

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 108: «Функциональные требования: чтение порога» · «Request URL | Dev: /alerts/saveLimit . Prod: —»

**Проблема.** Документ обещает чтение настроек экрана, но в спецификации API описан только метод сохранения `saveLimit` (строка 108).  
**Сценарий.** Клиент открывает экран настроек, мобильное приложение запрашивает текущие параметры, но эндпоинт чтения отсутствует, экран остаеться пустым.  
**Последствия.** Обещанную функцию показа нельзя реализовать и протестировать; объём работ недооценён.  
**Как исправить.** Добавить в спецификацию метод чтения (GET без побочных эффектов) со всеми показываемыми полями или убрать обещание чтения из требований.

**Варианты ответа:** A — описать отдельный GET-метод получения текущих настроек и накопленных расходов карты; B — добавить чтение настроек в параметры или ответ текущего метода `saveLimit`, изменив логику…

#### <a id="d-02"></a>🔴 D-02. Критерий приёмки №2 противоречит правилу Ф-2

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Правило Ф-2 определяет месяц по дате покупки в Алматы (январь), а критерий приемки №2 ожидает рост февральского счетчика (строка 64).  
**Сценарий.** Покупка 31 января в 23:58 проведена 1 февраля по Алматы. Ф-2 требует отнести ее к январю, а критерий приёмки ожидает февраль.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик вырос на 4 000 ₸», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик вырос на 4 000 ₸», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Январский счётчик вырос на 4 000 ₸»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик вырос на 4 000 ₸» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — относить к январю по дате совершения покупки в Алматы, исправив ожидаемый результат…; B — относить к февралю по дате проведения операции в процессинге, изменив правило определения…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸"), [R-06 / Ф-2](#r-06 "Правила учета операций в расходах месяца") · нашли: тестировщик*

#### <a id="d-03"></a>🔴 D-03. Ошибка валидации возвращает HTTP 200 вместо 400

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Логика метода возвращает результат ERROR (строка 121), а пример ответа дает статус 200 (строка 167), хотя для неверных параметров заявлен статус 400 (строка 163).  
**Сценарий.** Клиент отправляет недопустимую сумму, сервер возвращает HTTP 200 с телом ERROR, и приложение ошибочно считает операцию успешной.  
**Последствия.** Мобильный банк не сможет штатно обработать ошибку валидации, клиент получит ложное подтверждение сохранения настроек.  
**Как исправить.** Возвращать статус 400 Bad Request при ошибке валидации суммы и параметров запроса вместо 200 OK.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «400. Unsuccessful — Bad request {"message":"Проверьте сумму"}»  
**Вопрос владельцу.** Какой статус-код HTTP и тело ответа должны возвращаться клиенту при отклонении некорректной суммы порога в методе сохранения? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — возвращать HTTP 400 с JSON-структурой ошибки валидации параметров без поля result; B — возвращать HTTP 200 с телом содержащим результат ERROR и сообщение об ошибке под полем…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-21](#r-21 "Откат состояния при ошибке суммы"), [R-30](#r-30 "Правило определения успешности ответа"), [R-36](#r-36 "Код 400 — неверно заполненные параметры запроса"), [R-37](#r-37 "Пример успешного ответа или ошибки валидации") · нашли: архитектор, правило «контракт API»*

#### <a id="d-04"></a>🟠 D-04. Несоответствие единиц суммы покупки и порога

- Ф-1, строка 37: «целый порог от 1 000 до 1 000 000 ₸ включительно»
- Часть A › Требования к данным, строка 49: «сумму покупки в тиынах»

**Сценарий.** Покупка на 150 000 тиынов сравнивается с порогом 50 000 тенге без конвертации, что приводит к ложному срабатыванию.  
**Последствия.** Ложные срабатывания порога и отправка некорректных push-уведомлений клиентам.  
**Как исправить.** Указать в правилах пересчета явную конвертацию сумм операций из тиынов в тенге (1 тенге = 100 тиынов) перед суммированием и сравнением с порогом.  
**Было → стало.** Строка 49: «сумму покупки в тиынах» → «Сумма покупки хранится в тиынах и делится на 100 для получения суммы в тенге перед суммированием и сравнением с порогом.»  
**Вопрос владельцу.** В каких единицах измерения хранить сумму покупки для корректного сравнения с порогом? → [Q-04](#q-04) (варианты ответа)

#### <a id="d-05"></a>🟠 D-05. Нет атрибутов для учета типов операций и возвратов

- Ф-2, строка 38: «В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются»
- Часть A › Требования к данным, строка 49: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге»

**Проблема.** Модель данных (строка 49) не содержит признака типа операции и ссылки на исходную операцию для обработки возвратов по Ф-2.  
**Сценарий.** При поступлении возврата сервис не может определить тип операции и сопоставить ее с исходным месяцем покупки.  
**Последствия.** Разработчики не смогут реализовать корректный пересчет расходов при возвратах и отфильтровать исключаемые типы операций.  
**Как исправить.** Дополнить модель данных полями: тип операции (покупка, возврат, перевод, снятие наличных) и идентификатор исходной операции для возврата.  
**Было → стало.** Строка 49: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге» → «Хранить идентификатор карты, месяц, идентификатор операции, тип операции, идентификатор исходной операции, сумму покупки в тиынах, признак отправки и порог в тенге.»

#### <a id="d-06"></a>🟠 D-06. Норматив передачи push в течение минуты неизмерим

**Где:** Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Требование «в течение минуты» не задает перцентиль успешности и уровень нагрузки (строка 46).  
**Сценарий.** Нагрузочный тест показывает задержку для 5% запросов более минуты, но критерий прохождения теста не определен.  
**Последствия.** Тестировщик не напишет нагрузочный тест с критерием прохождения, приёмка требования превратится в спор, а деградацию под нагрузкой банк увидит только в эксплуатации.  
**Как исправить.** Записать норматив измеримо: значение с единицей, точку начала и конца замера, долю событий (перцентиль) и нагрузку, при которой он выполняется.  
*Существенный, блокирует тестирование · критерий «Проверяемость» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.6) · требование [R-10](#r-10 "Таймаут передачи push на отправку") · нашли: тестировщик*

#### <a id="d-07"></a>🟠 D-07. Метод `saveLimit` изменяет данные, но использует GET

- Часть B › Общие параметры, строки 103, 104, 108 и 109: «Сохранение порога» · «REST type | GET» · «/alerts/saveLimit» · «CURL | curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data…»
- Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения»

**Проблема.** Метод сохранения настройки использует HTTP GET (строка 104) и меняет состояние (строка 120), что нарушает REST и RFC 9110.  
**Сценарий.** Клиент сохраняет порог через GET с параметрами в URL, которые оседают в логах прокси, а повторный запрос кэшируется.  
**Последствия.** Разработка реализует небезопасный контракт; риск ИБ — идентификаторы и значения в журналах; автотесты контракта и шлюз API с политикой «GET только на чтение» его отклонят.  
**Как исправить.** Заменить GET на POST или PUT (PATCH — для частичного изменения), параметры передавать в теле запроса JSON и описать его схему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 104: «REST type | GET» → «REST type: <уточнить: PUT или POST>. Параметры передаются в теле запроса (application/json).»  
**Вопрос владельцу.** Требуется ли использовать метод POST для изменения настроек? → [Q-05](#q-05) (варианты ответа)  
*Существенный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-16](#r-16 "Параметры и параметры вызова метода REST API"), [R-20](#r-20 "Сохранение настройки и возврат результата") · нашли: правило «контракт API», архитектор, проверка набора, риски*

#### <a id="d-08"></a>🟠 D-08. Несоответствие типов полей amount и enabled в API

- Часть B › Query-параметры, строки 143 и 144: «amount | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | limit_kzt» · «enabled | integer»
- Часть B › Ответ, строки 156 и 157: «amount | string | При успехе | Порог в тенге | limit_kzt» · «enabled | string»

**Проблема.** Параметры amount и enabled в запросе определены как integer (строки 143, 144), а в ответе — как string (строки 156, 157).  
**Сценарий.** Клиент ожидает в ответе числовые типы согласно запросу, но получает строки, что вызывает ошибку десериализации.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»

#### <a id="d-09"></a>🟠 D-09. Заголовок Content-Type указан при отсутствии тела

**Где:** Часть B › Request body, строки 147 и 148: «Content-Type: application/json» · «Тело не используется»

**Проблема.** У метода `saveLimit` указан заголовок Content-Type: application/json при явном указании «Тело не используется» (строки 147, 148).  
**Сценарий.** Клиент отправляет запрос с заголовком и пустым телом, шлюз отклоняет его со статусом 400 или 415.  
**Последствия.** Расхождение реализаций клиента и сервера, лишний спор при приёмке контракта.  
**Как исправить.** Убрать Content-Type для запроса без тела или описать тело запроса и его поля; если параметры переносятся в тело, описать его схему.  
**Предлагаемая формулировка.** «Request body: не используется; заголовок Content-Type не передаётся.»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требование [R-29](#r-29 "Формат и отсутствие тела запроса") · нашли: правило «контракт API»*

#### <a id="d-10"></a>🟠 D-10. Открытый перечень неуспешных результатов API

**Где:** Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»

**Проблема.** Правило ответов использует формулировку «и далее» для перечня кодов ошибок (строка 151).  
**Сценарий.** При получении неустановленного кода ответа клиентская и серверная команды трактуют его по-разному.  
**Последствия.** Реализация и тесты расходятся на непоименованных значениях; спор при приёмке.  
**Как исправить.** Заменить открытый перечень полным списком значений или правилом, по которому значение однозначно относится к перечню.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Если результат 400, 401 и <уточнить: полный перечень>»  
**Вопрос владельцу.** Какие конкретно коды возврата нужно включить в спецификацию API?

#### <a id="d-11"></a>🟠 D-11. Код 201 упомянут в правиле, но отсутствует в статусах

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»

**Проблема.** Текст правила упоминает код 201 (строка 151), но в перечне статусов он не описан, а код 200 подписан как Created (строка 165).  
**Сценарий.** Сервер возвращает 201, приложение не находит его в спецификации и обрабатывает как ошибку.  
**Последствия.** Клиент обработает ответ как неизвестную ошибку; спор при приёмке о правильном коде; автотесты контракта нельзя написать однозначно.  
**Как исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требование [R-30](#r-30 "Правило определения успешности ответа") · нашли: правило «контракт API»*

#### <a id="d-12"></a>🟠 D-12. Поле result отсутствует в примерах ответов ошибок

- Часть B › Ответ, строка 155: «result | string | OK / ERROR»

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
