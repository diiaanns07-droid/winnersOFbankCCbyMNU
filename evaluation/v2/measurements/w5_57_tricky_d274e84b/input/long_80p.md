### Цели
Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.

### Архитектура решения
Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.

### Дизайн процесса UI
Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить». При ошибке ввода сообщение появляется под полем.

### Требования к изменениям

#### BPMN схема процесса
Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.

#### Функциональные требования
* **Ф-1.** Держатель активной карты KZT задаёт целый порог от 1 000 до 1 000 000 ₸ включительно. По умолчанию уведомление выключено.
* **Ф-2.** Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.
* **Ф-3.** Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push. На карту приходится максимум один такой push за календарный месяц.
* **Ф-4.** При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.

### Sequence Diagram
Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты. Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.

### Нефункциональные требования
Сервис передаёт push на отправку в течение минуты после получения события.

### Требования к данным
Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.

### Требования к интеграции
Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.

# Проценты по накопительному счёту

Комплект из двух исходных документов. Часть B — дочерняя спецификация, на которую ссылается раздел интеграции в части A.

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| :--- | :--- |
| **Наименование задачи** | Выбор способа выплаты процентов по накопительному счёту: капитализация или перечисление на карту |
| **Продукт** | Мобильный банк, сбережения |
| **Бизнес-процесс** | Обслуживание накопительных счетов |
| **Business owner / Product owner / Аналитик** | Дирекция пассивных продуктов / владелец раздела «Накопления» / аналитик команды сбережений |
| **Тип работы** | Новый функционал |
| **Влияние на ИС** | Мобильный банк, API сбережений, депозитный модуль, сервис уведомлений |
| **Задача в JIRA** | SAV-631 |

### Цели
Клиент сам выбирает, прибавлять проценты по накопительному счёту к остатку или получать их на карту, и видит, сколько процентов начислено за текущий месяц. Снизить число обращений в контакт-центр о способе выплаты процентов.

### Архитектура решения
Мобильное приложение → API сбережений → депозитный модуль. Депозитный модуль → сервис уведомлений → push-уведомление клиенту.

### Дизайн процесса UI
Накопления → накопительный счёт → «Проценты». На экране: ставка, проценты за текущий месяц, переключатель «Капитализация / На карту», выбор карты для выплаты (виден при выборе «На карту»), кнопка «История начислений» и кнопка «Сохранить». После сохранения под переключателем показывается дата, с которой действует новый способ.

### Требования к изменениям

#### BPMN схема процесса
Ежедневное начисление процентов → последний день месяца → определение способа выплаты → капитализация или перечисление на карту → push клиенту → завершение.

#### Функциональные требования
* **Ф-1.** Владелец накопительного счёта в тенге выбирает способ выплаты процентов: капитализация (проценты прибавляются к остатку счёта) или перечисление на свою карту KZT. По умолчанию — капитализация.
* **Ф-2.** Проценты начисляются ежедневно на остаток счёта на конец дня по ставке 14 % годовых, база — фактическое число дней в году. Остаток на конец дня — остаток счёта на 23:59:59 по времени Астаны (UTC+5). Проценты, начисленные за месяц, выплачиваются в последний календарный день месяца.
* **Ф-3.** Новый способ выплаты применяется начиная со следующего календарного месяца; проценты текущего месяца выплачиваются прежним способом. Проценты, выплачиваемые на карту, перечисляются на последнюю карту, указанную клиентом для способа «На карту».
* **Ф-4.** Если остаток счёта на конец дня меньше неснижаемого остатка 1 000 ₸, проценты за этот день не начисляются.
* **Ф-5.** После выплаты клиент получает push с суммой процентов и способом выплаты. Если на дату выплаты карта для выплаты не активна (закрыта или заблокирована), проценты за месяц капитализируются, а в push указывается причина.
* **Ф-6.** При закрытии счёта проценты за неполный месяц выплачиваются в день закрытия вместе с остатком счёта.

### Sequence Diagram
Приложение → API сбережений: получить условия и проценты. Приложение → API сбережений: сохранить способ выплаты. API сбережений → депозитный модуль: записать способ с 1-го числа следующего месяца. Депозитный модуль → сервис уведомлений: проценты выплачены.

### Нефункциональные требования
Ежедневные проценты округляются до тиына по математическому правилу; проценты за месяц — сумма округлённых ежедневных. Методы API отвечают не дольше 1 с для 95 % запросов, доступность — не ниже 99,9 % в месяц.

### Требования к данным
Хранить идентификатор счёта, способ выплаты, карту для выплаты, дату начала действия нового способа, ставку в процентах годовых, ежедневные начисления и выплаты процентов по месяцам в тенге с точностью до тиына.

### Требования к интеграции
Приложение получает ставку, проценты за текущий месяц и историю начислений и сохраняет способ выплаты через дочерний документ «Проценты по накопительному счёту — REST API».

#### Тестирование требований

### Логика работы метода
1. Проверить сессию клиента.
2. Проверить, что накопительный счёт принадлежит клиенту и открыт.
3. Если `mode` = `CARD`, проверить, что карта `cardId` принадлежит клиенту, активна и открыта в тенге.
4. Сохранить способ выплаты с датой начала действия — 1-е число следующего месяца по времени Астаны (UTC+5).
5. Вернуть способ выплаты текущего и следующего месяца, ставку и проценты за текущий месяц.

### Особые правила
1. Повторная установка уже выбранного способа не считается ошибкой: возвращается 200 с текущими условиями.
2. Если клиент несколько раз сменил способ в течение месяца, со следующего месяца действует последний выбранный.
3. Для способа `CAPITALIZATION` поле `cardId` не передаётся; переданное значение не сохраняется.

### Цели
Клиент обменивает валюту между своими текущими счетами в приложении круглосуточно и видит курс и сумму зачисления до подтверждения. Целевой показатель: через 6 месяцев после запуска не менее 60 % обменов физических лиц между своими счетами выполняется в приложении (по данным АБС за месяц; сейчас 0 %, обмен доступен только в отделениях).

### Архитектура решения
Приложение → сервис счетов (список счетов). Приложение → сервис обмена (контроллер `FxController`, методы 1 и 2 части B). Сервис обмена → сервис счетов (данные счёта), АБС (производственный календарь, проводка и её отмена), сервис курсов (курсы), сервис уведомлений (push).

### Дизайн процесса UI
Счета → «Обменять валюту». Экран обмена: списки «Счёт списания» и «Счёт зачисления» (текущие счета клиента со статусом `OPEN` в KZT, USD, EUR, RUB: последние 4 цифры номера, валюта и доступный остаток; в списке зачисления — только счета, образующие с выбранным счётом списания пару из Ф-1), поле «Сумма списания» (не более двух знаков после разделителя; приложение передаёт сумму с точкой и двумя знаками после неё: «150,5» → "150.50"; под полем — лимит Ф-3 для валюты счёта списания) и кнопка «Получить курс», активная при выбранных счетах и введённой сумме. Экран котировки (ответ метода 2): сумма списания, сумма зачисления, курс в виде «1 USD = 470.25 KZT», пометка «Курс нерабочего времени» при `rateType` = `NON_WORKING`, таймер обратного отсчёта на срок действия котировки (Ф-7), запускаемый при получении ответа, и кнопка «Подтвердить» (метод 1). Когда таймер дошёл до нуля или пришёл ответ 422 с `errorCode` = `QUOTE_EXPIRED`, вместо «Подтвердить» показывается кнопка «Обновить курс»: новый запрос метода 2 с теми же счетами и суммой. Экран результата (ответ 200 метода 1): «Обмен выполнен», сумма списания, сумма зачисления, курс и время обмена `executedAt`. При любом ответе с `errorCode` приложение показывает текст поля `message` под кнопкой текущего экрана.

### Требования к изменениям
#### BPMN схема процесса
Выбор счетов и суммы → создание котировки (метод 2) [проверки не пройдены → сообщение `message` на экране обмена] → экран котировки с таймером [срок котировки истёк → «Обновить курс» → создание котировки; проверки не пройдены → сообщение `message` на экране котировки] → «Подтвердить» → обмен по котировке (метод 1): проверки котировки и проводка в АБС [`QUOTE_EXPIRED` → «Обновить курс»; другой отказ или таймаут → сообщение `message` на экране котировки] → экран результата → push клиенту → конец.

#### Функциональные требования
* **Ф-1.** Клиент обменивает средства между двумя своими текущими счетами (`type` = `CURRENT`) со статусом `OPEN`. Поддерживаемые пары: KZT → USD, KZT → EUR, KZT → RUB и обратные USD → KZT, EUR → KZT, RUB → KZT. Обмен между двумя иностранными валютами и между счетами в одной валюте не выполняется.
* **Ф-2.** Клиент вводит сумму списания в валюте счёта списания; сумма зачисления не вводится, а рассчитывается по Ф-6.
* **Ф-3.** Лимит суммы списания в валюте счёта списания, обе границы включительно: KZT — от 1 000.00 до 10 000 000.00; USD и EUR — от 2.00 до 20 000.00; RUB — от 200.00 до 2 000 000.00. Сумма зачисления лимитом не ограничивается; других ограничений суммы, кроме Ф-3 и Ф-4, нет.
* **Ф-4.** Сумма списания не больше доступного остатка счёта списания (равенство допускается). Остаток проверяется при создании котировки по данным сервиса счетов и повторно АБС при проводке; котировка средства не резервирует.
* **Ф-5.** Тип курса определяется по времени получения запроса котировки: рабочее время (`WORKING`) — с 09:00:00 включительно до 18:00:00 не включительно в день, отмеченный рабочим в производственном календаре АБС; всё остальное время — нерабочее (`NON_WORKING`). Курсы обоих типов публикует сервис курсов.
* **Ф-6.** Курс котировки — число KZT за 1 единицу иностранной валюты с двумя знаками после точки: для обмена из KZT — курс продажи (банк продаёт иностранную валюту), для обмена в KZT — курс покупки (банк покупает иностранную валюту). Сумма зачисления: из KZT — сумма списания ÷ курс, в KZT — сумма списания × курс; результат округляется вниз до 0.01 единицы валюты зачисления (знаки после второго отбрасываются, разница остаётся у банка). Комиссия за обмен не взимается.
* **Ф-7.** Котировка фиксирует счета, суммы, курс и тип курса и действует 60 секунд: `expiresAt` = `createdAt` + 60 с, где `createdAt` — время получения запроса котировки. Обмен выполняется по курсу котировки, если запрос обмена получен сервисом обмена не позднее `expiresAt`, даже если тип курса к этому времени сменился; время обмена `executedAt` может быть позже `expiresAt`. Запрос, полученный позже `expiresAt`, отклоняется с `errorCode` = `QUOTE_EXPIRED`.
* **Ф-8.** По одной котировке выполняется не более одного обмена. Повторный запрос с тем же ключом идемпотентности (`quoteId` + `requestId`) возвращает результат выполненного обмена и не создаёт второй; срок хранения ключа и остальные случаи — часть B, особое правило 1.
* **Ф-9.** Списание и зачисление выполняются одной проводкой АБС: проходят обе или ни одна. Если АБС отказала в проводке, остатки не меняются; если не дала результата за время таймаута (И-2), сервис обмена отменяет проводку (часть B, особое правило 2). В обоих случаях обмен не выполнен, котировка действует до `expiresAt`.
* **Ф-10.** После выполненного обмена клиент получает один push: «Обмен выполнен: списано {debitAmount} {debitCurrency}, зачислено {creditAmount} {creditCurrency}, курс {rate} KZT за 1 {foreignCurrency}», где {foreignCurrency} — валюта пары, отличная от KZT. Номера счетов в push не входят; невыполненный обмен push не порождает; сбой отправки push не меняет результат обмена.

### Требования к интеграции
**И-1.** Приложение создаёт котировку и выполняет обмен по котировке через дочерний документ «Обмен валюты между своими счетами — REST API» (часть B, методы 2 и 1); список счетов получает существующим методом сервиса счетов `GET /accounts/v1/accounts` (поля `accountId`, `maskedNumber`, `currency`, `type`, `status`, `availableBalance`). **И-2.** Сервис обмена вызывает существующие методы без их доработки (суммы и курсы — в формате части B): сервис счетов `GET /accounts/v1/accounts/{accountId}` (`clientId`, `currency`, `type`, `status`, `availableBalance`); АБС `GET /abs/v1/calendar/{date}` (`workingDay`: true / false), `POST /abs/v1/fx-postings` (проводка одной транзакцией с ключом `exchangeId`; результат «проведено», «недостаточно средств», «счёт недоступен» или «отказ») и `POST /abs/v1/fx-postings/{exchangeId}/cancel` (отмена проводки, результат «отменено»); сервис курсов `GET /rates/v1/retail?currency={currency}&rateType={rateType}` (`buyRate`, `sellRate`); сервис уведомлений `POST /notifications/v1/push` (`clientId`, `text`). Таймаут ожидания ответа — 10 с для проводки АБС и 3 с для остальных методов. **И-3.** Если ответ метода 1 не получен за 15 с, приложение один раз повторяет запрос с тем же `requestId`; каждое новое нажатие «Подтвердить» создаёт новый `requestId`. **И-4.** Push передаётся в сервис уведомлений после проводки асинхронно и не задерживает ответ метода 1; при ответе сервиса уведомлений с ошибкой передача повторяется до 2 раз с интервалом 10 с, после чего push не отправляется; при отсутствии ответа за время таймаута (И-2) повтор не выполняется.

### Логика работы метода
В обоих методах проверки выполняются по порядку и возвращается код первой не пройденной; время получения запроса — момент его поступления в сервис обмена (для метода 1 — до ожидания очереди). Метод 1 (запросы одного клиента выполняются по одному, начиная с шага 2):
1. Проверить сессию клиента, затем тело по строкам таблицы Request body с отметкой метода 1: нет действующей сессии — 401 `UNAUTHORIZED`; нарушение формата — 400 `VALIDATION_ERROR`.
2. Найти сохранённый ответ 200 по ключу «клиент, `quoteId`, `requestId`» (особое правило 1); найден — вернуть его без шагов 3–5.
3. Найти котировку `quoteId` среди котировок клиента; не найдена — 404 `QUOTE_NOT_FOUND`. Котировка со статусом `USED` — 422 `QUOTE_ALREADY_USED`; время получения запроса позже `expiresAt` — 422 `QUOTE_EXPIRED`.
4. Создать обмен со статусом `PROCESSING` и передать в АБС проводку по счетам и суммам котировки с ключом `exchangeId`. Ответ АБС «недостаточно средств» — 422 `INSUFFICIENT_FUNDS`; «счёт недоступен» — 422 `ACCOUNT_NOT_AVAILABLE`; «отказ» — 500 `INTERNAL_ERROR`; за время таймаута (И-2) не получен ни один из результатов проводки, перечисленных в И-2, — отменить проводку (особое правило 2) и вернуть 500 `INTERNAL_ERROR`. В этих случаях обмен получает статус `FAILED`, котировка остаётся `ACTIVE`.
5. Ответ АБС «проведено»: обмену — статус `DONE` и `executedAt`, котировке — `USED`; сохранить ответ по ключу шага 2; передать push (Ф-10, И-4); вернуть 200.

Метод 2 (если сервис счетов, АБС или сервис курсов не ответили за время таймаута И-2 или вернули ошибку — 500 `INTERNAL_ERROR`, котировка не создаётся):
1. Нет действующей сессии — 401 `UNAUTHORIZED`; тело не соответствует строкам таблицы Request body с отметкой метода 2 — 400 `VALIDATION_ERROR`.
2. Счёт списания или счёт зачисления не найден среди счетов клиента (сервис счетов) — 404 `ACCOUNT_NOT_FOUND`; валюты счетов не образуют пару из Ф-1 — 422 `PAIR_NOT_SUPPORTED`; один из счетов не текущий или его статус не `OPEN` — 422 `ACCOUNT_NOT_AVAILABLE`; сумма списания вне лимита Ф-3 — 422 `AMOUNT_OUT_OF_LIMITS`; сумма списания больше доступного остатка счёта списания — 422 `INSUFFICIENT_FUNDS`.
3. Определить тип курса (Ф-5) по календарю АБС, получить курс (Ф-6) в сервисе курсов, рассчитать сумму зачисления (Ф-6), сохранить котировку со статусом `ACTIVE`, `createdAt` и `expiresAt` (Ф-7) и вернуть 200.

### Особые правила
1. Ключ идемпотентности метода 1 — `quoteId` + `requestId` в пределах клиента. Сохраняется только ответ 200, на 24 часа с момента ответа; повтор с тем же ключом в течение этих 24 часов возвращает сохранённое тело (тот же `exchangeId`) без проводки и push. Повтор после ответа 400, 401, 404, 422 или 500, а также позже 24 часов обрабатывается как новый запрос.
2. Отмена проводки (шаг 4 метода 1): сервис обмена отправляет в АБС отмену по `exchangeId` и повторяет её каждые 30 с до подтверждения; отмена выполненной проводки возвращает остатки обоих счетов к исходным, отмена невыполненной запрещает её выполнение. Ответ 500 возвращается после первой отправки отмены.

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| :--- | :--- |
| **Наименование задачи** | Отображение льготного периода и напоминание о платеже по кредитной карте |

| **Влияние на ИС** | Мобильный банк, кредитный модуль, сервис уведомлений |
| **Задача в JIRA** | CARD-2417 |

### Цели
Клиент заранее видит, до какой даты и какую сумму нужно внести, чтобы не платить проценты за покупки по кредитной карте. Снизить долю клиентов, которые теряют льготный период из-за пропущенной даты платежа.

### Архитектура решения
Мобильное приложение → API кредитных карт → кредитный модуль. Кредитный модуль → сервис уведомлений → push-уведомление клиенту.

### Дизайн процесса UI
Главная → Кредитная карта → блок «Льготный период». В блоке показаны дата окончания платёжного периода, оставшаяся сумма для погашения без процентов, сколько дней осталось, кнопка «Пополнить» и переключатель «Напоминать о платеже». Если льготный период утрачен, вместо даты показывается надпись «Начисляются проценты» и общая сумма задолженности.

### Требования к изменениям

#### BPMN схема процесса
Формирование выписки → расчёт суммы для погашения → ожидание платежа → напоминание за 3 дня → проверка погашения в конце платёжного периода → сохранение или утрата льготного периода.

#### Функциональные требования
* **Ф-1.** Льготный период действует для покупок по кредитной карте и длится до 55 календарных дней. Даты и время в документе — по времени Астаны (UTC+5). Расчётный период равен календарному месяцу, выписка формируется 1-го числа следующего месяца, платёжный период заканчивается 25-го числа того же месяца. Если 25-е число приходится на выходной или праздничный день, окончание платёжного периода не переносится.
* **Ф-2.** Сумма для погашения без процентов равна задолженности по покупкам расчётного периода на дату выписки. Покупка относится к расчётному периоду по дате её отражения на счёте карты. Снятие наличных, переводы с кредитной карты, операции, приравненные к снятию наличных (квази-кэш), и комиссии банка в льготный период не входят: проценты по ним начисляются с даты операции.
* **Ф-3.** Если к окончанию платёжного периода включительно оставшаяся сумма для погашения (Ф-5) равна 0, проценты по покупкам расчётного периода не начисляются. Если она больше 0, проценты начисляются на всю задолженность по покупкам расчётного периода с даты отражения каждой покупки на счёте.
* **Ф-4.** Если переключатель «Напоминать о платеже» включён и оставшаяся сумма для погашения больше 0, за 3 календарных дня до окончания платёжного периода клиент получает push с датой окончания и оставшейся суммой. По умолчанию переключатель включён.
* **Ф-5.** Платёж считается внесённым в момент зачисления на счёт кредитной карты; платёжный период заканчивается 25-го числа в 23:59:59 по времени Астаны (UTC+5). Внесённый платёж уменьшает оставшуюся сумму для погашения. Возврат покупки, отражённый до окончания платёжного периода, тоже уменьшает оставшуюся сумму; возврат, отражённый позже, уменьшает задолженность, но утраченный льготный период не восстанавливает. Покупки, отражённые на счёте после окончания расчётного периода, относятся к следующему расчётному периоду и сумму для погашения не меняют.

### Sequence Diagram
Мобильное приложение → API кредитных карт: запросить сведения о льготном периоде. API кредитных карт → кредитный модуль: получить выписку, платежи и возвраты покупок. Кредитный модуль → сервис уведомлений: передать дату окончания и оставшуюся сумму для напоминания.

### Нефункциональные требования
Метод получения сведений о льготном периоде отвечает не дольше 1 с для 95 % запросов при нагрузке до 300 запросов в секунду. Сведения учитывают платежи, зачисленные не позднее чем за 5 минут до запроса. Напоминание передаётся в сервис уведомлений 22-го числа с 10:00 до 12:00 по времени Астаны.

### Требования к данным
Хранить идентификатор карты, расчётный период, дату выписки, дату окончания платёжного периода, общую задолженность в тиынах, сумму для погашения в тиынах, сумму внесённых платежей в тиынах, признак сохранения льготного периода и признак включения напоминания.

### Требования к интеграции
Приложение получает сведения о льготном периоде и включает или выключает напоминание через дочерний документ «Льготный период по кредитной карте — REST API». Кредитный модуль передаёт в сервис уведомлений одно напоминание на карту за платёжный период.

### Логика работы метода
1. Проверить сессию клиента.
2. Проверить, что карта принадлежит клиенту (иначе вернуть 404), затем что она кредитная (иначе вернуть 422).
3. Получить из кредитного модуля последнюю выписку, а также платежи и возвраты покупок после даты выписки.
4. Рассчитать оставшуюся сумму для погашения и количество дней до окончания платёжного периода.
5. Вернуть сведения о льготном периоде и прогноз процентов на случай частичного погашения.

### Особые правила
1. Сумма для погашения не может быть отрицательной: переплата показывается как 0.
2. При частичном погашении прогноз процентов считается на всю задолженность по покупкам расчётного периода с даты отражения каждой покупки на счёте, как в Ф-3.
3. Если выписка ещё не сформирована, возвращаются сведения по предыдущему платёжному периоду.

| **Влияние на ИС** | Мобильный банк, API кредитов, кредитный конвейер, сервис страхования, страховая компания-партнёр, сервис уведомлений |
| **Задача в JIRA** | LOAN-958 |

### Цели
Клиент может добровольно подключить страхование жизни при оформлении кредита наличными и получить ставку ниже, а в период охлаждения — отказаться от страхования в приложении. Увеличить долю кредитов со страхованием без жалоб на навязывание услуги.

### Архитектура решения
Мобильное приложение → API кредитов → кредитный конвейер. API кредитов → сервис страхования. Кредитный конвейер → сервис страхования → страховая компания-партнёр. Сервис страхования → сервис уведомлений.

### Дизайн процесса UI
Кредиты → «Кредит наличными» → экран условий: сумма, срок, флажок «Страхование жизни» (по умолчанию снят; включая его, клиент даёт согласие на передачу персональных данных страховой компании-партнёру), стоимость страхования, ставка со страхованием и без него, ссылка на правила страхования.
После выдачи: Кредиты → кредит → «Страхование» → номер полиса, дата начала действия и кнопка «Отказаться от страхования».

### Требования к изменениям

#### BPMN схема процесса
Выбор условий кредита → подключение страхования по желанию клиента → расчёт премии → подписание договора кредита и заявления на страхование → выдача кредита и оплата премии → выпуск полиса → отказ в период охлаждения и возврат премии (если клиент отказался) → завершение.

#### Функциональные требования
* **Ф-1.** Страхование предлагается при оформлении кредита наличными от 300 000 до 5 000 000 ₸ на срок от 6 до 60 месяцев. Подключение добровольное: флажок по умолчанию снят, отказ от страхования не влияет на одобрение кредита.
* **Ф-2.** Страховая премия равна сумме кредита × 0,15 % × срок кредита в месяцах с округлением до целого тенге по математическим правилам; возврат по Ф-5 округляется так же. Премия оплачивается единовременно из суммы кредита при выдаче, страховая сумма равна сумме кредита.
* **Ф-3.** Ставка по кредиту со страхованием — 24 % годовых, без страхования — 27 % годовых.
* **Ф-4.** Клиент может отказаться от страхования в течение 14 календарных дней с даты выдачи кредита, которая является датой начала действия полиса (сроки в днях здесь и далее отсчитываются со дня, следующего за событием, даты — по времени Астаны, UTC+5: кредит выдан 1 марта — отказ возможен по 15 марта включительно); отказ считается оформленным в момент, когда клиент подтвердил его в приложении; премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней. После отказа ставка по кредиту повышается до 27 % годовых со дня отказа. По истечении 14 дней кнопка «Отказаться от страхования» недоступна.
* **Ф-5.** При полном досрочном погашении кредита страхование прекращается, клиенту возвращается часть премии за полные неиспользованные месяцы. При частичном досрочном погашении страхование, страховая сумма и премия не меняются.
* **Ф-6.** Страхование доступно клиенту от 18 лет, которому на дату окончания кредита будет не больше 65 полных лет.

Сервис страхования → сервис уведомлений: полис выпущен.

Передавать страховой компании-партнёру ИИН, ФИО, дату рождения и номер телефона клиента только после согласия клиента на передачу персональных данных; анкета здоровья не запрашивается.

### Логика работы метода
1. Проверить сессию клиента.
2. Проверить, что заявка на кредит принадлежит клиенту и ещё не подписана.
3. Проверить сумму кредита (300 000 – 5 000 000 ₸) и срок `term` (6–60).
4. Проверить возраст клиента. Если на дату подключения клиенту меньше 18 полных лет или на дату окончания кредита будет больше 65 полных лет, вернуть 422.
5. Рассчитать премию по Ф-2 и ставку со страхованием.
6. Если `consentPd` не равно `true`, вернуть 400. Передать ИИН, ФИО, дату рождения и номер телефона клиента страховой компании-партнёру для предварительной проверки, сохранить подключение страхования в заявке и вернуть результат; если страховая компания-партнёр отказала по результатам предварительной проверки, вернуть 422. Полис выпускается после выдачи кредита.

### Особые правила
1. Повторный вызов с теми же суммой и сроком возвращает действующие условия страхования.
2. Если клиент изменил сумму или срок после подключения, приложение вызывает метод повторно, и условия страхования пересчитываются; если повторный вызов вернул 400 или 422, ранее подключённое страхование снимается с заявки.
3. После отказа от страхования ставка по кредиту повышается до 27 % годовых со дня отказа (Ф-4).

### Общие сведения

| **Тип работы** | Новый функционал |

| **Задача в JIRA** | PAY-1182 |

### Цели
Клиент получает перевод от другого клиента банка, показав QR-код на экране телефона, без диктовки номера карты или телефона. Снизить число переводов по ошибочным реквизитам.

### Архитектура решения
Приложение получателя → сервис QR-кодов. Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод. Сервис переводов → сервис уведомлений.

### Дизайн процесса UI
Получатель: Платежи → «Получить по QR» → выбор карты зачисления, необязательное поле «Сумма, ₸» и кнопка «Создать QR». QR-код показывается с таймером обратного отсчёта и кнопкой «Отменить».
Отправитель: Платежи → «Сканировать QR» → экран подтверждения с маскированным именем получателя («Айгерим С.»), суммой, картой списания, надписью «Без комиссии» и кнопкой «Перевести». Если сумма задана в QR-коде, изменить её нельзя.

### Требования к изменениям

#### BPMN схема процесса
Создание QR-кода получателем → сканирование отправителем → проверка QR-кода → подтверждение отправителем → проверка антифродом → списание и зачисление → push получателю и отправителю → завершение.

#### Функциональные требования
* **Ф-1.** Получатель — клиент банка с активной картой KZT. QR-код создаётся без суммы или с суммой от 100 до 500 000 ₸ включительно; сумма — целое число тенге.
* **Ф-2.** QR-код действует 15 минут с момента создания. QR-код с суммой можно оплатить один раз, QR-код без суммы — несколько раз в течение срока действия. QR-код с суммой считается оплаченным с момента, когда сервис переводов принял перевод по нему в обработку; если перевод отклонён (`REJECTED`) или не выполнен из-за ошибки, QR-код снова можно оплатить до конца срока действия.
* **Ф-3.** Перед подтверждением отправитель видит маскированное имя получателя, сумму и надпись «Без комиссии». Для QR-кода без суммы отправитель вводит сумму от 100 до 500 000 ₸.
* **Ф-4.** Комиссия за перевод по QR-коду не взимается.
* **Ф-5.** Получатель может отменить QR-код, если он не оплачен (для QR-кода с суммой) и по нему нет перевода в обработке. Если отправитель подтверждает перевод после отмены, он получает «QR-код недействителен» (ответ 410). После отмены или истечения срока действия при сканировании показывается «QR-код недействителен».
* **Ф-6.** После зачисления получатель и отправитель получают push с суммой перевода и маскированным именем второй стороны.

### Sequence Diagram
Приложение получателя → сервис QR-кодов: создать QR-код. Приложение отправителя → сервис QR-кодов: получить данные QR-кода. Приложение отправителя → сервис переводов: выполнить перевод по QR-коду. Сервис переводов → антифрод: проверить операцию. Сервис переводов → сервис уведомлений: перевод зачислен.

### Нефункциональные требования
Создание QR-кода и получение его данных — не дольше 500 мс для 95 % запросов; перевод по QR-коду — не дольше 3 с для 95 % запросов от получения запроса до ответа. Сервис выдерживает 200 переводов по QR-коду в секунду.

### Требования к данным
QR-код содержит только идентификатор QR-кода; карта получателя и сумма хранятся в сервисе QR-кодов и в QR-код не выводятся. Хранить идентификатор QR-кода, идентификатор клиента-получателя, карту зачисления, сумму в тенге, время создания, срок действия `ttl` в минутах, статус (активен, оплачен, отменён, истёк) и идентификаторы переводов.

### Требования к интеграции
Приложения создают и отменяют QR-код, получают данные QR-кода перед подтверждением и выполняют перевод через дочерний документ «Перевод по QR-коду — REST API». Повторный запрос перевода с тем же `requestId` не создаёт второй перевод.

### Логика работы метода
1. Проверить сессию отправителя.
2. Проверить, что карта списания принадлежит отправителю, активна и открыта в тенге; если нет, вернуть 400.
3. Найти QR-код по `qrId`. Если QR-код не найден, вернуть 404. Если карта зачисления получателя закрыта или заблокирована, вернуть 410.
4. Проверить срок действия: текущее время не позже времени создания QR-кода + `ttl` минут. Если срок истёк или QR-код отменён, вернуть 410.
5. Если в QR-коде задана сумма, использовать её, а поле `amount` запроса не учитывать. Если суммы нет, поле `amount` обязательно: от 100 до 500 000 ₸, иначе вернуть 400.
6. Проверить, что QR-код с суммой ещё не оплачен; если оплачен, вернуть 410.
7. Передать операцию в антифрод. При отказе антифрода вернуть 200 со `status` = `REJECTED`.
8. Выполнить списание и зачисление одной операцией сервиса переводов (если на карте списания недостаточно средств или произошёл сбой, не проводится ни одна из них; ответ 400 или 500 соответственно) и вернуть результат.

### Особые правила
1. QR-код без суммы, как и QR-код с суммой, действует 15 минут с момента создания (Ф-2).
2. Повторный запрос с тем же `requestId` возвращает результат первого запроса.

### Схема
```text
Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов (антифрод, списание, зачисление) → QrTransferController → приложение.
```

**400.** Ответ в случае, если параметры запроса заполнены неверно, карта списания недоступна или на ней недостаточно средств.

**404.** Ответ в случае, если QR-код не найден.

### Цели
Клиент досрочно гасит кредит наличными — частично или полностью — в приложении без визита в отделение и до подтверждения видит проценты, новый ежемесячный платёж или новый срок. Через 6 месяцев после запуска не менее 50 % досрочных погашений кредитов наличными за календарный месяц проводится в мобильном банке.
### Архитектура решения
Мобильное приложение → сервер мобильного банка (существующие методы: кредиты, счета и карты, график платежей). Мобильное приложение → сервис досрочного погашения (`EarlyRepaymentController`) → АБС (данные кредита, расчёт, проведение, статус операции). Сервис досрочного погашения → сервис уведомлений → push клиенту.
### Дизайн процесса UI
Кредиты → карточка кредита наличными → кнопка «Досрочное погашение»; кнопка показывается для кредита в статусе «активен», если функциональность включена флагом сервера мобильного банка.
* **Экран «Досрочное погашение»** (метод 2): остаток основного долга, «Проценты на {дата погашения}», сумма полного погашения, дата очередного платежа; выбор вида — «Уменьшить платёж» (`PARTIAL_REDUCE_PAYMENT`), «Уменьшить срок» (`PARTIAL_REDUCE_TERM`), «Погасить полностью» (`FULL`); для частичного погашения поле «Сумма, ₸» (только цифры) с подсказкой «от {minPartialAmount} до {maxPartialAmount} ₸»; кнопка «Рассчитать» (метод 3). Если частичное погашение недоступно (Ф-4), «Уменьшить платёж» и «Уменьшить срок» неактивны с надписью «Доступно только полное погашение».
* **Экран «Подтверждение»**: сумма погашения, из неё проценты и в счёт основного долга, остаток основного долга после погашения; для частичного погашения — ежемесячный платёж, число оставшихся платежей, даты очередного и последнего платежа; для полного — «Кредит будет закрыт». Надпись «Без комиссии», список «Списать с» (текущие счета и дебетовые карты клиента в тенге в статусе «активен»: название и последние 4 цифры номера), кнопка «Подтвердить» (метод 1), неактивная до получения ответа.
* **Экран «Погашение проведено»**: списанная сумма и параметры кредита из ответа метода 1; для частичного погашения — кнопка «График платежей», для полного — надпись «Кредит полностью погашен».
* **Ошибки.** Ошибку 422 приложение показывает текстом из поля `message` на текущем экране; при `CALCULATION_OUTDATED` возвращает клиента на экран «Досрочное погашение» с обновлёнными условиями. При ответе 500 или отсутствии ответа за 30 с показывается «Не удалось получить результат» и кнопка «Повторить», которая отправляет тот же запрос с тем же ключом идемпотентности.
### Требования к изменениям
#### BPMN схема процесса
Открытие карточки кредита → получение условий → выбор вида и суммы → расчёт → выбор источника списания и подтверждение → проверки сервиса → проведение в АБС (списание, погашение процентов и основного долга, пересчёт графика или закрытие кредита) → экран результата → push → завершение. Проверка не пройдена → сообщение клиенту на текущем экране; расчёт устарел → возврат к получению условий.
#### Функциональные требования
Кредит — потребительский кредит наличными клиента. Во всём документе и в API суммы — целые тенге (₸), даты и время — по Астане (UTC+5).
* **Ф-1.** Досрочное погашение доступно клиенту по его кредиту в статусе «активен» (`ACTIVE`) без просроченной задолженности — круглосуточно в любой день, кроме даты очередного платежа (с 00:00:00 до 23:59:59 по Астане этой даты). Дата погашения — текущая дата по Астане; погашение будущей датой не предусмотрено. Комиссия за досрочное погашение не взимается.
* **Ф-2.** Виды погашения: частичное с уменьшением ежемесячного платежа (число оставшихся платежей не меняется), частичное с уменьшением срока (ежемесячный платёж не меняется, число оставшихся платежей пересчитывается по Ф-5 и не меняется, если суммы в основной долг недостаточно для сокращения хотя бы на один платёж), полное.
* **Ф-3.** Проценты начисляются за каждый календарный день на остаток основного долга из расчёта «годовая ставка / 360». Проценты по дату погашения = остаток основного долга × годовая ставка / 360 × число дней; число дней считается с даты предыдущего погашения (платёж по графику или досрочное погашение, а если погашений не было — дата выдачи кредита), не включая её, по дату погашения включительно. Сумма полного погашения = остаток основного долга + проценты по дату погашения.
* **Ф-4.** Сумма частичного погашения сначала погашает проценты по дату погашения, остальное идёт в основной долг. В основной долг направляется от 10 000 ₸ до «остаток основного долга − 10 000 ₸» включительно, поэтому сумма частичного погашения — от `minPartialAmount` (проценты по дату погашения + 10 000 ₸) до `maxPartialAmount` (сумма полного погашения − 10 000 ₸) включительно. Частичное погашение доступно, если остаток основного долга не меньше 20 000 ₸; иначе доступно только полное.
* **Ф-5.** После частичного погашения АБС пересчитывает график; число месяца платежей сохраняется (если в месяце нет такого числа — последний день месяца). Уменьшение платежа: новый ежемесячный платёж P = S × i / (1 − (1 + i)^(−n)), где S — остаток основного долга после погашения, i — годовая ставка / 12, n — число оставшихся платежей. Уменьшение срока: ежемесячный платёж сохраняется, новое число оставшихся платежей — наименьшее n, при котором P по той же формуле, округлённый по Ф-6, не больше текущего ежемесячного платежа. Проценты в платежах нового графика начисляются по Ф-3; последний платёж = остаток основного долга на его дату + проценты по эту дату. После полного погашения кредит получает статус «закрыт» (`CLOSED`).
* **Ф-6.** Проценты (Ф-3) и ежемесячный платёж (Ф-5) округляются до целого тенге один раз, после вычисления по формуле: дробная часть 0,5 и больше — вверх, меньше 0,5 — вниз.
* **Ф-7.** Перед проведением клиент видит расчёт на экране «Подтверждение». Расчёт действует до момента «время расчёта + 30 минут» включительно, но не позже 23:59:59 по Астане дня расчёта, и только пока по кредиту не проведено другое погашение. Погашение проводится по виду, сумме и дате погашения из расчёта; по одному расчёту проводится не более одного погашения.
* **Ф-8.** Источник списания — текущий счёт или дебетовая карта клиента в тенге в статусе «активен» с доступным остатком не меньше суммы погашения. Списание суммы погашения и погашение кредита АБС выполняет одной операцией: проводятся оба действия или ни одно.
* **Ф-9.** После проведения погашения клиент получает один push (номер договора — из данных кредита в АБС; суммы — с разделением разрядов пробелом; даты — ДД.ММ.ГГГГ). Уменьшение платежа: «Досрочное погашение по договору № {номер}: списано {amount} ₸. Новый ежемесячный платёж {monthlyPayment} ₸, ближайший — {nextPaymentDate}.» Уменьшение срока: «Досрочное погашение по договору № {номер}: списано {amount} ₸. Осталось платежей: {paymentsLeft}, последний — {lastPaymentDate}.» Полное: «Кредит по договору № {номер} полностью погашен. Списано {amount} ₸.»
### Sequence Diagram
Приложение → сервис досрочного погашения: условия (метод 2); сервис → АБС: данные кредита. Приложение → сервис: расчёт (метод 3); сервис → АБС: данные кредита и расчёт; сервис сохраняет расчёт и возвращает `calculationId`. Приложение → сервер мобильного банка: счета и карты (`GET /accounts`). Приложение → сервис: проведение (метод 1); сервис → АБС: данные кредита и проведение с `operationId`; АБС → сервис: результат; сервис → приложение: 200; сервис → сервис уведомлений: push (асинхронно).
### Нефункциональные требования
Время ответа на сервере (от получения запроса до отправки ответа, включая обращения к АБС): методы 2 и 3 — не более 1 с для 95 % запросов, метод 1 — не более 3 с для 95 % запросов. Ожидание ответа АБС на проведение — не более 10 с, ожидание ответа сервиса приложением — не более 30 с. Нагрузка: 100 запросов методов 2 и 3 и 20 запросов метода 1 в секунду одновременно при соблюдении времени ответа. Push передаётся в сервис уведомлений не позднее 60 с после проведения погашения для 99 % операций. Доступность сервиса досрочного погашения — не менее 99,5 % времени за календарный месяц. Методы доступны только по сессии клиента — владельца кредита; в журналах номер карты хранится только как последние 4 цифры; журнал аудита запросов метода 1 хранится 5 лет.
### Требования к данным
Расчёт (хранится 30 дней): `calculationId`, идентификаторы клиента и кредита, вид, сумма погашения, проценты по дату погашения, сумма в счёт основного долга, остаток основного долга после погашения, ежемесячный платёж, число оставшихся платежей, даты очередного и последнего платежа, время расчёта, `expiresAt`. Операция (хранится 5 лет): `operationId`, ключ идемпотентности, хеш `loanId` и тела запроса, идентификаторы клиента, кредита, расчёта и источника списания, статус (`PROCESSING` — в обработке, `DONE` — проведена, `REJECTED` — не проведена, `UNKNOWN` — результат не подтверждён), ответ 200, время создания, `executedAt`. Суммы — целые тенге; даты — `YYYY-MM-DD`, время — ISO 8601 со смещением `+05:00`.
### Требования к интеграции
Приложение получает условия, выполняет расчёт и проводит погашение через дочерний документ «Досрочное погашение кредита наличными — REST API». Повторный запрос проведения с тем же ключом идемпотентности не создаёт второе погашение. Правила Ф-3–Ф-6 совпадают с правилами, по которым АБС проводит досрочное погашение в отделениях; доработка АБС не требуется. Операции в статусе `UNKNOWN` сервис сверяет с АБС методом `GET /abs/prepayments/{operationId}` каждые 5 минут до получения статуса «проведена» (операция → `DONE`, сохраняется ответ 200, отправляется push) или «не найдена» (операция → `REJECTED`). Используются существующие методы:
* Сервер мобильного банка: `GET /loans` — кредиты клиента (`loanId`, вид, статус, ежемесячный платёж); `GET /accounts` — счета и карты клиента (`id`, тип, название, валюта, статус, доступный остаток, последние 4 цифры номера); `GET /loans/{loanId}/schedule` — график платежей.
* АБС: `GET /abs/loans/{loanId}` — номер договора, статус, остаток основного долга, ставка, дата предыдущего погашения, дата очередного платежа, ежемесячный платёж, число оставшихся платежей, просроченная задолженность; `POST /abs/loans/{loanId}/prepayments/calculate` — расчёт по Ф-3–Ф-6 на дату погашения; `POST /abs/loans/{loanId}/prepayments` — проведение с `operationId` (списание, погашение, пересчёт графика или закрытие кредита; повторный вызов с тем же `operationId` возвращает результат первого); `GET /abs/prepayments/{operationId}` — статус операции: проведена (с результатом проведения), в обработке, не найдена.
* Сервис уведомлений: `POST /notifications/push` — отправка push клиенту.

### Логика работы метода
1. Проверить сессию клиента; если её нет или она истекла — 401.
2. Проверить формат: `Idempotency-Key` и `calculationId` — UUID, `sourceId` — строка 1–64 символа; иначе — 400.
3. Найти кредит наличными `loanId` среди кредитов клиента; если не найден — 404.
4. Проверить ключ идемпотентности по особому правилу 2; новый ключ зарегистрировать с новым `operationId` и статусом операции `PROCESSING`.
5. Найти расчёт: не найден или создан для другого кредита — 422 `CALCULATION_NOT_FOUND`; расчёт не действует по Ф-7 — 422 `CALCULATION_OUTDATED`.
6. Проверить кредит по данным АБС: не в статусе «активен» — 422 `LOAN_NOT_ACTIVE`; есть просроченная задолженность — 422 `OVERDUE_DEBT`.
7. Передать в АБС `operationId`, вид, сумму и дату погашения из расчёта и `sourceId`. Отказ АБС из-за источника списания — 422 `SOURCE_UNAVAILABLE`, из-за доступного остатка — 422 `INSUFFICIENT_FUNDS`; ошибка АБС или нет ответа за 10 с — 500.
8. Перевести операцию в `DONE`, сохранить ответ по ключу, вернуть 200 и асинхронно передать push по Ф-9.
### Особые правила
1. Суммы — целые тенге; даты — `YYYY-MM-DD` по Астане; время — ISO 8601 со смещением `+05:00`.
2. Приложение создаёт новый ключ идемпотентности при каждом нажатии «Подтвердить»; «Повторить» отправляет тот же запрос с тем же ключом. Ключ уникален в пределах клиента, привязан к `loanId` и телу первого запроса и действует 30 дней (затем запрос с ним обрабатывается как новый). Тот же ключ с другим кредитом клиента (`loanId`) или другим телом — 409 `IDEMPOTENCY_KEY_REUSED`. Тот же ключ с тем же запросом: после 200 возвращается сохранённый ответ (тот же `operationId`) без обращения к АБС и без нового push; после 422 или 500 сервис запрашивает статус операции в АБС (`GET /abs/prepayments/{operationId}`): «проведена» — 200 с результатом этой операции, «в обработке» — 500, «не найдена» — запрос обрабатывается заново с тем же `operationId`.
3. Запросы метода 1 по одному кредиту обрабатываются последовательно: следующий ждёт завершения предыдущего. При ответе 422 операция получает статус `REJECTED`, при ответе 500 — `UNKNOWN` (сверка — часть A, «Требования к интеграции»).

### Цели
Клиент копит без отдельного решения о каждом взносе: разница между суммой покупки по карте и суммой, округлённой вверх до выбранного шага, ежедневно переводится с карточного счёта на его сберегательный счёт. Целевой показатель — 30 000 карт с включённой копилкой через 6 месяцев после запуска.

### Архитектура решения
Мобильное приложение → сервис копилки (новый) → карточный процессинг (проверка карты), сервис счетов (проверка счёта). Мобильное приложение → сервис счетов (список сберегательных счетов). Карточный процессинг → сервис копилки (события проведения операций). Сервис копилки → сервис переводов (ежедневный перевод), сервис уведомлений (push).

### Дизайн процесса UI
Карты → карта → «Копилка». На экране: переключатель «Копилка»; выбор «Округлять до» (100, 500 или 1 000 ₸); выбор «Сберегательный счёт» (название и последние четыре цифры номера из списка сберегательных счетов клиента, И-3); поле «Предел в месяц, ₸»; кнопка «Сохранить»; показатели «Накоплено сегодня», «Переведено в этом месяце» и «Осталось до предела» в тенге с двумя знаками после запятой. Экран заполняется методом 2, кнопка «Сохранить» вызывает метод 1 (часть B); любое изменение, в том числе выключение, применяется только после «Сохранить». При выключенном переключателе поля показывают сохранённые значения и не редактируются. При включённом переключателе кнопка «Сохранить» доступна, когда выбраны шаг и счёт и заполнен предел. Текст `message` ответа 422 показывается под полем: `STEP_NOT_ALLOWED` — «Округлять до», `LIMIT_OUT_OF_RANGE` — «Предел в месяц, ₸», `ACCOUNT_NOT_ELIGIBLE` — «Сберегательный счёт»; `CARD_NOT_ELIGIBLE` — над кнопкой «Сохранить». При ответе 500 показывается «Сервис временно недоступен, попробуйте позже», сохранённые настройки не меняются. Если у клиента нет открытого сберегательного счёта в тенге, вместо выбора счёта показывается «Откройте сберегательный счёт», и включить копилку нельзя. Если сохранённого счёта нет в списке (счёт закрыт), поле «Сберегательный счёт» показывается пустым и требует выбора перед сохранением при включённом переключателе.

### Требования к изменениям
#### BPMN схема процесса
Клиент включает копилку → проведение операции по карте → проверка типа операции и (для покупки) состояния копилки на время проведения → расчёт суммы округления → начисление в накопленную сумму за сутки (возврат до фиксации — исключение суммы округления исходной покупки) → 00:30 фиксация суммы к переводу с учётом остатка месячного предела → сумма к переводу больше 0,00 ₸: перевод на сберегательный счёт, иначе завершение → перевод выполнен: завершение; перевод не выполнен: push клиенту → завершение.

#### Функциональные требования
* **Ф-1.** Клиент подключает копилку к своей активной дебетовой карте в тенге; у карты не более одной копилки. Клиент задаёт шаг округления (100, 500 или 1 000 ₸), сберегательный счёт в тенге, открытый в банке на его имя (один счёт можно выбрать для нескольких карт), и месячный предел — целое число тенге от 1 000 до 500 000 ₸ включительно. По умолчанию копилка выключена.
* **Ф-2.** В копилке участвуют операции типа «покупка» (`PURCHASE`) по карте, в том числе покупки в интернете. Операции других типов (снятие наличных, переводы, платежи в мобильном банке, комиссии, возвраты) сумму округления не образуют. Сумма покупки — сумма проведения в тенге, списанная с карточного счёта, без комиссии банка. Сутки и месяц покупки определяются по времени её проведения в карточном процессинге по Астане (UTC+5); время авторизации не используется. Сутки — с 00:00:00 включительно до 00:00:00 следующего дня не включительно.
* **Ф-3.** Покупка участвует в копилке, если на время её проведения копилка включена; применяется шаг округления, действующий на это время. Сумма округления = наименьшее кратное шагу число, не меньшее суммы покупки, минус сумма покупки; расчёт — с точностью до тиына. Если сумма покупки кратна шагу, сумма округления равна 0,00 ₸. Для покупки 1 250,00 ₸: шаг 100 ₸ — 50,00 ₸, шаг 500 ₸ — 250,00 ₸, шаг 1 000 ₸ — 750,00 ₸. Накопленная сумма за сутки — сумма сумм округления покупок, проведённых в эти сутки, кроме исключённых по Ф-6.
* **Ф-4.** Ежедневно в 00:30:00 по Астане сервис копилки фиксирует сумму к переводу за предыдущие сутки по событиям, полученным раньше этого момента: накопленная сумма за сутки, но не больше остатка месячного предела. Если сумма к переводу больше 0,00 ₸, она переводится без комиссии с карточного счёта на сберегательный счёт, указанный в настройках на момент фиксации; иначе перевод не создаётся. Событие о покупке, полученное в момент фиксации за сутки её проведения или позже, сумму округления не образует. Выполненный перевод отражается в существующей истории операций карты и сберегательного счёта; push о нём не отправляется.
* **Ф-5.** Месячный предел ограничивает сумму, переведённую за месяц, — сумму выполненных ежедневных переводов за сутки одного календарного месяца; перевод за последние сутки месяца, выполняемый 1-го числа следующего месяца, относится к месяцу этих суток. Остаток месячного предела = месячный предел − сумма, переведённая за месяц, но не меньше 0,00 ₸. Часть накопленной суммы сверх остатка не переводится и на следующие сутки не переносится. Новый месячный предел применяется с ближайшей фиксации.
* **Ф-6.** Возврат (`REFUND`, полный или частичный) исключает сумму округления исходной покупки из накопленной суммы за сутки проведения этой покупки, если событие о возврате получено раньше фиксации суммы к переводу за эти сутки. Событие о возврате, полученное в момент фиксации или позже, зафиксированную сумму к переводу не меняет; переведённые средства остаются на сберегательном счёте. Исходная покупка определяется по `originalOperationId` события; если она в копилке не участвовала, возврат ничего не меняет.
* **Ф-7.** Достаточность средств проверяет сервис переводов при выполнении перевода: доступный остаток карточного счёта (собственные средства за вычетом сумм заблокированных авторизаций) должен быть не меньше суммы к переводу. Если перевод не выполнен, частичный перевод не делается, сумма к переводу на следующие сутки не переносится и в сумму, переведённую за месяц, не входит, а клиент получает push «Не удалось перевести N ₸ в копилку: причина», где N — сумма к переводу с двумя знаками после запятой и пробелом между разрядами (например, 1 250,00). Причины: `INSUFFICIENT_FUNDS` — «недостаточно средств на карте», `CARD_BLOCKED` — «карта заблокирована», `ACCOUNT_CLOSED` — «сберегательный счёт закрыт»; иной отказ или неуспех всех попыток при технических ошибках (И-4) — «ошибка перевода».
* **Ф-8.** После выключения копилки суммы округления по покупкам, проведённым начиная с момента выключения, не начисляются; суммы округления, начисленные до выключения, переводятся при фиксации за сутки проведения покупок по Ф-4 и Ф-5. Изменение шага округления действует для покупок, проведённых начиная с момента сохранения, и начисленные суммы не пересчитывает. При выключении настройки сохраняются и показываются при повторном включении.
* **Ф-9.** Повторная доставка события процессинга с тем же `operationId` накопленную сумму не меняет. Ежедневный перевод за одни сутки по одной карте выполняется не более одного раза.

### Sequence Diagram
Карточный процессинг → сервис копилки: событие проведения операции. Сервис копилки: начисление суммы округления или исключение по возврату. В 00:30 сервис копилки: фиксация суммы к переводу. Сервис копилки → сервис переводов: перевод с карточного счёта на сберегательный счёт; сервис переводов → сервис копилки: результат. Сервис копилки → сервис уведомлений: push, если перевод не выполнен. Мобильное приложение → сервис счетов: список сберегательных счетов. Мобильное приложение → сервис копилки: получить (метод 2) или сохранить (метод 1) настройки; сервис копилки → карточный процессинг и сервис счетов: проверка карты и счёта.

### Нефункциональные требования
**НФ-1.** Сумма округления начисляется не позже 60 с после получения события для 99 % событий при потоке до 500 событий в секунду. **НФ-2.** Методы 1 и 2 отвечают не дольше 300 мс для 95 % запросов при нагрузке 100 запросов в секунду; доступность методов — не ниже 99,9 % за календарный месяц. **НФ-3.** Ежедневные переводы за сутки, включая повторные попытки, завершаются до 02:00 по Астане; push о невыполненном переводе отправляется не позже 5 минут после окончательного отказа.

### Требования к данным
**Д-1.** Настройки копилки по карте (`roundup_settings`: карта, признак включения, шаг округления, сберегательный счёт, месячный предел) и история их изменений со временем сохранения (`roundup_settings_history`). **Д-2.** Участвующие покупки (`roundup_purchase`: `operationId`, карта, время проведения, сумма покупки, шаг, сумма округления, `operationId` возврата при исключении) и ежедневные переводы (`roundup_transfer`: карта, дата суток, месяц предела, накопленная сумма, сумма к переводу, ключ идемпотентности, статус «выполнен» или «не выполнен», причина, идентификатор перевода). **Д-3.** Суммы — в тенге с точностью до тиына (decimal(12,2)), шаг и предел — в целых тенге; время — по Астане (UTC+5) с указанием смещения; срок хранения — 5 лет.

### Требования к интеграции
**И-1.** Мобильное приложение получает и сохраняет настройки методами 2 и 1 дочернего документа «Копилка с округлением покупок по карте — REST API». Остальные взаимодействия — существующие методы других систем, без доработок. **И-2.** Карточный процессинг → сервис копилки: топик `card.operations.posted` — `operationId`, `cardId`, `operationType`, `amountKzt` (без комиссии), `postedAt` (со смещением), `originalOperationId` для `REFUND`; повторная доставка — по Ф-9. Сервис копилки → карточный процессинг: `GET /processing/v1/cards/{cardId}` — владелец, статус, тип и валюта карты. **И-3.** Мобильное приложение → сервис счетов: `GET /accounts/v1/clients/me/accounts?type=SAVINGS&currency=KZT` — открытые сберегательные счета клиента (идентификатор, название, последние четыре цифры номера). Сервис копилки → сервис счетов: `GET /accounts/v1/accounts/{accountId}` — владелец, тип, валюта и статус счёта. **И-4.** Сервис копилки → сервис переводов: `POST /transfers/v1/internal` с ключом идемпотентности `roundup-{cardId}-{YYYY-MM-DD}` (дата суток), таймаут ответа 30 с; отказ приходит с кодом причины (`INSUFFICIENT_FUNDS`, `CARD_BLOCKED`, `ACCOUNT_CLOSED` и другие). При ответе 5xx или таймауте повторная попытка с тем же ключом — через 5 минут после неуспешной; попытки после 01:50 не начинаются. Сервис копилки → сервис уведомлений: `POST /notifications/v1/push`.

### Логика работы метода
1. Проверить сессию клиента; если её нет или она истекла — 401.
2. Проверить тело по схеме: корректный JSON, обязательность и типы полей с учётом `enabled` (особое правило 2); при ошибке — 400.
3. Найти карту `cardId` в карточном процессинге; если карта не найдена или принадлежит другому клиенту — 404; если карточный процессинг не ответил — 500.
4. Если `enabled` = true, выполнить бизнес-проверки по порядку; первая непройденная возвращает 422 со своим `errorCode`: карта активна, дебетовая и открыта в тенге (`CARD_NOT_ELIGIBLE`); `roundingStep` равен 100, 500 или 1 000 (`STEP_NOT_ALLOWED`); `monthlyLimit` от 1 000 до 500 000 включительно (`LIMIT_OUT_OF_RANGE`); счёт `savingsAccountId` найден в сервисе счетов, принадлежит клиенту, сберегательный, в тенге и открыт (`ACCOUNT_NOT_ELIGIBLE`); если сервис счетов не ответил — 500. При `enabled` = false бизнес-проверки не выполняются.
5. Если значения отличаются от сохранённых, сохранить их и запись в истории настроек со временем сохранения (при `enabled` = false — только признак выключения); иначе ничего не менять. Вернуть 200 с состоянием копилки.

### Особые правила
1. Признак включения и шаг округления применяются к покупкам со временем проведения, равным времени сохранения или позже; сберегательный счёт и месячный предел — с ближайшей фиксации суммы к переводу в 00:30; начисленные суммы не пересчитываются (Ф-3, Ф-4, Ф-5, Ф-8).
2. При `enabled` = false поля `roundingStep`, `savingsAccountId` и `monthlyLimit` не проверяются и не сохраняются; ответ содержит ранее сохранённые значения.
3. Повторный запрос с тем же телом, прошедший шаги 1–4, возвращает 200 и текущее состояние, новую запись в истории настроек не создаёт; ключ идемпотентности не требуется.

### Статусы
**200.** Настройки сохранены или повторный запрос их не изменил; тело — состояние копилки. Пример: `{"enabled":true,"roundingStep":100,"savingsAccountId":"acc-7781","monthlyLimit":20000,"accruedToday":149.60,"transferredThisMonth":449.60,"limitRemaining":19550.40}`  
**400.** Тело не соответствует схеме: некорректный JSON, нет обязательного поля или неверный тип поля. Пример: `{"message":"Некорректный запрос"}`  
**401.** Нет действующей сессии клиента. Пример: `{"message":"Требуется вход"}`  
**404.** Карта не найдена среди карт клиента, в том числе карта другого клиента. Пример: `{"message":"Карта не найдена"}`  
**422.** Тело соответствует схеме, но значения не прошли бизнес-проверки шага 4 логики. `errorCode`: `CARD_NOT_ELIGIBLE` — карта не активна, не дебетовая или открыта не в тенге; `STEP_NOT_ALLOWED` — шаг не равен 100, 500 или 1 000; `LIMIT_OUT_OF_RANGE` — предел меньше 1 000 или больше 500 000; `ACCOUNT_NOT_ELIGIBLE` — счёт не найден, принадлежит другому клиенту, не сберегательный, открыт не в тенге или закрыт. Пример: `{"errorCode":"LIMIT_OUT_OF_RANGE","message":"Предел в месяц — от 1 000 до 500 000 ₸"}`  
**500.** Внутренняя ошибка сервиса копилки, или карточный процессинг либо сервис счетов не ответили. Пример: `{"message":"Сервис временно недоступен, попробуйте позже"}`

### Цели
Клиент сам получает выписку по своему счёту в PDF в мобильном банке, без визита в отделение и звонка в контакт-центр. Снизить число обращений за выпиской в отделения и контакт-центр на 30 % за три месяца после запуска по сравнению с тремя месяцами до запуска.
### Архитектура решения
Мобильное приложение → API-шлюз → сервис счетов (список счетов). Мобильное приложение → API-шлюз → сервис выписок (новый) → сервис счетов. Сервис выписок → очередь заданий → генератор PDF (компонент сервиса выписок) → АБС. Генератор PDF → файловое хранилище. Скачивание: мобильное приложение → API-шлюз → сервис выписок → файловое хранилище.
### Дизайн процесса UI
Счета → карточка счёта → «Выписка в PDF». Форма: счёт (выбран счёт, из карточки которого открыта форма; можно выбрать другой незакрытый счёт), поля «Дата начала» и «Дата окончания», «Язык выписки» (Русский / Қазақша / English, по умолчанию — язык интерфейса приложения), кнопка «Заказать» и ссылка «Мои выписки». Поля дат по умолчанию пустые; кнопка «Заказать» доступна, когда заполнены обе даты. Календарь не даёт выбрать дату раньше даты открытия счёта и позже вчерашнего дня, а дату окончания — раньше даты начала.
После нажатия «Заказать» открывается экран заказа: счёт («•• 4471»), период, язык, дата и время создания, статус. При ответе 422 экран заказа не открывается, а над кнопкой «Заказать» показывается текст по `errorCode` (часть B, ответ 422); при ответах 400, 404, 409 и 500 — «Не удалось оформить заказ. Попробуйте позже». При ответе 401 методов 1–4 открывается экран входа в приложение. Дата и время в приложении показываются по Астане. Тексты интерфейса даны на русском; для казахского и английского интерфейса используются их переводы. «Мои выписки» — список заказов клиента по всем счетам за последние 30 суток, от новых к старым; в строке те же поля, что на экране заказа; список обновляется при открытии экрана и жестом «потянуть вниз». Что видит клиент в каждом статусе заказа (на экране заказа и в списке «Мои выписки»):
* `IN_PROGRESS` — «Формируется» и подсказка «Можно закрыть экран, заказ останется в разделе „Мои выписки“»; кнопок нет. Пока экран заказа открыт, приложение запрашивает статус каждые 5 секунд.
* `READY` — «Готова», «Доступна до ДД.ММ.ГГГГ ЧЧ:ММ (по Астане)» по значению `fileExpiresAt` и кнопка «Скачать». Каждое нажатие «Скачать» запрашивает новую ссылку на скачивание (метод 4) и открывает по ней файл выписки (метод 5) в системном просмотрщике PDF. Если метод 4 вернул 410, показывается статус «Срок хранения истёк»; при других ошибках методов 2–5, кроме 401, — «Не удалось загрузить данные. Попробуйте позже».
* `FAILED` — «Не удалось сформировать»; `EXPIRED` — «Срок хранения истёк». В обоих статусах — кнопка «Заказать снова»: открывает форму с тем же счётом, периодом и языком.
### Требования к изменениям
#### BPMN схема процесса
Клиент выбирает счёт, период и язык → сервис выписок проверяет счёт, период и суточный предел → [нарушение — сообщение клиенту, заказ не создан, завершение] → заказ создан в статусе `IN_PROGRESS` → генератор PDF получает данные счёта, операции и остатки из АБС → [три попытки завершились ошибкой АБС или прошло 30 минут — `FAILED`, завершение] → файл выписки сохранён в файловом хранилище, `READY` → клиент получает ссылку на скачивание и скачивает файл выписки → через 7 суток после формирования — `EXPIRED`, файл удаляется → завершение.
#### Функциональные требования
* **Ф-1.** Клиент — физическое лицо с доступом в мобильный банк — заказывает выписку по своему незакрытому счёту (статус счёта в сервисе счетов — не `CLOSED`) из числа счетов, которые возвращает существующий метод сервиса счетов `GET /accounts`. Выписка по закрытому счёту в мобильном банке не заказывается.
* **Ф-2.** Период задаётся датой начала и датой окончания; обе даты входят в период. Дата начала — не раньше даты открытия счёта; дата окончания — не раньше даты начала и не позже вчерашнего дня; период — не длиннее 366 дней включительно. Даты периода, время в выписке и в приложении и границы суток определяются по Астане (UTC+5); вчерашний день — дата, предшествующая текущей дате по Астане в момент отправки заказа.
* **Ф-3.** Язык выписки — русский, казахский или английский (`ru`, `kk`, `en`). На выбранном языке выводятся заголовки и подписи выписки; описания операций выводятся так, как они записаны в АБС.
* **Ф-4.** Файл выписки (PDF) содержит: ФИО владельца, IBAN и валюту счёта, период, дату и время формирования, входящий остаток на 00:00:00 даты начала; операции, проведённые в АБС с 00:00:00 даты начала по 23:59:59 даты окончания, в порядке времени проведения (дата и время проведения, описание, сумма в валюте счёта, списания — со знаком минус); обороты по дебету и кредиту; исходящий остаток на 23:59:59 даты окончания. На каждой странице — номер заказа (`orderId`). Незавершённые операции (блокировки сумм) в выписку не входят. Если операций за период нет, вместо списка операций выводится строка «Операций за период нет».
* **Ф-5.** Выписка формируется асинхронно. Заказ создаётся в статусе `IN_PROGRESS` и переходит в `READY`, когда файл выписки сохранён в файловом хранилище, или в `FAILED`, если три попытки получить данные из АБС с интервалом 1 минута завершились ошибкой либо заказ не перешёл в `READY` за 30 минут с момента создания. `FAILED` — конечный статус.
* **Ф-6.** Срок хранения файла выписки — 7 суток (168 часов) с момента перехода заказа в `READY`; окончание срока — `fileExpiresAt`. В момент `fileExpiresAt` заказ переходит в `EXPIRED` (конечный статус), файл становится недоступен и ссылки на скачивание больше не выдаются; из файлового хранилища файл удаляется не позже чем через 1 час после `fileExpiresAt`. Ссылка на скачивание действует 15 минут с момента выдачи, но не дольше `fileExpiresAt`, и в пределах этого срока допускает повторное скачивание. Ссылка и файл доступны, пока текущее время меньше окончания их срока.
* **Ф-7.** Суточный предел — 10 заказов на клиента по всем его счетам. Сутки — с 00:00:00 до 23:59:59 по Астане, счётчик обнуляется в 00:00:00. В предел входят заказы, созданные в текущие сутки, кроме заказов в статусе `FAILED`. Заказ сверх предела не создаётся. Повтор запроса с тем же ключом идемпотентности нового заказа не создаёт и в предел не входит.
* **Ф-8.** Заказ хранится 30 суток с момента создания и всё это время виден в «Мои выписки»; затем запись о заказе удаляется, заказ пропадает из списка, методы 3 и 4 возвращают 404.
### Sequence Diagram
Все вызовы приложения проходят через API-шлюз. Приложение → сервис счетов: `GET /accounts` — счета клиента со статусом и датой открытия (существующий метод). Приложение → сервис выписок: создать заказ (метод 1). Сервис выписок → сервис счетов: `GET /accounts/{accountId}` — владелец, статус, дата открытия, IBAN (существующий метод). Сервис выписок → очередь заданий: задание на формирование; сервис выписок → приложение: 202. Генератор PDF → АБС: `GET /abs/v1/accounts/{accountId}/turnovers` — данные счёта, операции и остатки за период (существующий метод). Генератор PDF → файловое хранилище: сохранить файл выписки; генератор PDF → сервис выписок: `READY` или `FAILED`. Приложение → сервис выписок: статус заказа (метод 3) каждые 5 секунд, пока `IN_PROGRESS`; список заказов (метод 2) при открытии «Мои выписки»; ссылка на скачивание (метод 4), затем скачивание файла выписки по ссылке (метод 5). Сервис выписок → файловое хранилище: прочитать файл.
### Нефункциональные требования
Методы 1–4 части B отвечают не дольше 500 мс для 95 % запросов при суммарной нагрузке до 50 запросов в секунду; метод 5 начинает передачу файла не позже чем через 1 секунду для 95 % запросов. Выписка с числом операций до 5 000 формируется (от создания заказа до `READY`) не дольше 60 секунд для 95 % заказов. Доступность методов 1–5 — не ниже 99,5 % времени в календарный месяц. Файлы выписок хранятся в зашифрованном виде (AES-256); ссылка на скачивание не содержит номера счёта и персональных данных клиента.
### Требования к данным
Хранить заказ: `order_id` (UUID), `client_id`, `account_id`, `account_mask`, `date_from`, `date_to`, `language`, `status`, `idempotency_key`, `created_at`, `ready_at`, `file_expires_at`, `failure_reason` (`ABS_ERROR` или `TIMEOUT`), `file_key` (ключ файла в файловом хранилище). Отметки времени хранятся в UTC и выдаются в API со смещением Астаны (`+05:00`). Сроки: запись о заказе — 30 суток с `created_at` (Ф-8); файл выписки — 168 часов с `ready_at`, удаление из файлового хранилища — не позже чем через 1 час после `file_expires_at` (Ф-6); события «заказ создан», «ссылка выдана», «файл скачан» в журнале аудита мобильного банка — 5 лет.
### Требования к интеграции
* Приложение создаёт заказ, получает список и статус заказов, ссылку на скачивание и файл выписки через дочерний документ «Заказ выписки по счёту в PDF — REST API» (методы 1–5).
* Используются существующие методы, изменений в сервисе счетов и АБС не требуется: приложение получает счета клиента методом сервиса счетов `GET /accounts` (поля `accountId`, `iban`, `status`, `openDate`); сервис выписок проверяет владельца, статус и дату открытия счёта методом `GET /accounts/{accountId}` (поля `clientId`, `status`, `openDate`, `iban`); генератор PDF получает данные методом АБС `GET /abs/v1/accounts/{accountId}/turnovers?dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD` (ФИО владельца, IBAN, валюта счёта, входящий и исходящий остатки, операции с датой и временем проведения, описанием и суммой).
* Приложение создаёт новый ключ идемпотентности (`Idempotency-Key`) при каждом нажатии «Заказать»; если ответ не получен (таймаут или обрыв связи), повторяет запрос с тем же ключом не больше двух раз. Повтор с тем же ключом не создаёт второй заказ.
### Требования к тестированию
#### Тестирование требований
* Ветки правил проверяются по таблице «Критерии приемки» на тестовом контуре; текущее время задаётся тестовыми часами сервиса выписок по Астане. Ветки, которые календарь формы не допускает (даты вне диапазона, дата окончания раньше даты начала), проверяются вызовом метода 1 напрямую. Содержимое файла выписки сверяется с данными АБС за период: входящий и исходящий остатки, число операций, обороты по дебету и кредиту.
* НФТ проверяются нагрузочным тестом: 50 запросов в секунду к методам 1–4 в течение 30 минут и 1 000 заказов выписок по 5 000 операций; заказы распределяются по тестовым клиентам не больше 10 на клиента в сутки (Ф-7); результат — 95-й перцентиль времени.
### Критерии приемки
Если в строке не указано иное: текущее время — 10.03.2026 12:00 по Астане, счёт открыт 10.06.2024 и не закрыт, период — 01.01.2026–28.02.2026, язык — русский, за текущие сутки клиент не создавал заказов.

### Логика работы метода
1. Проверить сессию клиента; если сессии нет или она истекла, вернуть 401 `UNAUTHORIZED`.
2. Проверить заголовок `Idempotency-Key` и тело по разделу «Параметры запроса»; при нарушении формата вернуть 400 `VALIDATION_ERROR`.
3. Если у клиента есть заказ с тем же `Idempotency-Key`: при совпадении `accountId`, `dateFrom`, `dateTo` и `language` вернуть 202 с этим заказом (статус — на момент повтора), иначе вернуть 409 `IDEMPOTENCY_KEY_CONFLICT`; шаги 4–7 не выполняются, суточный предел не проверяется.
4. Получить счёт методом сервиса счетов `GET /accounts/{accountId}`. Если счёт не найден или принадлежит другому клиенту, вернуть 404 `ACCOUNT_NOT_FOUND`; если статус счёта `CLOSED` — 422 `ACCOUNT_CLOSED`.
5. Проверить период (Ф-2) в порядке `PERIOD_INVALID`, `DATE_TO_AFTER_YESTERDAY`, `DATE_FROM_BEFORE_OPENING`, `PERIOD_TOO_LONG`; при первом нарушении вернуть 422 с его кодом.
6. Проверить суточный предел (Ф-7): если за текущие сутки у клиента уже 10 заказов не в статусе `FAILED`, вернуть 422 `DAILY_LIMIT_EXCEEDED`.
7. Создать заказ в статусе `IN_PROGRESS`, поставить задание генератору PDF и вернуть 202. Шаги 3, 6 и 7 выполняются атомарно для клиента: параллельные запросы не превышают суточный предел и не создают двух заказов с одним ключом.
### Особые правила
1. Даты, время и сутки — по Астане (UTC+5); текущие дата и время берутся по часам сервиса выписок, а не устройства клиента. `dateFrom` и `dateTo` — календарные даты; поля даты и времени в ответах — ISO 8601 со смещением `+05:00`.
2. Длина периода — число дней от `dateFrom` до `dateTo`, обе даты включительно: от 1 до 366.
3. Ключ идемпотентности сохраняется только вместе с созданным заказом и хранится 30 суток (Ф-8); после удаления записи о заказе запрос с тем же ключом обрабатывается как новый. Если заказ не создан (ответы 400, 401, 404, 409, 422), ключ не сохраняется.
### Схема
```text
Приложение → StatementOrderController → сервис счетов; StatementOrderController → очередь заданий; StatementOrderController → приложение (202). Асинхронно: очередь заданий → генератор PDF → АБС; генератор PDF → файловое хранилище; генератор PDF → StatementOrderController (READY или FAILED).
```

### Статусы
**202.** Заказ принят: создан новый заказ или получен повтор с тем же `Idempotency-Key` и теми же параметрами (возвращается существующий заказ). Пример: `{"orderId":"b1d4e7a0-2c5f-4e8b-9a3d-6f1c0e2b7a94","accountId":"acc-7781","accountMask":"•• 4471","dateFrom":"2026-01-01","dateTo":"2026-02-28","language":"ru","status":"IN_PROGRESS","createdAt":"2026-03-10T12:00:05+05:00","fileExpiresAt":null}`.  
**400.** Нарушен формат: нет обязательного параметра, значение не соответствует формату или размеру, дата не существует (например, `2026-02-30`), `language` не из списка, `Idempotency-Key` не UUID. Пример: `{"errorCode":"VALIDATION_ERROR","message":"dateTo: ожидается дата YYYY-MM-DD"}`.  
**401.** Нет действующей сессии клиента. Пример: `{"errorCode":"UNAUTHORIZED","message":"Нет действующей сессии"}`.  
**404.** Счёт не найден или принадлежит другому клиенту. Пример: `{"errorCode":"ACCOUNT_NOT_FOUND","message":"Счёт не найден"}`.  
**409.** `Idempotency-Key` уже использован клиентом для заказа с другими параметрами. Пример: `{"errorCode":"IDEMPOTENCY_KEY_CONFLICT","message":"Ключ использован с другими параметрами"}`.  
**422.** Нарушено бизнес-правило; код — в `errorCode` (таблица ниже). Пример: `{"errorCode":"PERIOD_TOO_LONG","message":"Период длиннее 366 дней"}`.  
**500.** Внутренняя ошибка сервиса выписок или недоступен сервис счетов; повтор с тем же `Idempotency-Key` безопасен: если заказ успел создаться, возвращается он (202), второй заказ не создаётся. Пример: `{"errorCode":"INTERNAL_ERROR","message":"Ошибка сервиса"}`.

| errorCode (422) | Когда возникает | Текст в приложении |
| :--- | :--- | :--- |
| `ACCOUNT_CLOSED` | Статус счёта `CLOSED` | «Счёт закрыт. Выписку по закрытому счёту можно получить в отделении банка» |
| `PERIOD_INVALID` | `dateFrom` позже `dateTo` | «Дата начала позже даты окончания» |
| `DATE_TO_AFTER_YESTERDAY` | `dateTo` — сегодняшняя или более поздняя дата | «Дата окончания — не позже вчерашнего дня» |
| `DATE_FROM_BEFORE_OPENING` | `dateFrom` раньше даты открытия счёта | «Дата начала — не раньше даты открытия счёта» и дата открытия в формате ДД.ММ.ГГГГ |
| `PERIOD_TOO_LONG` | Период длиннее 366 дней | «Период — не длиннее 366 дней» |
| `DAILY_LIMIT_EXCEEDED` | За текущие сутки уже 10 заказов не в статусе `FAILED` | «Достигнут предел: 10 заказов в сутки. Новый заказ — с 00:00 по Астане» |
