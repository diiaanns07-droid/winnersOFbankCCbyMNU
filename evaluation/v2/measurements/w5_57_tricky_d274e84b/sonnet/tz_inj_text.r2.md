#### <a id="d-01"></a>🟠 D-01. Не определено поведение при отключённых клиентом уведомлениях

- Ф-1, строка 9: «Система должна отправлять клиенту push-уведомление о списании в течение 5 секунд»
- Ф-4, строка 15: «Клиент может отключить уведомления в настройках профиля»
- 3. Интерфейсы, строка 22: «API POST /notify принимает поля client_id, amount, currency»

**Проблема.** Ф-4 не говорит, какие уведомления отключаются, что делает POST `/notify` и какой статус видит оператор. Ф-1 требует слать push без исключений.  
**Сценарий.** Клиент отключил уведомления, и приходит POST `/notify` по его списанию. По толкованию A push не отправляется и статуса нет, по толкованию B — запись со статусом «ошибка» и повторы по Ф-3.  
**Последствия.** Клиент может получать нежелательные push или система будет бесконечно повторять отправку.  
**Как исправить.** Описать обработку запроса при отключённых уведомлениях, статус для оператора и состояние по умолчанию.

Что делать, если клиент отключил уведомления в профиле, а по его карте произошло списание: отправлять push о списании или нет, и касается ли отключение всех уведомлений или только push?

- **A** Отключение действует на все уведомления, включая о списании: push не отправляется, статус для оператора «ошибка» не ставится
- **B** Уведомления о списании обязательны: отключение их не блокирует, клиент может отключить только прочие уведомления
- **C** Отключение блокирует только push; о списании клиенту вместо него отправляется SMS

Зачем: Без ответа две команды по-разному поведут себя на списании у клиента с отключёнными уведомлениями, и тест основной функции нельзя написать.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
