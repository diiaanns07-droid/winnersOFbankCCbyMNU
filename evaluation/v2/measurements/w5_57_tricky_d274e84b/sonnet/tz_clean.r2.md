### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🟠 D-01. Не определено влияние отключения уведомлений (Ф-4) на отправку по Ф-1 и повторы Ф-3

- Ф-1, строка 9: «Ф-1. Система должна отправлять клиенту push-уведомление о списании в течение 5 секунд»
- Ф-3, строка 13: «При ошибке доставки система повторяет отправку до 3 раз с интервалом 1 минута»
- Ф-4, строка 15: «Ф-4. Клиент может отключить уведомления в настройках профиля»

**Проблема.** Ф-1 требует отправлять push о списании без условий, а Ф-4 позволяет отключить уведомления; что делает POST `/notify` для отключённого клиента, какой статус виден оператору и что с повторами Ф-3 при отключении между попытками — не сказано. Не ясно, отключаются все уведомления или только push.  
**Сценарий.** Клиент отключил уведомления, приходит POST `/notify` на списание 5000 KZT. Одна реализация пропустит отправку, другая отправит push по Ф-1; при отключении между повторами исход тоже разный.  
**Последствия.** Клиент может получать уведомления, которые отключил, или оператор не увидит, почему уведомления нет.  
**Как исправить.** Описать поведение при отключённых уведомлениях: отправка, статус для оператора, повторы, область отключения.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 15: «Ф-4. Клиент может отключить уведомления в настройках профиля» → «Ф-4. #### <a id="d-02"></a>🟠 D-02. Нет интерфейсов для чтения статуса и настройки уведомлений

- Ф-2, строка 11: «Ф-2. Оператор должен видеть статус доставки уведомления: «отправлено», «доставлено», «ошибка»»

**<a id="q-01"></a>Q-01** Влияние отключения уведомлений на отправку · можно ответить позже · кому: Владелец продукта · к [D-01](#d-01)  
Что должна делать система, если клиент отключил уведомления в профиле, а запрос на уведомление о списании уже пришёл или повторы ещё идут? Что при этом видит оператор и отключается только push или все каналы?  
Где: Ф-4, строка 15: «Ф-4. Клиент может отключить уведомления в настройках профиля.»; Ф-1, строка 9: «Ф-1. Система должна отправлять клиенту push-уведомление о списании в течение 5 секунд.»

- **A** Отключение действует на все уведомления: запрос принимается, отправка не выполняется, оператор видит новый статус «отключено клиентом», незавершённые повторы прекращаются
- **B** Отключение действует только на push: запрос принимается, push не отправляется, оператор видит новый статус «отключено клиентом», повторы прекращаются
- **C** Отключение не распространяется на уведомления о списании: они отправляются всегда, а отключаются только прочие уведомления

Зачем: Ф-1 требует отправлять всегда, Ф-4 позволяет отключить. Для одного клиента с отключённой настройкой команды реализуют разное поведение, и тест нельзя написать.

**<a id="q-02"></a>Q-02** Методы чтения статуса и отключения · можно ответить позже · кому: Архитектор · к [D-02](#d-02)  
Какими интерфейсами оператор получает статус доставки, а клиент отключает уведомления, если в разделе интерфейсов есть только POST `/notify`?  
Где: 3. Интерфейсы, строка 19: «API POST /notify принимает поля client_id, amount, currency.»; Ф-4, строка 15: «Ф-4. Клиент может отключить уведомления в настройках профиля.»

- **A** Добавить отдельный метод чтения статуса доставки для оператора и отдельный метод изменения настройки уведомлений клиента
- **B** Статус оператор получает через интерфейс банковского приложения оператора, а настройка отключения берётся из профиля клиента внешней системой; сервис только читает её
- **C** Добавить один метод чтения статуса, а настройка отключения хранится в сервисе уведомлений и меняется отдельным методом

Зачем: Без описанных операций нельзя реализовать Ф-2 и Ф-4, и неясно, кто хранит настройку.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
