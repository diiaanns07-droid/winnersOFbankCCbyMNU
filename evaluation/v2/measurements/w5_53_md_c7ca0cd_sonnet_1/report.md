### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Обещано чтение настроек через REST API, метода чтения нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 104: «Description | Сохранение порога. Функциональные требования: чтение порога» · «REST type | GET»

**Проблема.** Строка 52 обещает чтение настроек через дочерний документ, а в нём один метод `saveLimit`, который только сохраняет. Текущие порог, признак и «сумма за месяц» на экране (строка 29) получить нечем.  
**Сценарий.** Клиент открывает Карты → Расходы → Уведомления: приложению нечем получить порог, enabled и сумму за месяц, экран пуст.  
**Последствия.** Клиентский разработчик не может реализовать экран, а серверный не знает, какой метод чтения делать.  
**Как исправить.** Добавить в дочерний документ метод чтения настроек карты с ответом (порог, enabled, расходы за месяц) либо убрать обещание чтения и исправить Description.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/`<уточнить: путь метода чтения>?cardId=... → 200 {"amount":"<порог, тенге>","enabled":"0|1","spent":"<расходы за месяц>"}»  
**Вопрос владельцу.** Каким методом приложение получает порог, признак и сумму за месяц? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — добавить отдельный метод чтения, возвращающий порог, признак включения и сумму за месяц…; B — добавить два отдельных метода; C — расширить ответ метода сохранения суммой за месяц, а чтение настроек отдать отдельному…  
*Критичный, блокирует разработку и тестирование · критерий «Полнота набора» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.3) · требования [R-12](#r-12 "Настройки через REST API, идемпотентность событий"), [R-16](#r-16 "Общие параметры метода сохранения порога"), [R-03](#r-03 "Экран расходов: переключатель, порог, сумма, сохранение") · нашли: архитектор, проверка набора, правило «обещанные операции»*

#### <a id="d-02"></a>🔴 D-02. Недопустимая сумма: ответ 200 с ERROR или код 400

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** П. 5 логики (строка 121) и пример (строка 171) дают для неверной суммы 200 с result=ERROR, а статус 400 (строка 163) — для неверных параметров. По строке 151 код 200 считается успехом.  
**Сценарий.** amount=999: по логике и примеру ответ 200 {"result":"ERROR"} (успех по строке 151), по перечню статусов — 400 {"message":"Некорректный запрос"} (отказ).  
**Последствия.** Клиент может показать «сохранено», хотя порог не изменён, и пользователь не получит уведомление.  
**Как исправить.** Оставить для отклонённой суммы один исход: 400 с телом ошибки; убрать вариант ERROR из примера 200 и шага 5.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «400 {"result":"ERROR","message":"Проверьте сумму"} при amount вне 1 000–1 000 000; 200 только {"result":"OK","amount":"…","enabled":"…"}»  
**Вопрос владельцу.** Для неверной суммы возвращается 200 с ERROR или 400? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — статус 400 с телом {"message":"Проверьте сумму"}; B — статус 200 с result=ERROR, message и прежними значениями amount и enabled; C — статус 400 с result=ERROR, message и прежними значениями amount и enabled в теле  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-21](#r-21 "При отклонении суммы возврат состояния и ERROR"), [R-30](#r-30 "Правило успешности ответа по коду"), [R-35](#r-35 "Код 200 — успешное выполнение метода"), [R-36](#r-36 "Код 400 — неверно заполненные параметры запроса") · нашли: тестировщик, проверка набора, архитектор, правило «контракт API»*

#### <a id="d-03"></a>🔴 D-03. Не определено, какое событие считается «проведённой покупкой»

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель обещает уведомление «в момент покупки», а Ф-2 учитывает «проведённые» покупки; у карточной операции есть авторизация и клиринг, какое событие получает сервис расходов, не сказано. Срок в минуту отсчитывается от «получения события».  
**Сценарий.** Покупка 49 000 ₸ при пороге 50 000 ₸ авторизована в понедельник, клиринг через 2 дня: по толкованию «авторизация» push уходит сразу, по «проведение» — через 2 дня.  
**Последствия.** Разработка выбирает событие наугад, тестирование не может проверить срок «в течение минуты», клиент получает уведомление с опозданием или о расходе, который не состоялся.  
**Как исправить.** Зафиксировать этап операции (авторизация или клиринг), источник события и правило для отмены авторизации и отличающейся суммы.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки, по которым процессинг передал <уточнить: событие авторизации или клиринга>. Сумма берётся из <уточнить: авторизации или клиринга>; отменённая авторизация расходы не увеличивает.»  
**Вопрос владельцу.** Считать расходы по авторизации (сразу, возможны отмены) или по клирингу (через 1–3 дня)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — авторизация: расходы растут сразу при одобрении покупки, отмена авторизации уменьшает…; B — клиринг: расходы растут только при проведении по клирингу, push уходит после него; цель…  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Уведомлять клиента о достижении бюджета при покупке"), [R-06 / Ф-2](#r-06 "Правила учёта расходов за месяц"), [R-10](#r-10 "Передача push в течение минуты"), [R-09](#r-09 "Последовательность вызовов процессинга, расходов, настроек, push") · нашли: риски, аналитик, проверка набора*

#### <a id="d-04"></a>🔴 D-04. Критерий приёмки №2 противоречит правилу месяца в Ф-2

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Ф-2 относит расход к месяцу даты совершения покупки, а критерий приёмки для покупки 31 января ожидает рост февральского счётчика.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 по Алматы: по Ф-2 растёт январь, по приёмке — февраль.  
**Последствия.** Разработчик и тестировщик получат разный результат на стыке месяцев; push может уйти или не уйти не в том месяце.  
**Как исправить.** Выбрать одно событие для отнесения к месяцу (дата совершения или дата проведения) и привести Ф-2 и критерий приёмки к нему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц определяется по дате <уточнить: совершения или проведения> покупки в часовом поясе UTC+5.»  
**Вопрос владельцу.** Месяц определяется по дате совершения покупки или по дате её проведения? → [Q-04](#q-04) (варианты ответа)  
**Варианты ответа:** A — К январю; B — К февралю; C — месяц берётся по дате авторизации в часовом поясе Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Правила учёта расходов за месяц"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-05"></a>🔴 D-05. Ф-3 ограничивает push одним в месяц, Ф-4 снимает ограничение

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

#### <a id="d-15"></a>🟠 D-15. Источник последних четырёх цифр карты для push не определён

- Часть A › Sequence Diagram, строка 43: «Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога»

**Проблема.** В push передаются последние четыре цифры карты (строка 43), но в хранимых данных (строка 49) их нет, состав события процессинга не описан.  
**Сценарий.** Покупка доводит расходы до порога: сервис расходов знает `cardId`, но не может сформировать четыре цифры для push.  
**Последствия.** Сообщение клиенту нельзя сформировать без догадки об источнике номера.  
**Как исправить.** Указать источник последних четырёх цифр: поле события процессинга или вызов с `cardId`.

#### <a id="d-16"></a>🟠 D-16. Суммы в тиынах и порог в тенге без правила пересчёта

- Часть A › Требования к данным, строка 49: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге»

**Сценарий.** Расходы 5 000 000 тиын и порог 50 000 ₸: без пересчёта push уйдёт в 100 раз раньше или не уйдёт.

#### <a id="d-18"></a>🟠 D-18. Ответ при отклонении суммы с «прежним состоянием» не описан

#### <a id="d-19"></a>🟠 D-19. Типы amount и enabled в запросе и ответе различаются

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
