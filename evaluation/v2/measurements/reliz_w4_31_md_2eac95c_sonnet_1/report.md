### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Не определено, какое событие покупки считается «проведённой»

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель обещает уведомление «в момент покупки», а в расходы входят «проведённые покупки». Не сказано, что передаёт процессинг: авторизацию или клиринг. Минута из НФТ отсчитывается от неопределённого «события».  
**Сценарий.** Покупка 1 500 ₸ при расходах 48 500 ₸ и пороге 50 000 ₸ авторизована во вторник, клиринг в пятницу: при авторизации push во вторник, при проведении через три дня.  
**Последствия.** Разработка выберет событие наугад, тестирование не проверит срок «в течение минуты», клиент получит push с опозданием в днях или ложное уведомление по отменённой покупке.  
**Как исправить.** Зафиксировать этап (авторизация или проведение), источник события, учёт отличающейся суммы и судьбу отменённой авторизации; согласовать цель со сроком.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 43: «Процессинг → сервис расходов: проведена покупка» → «Покупка учитывается в расходах по событию <уточнить: авторизация или проведение> от процессинга; при отмене авторизации сумма <уточнить: исключается из расходов>; push передаётся в течение <уточнить: срок> после этого события.»  
**Вопрос владельцу.** Расходы считаются по авторизации (мгновенно, возможна отмена) или по проведению (через 1–3 дня)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — событие авторизации покупки; B — событие проведения покупки (клиринга), push приходит после проведения, возможно через 1–3…; C — расходы растут по авторизации, а при проведении сумма уточняется без повторного push  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Уведомить клиента о достижении бюджета при покупке"), [R-06 / Ф-2](#r-06 "Правила учёта расходов за месяц"), [R-09](#r-09 "Последовательность взаимодействия процессинга, расходов, настроек, push"), [R-10](#r-10 "Передача push на отправку в течение минуты") · нашли: риски, аналитик, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Критерий приёмки №2 противоречит Ф-2 по месяцу покупки

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»

**Проблема.** Ф-2 относит покупку к месяцу по дате совершения, а критерий приёмки для покупки от 31 января, проведённой 1 февраля, ожидает рост февральского счётчика.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03: по Ф-2 растёт январь, по приёмке — февраль.  
**Последствия.** Разработчик и тестировщик разойдутся при приёмке, на границе месяца push придёт или не придёт в неверном месяце.  
**Как исправить.** Определить одно событие, по дате которого покупка попадает в месяц, и привести Ф-2 и критерий приёмки к нему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц покупки определяется по дате <уточнить: совершения или проведения> покупки в часовом поясе <уточнить: UTC+N>.»  
**Вопрос владельцу.** По дате совершения или по дате проведения покупка относится к месяцу? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — месяц определяется по дате совершения покупки в часовом поясе Алматы; B — месяц определяется по дате проведения операции в часовом поясе Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Правила учёта расходов за месяц"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Ф-3 (один push в месяц) противоречит Ф-4

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 допускает максимум один push на карту в месяц, а Ф-4 велит слать push при следующем достижении нового порога «независимо от истории предыдущей настройки». Приоритет не задан.  
**Сценарий.** Порог 50 000, push в марте; порог повышен до 70 000, расходы 70 000 в марте: по Ф-3 push нет, по Ф-4 есть.  
**Последствия.** Разработчик и тестировщик по-разному решат, нужен ли второй push.  
**Как исправить.** Указать: лимит один на карту или один на каждую настройку порога.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Ф-3.... Максимум один push за календарный месяц на каждое значение порога <уточнить: на карту или на каждое значение порога>. Ф-4. При смене порога... действует то же ограничение.»  
**Вопрос владельцу.** Что верно: «второго push в марте нет: лимит один на месяц» (как в Ф-3) или «push отправляется независимо от прежнего push» (как в Ф-4)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — не более одного push на карту в календарный месяц при любой смене порога; B — один push на каждое значение порога в месяце; C — один push на карту в месяц  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Push при достижении порога, один в месяц"), [R-08 / Ф-4](#r-08 "Сохранение суммы при смене порога") · нашли: проверка набора, тестировщик*

#### <a id="d-04"></a>🔴 D-04. Обещано чтение порога и суммы, метода чтения нет

**Последствия.** Клиентское приложение нельзя реализовать без догадок, интегратор не знает контракта чтения.  
**Как исправить.** Добавить в часть B отдельную операцию чтения (GET) с параметром `cardId`. В ответе вернуть порог, enabled и сумму расходов за текущий месяц. Description у `saveLimit` исправить на «Сохранение порога».  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET <уточнить: путь метода чтения>?cardId=... → 200 {"amount":"50000","enabled":"1","spent":"<уточнить: единица суммы за месяц>"}»  
**Вопрос владельцу.** Каким методом приложение получает порог, переключатель и сумму за месяц? → [Q-04](#q-04) (варианты ответа)

**Сценарий.** Команда разработки или эксплуатации ищет значение (адрес, ссылку, параметр) и не находит его.  
**Последствия.** Работа останавливается на уточнении; в промышленную среду нечего настраивать.  
**Как исправить.** Указать значения или явно написать «не применяется» с причиной.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 108: «Prod: —» → «Prod: <уточнить: значение>; Swagger: <уточнить: значение>»

#### <a id="d-16"></a>🟠 D-16. Шаг 5 не определяет код и поля ответа при отказе

- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»

**Последствия.** Клиент и сервер по-разному разберут отказ, а экран покажет неверное состояние порога.

#### <a id="d-17"></a>🟠 D-17. Типы amount и enabled в запросе и ответе различаются

- Часть B › Query-параметры, строки 143 и 144: «amount | integer» · «enabled | integer»
- Часть B › Ответ, строки 156 и 157: «amount | string» · «enabled | string»

**Проблема.** amount и enabled в запросе integer (строка 143, строка 144), в ответе string (строка 156, строка 157).

**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Порог в тенге, обязательный"), [R-28](#r-28 "Признак включения, обязательный"), [R-32](#r-32 "Порог в ответе при успехе"), [R-33](#r-33 "Признак включения в ответе") · нашли: правило «контракт API»*

#### <a id="d-18"></a>🟠 D-18. Перечень кодов ответа противоречив и неполон

**Как исправить.** Оставить один код для чужой карты, остальные формулировки убрать или сузить.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
