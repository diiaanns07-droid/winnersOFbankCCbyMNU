**<a id="q-02"></a>Q-02** Статус QR-кода после оплаты и возврата · можно ответить позже · кому: Аналитик · к [D-07](#d-07), [D-08](#d-08)  
Какой статус получает QR-код при принятии перевода в обработку, какой после DONE и что происходит при REJECTED? Отдельно: меняется ли статус «оплачен» у QR-кода без суммы, который принимает несколько переводов?  
Где: Ф-2, строка 38: «QR-код с суммой считается оплаченным с момента, когда сервис переводов принял перевод по…»; Часть B › Методы сервиса QR-кодов, строка 212: «410 — QR-код с суммой уже оплачен, по QR-коду есть перевод в обработке»; Часть A › Требования к данным, строка 51: «статус (активен, оплачен, отменён, истёк)»

- **A** Для QR с суммой при принятии перевода в обработку статус становится «оплачен»; при REJECTED возвращается в «активен». Для QR без суммы статус остаётся «активен» после любых оплат, «оплачен» не используется. Проверка «перевод в обработке» делается по наличию перевода в статусе обработки.
- **B** Ввести новый статус «в обработке»: QR переходит в него при принятии перевода, при DONE — в «оплачен» (только для QR с суммой), при REJECTED — в «активен». Для QR без суммы статус «в обработке» на время одного перевода, затем «активен».
- **C** Статус «оплачен» ставится только при DONE, при принятии в обработку статус не меняется; REJECTED ничего не меняет. Для QR без суммы статус всегда «активен».

Зачем: Без ответа нельзя написать тест на повторную оплату, отмену при переводе в обработке и возврат после REJECTED: один и тот же вход даёт разный статус и разный код ответа (410 или 200) в зависимости от трактовки.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
