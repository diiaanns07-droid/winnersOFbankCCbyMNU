## <a id="s3"></a>3. Проверка каждого требования

### 3.1. Матрица: требование × нарушенный критерий

Столбцы: Од — однозначность; Пл — полнота требования; Ед — единичность; Пр — проверяемость; Кр — корректность; Ш — соответствие шаблону; Нб — критерии набора (раздел 4); Рс — ИБ и операционные риски. В клетке — самая серьёзная находка: 🔴 критичная, 🟠 существенная, 🟡 незначительная; «·» — нарушений нет. Критерии без нарушений во всём документе: необходимость, уместность (что, а не как), осуществимость, язык требований.

#### <a id="d-01"></a>🔴 D-01. Месяц покупки: Ф-2 по дате совершения, приёмка по дате проведения

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Строка 38 «Месяц определяется по дате совершения покупки в Алматы» против строки 64 «Февральский счётчик вырос на 4 000 ₸» для покупки 31 января 23:58, проведённой 1 февраля 00:03.  
**Сценарий.** Покупка 31.01 в 23:58 на 4 000 ₸ проведена 01.02 в 00:03. По Ф-2 сумма в январском счётчике, по критерию приёмки — в февральском.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸; февральский не меняется», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸; февральский не меняется», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Январский счётчик вырос на 4 000 ₸; февральский счётчик не изменился (0 ₸).»

#### <a id="d-05"></a>🟠 D-05. Событие «проведённая покупка»: авторизация или проведение не различены

- Часть A › Цели, строка 23: «в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Сценарий.** Покупка 4 000 ₸ авторизована 31.01 в 23:50 и проведена 02.02. По авторизации сумма растёт 31.01 и push уходит сразу; по проведению — 02.02. Авторизация отменена до проведения: ложный push по первому толкованию.  
**Последствия.** Клиент получает push на несколько дней раньше или позже, а при отмене авторизации — ложный push; обещание «в момент покупки» выполнимо только по авторизации, и разработка не знает, какое событие принимать от процессинга.

**<a id="q-03"></a>Q-03** Повторный push после смены порога в месяце · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03)  
Может ли клиент получить второй push в том же календарном месяце, если он изменил порог и накопленная сумма снова достигла нового порога? Правило про максимум одного push в месяц и правило о «независимо от истории настройки» дают разный ответ.  
Где: Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»; Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **A** Не более одного push за календарный месяц независимо от смены порога; после смены порога push не повторяется, сохраняется только накопленная сумма
- **B** Второй push в том же месяце отправляется один раз после каждого изменения порога, если накопленная сумма достигла нового порога

Зачем: Один и тот же сценарий смены порога даст либо один, либо два push в месяце, и приёмка по строке 40 расходится с правилом строки 39.

**<a id="q-04"></a>Q-04** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-04](#d-04), [D-18](#d-18)  
Что возвращает метод сохранения, если сумма порога вне диапазона от 1 000 до 1 000 000 ₸: HTTP 400 с сообщением или HTTP 200 с признаком ERROR? В логике сказано вернуть прежнее состояние и ERROR, в примере ответа ERROR стоит под заголовком 200, а в статусах 400 описан как ошибка параметров.  
Где: Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** HTTP 400 с телом {"message":"Проверьте сумму"}; настройка не меняется; HTTP 200 с result ERROR не используется. HTTP 200 остаётся только для result OK
- **B** HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; настройка не меняется; HTTP 400 используется только при отсутствии обязательного параметра

Зачем: Для amount=999 тест ожидает либо код 400, либо код 200 с ERROR; клиентская обработка ответа различается, и приёмка не может быть однозначной.

**<a id="q-05"></a>Q-05** Какое событие процессинга считать покупкой · можно ответить позже · кому: Владелец продукта · к [D-05](#d-05)  
Какое событие процессинга считается покупкой для расходов клиента: одобрение (авторизация, сумма может быть предварительной) или проведение (списание через 1–3 дня, сумма может отличаться)? В тексте сказано «проведённые покупки», а в последовательности событие названо «проведена покупка».  
Где: Ф-2, строка 38: «В расходы входят проведённые покупки»; Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»

- **A** Покупка учитывается при проведении (списании) с суммой проведения; одобрение без проведения в расходы не попадает
- **B** Покупка учитывается при одобрении (авторизации) с суммой одобрения; при последующем проведении с другой суммой разница корректирует расходы того же месяца

Зачем: Без выбора события сумма за месяц и момент push расходятся между разработкой и тестированием, а сроки push отличаются на 1–3 дня.

**<a id="q-06"></a>Q-06** Код ответа при запросе чужой карты · можно ответить позже · кому: ИБ · к [D-06](#d-06)  
Какой код возвращать, когда клиент запрашивает чужую карту: 403 или 404? В статусах описан 403 «доступ запрещён» для указанного ресурса, а в описании сказано, что для чужой карты возвращается 404, как и для отсутствующей карты.  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты»

- **A** 404 с телом {"message":"Карта не найдена"} и для чужой, и для отсутствующей карты; код 403 для карт не используется
- **B** 403 для чужой карты и 404 для отсутствующей; такой ответ позволяет определить, что карта существует

Зачем: Разница кодов позволяет по ответу узнать, существует ли чужая карта, и тест на доступ по-разному проверит статус; ИБ должна решить, допустимо ли это раскрытие.

**<a id="q-07"></a>Q-07** Защита от повторной доставки события · можно ответить позже · кому: Архитектор · к [D-16](#d-16)  
По какому признаку распознаётся повторная доставка события процессинга и как долго хранятся идентификаторы операций? Документ требует сохранять исходный итог при повторе, но не говорит, по какому полю повтор узнаётся и что происходит с push при повторе.  
Где: Часть A › Требования к интеграции, строка 52: «Повторная доставка одного события процессинга сохраняет исходный итог»; Часть A › Требования к данным, строка 49: «идентификатор операции, сумму покупки в тиынах»

- **A** Повтор распознаётся по идентификатору операции; идентификаторы хранятся 90 дней; при повторе итог и признак отправки push не меняются
- **B** Повтор распознаётся по паре идентификатора карты и идентификатора операции; идентификаторы хранятся 1 год; при повторе push повторно не отправляется

Зачем: Без ключа дедупликации и срока хранения повторное событие либо удвоит сумму, либо повторно отправит push, и тест на идемпотентность не сможет проверить результат.

**<a id="q-08"></a>Q-08** Срабатывание при выключенном уведомлении · можно ответить позже · кому: Владелец продукта · к [D-13](#d-13)  
Что происходит с покупками, когда уведомление выключено? По умолчанию уведомление выключено, но правило про push не говорит, учитываются ли покупки в это время и отправляется ли push.  
Где: Ф-1, строка 37: «По умолчанию уведомление выключено»; Ф-3, строка 39: «клиент получает push»

- **A** Расходы учитываются всегда; push отправляется только при включённом уведомлении
- **B** Расходы учитываются и push отправляется только с момента включения уведомления; покупки до включения в сумму не входят

Зачем: Без ответа при выключенном уведомлении команды по-разному посчитают накопленную сумму, и сохранённый итог после включения будет разным.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
