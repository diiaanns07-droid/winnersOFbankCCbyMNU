#### <a id="d-01"></a>🔴 D-01. Противоречие в определении месяца покупки между правилом Ф-2 и критерием приёмки

- Ф-2, строка 38: «Ф-2. Месяц определяется по дате совершения покупки в Алматы»
- Часть A › Критерии приемки, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Правило Ф-2 относит покупку к месяцу совершения (31 января), а критерий приёмки — к месяцу проведения (1 февраля).  
**Сценарий.** Покупка совершена 31 января в 23:58 и проведена 1 февраля в 00:03. По Ф-2 сумма идет в январь, по критерию приёмки — в февраль.  
**Последствия.** Разработка и тестирование реализуют разные механизмы агрегации расходов по месяцам, из-за чего клиенты получат неверный расчёт лимита и ошибочные push-уведомления.  
**Как исправить.** Согласовать единый подход к определению месяца операции и синхронизировать требование Ф-2 с критериями приёмки.  
**Было → стало.** Строка 38: «Ф-2. Месяц определяется по дате совершения покупки в Алматы» → «Ф-2. Месяц определяется по дате проведения покупки по времени Алматы (UTC+5). **Вопрос владельцу.** По дате какого события операция относится к календарному месяцу: по дате совершения покупки клиентом или по дате её проведения в процессинге? → [Q-01](#q-01) (варианты ответа)

#### <a id="d-03"></a>🔴 D-03. Возврат ошибки валидации с кодом HTTP 200 вместо 400

- Часть B › Логика работы метода, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»

**Проблема.** При отклонении неверной суммы логика метода и пример возвращают статус HTTP 200 с result ERROR, противореча коду 400.  
**Сценарий.** Клиент передает неверную сумму amount=500. Сервер возвращает HTTP 200 OK с телом ERROR, клиент воспринимает вызов как успешный.  
**Последствия.** Клиентское приложение посчитает операцию сохранения успешной по коду 200, что приведёт к рассинхронизации состояния UI и бэкенда.  
**Как исправить.** Исключить тело с result ERROR из успешного ответа HTTP 200 и возвращать стандартный код HTTP 400 Bad Request при невалидной сумме.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «При отклонении суммы возвращать HTTP статус 400 Bad Request с телом {"message":"Проверьте сумму"}.»  
**Вопрос владельцу.** Должна ли ошибка валидации суммы возвращать HTTP 400 вместо HTTP 200? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — возвращать HTTP 400 Bad Request при любой ошибке валидации входных данных; B — возвращать HTTP 200 OK с телом результата ERROR при отклонении суммы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-21](#r-21 "Шаг 5 логики метода: откат при отклонении суммы"), [R-30](#r-30 "Правило успешности и неуспешности ответа"), [R-36](#r-36 "Статус 400 неверных параметров запроса") · нашли: тестировщик, архитектор*

#### <a id="d-06"></a>🟠 D-06. Конфликт лимита push в месяц и отправки при смене порога

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
