#### <a id="d-01"></a>🔴 D-01. Месяц покупки: дата совершения в Ф-2 против приёмки на проведение

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Ф-2 (строка 38) «Месяц определяется по дате совершения покупки в Алматы» относит покупку к месяцу совершения, а критерий приёмки (строка 64) «Февральский счётчик вырос на 4 000 ₸» относит её к месяцу проведения.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03. По Ф-2 сумма в январе, по приёмке в феврале; тест по одному из двух мест упадёт.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸, февральский не меняется», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Изменить правило Ф-2 так, чтобы оно давало «Февральский счётчик вырос на 4 000 ₸» (формулировка ниже), или, если правило Ф-2 верно, исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸, февральский не меняется». Решает владелец продукта.  
**Предлагаемая формулировка.** «Покупка относится к месяцу даты совершения (Ф-2). Ожидаемо: январский счётчик вырос на 4 000 ₸, февральский счётчик не изменился.»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик +4 000 ₸, февральский не меняется» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-01](#q-01) (варианты ответа)

- **B** По дате проведения покупки в часовом поясе Алматы; покупка от 31 января в 23:58, проведённая 1 февраля в 00:03, попадает в февраль
- **C** По дате совершения покупки; проведение при переходе месяца переносит сумму в текущий месяц, если совершение пришлось на предыдущий

Зачем: Для покупки 31 января в 23:58, проведённой 1 февраля, разные команды запишут сумму либо в январь, либо в февраль, и приёмочный тест даст разный итог.

**<a id="q-02"></a>Q-02** Какое событие считается покупкой · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)  
Считается ли покупкой для расходов и push одобренная авторизация или клиринговое проведение, и что происходит с авторизацией, которую банк отменил?  
Где: Ф-2, строка 38: «В расходы входят проведённые покупки»; Часть A › Цели, строка 23: «узнать о достижении личного бюджета в момент покупки»

- **A** Покупкой считается одобренная авторизация; при её отмене сумма вычитается из расходов месяца и push, уже отправленный, не отзывается
- **B** Покупкой считается клиринговое проведение; push приходит с задержкой 1–3 дня, цель «в момент покупки» в требованиях снимается
- **C** Покупкой считается одобренная авторизация; отменённая авторизация не учитывается, а уже учтённые суммы не пересчитываются

Зачем: Если учёт идёт по авторизации, а тесты проверяют проведение, push придёт на 1–3 дня позже или вообще не придёт для отменённых операций, и приёмка даст разный результат.

**<a id="q-03"></a>Q-03** Повторный push в месяце после смены порога · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03)

Где: Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»; Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **A** Нет, не более одного push на карту за месяц независимо от смены порога; второй push не отправляется
- **B** Да, push отправляется при каждом переходе через новый порог в месяце, ограничение «один push в месяц» действует только при неизменном пороге
- **C** Да, push отправляется при переходе через новый порог только если клиент изменил порог на сумму не меньше 10 000 ₸ от прежнего значения

Зачем: Без выбора одна команда отправит второй push в месяце, другая не отправит, и тест Ф-4 будет пройден или провален в зависимости от трактовки.

**<a id="q-04"></a>Q-04** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-04](#d-04), [D-20](#d-20)

Где: Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** Код 400 с телом {"result":"ERROR","message":"Проверьте сумму"}; код 200 и 201 считаются успешными только при результате OK; код 201 из правила успеха удаляется
- **B** Код 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; код 400 используется только при синтаксически неверном запросе
- **C** Код 400 с телом {"message":"Проверьте сумму"}; поле result в ответах об ошибке не передаётся

Зачем: На сумму 999 ₸ один тест ждёт статус 400, другой статус 200 с ERROR; клиент мобильного приложения по-разному обработает ошибку.

- **B** Метод чтения возвращает только порог и признак включения; сумма за месяц на экране не выводится и убирается из требования экрана

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
