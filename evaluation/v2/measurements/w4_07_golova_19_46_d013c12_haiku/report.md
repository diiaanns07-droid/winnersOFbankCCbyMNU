#### <a id="d-01"></a>🔴 D-01. Чтение порога обещано, но операции чтения в API нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»
- Часть B › Общие параметры, строка 103: «Сохранение порога. Функциональные требования: чтение порога»
- Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения»

**Проблема.** Документ обещает чтение настроек (строка 52, строка 103 «чтение порога»), но спецификация описывает только сохранение: единственный метод — `saveLimit` (строка 108), логика строки 120 — замена настройки.  
**Сценарий.** Клиент открывает экран «Уведомления»: приложение должно показать текущий порог, но вызова чтения нет. Сервис расходов тоже не получает порог.  
**Последствия.** Экран не заполняется текущим порогом; сервис расходов не получает порог; разработка не знает, что вызывать.  
**Как исправить.** Описать метод чтения порога карты с параметрами, ответом и кодами.  
**Предлагаемая формулировка.** «Метод чтения порога карты: параметр `cardId`, ответ {result, amount, enabled}, коды 200, 401, 403, 404, 500.»  
**Вопрос владельцу.** Какой метод и путь использует приложение для чтения текущего порога? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — отдельный метод чтения по `cardId`; B — чтение выполняется тем же методом сохранения без параметров amount и enabled; C — приложение получает настройки при входе из сервиса настроек без отдельного метода в этом…  
*Критичный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-12](#r-12 "Обмен настройками с REST API, повтор события"), [R-16](#r-16 "Метод сохранения и чтения порога карты"), [R-03](#r-03 "Экран настройки порога и суммы за месяц"), [R-09](#r-09 "Последовательность вызовов сервисов при покупке") · нашли: проверка набора, правило «обещанные операции», архитектор*

#### <a id="d-02"></a>🔴 D-02. Событие «покупка» не определено: авторизация или проведение

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Часть A › BPMN схема процесса, строка 34: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Ф-2 считает «проведённые покупки» (строка 38), sequence называет «проведена покупка» (строка 43), цель обещает реакцию «в момент покупки» (строка 23), а процесс отправляет push после проведения (строка 34). Не сказано, авторизация это или клиринг.  
**Сценарий.** Покупка 10 января в 12:00 на 5 000 ₸ при пороге 5 000 ₸: по авторизации push 10 января, по клирингу через два дня — 12 января. Исход для одной покупки разный.  
**Последствия.** Разработка не знает, какое событие принимать из процессинга; клиент получит уведомление с задержкой в дни или не получит его вовремя, а приёмка спорит по датам учёта.  
**Как исправить.** Зафиксировать в требованиях событие, которое учитывается, и согласовать срок push с обещанием цели.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки, по которым процессинг передал событие <уточнить: авторизация или проведение>; push отправляется в течение минуты после этого события.»  
**Вопрос владельцу.** Что считается учётным событием покупки: одобренная авторизация или проведённая (клиринговая) операция, и допустим ли push через дни после покупки? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — учитывается одобренная авторизация; B — учитывается клиринговая (проведённая) операция  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Узнать о достижении бюджета при покупке"), [R-04](#r-04 "Порядок обработки покупки до отправки push"), [R-06 / Ф-2](#r-06 "Подсчёт расходов по дате покупки в Алматы"), [R-09](#r-09 "Последовательность вызовов сервисов при покупке"), [R-10](#r-10 "Передача push в течение минуты после события") · нашли: риски, аналитик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Критерий приёмки №2 относит покупку к другому месяцу, чем Ф-2

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Ф-2 относит месяц по дате совершения покупки (строка 38): покупка 31 января 23:58 — январская. Критерий строки 64 ожидает рост февральского счётчика, то есть отнесение по дате проведения.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸: по Ф-2 растёт январский счётчик, по критерию приёмки — февральский. Код, верный по Ф-2, упадёт на тесте по критерию.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик растёт на 4 000 ₸, февральский не меняется», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик растёт на 4 000 ₸, февральский не меняется», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Январский счётчик вырос на 4 000 ₸; февральский счётчик не изменился.»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик растёт на 4 000 ₸, февральский не меняется» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — по дате совершения в Алматы; B — по дате проведения в Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸"), [R-06 / Ф-2](#r-06 "Подсчёт расходов по дате покупки в Алматы") · нашли: тестировщик, аналитик, проверка набора*

#### <a id="d-04"></a>🔴 D-04. Ф-3 и Ф-4 по-разному решают второй push в месяце

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 (строка 39) разрешает максимум один push за календарный месяц. Ф-4 (строка 40) требует push при следующем достижении порога независимо от истории. Исключение из Ф-3 не названо.  
**Сценарий.** Порог 50 000 ₸, push уже отправлен; порог поднят до 100 000 ₸; покупка доводит расходы до 100 000 ₸. Ф-3 запрещает второй push, Ф-4 требует его.  
**Последствия.** Клиент получит второй push в месяце; тест по Ф-3 и Ф-4 даст разный итог.  
**Как исправить.** Зафиксировать, действует ли лимит одного push в месяц при смене порога, и убрать противоречащую фразу.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Если накопленная сумма ниже нового порога, следующее достижение вызывает push, только если за календарный месяц push ещё не отправлялся; <уточнить: push сверх месячного лимита или нет>.»

Где: Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»; Часть B › Общие параметры, строка 103: «Сохранение порога. Функциональные требования: чтение порога»; Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения.»

- **A** Отдельный метод чтения по `cardId`: возвращает result OK, amount в тенге и enabled 0 или 1; для чужой карты 404 по описанию ошибок
- **B** Чтение выполняется тем же методом сохранения без параметров amount и enabled: при их отсутствии возвращаются текущие значения
- **C** Приложение получает настройки при входе из сервиса настроек без отдельного метода в этом документе

Зачем: Без метода чтения экран не покажет текущий порог, и тесты чтения написать нельзя; разработчики выберут разные способы.

**<a id="q-02"></a>Q-02** Учётное событие покупки и срок push · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)  
Что считается учётным событием покупки: одобренная авторизация или проведённая клиринговая операция? От этого зависит, придёт ли push в момент покупки или через несколько дней после неё.  
Где: Ф-2, строка 38: «В расходы входят проведённые покупки»; Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»; Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»

- **A** Учитывается одобренная авторизация; push отправляется в течение минуты после неё; клиринг на счётчик не влияет
- **B** Учитывается клиринговая (проведённая) операция; push отправляется в течение минуты после клиринга и может прийти через несколько дней после покупки

Зачем: Цель обещает push в момент покупки, а событие может наступать через дни; команды заложат разные источники событий и разные сроки.

**<a id="q-03"></a>Q-03** Месяц покупки: дата совершения или проведения · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03)  
К какому календарному месяцу относится покупка: по дате её совершения в Алматы или по дате проведения в Алматы? Правило и критерий приёмки для покупки 31 января в 23:58, проведённой 1 февраля в 00:03, дают разные месяцы.  
Где: Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»; критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы» · «Февральский счётчик вырос на 4 000 ₸»

- **A** По дате совершения в Алматы: покупка от 31 января 23:58 относится к январю, критерий приёмки переписывается
- **B** По дате проведения в Алматы: покупка, проведённая 1 февраля 00:03, относится к февралю, правило про дату совершения переписывается

Зачем: Тест на границе месяца получит разный результат в зависимости от того, какую дату взяла команда; счётчик расходится на 4 000 ₸.

**<a id="q-04"></a>Q-04** Повторный push в месяц после смены порога · ⛔ блокирует · кому: Владелец продукта · к [D-04](#d-04)  
Может ли после смены порога в том же календарном месяце прийти второй push? Правило одного push в месяц и правило отправки push при достижении нового порога дают противоположный ответ.  
Где: Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»; Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **A** Не более одного push на карту за календарный месяц, в том числе после смены порога; после уже отправленного push в этом месяце новый порог push не вызывает
- **B** Push отправляется при каждом переходе суммы через порог, включая повторный в том же месяце после смены порога, без ограничения одним push в месяц

Зачем: Для одного и того же сценария один вариант даёт второй push, другой нет; тест на количество push не может быть написан однозначно.

**<a id="q-05"></a>Q-05** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-05](#d-05)  
Какой HTTP-код получает приложение, если сумма порога вне диапазона 1 000–1 000 000: 200 с result ERROR или 400? Пример ответа и правило ошибки дают 200, а описание кода 400 относит его к неверным параметрам запроса.  
Где: Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»

- **A** Сумма вне диапазона: HTTP 200 с result ERROR; HTTP 400 только при отсутствии или неверном формате параметров (например, нецелое число)
- **B** Любая неверная сумма и любой неверный параметр: HTTP 400 с телом result ERROR и message; статус 200 только при успехе

Зачем: Клиент и тесты получат разный код на одну и ту же неверную сумму, что ломает обработку ошибок в приложении.

**<a id="q-06"></a>Q-06** HTTP-метод сохранения порога · можно ответить позже · кому: Архитектор · к [D-07](#d-07)  
Каким HTTP-методом и откуда передаются параметры сохранения порога? Метод назван `saveLimit` и меняет данные, но описан как GET, а параметры идут в строке адреса.  
Где: Часть B › Общие параметры, строки 104 и 108: «REST type | GET» · «Dev: /alerts/saveLimit»; Часть B › Request body, строка 147: «Content-Type: application/json .»

- **A** POST с параметрами `cardId`, amount и enabled в теле запроса в формате application/json; чтение отдельным GET
- **B** PUT с параметрами в теле запроса в формате application/json; чтение отдельным GET

Зачем: GET с изменением данных кэшируется и логируется вместе с параметрами в строке адреса; команды реализуют разные методы, и клиенты по-разному повторяют запрос.

**<a id="q-07"></a>Q-07** Код ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-24](#d-24)  
Какой код получает клиент, запросивший чужую карту: 404 или 403? Раздел 403 говорит о запрещённом доступе, а текст под ним требует 404 для чужой карты.  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты»

- **A** 404 с одинаковым телом для чужой и отсутствующей карты; код 403 для карты не используется, чтобы не раскрывать наличие чужой карты
- **B** 403 для чужой карты с телом message; 404 только для отсутствующей карты

Зачем: Различие 403 и 404 позволяет перебирать идентификаторы карт и узнавать, чьи они; тесты по коду ответа дадут разный результат.

**<a id="q-08"></a>Q-08** Push при понижении порога ниже накопленной суммы · можно ответить позже · кому: Владелец продукта · к [D-14](#d-14)  
Нужно ли отправлять push сразу после понижения порога, если накопленная сумма за месяц уже равна новому порогу или выше? Правило про переход снизу вверх этот случай не описывает.  
Где: Ф-4, строка 40: «Если она ниже нового порога, следующее достижение вызывает push»; Ф-3, строка 39: «Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент…»

- **A** Нет: push отправляется только при переходе накопленной суммы от ниже порога к порогу или выше по покупке; при смене порога push не отправляется
- **B** Да: при сохранении порога, если накопленная сумма уже не ниже него и push за месяц ещё не отправлялся, push отправляется сразу

Зачем: При понижении порога команды по-разному решат, есть ли push в момент сохранения настройки, и тест на этот случай будет давать разный итог.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
