#### <a id="d-01"></a>🔴 D-01. Чтение порога обещано, но ни одна операция чтения не описана

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строка 103: «Description | Сохранение порога. Функциональные требования: чтение порога»
- Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения»
- Часть B › Query-параметры, строка 143: «amount | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | limit_kzt»

**Проблема.** Строка 52 «Приложение читает и сохраняет настройки» и строка 103 «Функциональные требования: чтение порога» обещают чтение, но в API описан только `saveLimit`; amount обязателен (строка 143). Сумма за месяц с экрана (строка 29) тоже не возвращается.  
**Сценарий.** Клиент открывает экран: вызов только с `cardId` даёт 400 (amount обязателен) или перезаписывает настройку (шаг 4, строка 120). Текущий порог и сумма за месяц не показываются.  
**Последствия.** Экран не может показать действующий порог без его перезаписи; обещание чтения не выполнено.  
**Как исправить.** Добавить в контракт отдельную операцию чтения настройки карты с описанием параметров и тела ответа, либо убрать «чтение порога» из Description и раздела интеграции.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET <уточнить: путь чтения настройки>; параметр `cardId` обязательный; 200 {"result":"OK","amount":"<порог, тенге>","enabled":"0" или "1"}»  
**Вопрос владельцу.** Какой путь и метод у операции чтения порога, если `saveLimit` только сохраняет? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — отдельный метод чтения по образцу описанного; B — тот же метод сохранения с необязательным параметром amount  
*Критичный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-03](#r-03 "Экран настройки порога в разделе Расходы"), [R-12](#r-12 "Чтение и сохранение настроек через REST API"), [R-16](#r-16 "Метод сохранения порога: общие параметры вызова"), [R-27](#r-27 "Порог в тенге, обязательный") · нашли: архитектор, проверка набора, правило «обещанные операции»*

#### <a id="d-02"></a>🔴 D-02. Покупка 31 января: по Ф-2 январь, по приёмке февраль

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Строка 38 «Месяц определяется по дате совершения покупки в Алматы» относит покупку к январю; строка 64 «Февральский счётчик вырос на 4 000 ₸» относит ту же покупку к февралю.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸, проведена 1 февраля в 00:03 по Алматы: по Ф-2 январь +4 000, по приёмке февраль +4 000. Код по Ф-2 упадёт на тесте приёмки.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸, февральский без изменений», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸, февральский без изменений», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Покупка относится к январю: январский счётчик +4 000 ₸, февральский счётчик без изменений.»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик +4 000 ₸, февральский без изменений» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — по дате совершения покупки в Алматы; B — по дате проведения покупки в Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Учёт месяца по Алматы, возвраты и исключения"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Неверная сумма: HTTP 400 или HTTP 200 с ERROR в теле

- Логика работы метода, п. 5, строка 121: «При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Строка 163 «400. Ответ в случае, если параметры запроса заполнены неверно» против строки 171 с result ERROR под статусом 200 (строка 165). строка 151 считает 200 успехом, 400 отказом, поэтому одна ошибка даёт разный исход.  
**Сценарий.** amount=999 (ниже 1 000 по Ф-1): по строке 171 HTTP 200 с ERROR, клиент видит успешный статус; по строке 163 HTTP 400. Тест не выберет ожидаемый результат.  
**Последствия.** Клиент и тест получат разные коды при одинаковом вводе; успех и отказ спорны.  
**Как исправить.** Выбрать один код для неверной суммы и отразить его в статусах и в примере.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «200 — только успешное выполнение. Неверные параметры — 400 с телом <уточнить: поля ответа об ошибке>.»  
**Вопрос владельцу.** Что верно: «HTTP 400 с сообщением о неверных параметрах» (как в «Статус 400») или «HTTP 200 с телом result ERROR, как в примере блока 200» (как в «Ответ: result»)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — HTTP 400 с телом, где result равен ERROR и message «Проверьте сумму»; B — HTTP 200 с телом, где result равен ERROR и message «Проверьте сумму»

#### <a id="d-16"></a>🟠 D-16. Повтор события процессинга не распознаётся: ключ дедупликации не назван

**<a id="q-02"></a>Q-02** Месяц покупки: совершение или проведение · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)

Где: Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»; критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸» · «Февральский счётчик вырос на 4 000 ₸»

- **A** По дате совершения покупки в Алматы: покупка 31 января, проведённая 1 февраля, входит в январь; пример приёмки меняется на январский счётчик
- **B** По дате проведения покупки в Алматы: покупка 31 января, проведённая 1 февраля, входит в февраль; правило по дате совершения удаляется

Зачем: На одной операции две команды дадут разный месяц и разный счётчик, и приёмочный тест на границе месяца нельзя написать однозначно.

**<a id="q-03"></a>Q-03** Код ответа при неверной сумме · ⛔ блокирует · кому: Архитектор · к [D-03](#d-03), [D-19](#d-19)  
Для суммы вне диапазона пример ответа даёт HTTP 200 с result ERROR, а описание статуса 400 говорит о неверных параметрах запроса. Какой HTTP-статус получает ответ при сумме вне диапазона и в каком виде приходит тело?  
Где: Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Логика работы метода, п. 5, строка 121: «При отклонении суммы вернуть прежнее состояние и результат ERROR»

- **A** HTTP 400 с телом, где result равен ERROR и message «Проверьте сумму»; настройка не меняется; HTTP 200 для этого случая не используется
- **B** HTTP 200 с телом, где result равен ERROR и message «Проверьте сумму»; настройка не меняется; HTTP 400 только при отсутствии обязательного параметра

Зачем: Клиент и тесты по-разному трактуют 200 и 400 как успех или отказ, и мобильное приложение может показать успех при отклонённой сумме.

**<a id="q-04"></a>Q-04** Какое событие считается покупкой · ⛔ блокирует · кому: Владелец продукта · к [D-04](#d-04)  
Цель обещает push в момент покупки, а расходы учитываются по проведённым покупкам, которые могут прийти через несколько дней после авторизации. Что считается покупкой для порога: одобренная авторизация или операция, проведённая после клиринга?  
Где: Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»; Ф-2, строка 38: «В расходы входят проведённые покупки.»; Часть A › BPMN схема процесса, строка 34: «Проведение покупки → пересчёт расходов»

- **A** Покупка это одобренная авторизация: расходы и проверка порога выполняются при одобрении, push уходит не позже минуты после одобрения; отмена авторизации уменьшает расходы месяца исходной покупки
- **B** Покупка это операция, проведённая после клиринга: расходы и проверка порога выполняются при проведении, push уходит не позже минуты после проведения; срок от совершения до push не гарантируется

Зачем: Без выбора события не определено, какие операции попадают в расходы и когда должен уйти push, и два разработчика сделают разную логику.

**<a id="q-05"></a>Q-05** Повторный push и понижение порога · ⛔ блокирует · кому: Владелец продукта · к [D-05](#d-05), [D-12](#d-12)  
Правило разрешает не более одного push за календарный месяц, а правило смены порога требует push при следующем достижении даже после него. Что происходит при смене порога в месяце, где push уже был, и при понижении порога ниже накопленной суммы?  
Где: Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц.»; Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей…» · «При изменении порога накопленная сумма сохраняется.»

- **A** Не более одного push на карту за календарный месяц, включая смену порога; если push в месяце уже был, новый порог повторного push не вызывает; если не был, push уходит при первом достижении порога, в том числе сразу после понижения порога ниже накопленной суммы
- **B** Один push на пару месяц и порог: при смене порога в том же месяце push уходит при первом достижении нового порога, в том числе сразу после понижения порога ниже накопленной суммы

Зачем: Без ответа на одном и том же входе смена порога даёт то один push, то ни одного, и тест на лимит push нельзя написать.

**<a id="q-06"></a>Q-06** Код ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-06](#d-06)  
Для карты другого клиента статусы описывают 403, а текст ниже говорит о 404, как для отсутствующей карты. Какой код получает запрос на чужую карту?  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты.»

- **A** HTTP 404 с телом «Карта не найдена» для чужой и отсутствующей карты; код 403 для карт не используется
- **B** HTTP 403 с телом «Доступ запрещён» для чужой карты; HTTP 404 только для отсутствующей карты

Зачем: Разный код для чужой карты позволяет по ответу определить, существует ли карта клиента, и тесты на доступ расходятся.

**<a id="q-07"></a>Q-07** Единицы суммы покупок и порога · можно ответить позже · кому: Архитектор · к [D-07](#d-07)

Где: Часть A › Требования к данным, строка 49: «сумму покупки в тиынах»; Особые правила, п. 1, строка 124: «Целое число тенге, обе границы включены»

- **A** Хранить и сравнивать в тиынах: порог умножается на 100 при сравнении; в ответе API порог переводится в тенге целым числом
- **B** Хранить и сравнивать в тенге целыми числами: сумма каждой покупки переводится в тенге с округлением вниз до целого тенге перед добавлением к накопленной сумме

Зачем: Разные единицы и округление дают разный момент перехода порога на одной и той же сумме, например на границе 50 000 ₸.

**<a id="q-08"></a>Q-08** Метод изменения настройки через GET · можно ответить позже · кому: Архитектор · к [D-17](#d-17)  
Метод сохранения порога называется `saveLimit` и меняет настройку, но объявлен как GET с параметрами в строке запроса, а тело запроса описано как не используемое. Каким типом запроса и как передаются параметры?

- **A** Метод записи POST, параметры `cardId`, amount и enabled передаются в теле в формате application/json, не в строке URL

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
