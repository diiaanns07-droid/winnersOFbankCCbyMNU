### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Месяц покупки: дата совершения или дата проведения

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Строка 38 относит покупку к месяцу по дате совершения, а критерий в строке 64 для покупки от 31 января ожидает рост февральского счётчика по дате проведения 1 февраля. Два места дают разный месяц.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸, проведена 1 февраля в 00:03. По строке 38 сумма в январе; по строке 64 — в феврале, февральский счётчик растёт на 4 000 ₸. Приёмка и правило расходятся.  
**Последствия.** Разработчик и тестировщик по разным местам документа закладывают разный месяц, и приёмка этого сценария либо провалится, либо пройдёт по неверной логике учёта.  
**Как исправить.** Назвать одно событие, по дате которого покупка относится к месяцу, и привести критерий приёмки к этому событию.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц определяется по дате <уточнить: совершения или проведения> покупки в Алматы.»  
**Вопрос владельцу.** По какой дате относить покупку к месяцу: по дате совершения (31 января) или по дате проведения процессингом (1 февраля)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — месяц по дате совершения покупки в Алматы; B — месяц по дате проведения процессингом в Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-06 / Ф-2](#r-06 "Учёт месяца по Алматы и расходов по проведённым покупкам"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Чтение порога и суммы за месяц не описано ни одной операцией

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»
- Часть B › Общие параметры, строки 103 и 109: «Сохранение порога. Функциональные требования: чтение порога» · «curl -G "$BASE/alerts/saveLimit»

**Проблема.** Строки 52 и 103 обещают чтение порога через REST API, строка 29 показывает сумму за месяц на экране. В разделе API описан только метод сохранения `saveLimit` (строки 103–121).  
**Сценарий.** Приложение открывает экран Уведомления для карты demo-42: метода чтения нет, текущий порог и сумма не получаются. Сохранение без чтения перезаписывает настройку.  
**Последствия.** Экран не может показать текущий порог и сумму за месяц, а сохранение без чтения перезаписывает настройку.  
**Как исправить.** Добавить отдельную операцию чтения настроек карты с полями ответа порога, признака и суммы за месяц, либо убрать обещание чтения из строк 52, 103 и 29.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/getLimit?cardId=`\<`cardId`> — ответ 200: {"result":"OK","amount":"<порог, тенге>","enabled":"0|1","`monthSum`":"<сумма за месяц, тенге>"}; <уточнить: имя поля `monthSum` и единица суммы>»  
**Вопрос владельцу.** Должна ли операция чтения возвращать сумму за месяц или она берётся из другого интерфейса? → [Q-02](#q-02) (варианты ответа)

#### <a id="d-03"></a>🔴 D-03. Ошибка суммы: HTTP 200 с ERROR или HTTP 400

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Строка 151 считает 200 успешным, строка 171 для неверной суммы отдаёт 200 с result ERROR; строка 163 для неверных параметров задаёт 400. Шаг 5 в строке 121 не называет HTTP-код.  
**Сценарий.** Запрос с amount=500: по строкам 151 и 171 это успех (200), по строке 163 — отказ (400). Клиент, смотрящий на код 200, покажет «сохранено».  
**Последствия.** Клиент, который смотрит на HTTP-код, сочтёт отказ успехом и не покажет ошибку пользователю.  
**Как исправить.** Для отклонения суммы возвращать только 400 с телом с полем message; пример с ERROR под 200 убрать или заменить.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «400, {"message":"Проверьте сумму"} — для amount вне 1 000–1 000 000; 200 с result OK только при успешном сохранении.»  
**Вопрос владельцу.** Что верно: «результат ERROR в теле; HTTP-код не назван, пример ответа с ERROR стоит под статусом 200» (как в «Логика работы метода, п. 5») или «HTTP 400 с ответом о неверных параметрах» (как в «Статус 400»)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму"}; B — HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; C — HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний…

#### <a id="d-04"></a>🔴 D-04. Ф-4 снимает ограничение одного push в месяц из Ф-3

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Строка 39 ограничивает push одним за календарный месяц, строка 40 говорит, что следующее достижение порога вызывает push независимо от истории настройки. Число push за месяц различается.  
**Сценарий.** Порог 50 000, расходы 60 000, push отправлен. Порог повышен до 70 000. Покупка 10 000: по строке 39 второго push нет, по строке 40 push уходит.  
**Последствия.** Разный число push за месяц у разработки и тестирования; клиент получает спорные уведомления.  
**Как исправить.** Явно указать, что Ф-4 не отменяет лимит одного push за месяц, либо разрешить второй push.

*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-21](#r-21 "Возврат прежнего состояния и ERROR при отклонении суммы"), [R-32](#r-32 "Порог в тенге при успешном сохранении"), [R-33](#r-33 "Признак включения в ответе, «0» или «1»") · нашли: архитектор*

#### <a id="d-24"></a>🟠 D-24. Типы amount и enabled различаются в запросе и ответе

- Часть B › Query-параметры, строки 143 и 144: «amount | integer» · «enabled | integer»
- Часть B › Ответ, строки 156 и 157: «amount | string» · «enabled | string»

**Проблема.** Строки 143 и 144 задают amount и enabled как integer, строки 156 и 157 — как string для тех же полей.  
**Сценарий.** Клиент отправляет amount 50000 как integer и получает «50000» как string; строгий разбор ответа или сравнение значений падает.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»  
*Существенный, блокирует разработку · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-27](#r-27 "Порог в тенге, обязательный, целый"), [R-32](#r-32 "Порог в тенге при успешном сохранении"), [R-28](#r-28 "Признак включения 0 или 1, обязательный"), [R-33](#r-33 "Признак включения в ответе, «0» или «1»") · нашли: правило «контракт API»*

#### <a id="d-25"></a>🟠 D-25. Перечень кодов ответа: 201 не описан, список открыт «и далее»

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»

**Проблема.** Строка 151 называет успешным 201, в перечне статусов (строки 162–176) кода 201 нет. строка 165 подписывает 200 как «Created». строка 151 «и далее» делает перечень неполным.  
**Сценарий.** Сервер возвращает 201 при сохранении: клиент не знает, это успех или ошибка. Код вне перечня попадает или не попадает в «и далее» по выбору реализации.  
**Последствия.** Клиент обработает ответ как неизвестную ошибку; спор при приёмке о правильном коде; автотесты контракта нельзя написать однозначно.  
**Как исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»  
*Существенный, блокирует разработку · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-30](#r-30 "Коды 200 и 201 успешны, остальные неуспешны"), [R-35](#r-35 "Успешное выполнение метода, код 200") · нашли: правило «контракт API», правило «размытые слова»*

#### <a id="d-26"></a>🟠 D-26. Ответы об ошибке не содержат поле result из таблицы ответа

- Часть B › Ответ, строка 155: «result | string | OK / ERROR»
- Часть B › 400. Unsuccessful — Bad request, строка 180: «{"message":"Некорректный запрос"}»
- Часть B › 401. Unsuccessful — Unauthorized, строка 185: «{"message":"Требуется вход"}»
- Часть B › 403. Unsuccessful — Forbidden, строка 192: «{"message":"Карта не найдена"}»

**Проблема.** Строка 155 задаёт result как OK / ERROR без условия. Примеры ошибок строк 180 и 185 содержат только message, поля result в них нет.  
**Сценарий.** Клиент читает result в ответе 400 и получает пустое значение; сообщение об ошибке показывается как неизвестная ошибка.  
**Последствия.** Разные реализации обработки ошибок у клиента и сервера; тесты контракта на ошибки не написать.  
**Как исправить.** Либо добавить result во все тела ошибок, либо указать в таблице ответа, при каких кодах поле result присутствует.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «result | <уточнить: тип> | Обязательно во всех ответах | Признак результата»  
*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-31](#r-31 "Исход сохранения: OK или ERROR"), [R-40](#r-40 "Чужая или отсутствующая карта, код 404 и тело") · нашли: правило «контракт API»*

- **A** Не более одного push за календарный месяц в любом случае; если при сохранении нового порога накопленная сумма уже равна новому порогу или выше, push не отправляется до следующего календарного месяца
- **B** Не более одного push за месяц на каждый порог: после изменения порога push отправляется при переходе через новый порог, но не более двух push за месяц; при сохранении порога, уже пройденного накопленной суммой, push отправляется сразу

Зачем: Одна и та же смена порога даст у одной команды второй push, у другой — ни одного, и тест на сценарий «снизил порог» не имеет однозначного ожидаемого результата.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
