### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Месяц покупки 31 января: Ф-2 и критерий приёмки №2 расходятся

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Ф-2 относит покупку к месяцу совершения («Месяц определяется по дате совершения покупки в Алматы», строка 38). Критерий приёмки №2 ожидает рост февральского счётчика после проведения 1 февраля («Февральский счётчик вырос на 4 000 ₸», строка 64).  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 по Алматы. По Ф-2: январский счётчик +4 000 ₸, февральский без изменений. По строке 64: февральский счётчик +4 000 ₸.  
**Последствия.** Разработчик и тестировщик получат разные значения счётчиков на стыке месяца, и приёмочный тест на границе месяца не пройдёт у одной из сторон.  
**Как исправить.** Назвать одно событие, по дате которого покупка относится к месяцу, и привести к нему Ф-2 и критерий приёмки.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц определяется по дате <уточнить: совершения или проведения> покупки в Алматы.»  
**Вопрос владельцу.** По дате совершения или по дате проведения покупки относить её к календарному месяцу в Алматы? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — по дате проведения покупки в Алматы; B — по дате совершения покупки в Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Учёт расходов по дате в Алматы, с возвратами"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Ф-3 и Ф-4 расходятся о втором push в месяце при повышении порога

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 разрешает «максимум один такой push за календарный месяц» (строка 39). Ф-4 требует push при достижении «независимо от истории предыдущей настройки» (строка 40). Для одного входа число push противоречит.  
**Сценарий.** Порог 50 000 ₸, сумма 50 000 ₸, push отправлен. Порог повышен до 80 000 ₸, покупка доводит сумму до 80 000 ₸. По Ф-3 второго push быть не должно, по Ф-4 push обязан уйти.  
**Последствия.** Разное число push по одному сценарию; тест и приёмка получат разный результат.  
**Как исправить.** Зафиксировать: максимум один push за месяц, включая push после смены порога.  
**Вопрос владельцу.** Что верно: «второго push в месяце быть не должно» (как в Ф-3) или «push обязан уйти независимо от уже отправленного push» (как в Ф-4)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — не более одного push за календарный месяц на карту, включая случаи после смены порога; B — push отправляется при каждом переходе через порог независимо от числа push в месяце; C — не более одного push за календарный месяц  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Push при переходе через порог, не более одного в месяц"), [R-08 / Ф-4](#r-08 "Накопленная сумма сохраняется при смене порога") · нашли: проверка набора*

#### <a id="d-03"></a>🔴 D-03. Сумма 999 ₸: отказ описан и кодом 400, и кодом 200 с ERROR

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Для суммы вне диапазона строки 163 задаёт 400, а строка 121 и пример строки 171 — 200 с result ERROR. строка 151 считает ответ 200 успешным, поэтому один вход получает и успех, и отказ.  
**Сценарий.** amount=999, enabled=1: по строке 151 приложение видит успех (200), по строке 163 ожидается 400, по строке 171 тело ERROR. Клиент может увидеть «Сохранено» при отклонённом пороге.  
**Последствия.** Отказ по сумме может быть принят клиентом и тестом как успешный ответ.  
**Как исправить.** Зафиксировать один HTTP-код и исход для отклонённой суммы.  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «При amount вне 1 000–1 000 000 или enabled не 0/1 метод возвращает HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму"}, настройка не меняется.»  
**Вопрос владельцу.** Что верно: «возвращается результат ERROR и прежнее состояние» (как в «Логика работы метода, п. 5») или «ответ с кодом 200 или 201 считается успешным; код 400 — неуспешным» (как в «описание API, строка 151»)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — неверная сумма даёт HTTP 400 с телом {"message":"Проверьте сумму"}; B — неверная сумма даёт HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; C — неверная сумма даёт HTTP 400 с телом, где поле result равно ERROR и есть message  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-21](#r-21 "Возврат прежнего состояния при ошибке суммы"), [R-30](#r-30 "Правило успешного и неуспешного ответа"), [R-36](#r-36 "Код 400 — параметры запроса заполнены неверно"), [R-31](#r-31 "Исход сохранения OK или ERROR") · нашли: проверка набора, тестировщик, архитектор, правило «контракт API»*

#### <a id="d-04"></a>🟠 D-04. Не определено, какой этап покупки запускает push: авторизация или клиринг

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»

**Проблема.** Слова «проведённые» (строка 38) и «проведена» (строка 43) не указывают этап: одобренная авторизация или клиринг через 1–3 дня. Цель требует уведомления «в момент покупки» (строка 23).  
**Сценарий.** Покупка 10 января на 20 000 ₸ при пороге 15 000 ₸: авторизация 10 января, клиринг 12 января. Push уходит 10-го или 12-го. Покупка 31 января 23:58 относится к январю или к февралю в зависимости от этапа.  
**Последствия.** Клиент получает уведомление на 1–3 дня позже обещанного или в другом месяце; банк и разработка выбирают этап наугад, а при приёмке невозможно доказать соответствие цели.  
**Как исправить.** Записать в Ф-2 и в sequence-диаграмме конкретное событие процессинга (авторизация или клиринг) и обработку отмены авторизации до него.

**<a id="q-01"></a>Q-01** Месяц отнесения покупки · ⛔ блокирует · кому: Владелец продукта · к [D-01](#d-01)  
К какому календарному месяцу в Алматы относить покупку: по дате её совершения или по дате проведения? Правило Ф-2 говорит про дату совершения, а приёмочная строка про покупку 31 января в 23:58, проведённую 1 февраля в 00:03, требует, чтобы она попала в февральский счётчик.

**<a id="q-02"></a>Q-02** Повторный push и смена порога · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02), [D-12](#d-12)  
Может ли в одном календарном месяце уйти второй push после смены порога? Ф-3 говорит максимум один push в месяц, Ф-4 говорит, что push обязан уйти при следующем достижении независимо от истории. Также не описано, что делать при понижении порога до значения, которое уже не выше накопленной суммы.  
Где: Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц.»; Ф-4, строка 40: «Если она ниже нового порога, следующее достижение вызывает push»

- **A** Не более одного push за календарный месяц на карту, включая случаи после смены порога; при понижении порога до значения, не выше накопленной суммы, push не отправляется
- **B** Push отправляется при каждом переходе через порог независимо от числа push в месяце; при понижении порога до значения не выше накопленной суммы push отправляется сразу
- **C** Не более одного push за календарный месяц; при понижении порога до значения не выше накопленной суммы push отправляется сразу, если за месяц push ещё не уходил

Зачем: После смены порога две команды по-разному решат, отправлять ли второй push в месяце и что делать при понижении порога, и тест этого сценария даст разные ожидаемые результаты.

**<a id="q-03"></a>Q-03** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-03](#d-03), [D-18](#d-18)  
Что получает приложение, если сумма порога вне диапазона 1 000–1 000 000 ₸: HTTP 400 с сообщением об ошибке или HTTP 200 с результатом ERROR? Сейчас шаг логики и пример ответа говорят про 200 с ERROR, а перечень кодов и правило успешного ответа относят неверные параметры к 400.  
Где: Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; Часть B › Ответ, строка 151: «Если результат 400, 401 и далее — неуспешный.»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно.»

- **A** Неверная сумма даёт HTTP 400 с телом {"message":"Проверьте сумму"}; код 200 используется только для успешного сохранения, шаг 5 и пример с result ERROR удаляются
- **B** Неверная сумма даёт HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму"}; код 400 только для синтаксически неверного запроса (нет обязательного параметра или он не числовой)
- **C** Неверная сумма даёт HTTP 400 с телом, где поле result равно ERROR и есть message; поле result присутствует во всех ответах с ошибкой

Зачем: Без выбора два места дают разный исход для одного входа: успех или отказ, и тесты на код ответа нельзя написать однозначно.

**<a id="q-04"></a>Q-04** Событие, запускающее учёт покупки · можно ответить позже · кому: Владелец продукта · к [D-04](#d-04), [D-24](#d-24)  
Какое событие считать покупкой для учёта расходов и отсчёта срока push: одобрение авторизации в момент оплаты или проведение операции после клиринга (через 1–3 дня)? Цель требует уведомления в момент покупки, а в документе слово «проведённые» не привязано к этапу.  
Где: Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»; Ф-2, строка 38: «В расходы входят проведённые покупки.»; Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

- **A** Событие — одобрение авторизации; расходы и срок в одну минуту отсчитываются от него
- **B** Событие — проведение операции после клиринга; срок в одну минуту отсчитывается от получения этого события, уведомление в момент оплаты не обещается
- **C** Событие — одобрение авторизации для учёта расходов; push-уведомление отправляется, когда клиринг подтверждает покупку, срок в одну минуту отсчитывается от клиринга

Зачем: Без выбора этапа нельзя определить, какая сумма попадает в счётчик в момент покупки и когда начинается отсчёт минуты, поэтому тесты задержки и состава расходов не пишутся.

**<a id="q-05"></a>Q-05** Чтение порога и суммы за месяц · можно ответить позже · кому: Архитектор · к [D-05](#d-05)

Где: Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»; Часть B › Общие параметры, строка 103: «Сохранение порога. - **B** Сумму за месяц и порог возвращать в ответе метода сохранения при успешном вызове; отдельного чтения нет, экран после открытия не загружает текущие значения

Зачем: Экран не может показать текущий порог и сумму, а приложение не знает, какой запрос их получает, поэтому тесты экрана и раздел интеграции не реализуемы.

- **B** Ключ — идентификатор операции; повтор не меняет накопленную сумму, но при неотправленном push повторно пытается отправку один раз

- **B** Для чужой карты возвращать 403 с телом {"message":"Доступ запрещён"}; 404 только для реально отсутствующей карты

Зачем: Разный код раскрывает или скрывает факт существования чужой карты, и тесты безопасности и клиентского сообщения дадут разный результат.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
