- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»

- Часть B › Общие параметры, строка 108: «Request URL | Dev: /alerts/saveLimit . Prod: —»

#### <a id="d-02"></a>🔴 D-02. Не определено, какое событие процессинга (авторизация или проведение) запускает правило

**Требования:** [R-01](#r-01 "Уведомлять клиента о достижении личного бюджета при покупке"), [R-04](#r-04 "Процесс: покупка, пересчёт, проверка порога, push"), [R-06 / Ф-2](#r-06 "Правила определения месяца и состава расходов, возвраты"), [R-09](#r-09 "Последовательность взаимодействия процессинга, расходов, настроек и push"), [R-10](#r-10 "Передача push на отправку в течение минуты") · **Критерий:** Однозначность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · **Вид:** неоднозначность · **Блокирует:** разработку и тестирование · **Нашли:** риски, проверка набора

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Часть A › Функциональные требования, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** «Проведена покупка» не различает авторизацию и финансовое проведение; из-за этого цель «в момент покупки» не согласуется с учётом только проведённых покупок.  
**Сценарий.** Покупка 1 500 ₸ одобрена 10-го, проведена 12-го: по одному толкованию push 10-го, по другому 12-го.  
**Последствия.** Нельзя выбрать событие для приёма из процессинга; обещание «в момент покупки» и «в течение минуты» невыполнимо при учёте только проведённых покупок; при отмене авторизации возможно ложное уведомление, при проведении иной суммы — неверный счётчик.  
**Что исправить.** Зафиксировать событие процессинга (авторизация или проведение), его источник и правило для отмены авторизации и расхождения сумм; привести цель и срок реакции в соответствие.  
**Было → стало.** Строка 38: «В расходы входят проведённые покупки» → «Расходы увеличиваются при получении от процессинга события <уточнить: авторизация или проведение (клиринг)> на сумму <уточнить: авторизованную или проведённую>; отмена авторизации уменьшает расходы на ту же сумму.»  
**Вопрос владельцу.** Какое событие процессинга считается покупкой для уведомления: одобрение или проведение, и что делать при отмене одобрения? → [Q-02](#q-02)

Где: строка 38 «Месяц определяется по дате совершения покупки в Алматы.»; строка 64 «Февральский счётчик вырос на 4 000 ₸»; строка 39 «На карту приходится максимум один такой push за календарный месяц.»

- **A** Месяц определяется по дате и времени совершения покупки в часовом поясе Алматы; покупка 31.01 23:58 относится к январю, февральский счётчик не растёт; лимит push считается по тому же месяцу; критерий приёмки исправляется.
- **B** Месяц определяется по дате проведения в часовом поясе Алматы; покупка 31.01 23:58, проведённая 01.02 00:03, относится к февралю; лимит push считается по месяцу проведения; формулировка о дате совершения заменяется.

Зачем: Для одного входа расходятся правило и критерий приёмки: растёт январь или февраль. Тест на границе месяцев и признак отправки привязать нельзя.

**<a id="q-05"></a>Q-05** Код и тело ответа при недопустимой сумме · ⛔ блокирует · кому: Архитектор · к [D-05](#d-05), [D-19](#d-19), [D-21](#d-21)  
Какой HTTP-код и какое тело ответа возвращает метод сохранения порога, если сумма вне диапазона 1 000–1 000 000 ₸, и возвращаются ли при этом прежние значения порога и признака включения?  
Где: строка 121 «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; строка 151 «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.»; строка 171 «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** Код 400, тело {"result":"ERROR","message":"Проверьте сумму"}; настройка не меняется; прежние amount и enabled в ответе не возвращаются; успешным считается только код 200.
- **B** Код 400, тело с result ERROR, message и прежними amount и enabled; настройка не меняется; успешным считается только код 200.
- **C** Код 200 с телом result ERROR и message; настройка не меняется; код 400 остаётся только для неверного формата параметров.

Зачем: При amount=500 одна команда вернёт 200 с ERROR, другая 400. Клиент и тесты по-разному определят успех.

**<a id="q-06"></a>Q-06** Push при включении порога с уже достигнутой суммой · не блокирует · кому: Владелец продукта · к [D-10](#d-10)  
Нужно ли отправлять push, если клиент включил или снизил порог, а расходы месяца уже не ниже нового порога?  
Где: строка 37 «По умолчанию уведомление выключено.»; строка 39 «Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент…»

- **A** Push не отправляется: только при переходе от суммы ниже порога к сумме не ниже порога при новой покупке; если расходы уже не ниже порога, push не будет до следующего месяца.
- **B** Push отправляется сразу при сохранении настройки, если расходы не ниже порога и push в этом месяце не отправлялся.
- **C** Push отправляется при следующей покупке после включения, если расходы на тот момент не ниже порога и push в месяце не отправлялся.

Зачем: Расходы 60 000 ₸, клиент включает порог 50 000 ₸: push сразу, при следующей покупке или никогда — тест на этот вход неоднозначен.

**<a id="q-07"></a>Q-07** Кто вправе задавать порог по карте · не блокирует · кому: Владелец продукта · к [D-11](#d-11)  
Вправе ли держатель дополнительной карты задавать порог по своей карте, или только владелец счёта? Какая проверка принадлежности карты выполняется в методе?  
Где: строка 37 «Держатель активной карты KZT задаёт целый порог»; строка 105 «Bearer, сессия владельца карты»; строка 118 «2. Проверить принадлежность карты клиенту»

- **A** Порог задаёт только держатель этой карты; метод проверяет, что карта выпущена на клиента из сессии; владелец счёта не может менять порог чужой дополнительной карты.
- **B** Порог по любой карте счёта задаёт только владелец счёта; держатель дополнительной карты получает отказ.
- **C** Порог вправе задавать и держатель карты, и владелец счёта; метод проверяет, что клиент из сессии — один из них.

Зачем: Для дополнительной карты проверка владельца откажет, а проверка держателя пропустит. Реализация и тесты прав доступа разойдутся.

**<a id="q-08"></a>Q-08** Состав операций, входящих в расходы · не блокирует · кому: Владелец продукта · к [D-12](#d-12)  
Какие типы операций входят в расходы месяца кроме покупок: пополнение электронных кошельков, комиссии банка, покупки в иной валюте?  
Где: строка 38 «Переводы и снятие наличных исключаются.»; строка 37 «Держатель активной карты KZT»

- **A** В расходы входят только покупки у торговцев в тенге; пополнение кошельков, комиссии банка, переводы, снятие наличных и операции в иной валюте исключаются.
- **B** В расходы входят покупки в тенге и в иной валюте (пересчёт в тенге по курсу проведения); пополнение кошельков, комиссии, переводы и снятие наличных исключаются.
- **C** В расходы входят покупки (в том числе в иной валюте) и пополнение кошельков; комиссии, переводы и снятие наличных исключаются.

Зачем: Пополнение кошелька на 20 000 ₸ при расходах 30 000 ₸ и пороге 50 000 ₸: одна команда отправит push, другая нет.

**<a id="q-09"></a>Q-09** Какая сумма указывается в push · не блокирует · кому: Владелец продукта · к [D-15](#d-15)  
Какая величина передаётся в push вместе с последними четырьмя цифрами карты: расходы месяца, сумма последней покупки или порог?  
Где: строка 43 «передать последние четыре цифры карты и сумму при достижении порога»

- **A** Расходы месяца на момент достижения порога, целое число тенге, формат «50 000 ₸».
- **B** Порог, при достижении которого отправлен push, целое число тенге, формат «50 000 ₸».
- **C** Сумма покупки, вызвавшей достижение порога, в тенге с точностью до тиына, формат «1 500,00 ₸».

Зачем: Расходы 48 500, покупка 1 500, порог 50 000: разработчики передадут разные числа, тест на текст push не напишешь.

**<a id="q-10"></a>Q-10** Ключ распознавания повторного события · не блокирует · кому: Архитектор · к [D-16](#d-16)  
По какому полю распознаётся повторная доставка события процессинга и как отличить повтор от возврата с тем же идентификатором операции?  
Где: строка 52 «Повторная доставка одного события процессинга сохраняет исходный итог.»; строка 49 «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах…»

- **A** Повтор определяется по паре «идентификатор операции» и тип операции (покупка или возврат); дубль игнорируется без изменения расходов и без нового push.
- **B** Повтор определяется по идентификатору события процессинга, который хранится вместе с операцией; дубль игнорируется, возврат имеет собственный идентификатор.
- **C** Повтор определяется по сочетанию идентификатора карты, идентификатора операции и суммы; при совпадении события игнорируются, при расхождении суммы фиксируется ошибка.

Зачем: Покупка 4 000 ₸ приходит дважды: расходы вырастут на 8 000 ₸ либо повтор будет отброшен — тест идемпотентности без ключа не написать.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
