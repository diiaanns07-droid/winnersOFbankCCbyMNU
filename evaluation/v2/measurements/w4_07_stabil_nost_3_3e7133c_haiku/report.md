### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Месяц покупки: Ф-2 и критерий приёмки дают разные даты

- Часть A › Цели, строка 23: «в момент покупки»
- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу по дате совершения, критерий приёмки (строка 64) по дате проведения. Цель (строка 23) обещает реакцию «в момент покупки», но учёт идёт по проведению.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸ проведена 1 февраля в 00:03. По Ф-2 растёт январский счётчик, по критерию приёмки, строка 2, растёт февральский на 4 000 ₸.  
**Последствия.** Разработчик выберет одну дату, тестировщик проверит другую, и приёмка по месяцу упадёт; клиент увидит неверный итог за месяц и неверный срок push.  
**Как исправить.** Заменить в Ф-2 событие на одно явно названное и привести критерий приёмки к нему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц определяется по дате <уточнить: совершения или проведения> покупки в Алматы.»  
**Вопрос владельцу.** По какой дате относить покупку к месяцу: дате совершения или дате проведения покупки? Если проведения, то цель «в момент покупки» нужно переформулировать. → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — месяц определяется по дате совершения покупки в Алматы; B — месяц определяется по дате проведения покупки в Алматы; C — месяц определяется по дате совершения покупки в Алматы, а покупки, проведённые позже…  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-06 / Ф-2](#r-06 "Определение месяца и состав учитываемых расходов"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Чтение порога и суммы обещано, но операции чтения нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строка 103: «Description | Сохранение порога. Функциональные требования: чтение порога»
- Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения»

**Проблема.** Строки 52 и 103 обещают чтение порога, экран (строка 29) показывает порог и сумму за месяц, но в API описан только метод `saveLimit` (строки 104–108), который заменяет настройку (строка 120). Операции чтения нет, сумма в ответе не возвращается.  
**Сценарий.** Клиент открывает экран у карты с порогом 50 000 ₸ после перезапуска: текущий порог и сумму за месяц приложению не из чего получить; единственный вызов перезаписывает настройку.  
**Последствия.** Экран настроек не может показать сохранённый порог без побочной записи, интегратор и тестировщик не имеют контракта чтения.  
**Как исправить.** Добавить в дочерний документ операцию чтения порога с методом, путём, параметром `cardId` и телом ответа с полями result, amount, enabled, и указать её в разделе интеграции.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «<уточнить: путь и метод чтения порога>?cardId=<строка 1–64>: 200, {"result":"OK","amount":"<порог в тенге>","enabled":"0 или 1"}; 404, {"message":"Карта не найдена"}»  
**Вопрос владельцу.** Нужен ли отдельный метод чтения или чтение входит в другой существующий метод? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — отдельный метод чтения по образцу описанного метода с параметрами карты и ответом с…; B — один метод с режимом чтения и записи; C — отдельный метод чтения только порога и признака

#### <a id="d-03"></a>🔴 D-03. Ф-3 и Ф-4 расходятся: второй push в месяц при повышении порога

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 (строка 39) задаёт максимум один push за календарный месяц, Ф-4 (строка 40) «независимо от истории предыдущей настройки» вызывает push при достижении нового порога. Исключение из Ф-3 не объявлено; фраза читается двояко.  
**Сценарий.** Push в январе при 50 000 ₸; порог поднят до 100 000 ₸; накоплено 60 000 ₸; покупка доводит до 100 000 ₸. По Ф-3 второго push нет, по Ф-4 push уходит: два push за месяц.  
**Последствия.** Клиент получит два push за месяц; приёмка и реализация решат по-разному.  
**Как исправить.** В Ф-4 сохранить ограничение одного push в календарный месяц.  
**Предлагаемая формулировка.** «Если накопленная сумма ниже нового порога, следующее достижение вызывает push, если в текущем календарном месяце push ещё не отправлялся; иначе push не отправляется.»  
**Вопрос владельцу.** Что верно: «второй push в январе не отправляется» (как в Ф-3) или «push отправляется при достижении нового порога» (как в Ф-4)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — не более одного push за календарный месяц всегда; B — второй push в месяц разрешён только при повышении порога выше накопленной суммы; C — push отправляется при каждом переходе накопленной суммы к новому порогу без ограничения…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Push при пересечении порога, один раз в месяц"), [R-08 / Ф-4](#r-08 "Сохранение накопленной суммы при смене порога") · нашли: проверка набора, аналитик*

#### <a id="d-04"></a>🔴 D-04. Неверная сумма: успех 200 с ERROR или отказ 400

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Шаг 5 (строка 121) и пример (строка 171) дают ответ ERROR с кодом 200, который строк 151 и 165 считают успешным. строка 163 для неверных параметров задаёт код 400. Исход одного входа описан двумя способами.  
**Сценарий.** Запрос `saveLimit` с amount=999 (ниже 1 000): по строке 121, строки 171 и 151 — успех с кодом 200 и result=ERROR; по строке 163 — отказ с кодом 400. Клиент, смотрящий на код, покажет сохранение как успешное.  
**Последствия.** Клиент покажет успешное сохранение при отказе сервера, либо реализация и тесты разойдутся по коду ответа.

**Вопрос владельцу.** Может ли держатель дополнительной карты, не являющийся владельцем счёта, задавать порог?

#### <a id="d-14"></a>🟠 D-14. Порог понижен ниже накопленной суммы: ветка не описана

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «Если она ниже нового порога, следующее достижение вызывает push»

#### <a id="d-15"></a>🟠 D-15. Сумма в push: покупка или накопленная сумма не названа

#### <a id="d-16"></a>🟠 D-16. Тиыны и тенге без правила пересчёта и округления

#### <a id="d-17"></a>🟠 D-17. Повтор события процессинга: ключ дедупликации не назван

**<a id="q-01"></a>Q-01** Момент отнесения покупки к месяцу · ⛔ блокирует · кому: Владелец продукта · к [D-01](#d-01)

- **A** Месяц определяется по дате совершения покупки в Алматы; пример с проведением 1 февраля относит покупку к январю, цель «в момент покупки» сохраняется

- **C** Месяц определяется по дате совершения покупки в Алматы, а покупки, проведённые позже совершения, относятся к месяцу проведения

- **B** Один метод с режимом чтения и записи; сервис расходов получает порог из общего хранилища настроек без вызова метода приложения

Зачем: Разработка и тест на смену порога дадут разный итог: одна команда отправит второй push, другая нет, и приёмка не сможет подтвердить ни один вариант.

**<a id="q-04"></a>Q-04** Код ответа при недопустимой сумме · ⛔ блокирует · кому: Архитектор · к [D-04](#d-04)  
Что возвращает метод при сумме вне диапазона 1 000–1 000 000: HTTP 400 или HTTP 200 с телом result=ERROR? Логика и пример ответа описывают один случай по-разному, а ветка отказа не имеет полного тела ответа.  
Где: Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»; Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** Код 400 с телом result=ERROR и message; статус 200 в этом случае не используется
- **B** Код 200 с телом result=ERROR и message; код 400 остаётся только для неверного формата запроса
- **C** Код 400 для любого отказа по сумме, тело {"result":"ERROR","message":"Проверьте сумму"} без поля amount

Зачем: Тестировщик и клиент приложения по-разному обработают один и тот же отказ: один будет искать статус 400, другой разбирать тело при 200.

**<a id="q-05"></a>Q-05** Код ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-05](#d-05)  
Какой код возвращается, если карта принадлежит другому клиенту: 403 или 404? Описание статуса 403 говорит про запрещённый доступ, а примечание к 403 отдаёт 404 для чужой карты.  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты»

- **A** 404 для чужой и отсутствующей карты одинаково, с текстом «Карта не найдена»; статус 403 для этого метода не используется
- **B** 403 для чужой карты и 404 только для отсутствующей карты
- **C** 403 для чужой карты с текстом «Доступ запрещён»; для отсутствующей карты 404

Зачем: Без решения нельзя написать тест на чужую карту, а код 403 против 404 раскрывает клиенту, существует ли чужая карта.

**<a id="q-06"></a>Q-06** Учёт покупок при выключенном уведомлении и отменах · можно ответить позже · кому: Владелец продукта · к [D-10](#d-10), [D-06](#d-06), [D-27](#d-27)  
Копятся ли покупки месяца, пока уведомление выключено, и что означает включение и выключение для накопленной суммы? Документ не говорит, учитываются ли покупки до первого включения и что делает выключение, а также какие операции, кроме переводов и снятия наличных, исключаются.  
Где: Ф-1, строка 37: «По умолчанию уведомление выключено»; Часть B › Query-параметры, строка 144: «Признак включения»; Ф-2, строка 38: «Переводы и снятие наличных исключаются»

- **A** Покупки копятся всегда, независимо от признака; включение даёт push при достижении порога по накопленной сумме месяца
- **B** Покупки копятся только при включённом уведомлении; включение начинает учёт с нуля в текущем месяце
- **C** Покупки копятся всегда; включение даёт push при достижении порога, выключение прекращает отправку push, но не сбрасывает сумму

Зачем: Для одного и того же набора покупок клиент с включённым уведомлением может получить push или не получить его, и тест на включение и выключение нельзя написать.

**<a id="q-07"></a>Q-07** Метод изменения настройки и тип запроса · можно ответить позже · кому: Архитектор · к [D-07](#d-07)  
Каким типом запроса объявляется метод сохранения порога, который меняет настройку? В документе метод с именем сохранения объявлен как GET, а параметры карты, порога и признака передаются в строке запроса.  
Где: Часть B › Общие параметры, строки 104, 108 и 109: «REST type | GET» · «Dev: /alerts/saveLimit» · «curl -G»

- **A** Метод сохранения объявляется как POST, параметры `cardId`, amount и enabled передаются в теле в формате JSON, согласно Content-Type
- **B** Метод сохранения объявляется как POST, параметры передаются в строке запроса, тело не используется
- **C** Метод сохранения остаётся GET, но меняется его название на метод чтения, а сохранение выполняется отдельным POST-методом

Зачем: GET-запрос кэшируется и повторяется прокси, а параметры оседают в журналах; тест на повтор и на журналирование не может быть написан без решения.

**<a id="q-08"></a>Q-08** Перевод тиынов в тенге при сравнении с порогом · можно ответить позже · кому: Владелец продукта · к [D-16](#d-16)  
Как сравнивать накопленную сумму покупок, которая хранится в тиынах, с порогом, который задаётся в тенге? Документ не говорит, как переводить тиыны в тенге при сравнении и округлении.  
Где: Часть A › Требования к данным, строка 49: «сумму покупки в тиынах, признак отправки и порог в тенге»; критерий приёмки №1, строка 63: «Расходы 48 500 ₸, порог 50 000 ₸»

- **A** Накопленная сумма в тиынах делится на 100 с отбрасыванием дробной части, сравнивается с порогом в тенге; целые тенге
- **B** Накопленная сумма в тиынах переводится в тенге с округлением до ближайшего целого тенге по правилу «от 0,5 вверх»
- **C** Порог переводится в тиыны (умножением на 100), сравнение и хранение накопленной суммы выполняются только в тиынах

Зачем: При накоплении копеек разные реализации дадут разный момент push на границе порога, например на сумме 49 999 тиынов.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
