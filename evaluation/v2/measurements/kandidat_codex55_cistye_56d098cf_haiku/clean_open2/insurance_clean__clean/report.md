### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Возврат премии при погашении и отказе в 14 дней не определён

- Ф-4, строка 40: «премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней»
- Ф-5, строка 41: «При полном досрочном погашении кредита страхование прекращается, клиенту возвращается часть премии за полные неиспользованные…»
- Часть B › Методы расчёта и отказа, строка 221: «409 — прошло больше 14 дней или отказ уже оформлен»

**Проблема.** Ф-4 (строка 40) велит вернуть полную премию при отказе в течение 14 дней, Ф-5 (строка 41) — возврат за неиспользованные месяцы при полном погашении. Для одного кредита оба могут сработать; документ не говорит, возвращается ли премия дважды. строка 221 не проверяет погашение.  
**Сценарий.** Кредит 1 000 000 ₸ на 24 мес, премия 36 000 ₸, выдан 1 марта. 5 марта погашен полностью: по Ф-5 возврат 36 000 ₸. 8 марта отказ: по Ф-4 ещё 36 000 ₸. Итог 36 000 или 72 000 ₸ — документ не выбирает.  
**Последствия.** Банк может выплатить премию дважды, разработка и тестирование выберут исход наугад, при приёмке возникнет спор о сумме возврата клиенту.  
**Как исправить.** Добавить в Ф-4 и Ф-5 правило приоритета: при полном досрочном погашении отказ от страхования не даёт второго возврата, либо отказ после погашения недоступен.  
**Предлагаемая формулировка.** «Ф-4 (дополнение): если кредит полностью погашен до отказа, премия возвращается однократно по Ф-5, а отказ по Ф-4 не выполняется и возвращает 0 ₸ дополнительно.»  
**Вопрос владельцу.** Что должно происходить при отказе от страхования после полного досрочного погашения: однократный возврат по Ф-5, или возврат по Ф-4 полностью, или отказ недоступен? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — после полного досрочного погашения отказ недоступен; B — отказ в течение 14 дней возвращает полную премию независимо от погашения; C — после полного досрочного погашения отказ возможен в течение 14 дней, но возвращается…  
*Критичный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-08 / Ф-4](#r-08 "Отказ от страхования в 14 дней, возврат премии"), [R-09 / Ф-5](#r-09 "Досрочное погашение: прекращение и возврат премии"), [R-49](#r-49 "Отказ от страхования в течение 14 дней") · нашли: риски, проверка набора*

#### <a id="d-02"></a>🟠 D-02. Повторный вызов для подписанной заявки: 200 или 409

- Особые правила, п. 1, строка 128: «Повторный вызов с теми же суммой и сроком возвращает действующие условия страхования»
- Часть B › Статусы, строка 169: «409. Ответ в случае, если заявка уже подписана»

**Проблема.** Особое правило 1 (строка 128) велит возвращать действующие условия при повторном вызове с теми же суммой и сроком, без ограничения по статусу заявки. Статус 409 (строка 169) и шаг 2 (строка 121) требуют отказа для подписанной заявки.  
**Сценарий.** Заявка подписана, клиент повторно вызывает подключение с суммой 1 000 000 ₸ и сроком 24 мес: по строке 128 ответ успешный с условиями, по строке 169 — 409 «Заявка уже подписана».  
**Последствия.** Разработчики по-разному обработают повтор, тесты на идемпотентность разойдутся.  
**Как исправить.** Указать, что возвращает повторный вызов для каждого состояния заявки: до подписания, после подписания и после отказа.  
**Вопрос владельцу.** Что возвращает повторный вызов с теми же суммой и сроком после подписания заявки: действующие условия (200) или ошибку 409?  
*Существенный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-21](#r-21 "Проверка принадлежности заявки и статуса подписания"), [R-26](#r-26 "Повторный вызов возвращает действующие условия"), [R-43](#r-43 "Код 409 — заявка уже подписана") · нашли: аналитик*

#### <a id="d-03"></a>🟠 D-03. Нижний возрастной порог 18 лет не проверяется логикой метода

- Ф-6, строка 42: «Страхование доступно клиенту от 18 лет»
- Логика работы метода, п. 4, строка 123: «Проверить возраст клиента на дату окончания кредита»

**Проблема.** Ф-6 (строка 42) задаёт нижнюю границу 18 лет, но шаг 4 (строка 123) проверяет только верхнюю границу 65 лет. Код ответа для клиента младше 18 лет не задан, дата, на которую считается 18 лет, не названа.

**Последствия.** Разработчик реализует только проверку 65 лет, тестировщик ожидает отказ по Ф-6, и банк выдаёт страховку лицу, которому она запрещена.  
**Как исправить.** Добавить в пункт 4 проверку минимального возраста 18 лет на согласованную дату и единый ответ 422.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 123: «Проверить возраст клиента на дату окончания кредита» → «4. #### <a id="d-04"></a>🟠 D-04. Архитектура расходится с sequence и схемой метода по вызову страхования

- Часть A › Архитектура решения, строка 25: «Мобильное приложение → API кредитов → кредитный конвейер»
- Часть A › Sequence Diagram, строка 45: «Приложение → API кредитов: подключить страхование к заявке»
- Часть B › Схема, строка 134: «Приложение → LoanInsuranceController → сервис страхования»

**Проблема.** Строка 25 задаёт путь API кредитов → кредитный конвейер → сервис страхования, без прямого вызова сервиса страхования из API. строки 45 и 134 дают вызов из API (или контроллера) в сервис страхования для расчёта и проверки клиента.  
**Сценарий.** Разработчик по архитектуре вызывает сервис страхования только из конвейера при выдаче; расчёт премии и предварительная проверка из API по строкам 45 и 134 не реализуются.  
**Последствия.** Расхождение архитектуры и реализации; вызов из API не согласован с архитектурным ревью.  
**Как исправить.** Добавить в архитектуру связь API кредитов → сервис страхования.  
**Было → стало.** Строка 25: «Мобильное приложение → API кредитов → кредитный конвейер» → «Архитектура: Мобильное приложение → API кредитов → кредитный конвейер; API кредитов → сервис страхования; Кредитный конвейер → сервис страхования → страховая компания-партнёр.»

#### <a id="d-05"></a>🟠 D-05. Правило округления премии до тенге не задано

- Часть B › Ответ, строка 160: «Страховая премия, ₸»

**Проблема.** Строка 38 даёт дробную премию (сумма × 0,15 % × срок), а строка 160 задаёт премию целым числом в тенге. Способ округления (вверх, вниз, к ближайшему) не указан.  
**Сценарий.** Сумма 333 333 ₸ на 7 мес: 333 333 × 0,15 % × 7 = 3 499,9965 ₸. Округление вверх дает 3 500 ₸, вниз — 3 499 ₸; расходятся премия и сумма возврата по Ф-4.  
**Последствия.** Разработчик и тестировщик получат разные суммы премии и разные суммы возврата.  
**Как исправить.** Указать правило округления премии до целых тенге.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Страховая премия равна сумме кредита × 0,15 % × срок кредита в месяцах» → «Страховая премия равна сумме кредита × 0,15 % × срок кредита в месяцах, округлённой <уточнить: вверх, вниз или к ближайшему> до целых тенге.»  
**Вопрос владельцу.** Как округлять премию до целых тенге: вверх, вниз или к ближайшему?  
*Существенный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-06 / Ф-2](#r-06 "Расчёт премии и оплата при выдаче"), [R-37](#r-37 "Страховая премия в тенге") · нашли: аналитик*

#### <a id="d-06"></a>🟠 D-06. Счёт и срок возврата части премии при погашении не заданы

- Ф-4, строка 40: «премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней»
- Ф-5, строка 41: «клиенту возвращается часть премии за полные неиспользованные месяцы»

**Проблема.** Ф-4 (строка 40) задаёт счёт и срок возврата премии (текущий счёт, 7 рабочих дней). Ф-5 (строка 41) говорит только о «части премии» без счёта зачисления и срока выплаты.  
**Сценарий.** Кредит полностью погашен на 10-м месяце, возврат 21 000 ₸ начислен. Документ не говорит, на текущий счёт или на счёт погашения и в какой срок выплатить; срок проверить нельзя.  
**Последствия.** Разработчик выберет счёт и срок сам, тестировщик не сможет проверить срок выплаты.  
**Как исправить.** Дописать в Ф-5 счёт зачисления и срок возврата, как в Ф-4.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 41: «клиенту возвращается часть премии за полные неиспользованные месяцы» → «При полном досрочном погашении кредита страхование прекращается, клиенту возвращается часть премии за полные неиспользованные месяцы на <уточнить: текущий счёт клиента или счёт погашения кредита> в течение <уточнить: срок в рабочих днях>.»  
**Вопрос владельцу.** Куда и в какой срок возвращается часть премии при полном досрочном погашении: на текущий счёт клиента, как при отказе, или на счёт погашения?  
*Существенный, блокирует тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-08 / Ф-4](#r-08 "Отказ от страхования в 14 дней, возврат премии"), [R-09 / Ф-5](#r-09 "Досрочное погашение: прекращение и возврат премии") · нашли: аналитик*

**<a id="q-01"></a>Q-01** Возврат премии при отказе после полного погашения · ⛔ блокирует · кому: Владелец продукта · к [D-01](#d-01)  
Если клиент полностью досрочно погасил кредит и потом в течение 14 дней нажимает «Отказаться от страхования», какая сумма возвращается? В правиле про отказ сказано, что премия возвращается полностью, а в правиле про досрочное погашение — только за неиспользованные месяцы. Метод отказа при этом проверяет только срок и повторный отказ, но не факт погашения.  
Где: Ф-4, строка 40: «премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней»; Ф-5, строка 41: «При полном досрочном погашении кредита страхование прекращается»; Часть B › Методы расчёта и отказа, строка 221: «409 — прошло больше 14 дней или отказ уже оформлен»

- **A** После полного досрочного погашения отказ недоступен: метод отказа возвращает 409, а премия возвращается только по правилу досрочного погашения за полные неиспользованные месяцы, однократно
- **B** Отказ в течение 14 дней возвращает полную премию независимо от погашения; правило досрочного погашения к такому кредиту не применяется
- **C** После полного досрочного погашения отказ возможен в течение 14 дней, но возвращается только сумма за полные неиспользованные месяцы; полная премия возвращается только при отказе без погашения

Зачем: Без решения нельзя написать тест на сумму возврата при погашении внутри 14-дневного окна: разработка и тестирование дадут разные суммы (полная премия или часть) и разные коды ответа метода отказа.

**<a id="q-02"></a>Q-02** Дата проверки минимального возраста 18 лет · можно ответить позже · кому: Владелец продукта · к [D-03](#d-03)  
На какую дату проверяется минимальный возраст клиента 18 лет? Правило о возрасте задаёт верхнюю границу 65 лет на дату окончания кредита, а нижняя граница 18 лет в тексте метода не проверяется и привязки по дате не имеет.  
Где: Ф-6, строка 42: «Страхование доступно клиенту от 18 лет, которому на дату окончания кредита будет не…»; Логика работы метода, п. 4, строка 123: «Проверить возраст клиента на дату окончания кредита»

- **A** 18 лет проверяется на дату выдачи кредита, 65 лет — на дату окончания кредита; при нарушении любой границы возвращается 422
- **B** 18 лет и 65 лет проверяются на дату подачи заявки на страхование; при нарушении любой границы возвращается 422
- **C** 18 лет и 65 лет проверяются на дату окончания кредита; при нарушении любой границы возвращается 422

Зачем: Клиент, которому 17 лет и 364 дня в день выдачи и 18 лет в день окончания, получит разный ответ в разработке и тестах, поэтому граничные тесты по возрасту нельзя написать однозначно.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
