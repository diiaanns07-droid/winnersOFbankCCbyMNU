**<a id="q-01"></a>Q-01** Момент перехода льготного периода в статус «утрачен» · можно ответить позже · кому: Владелец продукта · к [D-05](#d-05), [D-08](#d-08)  
В какой момент льготный период переходит в статус «утрачен» (LOST): уже при первом неполном внесении суммы для погашения или только по окончании платёжного периода, если сумма не внесена полностью? От этого зависит, какой статус получит клиент, который внёс часть суммы до 25-го числа.  
Где: Часть A › Дизайн процесса UI, строка 28: «Если льготный период утрачен, вместо даты показывается надпись «Начисляются проценты»»; Часть B › Ответ, строка 154: «ACTIVE / LOST»; Ф-5, строка 40: «возврат, отражённый позже, уменьшает задолженность, но утраченный льготный период не…»

- **A** Статус «утрачен» (LOST) устанавливается только по окончании платёжного периода: в 25-е число в 23:59:59 по времени Астаны, если сумма для погашения не внесена полностью. До этого момента статус ACTIVE независимо от частичных платежей.
- **B** Статус «утрачен» (LOST) устанавливается в момент первого внесения суммы меньше суммы для погашения. После этого статус LOST до конца платёжного периода, даже если оставшаяся сумма внесена позже.

Зачем: Без ответа нельзя реализовать поле status в ответе метода 1 и экран блока «Льготный период»: для клиента с частичным платежём до 25-го числа две команды вернут разные статусы и разные тексты на экране.

**<a id="q-02"></a>Q-02** Источник данных для прогноза процентов · можно ответить позже · кому: Архитектор · к [D-09](#d-09)  
Откуда метод получения сведений о льготном периоде берёт данные для поля прогноза процентов: кредитный модуль отдаёт готовую сумму, или метод получает список покупок с датами отражения и процентную ставку и считает сумму сам? В текущем описании шаг получения данных содержит только выписку и платежи, а расчёт опирается на покупки с датами и на ставку, которых в этом шаге нет.  
Где: Логика работы метода, п. 5, строка 122: «5. Вернуть сведения о льготном периоде и прогноз процентов на случай частичного погашения»; Логика работы метода, п. 3, строка 120: «3. Получить из кредитного модуля последнюю выписку и платежи после даты выписки»; Ф-3, строка 38: «проценты начисляются на всю задолженность по покупкам расчётного периода с даты отражения…»

- **A** Кредитный модуль сам рассчитывает прогноз процентов по покупкам расчётного периода с дат их отражения и отдаёт метод готовую сумму в тиынах. Метод не считает проценты, а на шаге 3 получает эту сумму из кредитного модуля вместе с выпиской и платежами.
- **B** Метод получает из кредитного модуля список покупок расчётного периода (сумма и дата отражения) и действующую процентную ставку по карте, а сумму прогноза считает сам по правилу Ф-3 и возвращает в поле `interestForecast` в тиынах.
- **C** Поле `interestForecast` из ответа метода 1 убирается. Метод возвращает только `graceAmount` и `daysLeft`, а сумма процентов при частичном погашении в API не передаётся.

Зачем: Без выбора источника нельзя определить состав вызовов кредитного модуля, нельзя написать тест на значение `interestForecast`, и разработчик не знает, нужна ли процентная ставка в контракте.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
