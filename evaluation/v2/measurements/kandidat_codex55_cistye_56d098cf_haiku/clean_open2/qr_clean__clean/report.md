**<a id="q-01"></a>Q-01** Путь вызова сервиса переводов отправителем · можно ответить позже · кому: Архитектор · к [D-02](#d-02)  
Вызывает ли приложение отправителя сервис переводов напрямую или только через контроллер перевода по QR-коду, который сам обращается к сервису QR-кодов и сервису переводов?  
Где: Часть A › Sequence Diagram, строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду»; Часть B › Схема, строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов»

- **A** Приложение отправителя вызывает только QrTransferController; контроллер обращается к сервису QR-кодов и затем к сервису переводов, а прямой вызов сервиса переводов из приложения отсутствует
- **B** Приложение отправителя вызывает сервис переводов напрямую; контроллер и сервис QR-кодов в переводе не участвуют, а проверка QR-кода выполняется сервисом переводов

Зачем: Разные варианты дают разные точки контроля авторизации, идемпотентности и антифрода, и интеграционные команды разойдутся в реализации одного и того же запроса.

**<a id="q-02"></a>Q-02** Код ответа при карте, не принадлежащей клиенту · можно ответить позже · кому: Архитектор · к [D-17](#d-17)  
Какой код возвращать, когда карта, указанная в запросе, не принадлежит клиенту: в методе перевода (карта списания отправителя) и в методе создания QR-кода (карта зачисления получателя)?  
Где: Логика работы метода, п. 2, строка 122: «карта списания принадлежит отправителю, активна и открыта в тенге; если нет, вернуть 400»; Часть B › Методы сервиса QR-кодов, строка 210: «404 — карта не найдена или принадлежит другому клиенту»

- **A** В обоих методах карта, не принадлежащая клиенту, даёт 400 вместе с неактивной картой; 404 только когда QR-код с таким `qrId` не найден
- **B** В обоих методах карта, не принадлежащая клиенту, даёт 404 как «карта не найдена»; 400 только для неверного формата и недоступной карты списания
- **C** В методе перевода карта, не принадлежащая отправителю, даёт 400; в методе создания QR-кода карта, не принадлежащая получателю, даёт 404

Зачем: Без решения две команды по-разному реализуют проверку владения картой, и тесты на один и тот же вход будут давать разный код ответа.

**<a id="q-03"></a>Q-03** Статус QR-кода после отклонения перевода · можно ответить позже · кому: Владелец продукта · к [D-06](#d-06)  
Что происходит со статусом QR-кода с суммой, если перевод по нему отклонён антифродом: возвращается ли он в статус «активен» до конца срока действия, и как это связано с проверкой повторной оплаты?  
Где: Ф-2, строка 38: «если перевод отклонён (REJECTED), QR-код снова можно оплатить до конца срока действия»; Часть A › Требования к данным, строка 51: «статус (активен, оплачен, отменён, истёк) и идентификаторы переводов»; Логика работы метода, п. 6, строка 126: «если оплачен, вернуть 410»

- **A** После REJECTED статус «оплачен» снимается, QR-код снова становится «активен» и может быть оплачен повторно до истечения срока действия
- **B** После REJECTED QR-код получает отдельный статус «отклонён», который допускает повторную оплату до истечения срока действия; статус «оплачен» не ставится до DONE
- **C** После REJECTED QR-код с суммой остаётся «оплачен» и больше не принимает переводы; повторная оплата возможна только через новый QR-код

Зачем: Без ответа не известно, вернёт ли повторный запрос на оплату после отказа антифрода код 200 или 410, и тестировщик не может написать проверку для шага 6 логики метода.

**<a id="q-04"></a>Q-04** Хранение requestId и результата перевода · можно ответить позже · кому: Архитектор · к [D-11](#d-11)  
Нужно ли хранить ключ `requestId` и результат первого перевода (статус, `transferId`, сумму, маскированное имя) и на какой срок, чтобы повтор запроса вернул прежний результат?  
Где: Особые правила, п. 2, строка 132: «Повторный запрос с тем же requestId возвращает результат первого запроса.»; Часть A › Требования к данным, строка 51: «Хранить идентификатор QR-кода, идентификатор клиента-получателя, карту зачисления, сумму…»; Часть B › Request body, строка 152: «Ключ идемпотентности | request_id»

- **A** Хранить `request_id` и результат перевода (status, `transferId`, amount, `recipientName`) 24 часа с момента первого запроса; повтор после истечения срока обрабатывается как новый запрос
- **B** Хранить `request_id` и результат перевода бессрочно, пока существует QR-код; повтор возвращает сохранённый результат
- **C** Хранить `request_id` и результат перевода 7 дней с момента первого запроса; повтор в этот срок возвращает сохранённый результат

Зачем: Поле `request_id` пишется в хранилище, но в перечне хранимых данных его нет, а результата первого запроса нет вовсе; без срока хранения нельзя написать тест на повтор и определить, создаётся ли второй перевод.

**<a id="q-05"></a>Q-05** Доступ к данным QR-кода по qrId · можно ответить позже · кому: ИБ · к [D-15](#d-15)  
Кто может получить имя получателя и сумму QR-кода по его идентификатору через метод получения данных QR-кода: любая авторизованная сессия клиента, знающая `qrId`, или только сессия, которая сканирует этот QR-код?  
Где: Часть B › Методы сервиса QR-кодов, строки 206 и 211: «Методы 2–4 используют ту же авторизацию (Bearer, сессия клиента)» · «GET /qr/{qrId}»; Часть A › Требования к интеграции, строка 54: «получают данные QR-кода перед подтверждением»

- **A** Данные QR-кода отдаются только сессии клиента, которая запросила их первой после создания QR-кода; для любой другой сессии возвращается 404
- **B** Данные QR-кода отдаются любой авторизованной сессии клиента, знающей `qrId`, кроме самого получателя, который создал этот QR-код
- **C** Данные QR-кода отдаются любой авторизованной сессии клиента, знающей `qrId`; дополнительных ограничений по владению нет

Зачем: Без ответа нельзя реализовать проверку доступа к имени получателя и сумме, а короткий предсказуемый `qrId` позволяет перебрать чужие QR-коды.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
