### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. После 422 повтор с тем же ключом даёт 200

- Особые правила, п. 2, строка 139: «после 422 или 500 сервис запрашивает статус операции в АБС (GET /abs/prepayments/{operationId}): «проведена» — 200 с результатом…»
- Особые правила, п. 3, строка 140: «При ответе 422 операция получает статус REJECTED, при ответе 500 — UNKNOWN»
- Часть B › Ответ, строка 158: «При кодах 400, 401, 404, 409 и 422 погашение по этому запросу не проведено»

**Проблема.** Строка 158: «При кодах 400, 401, 404, 409 и 422 погашение по этому запросу не проведено»; строка 139: после 422 сервис запрашивает статус в АБС, «проведена» — 200 с результатом этой операции. Один вход даёт отказ и успех.  
**Сценарий.** АБС отвечает отказом `INSUFFICIENT_FUNDS` (422), но операция в АБС проведена. Клиент нажимает «Повторить» с тем же ключом: получает 200 и push при уже показанном отказе.  
**Последствия.** Клиент видит отказ, а деньги списаны; без правила решения спор при приёмке неразрешим.  
**Как исправить.** Определить, что при 422 сервис не обращается к АБС, или что при статусе АБС «проведена» операция переводится в DONE и результат 200 — единое правило для обоих мест.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 140: «При ответе 422 операция получает статус REJECTED, при ответе 500 — UNKNOWN» → «При ответе 422 операция REJECTED и повтор с тем же ключом: АБС «проведена» → операция DONE, 200 с результатом (строка 139 исключает 422 из этого правила либо явно заменяет строку 158) — <уточнить: выбранное правило>.»  
**Вопрос владельцу.** Допустимо ли, что после 422 АБС показывает проведённое погашение? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — после 422 сервис не обращается к АБС; B — после 422 сервис сверяет статус в АБС  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-067](#r-067 "Критерий успешного и неуспешного ответа"), [R-086](#r-086 "Код 422 — бизнес-проверка не пройдена, причина в errorCode"), [R-061](#r-061 "Правила идемпотентности ключа и повторов"), [R-062](#r-062 "Последовательная обработка и статусы операции") · нашли: архитектор, проверка набора*

#### <a id="d-02"></a>🔴 D-02. UNKNOWN при «не найдена»: REJECTED против повторного проведения

- Часть A › Требования к интеграции, строка 48: «или «не найдена» (операция → REJECTED)»
- критерий приёмки №22, строка 80: «не найдена» — погашение проводится с тем же operationId»
- Особые правила, п. 2, строка 139: «не найдена» — запрос обрабатывается заново с тем же operationId»

**Проблема.** Строка 48: при «не найдена» «(операция → REJECTED)»; строка 80: при «не найдена» «погашение проводится с тем же `operationId`». Сверка и повтор дают разный исход для одной операции.  
**Сценарий.** После 500 по таймауту сверка через 5 минут переводит операцию в REJECTED. Клиент нажимает «Повторить» с тем же ключом: по строке 80 погашение проводится и списывает деньги при статусе REJECTED.  
**Последствия.** Статус операции и фактическое списание могут разойтись; спор о том, проведено ли погашение, не разрешается по документу.  
**Как исправить.** Указать единое поведение: REJECTED — финальный статус, повтор с тем же ключом возвращает 422 или новое проведение с новым `operationId`; либо сверка не выставляет REJECTED до истечения повтора.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Если АБС возвращает «не найдена» для UNKNOWN-операции — операция → REJECTED; повтор с тем же Idempotency-Key для REJECTED-операции — <уточнить: 422 или новое проведение с новым `operationId`>.»  
**Вопрос владельцу.** Может ли операция, переведённая в REJECTED сверкой, быть проведена повтором с тем же ключом? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — REJECTED — финальный статус; B — сверка не переводит операцию в REJECTED, пока не истекли 30 дней жизни ключа  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-049 / приёмка №22](#r-049 "Повтор после 500: проверка статуса в АБС"), [R-050 / приёмка №23](#r-050 "Сверка после 500 без повтора: один push"), [R-061](#r-061 "Правила идемпотентности ключа и повторов") · нашли: архитектор*

#### <a id="d-04"></a>🟠 D-04. Ответ АБС на проведение не различает отказы по источнику и остатку

- Часть A › Требования к интеграции, строка 50: «POST /abs/loans/{loanId}/prepayments — проведение с operationId (списание, погашение, пересчёт графика или закрытие кредита…»
- Логика работы метода, п. 7, строка 135: «Отказ АБС из-за источника списания — 422 SOURCE_UNAVAILABLE, из-за доступного остатка — 422 INSUFFICIENT_FUNDS»

**Проблема.** Строка 135: «из-за источника списания — 422 `SOURCE_UNAVAILABLE`, из-за доступного остатка — 422 `INSUFFICIENT_FUNDS`»; строка 50 не описывает ответ АБС на проведение и признаки этих отказов.  
**Сценарий.** АБС отказывает из-за недостатка средств; сервис не знает поля или кода, чтобы отличить отказ от отказа по счёту, и вернёт клиенту не тот `errorCode`.

**<a id="q-01"></a>Q-01** Повтор запроса после ответа 422 · ⛔ блокирует · кому: Архитектор · к [D-01](#d-01)  
В разделе особых правил сказано, что после 422 сервис запрашивает статус операции в АБС и при «проведена» возвращает 200, а в ответах метода 422 описан как «погашение не проведено». Что должен получить клиент, если он повторяет запрос с тем же ключом после 422?  
Где: Особые правила, п. 2, строка 139: «после 422 или 500 сервис запрашивает статус операции в АБС»; Часть B › Ответ, строка 158: «При кодах 400, 401, 404, 409 и 422 погашение по этому запросу не проведено»

- **A** После 422 сервис не обращается к АБС: повтор с тем же ключом возвращает сохранённый ответ 422 с тем же `errorCode`, без списания.
- **B** После 422 сервис сверяет статус в АБС; если АБС показывает «проведена», операция переводится в DONE, возвращается 200 с результатом, а для кода 422 в описании метода убирается фраза «погашение не проведено».

Зачем: Без решения один и тот же повтор после отказа может дать 422 или 200 с списанием, и тест на повтор после 422 не имеет одного ожидаемого результата.

**<a id="q-02"></a>Q-02** Статус REJECTED после сверки «не найдена» · ⛔ блокирует · кому: Архитектор · к [D-02](#d-02)

Где: Часть A › Требования к интеграции, строка 48: «или «не найдена» (операция → REJECTED)»; критерий приёмки №22, строка 80: ««не найдена» — погашение проводится с тем же operationId»

- **A** REJECTED — финальный статус: повтор с тем же ключом возвращает 422 с сохранённым `errorCode`, новое проведение возможно только с новым ключом идемпотентности.
- **B** Сверка не переводит операцию в REJECTED, пока не истекли 30 дней жизни ключа; до этого «не найдена» оставляет операцию UNKNOWN, а повтор с тем же ключом проводит погашение с тем же `operationId`.

Зачем: Если сверка и повтор дают разный исход для одной операции, возможно двойное списание или списание по операции, которая в системе числится отказанной.

**<a id="q-03"></a>Q-03** Дата выдачи кредита для первого начисления процентов · можно ответить позже · кому: Архитектор · к [D-03](#d-03)

- **B** В поле даты предыдущего погашения АБС возвращает дату выдачи кредита, если погашений не было; отдельное поле не добавляется.

Зачем: Без даты начала начисления расчёт процентов по Ф-3 для первого периода не вычисляется, и критерии с датой выдачи не проверяются.

**<a id="q-04"></a>Q-04** Источник флага видимости кнопки · можно ответить позже · кому: Архитектор · к [D-05](#d-05)

- **A** В ответ GET `/loans` добавляется булево поле, которое показывает доступность досрочного погашения для каждого кредита.
- **B** Отдельный метод возвращает булево значение флага один раз на сессию; GET `/loans` не меняется.

Зачем: Без источника флага приложение не знает, показывать ли кнопку, и откат флагом не проверяется на клиенте.

**<a id="q-05"></a>Q-05** Предел сверки статуса «в обработке» · можно ответить позже · кому: Архитектор · к [D-12](#d-12), [D-06](#d-06)

Где: Часть A › Требования к интеграции, строка 48: «каждые 5 минут до получения статуса «проведена»»; Особые правила, п. 3, строка 140: «следующий ждёт завершения предыдущего»

- **A** Сверка каждые 5 минут до 1 часа; после этого операция остаётся UNKNOWN и выводится для ручной проверки, а следующий запрос по кредиту ждёт не дольше 30 с и затем получает 500.
- **B** Сверка каждые 5 минут до 24 часов; после этого операция переводится в отдельный статус «требует проверки», а следующий запрос по кредиту не ждёт и обрабатывается сразу.

Зачем: Без срока клиент видит 500 неограниченно долго, а следующий запрос по тому же кредиту может зависнуть или обработаться при незавершённой операции.

**<a id="q-06"></a>Q-06** Расчёт частичного погашения при остатке меньше 20 000 ₸ без суммы · можно ответить позже · кому: Тестирование · к [D-07](#d-07)

- **A** Расчёт частичного погашения без amount возвращает 400 `INVALID_REQUEST` в любом случае, а 422 `PARTIAL_NOT_AVAILABLE` возвращается только для расчёта с amount.
- **B** Расчёт частичного погашения при остатке меньше 20 000 ₸ возвращает 422 `PARTIAL_NOT_AVAILABLE` независимо от наличия amount; 400 — только для неизвестного type или некорректного amount.

Зачем: Тест на границу 19 999 ₸ без суммы получит разный код при одинаковом входе, и приёмка не сможет однозначно принять ответ.

**<a id="q-07"></a>Q-07** Push при переходе в DONE через сверку или повтор · можно ответить позже · кому: Архитектор · к [D-11](#d-11)  
Переход в DONE через сверку и через повтор после 500 описан по-разному: в одном месте push отправляется при переходе, в другом повтор с ответом 200 push не шлёт, а для повтора при статусе «проведена» push не указан. Сколько раз и когда клиент получает push за одно погашение?  
Где: Часть A › Требования к интеграции, строка 48: «операция → DONE, сохраняется ответ 200, отправляется push»; Особые правила, п. 2, строка 139: «без обращения к АБС и без нового push»

- **A** Push отправляется ровно один раз при первом переходе операции в DONE, независимо от того, выполнила переход сверка или повтор; повтор с ответом 200 push не отправляет.
- **B** Push отправляется только при переходе через сверку; повтор, который переводит операцию в DONE, push не отправляет, а клиент видит результат на экране.

Зачем: Если push уходит дважды или ни разу, клиент получает неверное уведомление о списании, а тест «один push» не воспроизводим для пути через повтор.

**<a id="q-08"></a>Q-08** Погашения, которые отменяют действие расчёта · можно ответить позже · кому: Владелец продукта · к [D-10](#d-10)  
Расчёт действует до тех пор, пока по кредиту не проведено «другое погашение». Должны ли погашения в отделении и платёж по графику отменять расчёт, сделанный в мобильном приложении?  
Где: Ф-7, строка 38: «только пока по кредиту не проведено другое погашение»

- **A** Отменяет любое погашение по кредиту: через приложение, в отделении и платёж по графику; сервис проверяет это по данным АБС при проведении.
- **B** Отменяет только погашение через мобильное приложение; погашения в отделении и платёж по графику расчёт не отменяют.

Зачем: Если погашение в отделении не отменяет расчёт, клиент может провести устаревшую сумму; если отменяет, подтверждение станет отказом без ошибки в приложении.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
