**<a id="q-01"></a>Q-01** Данные API в периоде без выписки · можно ответить позже · кому: Владелец продукта · к [D-08](#d-08)  
Что возвращает метод с 26-го числа до формирования выписки 1-го числа, когда текущий платёжный период уже закончился, а новая выписка ещё не готова? Сейчас правило возвращает предыдущий период, у которого срок уже прошёл, а поле дней не может быть отрицательным.  
Где: Особые правила, п. 3, строка 130: «Если выписка ещё не сформирована, возвращаются сведения по предыдущему платёжному периоду»; Часть B › Ответ, строка 159: «Количество календарных дней до окончания платёжного периода»; Ф-1, строка 36: «платёжный период заканчивается 25-го числа того же месяца»

- **A** Возвращать предыдущий платёжный период: status ACTIVE, если оставшаяся сумма для погашения равна 0, иначе LOST; `graceAmount` по этому периоду; `daysLeft` равен 0; `paymentDueDate` — дата окончания этого периода.
- **B** Возвращать текущий платёжный период по данным на дату запроса: `paymentDueDate` — 25-е число следующего месяца, `daysLeft` — количество дней до него, `graceAmount` — сумма покупок с 1-го числа месяца на дату запроса.

Зачем: Без правила на этот период тестирование не может ожидать конкретные значения status, `graceAmount` и `daysLeft`, а клиент увидит просроченную дату с отрицательным числом дней.

**<a id="q-02"></a>Q-02** Момент утраты льготного периода · можно ответить позже · кому: Владелец продукта · к [D-04](#d-04)  
Когда льготный период считается утраченным: только в конце платёжного периода или раньше, в момент, когда непогашенная сумма стала больше 0? От этого зависят значение status, надпись «Начисляются проценты» и ответ клиенту до 25-го числа.  
Где: Ф-3, строка 38: «Если она больше 0, проценты начисляются на всю задолженность по покупкам расчётного…»; Часть A › Дизайн процесса UI, строка 28: «Если льготный период утрачен, вместо даты показывается надпись «Начисляются проценты»»; Ф-5, строка 40: «утраченный льготный период не восстанавливает»

- **A** Льготный период утрачен с 23:59:59 25-го числа платёжного периода по времени Астаны, если к этому моменту оставшаяся сумма для погашения больше 0. До этого момента статус ACTIVE, даже если оставшаяся сумма уже больше 0.
- **B** Льготный период утрачен в момент, когда оставшаяся сумма для погашения впервые стала больше 0 после выписки. Статус LOST выставляется сразу и не возвращается к ACTIVE при последующем полном погашении.

Зачем: Без ответа на одном и том же входе (непогашенная сумма на 20-е число) статус и надпись на экране будут разными у разработки и тестирования, а приёмочный тест на статус нельзя написать.

**<a id="q-03"></a>Q-03** Единицы сумм в API и критериях приёмки · можно ответить позже · кому: Архитектор · к [D-16](#d-16)  
В каких единицах проверять суммы: критерии приёмки пишут тенге, а поля ответа `graceAmount` и `totalDebt` передаются в тиынах. Какое правило пересчёта применять, чтобы тест сравнивал одно и то же значение?  
Где: критерий приёмки №1, строка 63: «Задолженность по покупкам февраля 120 000 ₸, выписка от 1 марта»; Часть B › Ответ, строка 158: «Оставшаяся сумма для погашения без процентов, тиыны»

- **A** Все суммы в API и в критериях приёмки передаются в тиынах, где 1 ₸ = 100 тиын: критерии переписываются, например, 120 000 ₸ записывается как 12 000 000 тиын.
- **B** Суммы в API передаются в тенге целым числом: поля `graceAmount` и `totalDebt` переименовываются под тенге, тиыны не используются ни в API, ни в данных.

Зачем: Тест с суммой 120 000 ₸ и ответ 12000000 тиын не сравниваются без правила пересчёта, и две команды по-разному проверят одно и то же значение.

**<a id="q-04"></a>Q-04** Источник дат покупок для прогноза процентов · можно ответить позже · кому: Архитектор · к [D-18](#d-18)  
Откуда метод получает покупки с датами отражения для расчёта прогноза процентов? Шаг получения данных перечисляет выписку, платежи и возвраты, но не сами покупки, а прогноз считается от даты отражения каждой покупки.  
Где: Логика работы метода, п. 3, строка 123: «Получить из кредитного модуля последнюю выписку, а также платежи и возвраты покупок после…»; Часть B › Ответ, строка 160: «Прогноз процентов по ставке тарифа карты за дни с даты отражения каждой покупки по дату…»

- **A** Кредитный модуль отдаёт вместе с выпиской список покупок расчётного периода с датой отражения и суммой каждой покупки; метод считает прогноз по этим данным.
- **B** Метод запрашивает у кредитного модуля список покупок расчётного периода с датами отражения отдельным вызовом, помимо выписки, платежей и возвратов.

Зачем: Без источника дат поле `interestForecast` нельзя вычислить, и разработка не знает, какой вызов модуля добавить в контракт.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
