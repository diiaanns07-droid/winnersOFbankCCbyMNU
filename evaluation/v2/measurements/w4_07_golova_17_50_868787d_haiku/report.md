#### <a id="d-02"></a>🔴 D-02. Ф-2 относит покупку к январю, приёмка — к февралю

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»

**Проблема.** Строка 38 «Месяц определяется по дате совершения покупки в Алматы» относит покупку к месяцу совершения; строка 64 «Февральский счётчик вырос на 4 000 ₸» для покупки «Покупка 31 января в 23:58 на 4 000 ₸» с проведением 1 февраля.  
**Сценарий.** Покупка 4 000 ₸ совершена 31 января в 23:58, проведена 1 февраля в 00:03 (Алматы): по Ф-2 сумма в январе, по критерию приёмки в феврале; один из тестов упадёт.  
**Последствия.** Разработчик и тестировщик расходятся в том, в каком месяце учитывать покупку, и приёмка по этому критерию не пройдёт при одной из реализаций.  
**Как исправить.** Заменить в Ф-2 дату совершения на дату проведения покупки и явно назвать событие, по которому операция попадает в учёт.  
**Было → стало.** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц определяется по дате проведения покупки в часовом поясе Алматы.»  
**Вопрос владельцу.** Относить ли покупку к месяцу по дате проведения (как в критерии приёмки) или по дате совершения в торговой точке? Вариант A: проведения; вариант B: совершения. → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — по дате проведения операции в процессинге, часовой пояс Алматы; B — по дате совершения покупки в торговой точке, часовой пояс Алматы

#### <a id="d-03"></a>🔴 D-03. Второй push в месяце: Ф-3 запрещает, Ф-4 велит слать

**<a id="q-07"></a>Q-07** Статус ответа для чужой карты · можно ответить позже · кому: ИБ · к [D-22](#d-22)  
Что возвращает метод при запросе с картой другого клиента: HTTP 404 «Карта не найдена», как для несуществующей карты, или HTTP 403 Forbidden? Раздел статусов называет оба варианта.  
Где: Часть B › 200. Successful — Created, строка 175: «403. Ответ в случае, если на указанный ресурс доступ запрещен»; Часть B › 403. Unsuccessful — Forbidden, строка 189: «Для чужой карты возвращается 404, как и для отсутствующей карты»

- **A** Чужая и отсутствующая карта дают HTTP 404 с телом {"message":"Карта не найдена"}; статус 403 для карты не используется
- **B** Чужая карта даёт HTTP 403 с телом {"message":"Доступ запрещён"}; отсутствующая карта даёт HTTP 404 «Карта не найдена»

Зачем: Ответ 403 раскрывает, что карта существует, и клиент может перебирать идентификаторы чужих карт; тест на чужую карту не может ожидать оба кода.

**<a id="q-08"></a>Q-08** HTTP-метод изменения порога · можно ответить позже · кому: Архитектор · к [D-16](#d-16)  
Каким HTTP-методом вызывать метод сохранения порога, который изменяет настройку карты? Сейчас указан GET, а параметры `cardId`, amount и enabled передаются в строке адреса.  
Где: Часть B › Общие параметры, строки 104 и 109: «REST type | GET» · «curl -G "$BASE/alerts/saveLimit"»

- **A** POST с параметрами в теле запроса в формате JSON (Content-Type application/json); раздел «Request body» описывает поля `cardId`, amount, enabled
- **B** PUT с параметрами в теле запроса в формате JSON; раздел «Request body» описывает поля `cardId`, amount, enabled

Зачем: GET с изменением данных кэшируется и повторяется прокси, а `cardId` и сумма попадают в журналы веб-сервера; клиент и сервер не могут согласовать контракт.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
