#### <a id="d-01"></a>🔴 D-01. Чтение порога обещано, но метода чтения в API нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 104: «Сохранение порога. Функциональные требования: чтение порога» · «REST type | GET»

**Проблема.** Раздел интеграции (строка 52) и Description (строка 103) обещают чтение настроек, но описан единственный метод `saveLimit`, возвращающий лишь результат сохранения. Порог, переключатель и сумма за месяц для экрана не отдаются.  
**Сценарий.** Клиент открывает Карты → Расходы → Уведомления: приложению нечем получить сохранённые порог, enabled и сумму за месяц, экран пуст или показывает значения по умолчанию.  
**Последствия.** Экран нельзя реализовать, чтение не тестируется.  
**Как исправить.** Добавить метод чтения настроек с запросом и ответом (порог, enabled, сумма за месяц) или убрать обещание чтения.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/`<уточнить: путь чтения>?cardId=... → 200 {"amount":"<порог, ₸>","enabled":"0|1","spent":"<уточнить: имя поля суммы за месяц>"}»  
**Вопрос владельцу.** Какой метод возвращает приложению порог и сумму за месяц? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — добавить в этот документ отдельный метод чтения; B — два отдельных метода чтения; C — чтение вне объёма задачи  
*Критичный, блокирует разработку и тестирование · критерий «Полнота набора» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.3) · требования [R-03](#r-03 "Экран уведомлений: переключатель, порог, сумма, сохранение"), [R-12](#r-12 "Настройки через REST API; идемпотентность повторной доставки"), [R-16](#r-16 "Общие параметры метода сохранения порога") · нашли: проверка набора, правило «обещанные операции», архитектор*

#### <a id="d-02"></a>🔴 D-02. Не определено событие «проведена покупка»: авторизация или клиринг

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель обещает push «в момент покупки», Ф-2 учитывает «проведённые покупки», в sequence событие названо «проведена покупка». Какой этап процессинга запускает пересчёт и push, не сказано.  
**Сценарий.** Покупка 1 500 ₸ при расходах 48 500 ₸ и пороге 50 000 ₸ авторизована в пятницу, проведена во вторник. По цели push в пятницу, по Ф-2 во вторник; при 30 января/2 февраля меняется ещё и месяц.  
**Последствия.** Разработка выбирает событие наугад, цель «в момент покупки» и минута из нефункционального требования несовместимы с клирингом; клиент получает уведомление с опозданием или с неверной суммой, при приёмке спор.  
**Как исправить.** Зафиксировать, какое событие процессинга (авторизация или клиринг) входит в расходы, как учитывается разница сумм и отмена авторизации, и согласовать с этим цель и срок push.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки по событию «<уточнить: авторизация или клиринг>»; при отмене авторизации сумма <уточнить: снимается/не учитывается>; push отправляется в течение минуты после получения этого события.»  
**Вопрос владельцу.** Расходы считаются по авторизации или по клирингу? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — авторизация (одобрение) покупки; B — проведение покупки (клиринг); C — авторизация даёт предварительный push, окончательный учёт и повторная проверка порога…  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Уведомить клиента о достижении личного бюджета"), [R-06 / Ф-2](#r-06 "Определение месяца и состава расходов"), [R-09](#r-09 "Последовательность взаимодействий процессинга, расходов, настроек, push"), [R-10](#r-10 "Передача push на отправку в течение минуты") · нашли: риски, аналитик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Критерий приёмки №2 противоречит правилу Ф-2 о месяце

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Ф-2 относит покупку к месяцу даты совершения, а строка приёмки для покупки от 31 января относит сумму к февралю (дата проведения).  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 по Алматы. По Ф-2 растёт январь, по приёмке — февральский счётчик на 4 000 ₸.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик вырос на 4 000 ₸, февральский не изменился», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик вырос на 4 000 ₸, февральский не изменился», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Январский счётчик вырос на 4 000 ₸, февральский не изменился (месяц по дате совершения 31 января, Алматы).»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик вырос на 4 000 ₸, февральский не изменился» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — по дате совершения (Алматы); B — по дате проведения (Алматы); C — по дате авторизации (Алматы)  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Определение месяца и состава расходов"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-04"></a>🔴 D-04. Ф-3 (один push в месяц) противоречит Ф-4

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 ограничивает карту одним push за календарный месяц, Ф-4 велит слать push при следующем достижении нового порога «независимо от истории». Ни одно место не объявлено исключением.  
**Сценарий.** Порог 50 000 ₸, push отправлен при 50 000. Порог поднят до 60 000, расходы дошли до 60 000 в том же месяце: по Ф-3 push нет, по Ф-4 есть.  
**Последствия.** Клиент получает или не получает уведомление о новом бюджете; тест нельзя принять, реализации разойдутся.  
**Как исправить.** Определить, сбрасывается ли признак отправки при смене порога, и согласовать Ф-3 и Ф-4.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 39: «На карту приходится максимум один такой push за календарный месяц» → «Ф-3. На карту при данном пороге приходится максимум один push за месяц; при изменении порога признак отправки <уточнить: сбрасывается / не сбрасывается>.»

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
