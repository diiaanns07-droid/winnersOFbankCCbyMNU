### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🟠 D-01. Параллельные запросы метода 1 по одной котировке дают две проводки

- Ф-8, строка 42: «По одной котировке выполняется не более одного обмена»
- критерий приёмки №12, строка 78: «Один — 200, другой — 422 QUOTE_ALREADY_USED; проводка одна»
- Часть B › Логика работы метода, строки 134 и 135: «Котировка со статусом USED — 422 QUOTE_ALREADY_USED» · «Создать обмен со статусом PROCESSING и передать в АБС проводку по счетам и суммам…»

**Проблема.** Строка 134 проверяет только статус USED, который ставится после DONE (строка 136). Пока первый обмен в PROCESSING, второй запрос проходит шаг 3 и шлёт вторую проводку. строка 78 требует «Один — 200, другой — 422 `QUOTE_ALREADY_USED`», логика это не даёт.  
**Сценарий.** Запросы R3 и R4 в 11:00:20.000 и 11:00:20.002 по котировке в статусе ACTIVE: первый ставит PROCESSING, второй проходит шаг 3 и создаёт вторую проводку в АБС. Списаний два.  
**Последствия.** Двойное списание по одной котировке и расхождение с критерием 12, который по тексту логики не воспроизводится.  
**Как исправить.** Добавить в шаг 3 проверку статуса обмена PROCESSING по этой котировке с явным ответом и кодом; уточнить ответ второму запросу, пока первый не завершён.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 134: «Котировка со статусом USED — 422 QUOTE_ALREADY_USED» → «Шаг 3 метода 1: котировка с обменом в статусе PROCESSING — не создавать второй обмен; ответ: <уточнить: код и `errorCode` для запроса, пришедшего во время PROCESSING>; котировка USED — 422 `QUOTE_ALREADY_USED`.»

#### <a id="d-02"></a>🟠 D-02. Неподтверждённая отмена проводки не имеет исхода и статуса

- Ф-9, строка 43: «Если АБС отказала в проводке, остатки не меняются; если не дала результата за время таймаута (И-2), сервис обмена отменяет…»
- Д-1, строка 53: «status (PROCESSING — проводка передана в АБС, DONE — проведена, FAILED — не выполнена)»
- Часть B › Логика работы метода, строка 135: «В этих случаях обмен получает статус FAILED, котировка остаётся ACTIVE»
- Особые правила, п. 2, строка 145: «повторяет её каждые 30 с до подтверждения»

**Проблема.** Строка 145 повторяет отмену «до подтверждения» и возвращает 500 после первой отправки. строка 135 ставит FAILED и котировку ACTIVE, а Д-2 (строка 53) не содержит статуса для незавершённой отмены. Исход неудачной отмены не задан.  
**Сценарий.** 27.11.2026 11:00:20: АБС провела списание 150.55 доллары США, но не ответила за 10 с; отмена не подтверждена, клиент получает 500, котировка ACTIVE. В 11:00:40 новый `requestId` создаёт второй обмен и второе списание.  
**Последствия.** Клиент теряет сумму второго списания до ручной сверки, банк получает спор о двойном списании и обращения в поддержку; разработка не знает, что делать с отменой, которая не подтверждается.  
**Как исправить.** Задать предельное время повторов отмены и исход, если отмена не подтверждена: котировка блокируется до сверки, новая проводка по ней не создаётся, клиенту выдаётся отдельный текст.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Если отмена проводки не подтверждена за <уточнить: время>, обмен получает статус <уточнить: статус>, котировка не принимает новых проводок до подтверждения отмены, клиент получает <уточнить: код и текст>.»  
**Вопрос владельцу.** При неподтверждённой отмене блокировать котировку до сверки с АБС или разрешить новую проводку по ней? → [Q-02](#q-02) (варианты ответа)  
*Существенный, блокирует разработку · критерий «ИБ и операционные риски» (Чек-лист ревью требований банка) · требования [R-13 / Ф-9](#r-13 "Списание и зачисление одной проводкой АБС"), [R-39](#r-39 "Создание обмена и проводка в АБС"), [R-46](#r-46 "Отмена проводки и повтор каждые 30 с"), [R-30 / приёмка №10](#r-30 "Таймауты АБС и сервиса курсов") · нашли: риски, архитектор*

**<a id="q-01"></a>Q-01** Второй запрос обмена во время выполнения · можно ответить позже · кому: Архитектор · к [D-01](#d-01)  
Какой ответ получает второй запрос метода 1 с другим `requestId`, если первый запрос по той же котировке уже создал обмен в статусе PROCESSING и проводка ещё не завершена? В одном месте написано, что второй запрос получает 422 `QUOTE_ALREADY_USED` и одна проводка, а в логике метода проверка срабатывает только по статусу USED, который ставится после проводки.  
Где: критерий приёмки №12, строка 78: «Один — 200, другой — 422 QUOTE_ALREADY_USED; проводка одна»; Часть B › Логика работы метода, строки 134 и 135: «Котировка со статусом USED — 422 QUOTE_ALREADY_USED» · «Создать обмен со статусом PROCESSING и передать в АБС проводку»

- **A** Второй запрос получает 422 `QUOTE_ALREADY_USED` с тем же текстом, что и для статуса USED; проверка статуса PROCESSING выполняется на шаге 3 до создания обмена
- **B** Второй запрос получает новый код 409 `QUOTE_IN_PROGRESS` с текстом «Обмен по курсу уже выполняется»; тело 422 `QUOTE_ALREADY_USED` остаётся только для статуса USED
- **C** Второй запрос ждёт результата первого до таймаута И-2 и получает тот же ответ 200 с тем же `exchangeId`, если первый завершился проводкой «проведено»

Зачем: Без решения две реализации дадут разные коды для одного входа, а критерий приёмки строки 12 не сможет проверить ни один из них, и появится вторая проводка по одной котировке.

**<a id="q-02"></a>Q-02** Исход неподтверждённой отмены проводки · можно ответить позже · кому: Архитектор · к [D-02](#d-02)  
Что происходит с обменом и котировкой, если после таймаута АБС отмена проводки не подтверждается? Сейчас обмен получает статус «не выполнен», котировка остаётся действующей, а отмена повторяется без предела, и при этом списание может остаться проведённым.  
Где: Ф-9, строка 43: «если не дала результата за время таймаута (И-2), сервис обмена отменяет проводку»; Особые правила, п. 2, строка 145: «повторяет её каждые 30 с до подтверждения»; Часть B › Логика работы метода, строка 135: «В этих случаях обмен получает статус FAILED, котировка остаётся ACTIVE»

- **A** Котировка блокируется до сверки с АБС; обмен получает новый статус «требует сверки»; новая проводка по котировке не выполняется, клиенту 500 `INTERNAL_ERROR`
- **B** Отмена повторяется каждые 30 с не более 10 раз (около 5 минут); если подтверждения нет, обмен получает статус «требует сверки», котировка блокируется, клиенту 500 `INTERNAL_ERROR`
- **C** Котировка остаётся ACTIVE, новая проводка по ней разрешена через 30 с после отмены без подтверждения; статус обмена FAILED

Зачем: Без решения при неподтверждённой отмене клиент может получить 500 и повторить обмен, а банк может списать деньги дважды, и тесты на остатки и статусы будут расходиться.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».
