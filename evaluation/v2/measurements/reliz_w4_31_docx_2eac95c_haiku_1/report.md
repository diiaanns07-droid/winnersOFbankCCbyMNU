#### <a id="d-01"></a>🔴 D-01. Чтение порога обещано, но ни одной операции чтения в API нет

- Часть A › Дизайн процесса UI, строка 19: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Sequence Diagram, строка 29: «Сервис расходов → настройки: получить порог карты»
- Часть A › Требования к интеграции, строка 35: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 67 и 72: «Функциональные требования: чтение порога» · «Dev: /alerts/saveLimit . Prod: —»

**Проблема.** Экран и интеграция обещают чтение порога (строка 19, строка 35, строка 67, строка 29), но описан только `saveLimit`: он требует amount и enabled и только сохраняет (строка 72, строка 97, строка 98). Метода чтения нет.  
**Сценарий.** Клиент открывает Карты → Расходы → Уведомления: экран должен показать сохранённый порог, но метода чтения нет. Сервис расходов по строке 29 не получает порог при покупке 1 500 ₸ при пороге 50 000 ₸.  
**Последствия.** Экран настроек не покажет сохранённый порог, а сервис расходов не сможет проверить порог при покупке; реализация чтения придётся додумывать.  
**Как исправить.** Добавить в дочернюю спецификацию операцию чтения порога карты с описанием запроса, ответа и кодов либо явно указать, что чтение выполняет `saveLimit` без изменения настроек.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/getLimit?cardId={cardId}` — чтение порога и признака включения; ответ 200 {"result":"OK","amount":"<уточнить: формат>","enabled":"0|1"}; ошибки 401, 404, 500 по общей таблице.»  
**Вопрос владельцу.** Какой метод и путь использовать для чтения порога, если `saveLimit` только сохраняет? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — отдельный метод чтения порога по идентификатору карты; B — сервис расходов получает порог и признак включения из данных события покупки, которые…; C — метод сохранения вызывается приложением с текущими значениями для получения настроек  
*Критичный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-03](#r-03 "Экран настройки порога и уведомлений"), [R-09](#r-09 "Последовательность вызовов сервисов расходов"), [R-12](#r-12 "Чтение и сохранение настроек через REST API"), [R-16](#r-16 "Метод сохранения порога, авторизация сессией") · нашли: правило «обещанные операции», архитектор, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Неверная сумма: код 200 с ERROR против кода 400

- Логика работы метода, п. 5, строка 84: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Статусы, строка 111: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 112 и 115: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»
- Часть B › 400. Unsuccessful — Bad request, строка 120: «{"message":"Некорректный запрос"}»

**Проблема.** Строка 103 считает 200 успешным ответом, а строка 115 отдаёт при отказе по сумме код 200 с result=ERROR. Статус 400 для неверных параметров описан в строках 111 и 120, и это другой исход по коду.  
**Сценарий.** amount=999: по строкам 103 и 115 — 200 с ERROR (успех по коду, отказ по телу); по строкам 111 и 120 — 400. Приложение, смотрящее на код, покажет сохранение порога как успешное.  
**Последствия.** Приложение будет по-разному обрабатывать отказ ввода: как успех или как ошибку HTTP, что ведёт к ложному подтверждению сохранения порога.  
**Как исправить.** Выбрать один код для отказа по сумме и описать тело ответа; код 200 не использовать для ERROR.  
**Было → стало.** Строка 115: «{"result":"ERROR","message":"Проверьте сумму"}» → «Ошибка суммы: HTTP 400, тело {"result":"ERROR","message":"Проверьте сумму"}; строка 115 и перечень статусов приведены к одному коду.»  
**Вопрос владельцу.** Что верно: «HTTP 400, параметры заполнены неверно» (как в «Статус 400») или «результат ERROR; пример ответа приведён под кодом 200» (как в «Логика работы метода, п. 5»)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний…; B — HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний…; C — HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму"} без прежнего порога  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-21](#r-21 "Возврат прежнего состояния при ошибке суммы"), [R-30](#r-30 "Правило успешного и неуспешного ответа"), [R-31](#r-31 "Исход сохранения: OK или ERROR"), [R-36](#r-36 "Статус 400 при неверных параметрах запроса") · нашли: архитектор, проверка набора, правило «контракт API»*

#### <a id="d-03"></a>🔴 D-03. Второй push за месяц после смены порога: Ф-3 запрещает, Ф-4 разрешает

- Ф-3, строка 26: «максимум один такой push за календарный месяц»
- Ф-4, строка 27: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 даёт максимум один push за календарный месяц (строка 26), Ф-4 говорит, что следующее достижение вызывает push независимо от истории (строка 27). Не сказано, распространяется ли лимит Ф-3 на этот push.  
**Сценарий.** Порог 50 000 ₸, накоплено 50 000 ₸, push №1. Порог повышен до 100 000 ₸, покупки доводят сумму до 100 000 ₸. По строке 27 push отправляется, по строке 26 второй push за месяц запрещён.  
**Последствия.** Клиент получит два push за месяц или разработчик выберет одно из правил; приёмка не определена.  
**Как исправить.** Зафиксировать: при смене порога лимит один push за месяц сохраняется, Ф-4 относится только к накопленной сумме.  
**Предлагаемая формулировка.** «Ф-4: При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push, если в текущем календарном месяце push по Ф-3 ещё не отправлялся; иначе push не отправляется (уточнить: подтвердить бизнесом).»  
**Вопрос владельцу.** Что верно: «push отправляется при достижении нового порога» (как в Ф-4) или «второй push за месяц запрещён» (как в Ф-3)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — нет: лимит один push за календарный месяц сохраняется при смене порога; Ф-4 относится…; B — да: после смены порога разрешён один новый push на новый порог в том же календарном…; C — да: push отправляется при каждом достижении порога без ограничения по месяцу, пока клиент…

#### <a id="d-04"></a>🟠 D-04. Покупка 31 января 23:58: Ф-2 и критерий приёмки дают разный месяц

- Ф-2, строка 25: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 42: «Покупка 31 января в 23:58 на 4 000 ₸»

**<a id="q-01"></a>Q-01** Источник порога и метод чтения порога · ⛔ блокирует · кому: Архитектор · к [D-01](#d-01), [D-08](#d-08)  
Каким методом приложение читает сохранённый порог для экрана и каким способом сервис расходов получает порог при покупке, если описан только метод сохранения?  
Где: Часть A › Требования к интеграции, строка 35: «Приложение читает и сохраняет настройки через дочерний документ»; Часть A › Sequence Diagram, строка 29: «Сервис расходов → настройки: получить порог карты»; Часть B › Общие параметры, строка 72: «Dev: /alerts/saveLimit»

- **A** Отдельный метод чтения порога по идентификатору карты; при успехе возвращает порог в тенге и признак включения; сервис расходов вызывает этот же метод при каждой покупке по карте, приложение — при открытии экрана
- **B** Сервис расходов получает порог и признак включения из данных события покупки, которые передаёт процессинг; приложение читает порог отдельным методом чтения по идентификатору карты
- **C** Метод сохранения вызывается приложением с текущими значениями для получения настроек; отдельного чтения нет, сервис расходов обращается к хранилищу настроек напрямую

Зачем: Без метода чтения экран не покажет порог, а сервис расходов не знает порог при покупке; разработчики реализуют разные пути получения порога.

**<a id="q-02"></a>Q-02** Код ответа при отказе по сумме · ⛔ блокирует · кому: Архитектор · к [D-02](#d-02), [D-19](#d-19), [D-22](#d-22)  
Какой HTTP-код и тело ответа получает клиент, если сумма порога отклонена: код 400 или код 200 с результатом ERROR, и что возвращается как прежний порог?  
Где: Часть B › Ответ, строка 103: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.»; Часть B › Статусы, строка 111: «400. Ответ в случае, если параметры запроса заполнены неверно.»; Часть B › 200. Successful — Created, строка 115: «{"result":"ERROR","message":"Проверьте сумму"}»

- **A** HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний порог>","enabled":"<прежний признак>"}; код 200 с ERROR не используется; во всех телах ошибок поле result присутствует
- **B** HTTP 200 с телом {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний порог>","enabled":"<прежний признак>"}; код 400 только для синтаксически неверного запроса без допустимой суммы
- **C** HTTP 400 с телом {"result":"ERROR","message":"Проверьте сумму"} без прежнего порога; клиент перечитывает порог отдельным запросом

Зачем: При amount=999 одна реализация покажет успех по коду 200, другая — ошибку по коду 400; тесты не смогут проверить единый исход.

**<a id="q-03"></a>Q-03** Второй push за месяц после смены порога · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03)  
Если клиент повысил порог после уже отправленного push за этот месяц и расходы достигли нового порога, должен ли прийти второй push в том же календарном месяце?  
Где: Ф-3, строка 26: «максимум один такой push за календарный месяц»; Ф-4, строка 27: «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **A** Нет: лимит один push за календарный месяц сохраняется при смене порога; Ф-4 относится только к сохранению накопленной суммы
- **B** Да: после смены порога разрешён один новый push на новый порог в том же календарном месяце; лимит один push относится к каждому порогу отдельно
- **C** Да: push отправляется при каждом достижении порога без ограничения по месяцу, пока клиент не выключит уведомление

Зачем: Порог 50 000 ₸ → 100 000 ₸ после push №1: одна реализация отправит второй push, другая нет; приёмка по этому сценарию не проходит однозначно.

**<a id="q-04"></a>Q-04** Событие и месяц учёта покупки · можно ответить позже · кому: Владелец продукта · к [D-04](#d-04), [D-05](#d-05)  
Какое событие процессинга запускает учёт покупки в расходах месяца и по дате какого события определяется месяц, если покупка 31 января 23:58 проводится 1 февраля 00:03?  
Где: Ф-2, строка 25: «Месяц определяется по дате совершения покупки в Алматы» · «В расходы входят проведённые покупки»; критерий приёмки №2, строка 42: «Покупка 31 января в 23:58 на 4 000 ₸»

- **A** Учёт и push запускаются событием проведения покупки; месяц определяется по дате проведения в Алматы; покупка 31 января 23:58, проведённая 1 февраля 00:03, относится к февралю
- **B** Учёт запускается одобренной авторизацией; месяц определяется по дате авторизации в Алматы; отмена авторизации уменьшает расходы месяца исходной авторизации
- **C** Учёт запускается авторизацией; месяц определяется по дате совершения покупки клиентом в Алматы; проведение на учёт не влияет

Зачем: Без выбора события и даты одна покупка попадает в разные месяцы, а счётчик и push при той же операции считаются по-разному.

**<a id="q-05"></a>Q-05** Кто вправе задать порог карты · можно ответить позже · кому: Владелец продукта · к [D-07](#d-07)

- **C** Накопление ведётся всегда с начала календарного месяца; при включении уведомления, если накопленная сумма уже не ниже порога, push не отправляется до следующего месяца

Зачем: Клиент с 40 000 ₸ и порогом 50 000 ₸ при включении и покупке 15 000 ₸ получит push по одной трактовке и не получит по другой.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
