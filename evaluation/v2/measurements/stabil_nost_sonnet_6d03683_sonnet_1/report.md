**Было → стало.** Строка 108: «Prod: —» → «Prod: <уточнить: значение>; Swagger: <уточнить: значение>»

#### <a id="d-17"></a>🟠 D-17. Типы amount и enabled различаются в запросе (integer) и ответе (string)

**Требования:** [R-27](#r-27 "amount, integer, обязательный порог 1 000–1 000 000"), [R-28](#r-28 "enabled, integer, обязательный признак 0 или 1"), [R-32](#r-32 "amount, строка, порог в тенге при успехе"), [R-33](#r-33 "enabled, строка «0» или «1», признак включения") · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** контракт API · **Блокирует:** разработку · **Нашли:** архитектор, правило «api.field_types.saveLimit»

- Часть B › Query-параметры, строка 143: «amount | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | limit_kzt»
- Часть B › Query-параметры, строка 144: «enabled | integer»
- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»
- Часть B › Ответ, строка 157: «enabled | string | «0» или «1» | Признак включения | enabled»

**Проблема.** В запросе amount и enabled — integer (строки 143–144), в ответе тех же полей — string (строки 156–157). Типизированный клиент и контрактные тесты расходятся.  
**Сценарий.** Клиент отправляет amount как integer и получает обратно значение типа string; строгий разбор ответа или сравнение отправленного и сохранённого значения не проходит.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Что исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Было → стало.** Строка 143: «amount | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | limit_kzt» → «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»

#### <a id="d-18"></a>🟠 D-18. Перечень кодов ответа неполон: 201 не описан, 200 назван Created, список открыт

**Требования:** [R-30](#r-30 "Успех при 200 или 201, неуспех при 400, 401 и далее") (Успех при 200 или 201, неуспех при 400, 401 и…), [R-35](#r-35 "200: успешное выполнение метода") (200: успешное выполнение метода) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, правило «api.status_201», правило «language.open_list»

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»

**Проблема.** строка 151 считает успехом 200 и 201, но 201 нигде не описан. Заголовок строка 165 «200. Successful — Created» соответствует коду 201. Неуспех задан открытым перечнем «400, 401 и далее».  
**Сценарий.** Сервер при первом сохранении возвращает 201. Тела и условия для него нет. Код 404 или 429 одна команда отнесёт к «и далее», другая нет.  
**Последствия.** Клиент обработает ответ как неизвестную ошибку; спор при приёмке о правильном коде; автотесты контракта нельзя написать однозначно.  
**Что исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Было → стало.** Строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный» → «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»

#### <a id="d-19"></a>🟠 D-19. Тела ответов 400, 401, 403, 500 не содержат поле result

**Требования:** [R-31](#r-31 "result, строка OK или ERROR, исход сохранения"), [R-34](#r-34 "message, строка, описание ошибки при ошибке"), [R-36](#r-36 "400: параметры запроса заполнены неверно"), [R-37](#r-37 "401: запрос без необходимой авторизации"), [R-39](#r-39 "500: внутренняя ошибка сервера") · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** контракт API · **Блокирует:** разработку · **Нашли:** архитектор, правило «api.result_field_missing.result»

- Часть B › Ответ, строка 155: «result | string | OK / ERROR | Исход сохранения | —»
- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»
- Часть B › 400. Unsuccessful — Bad request, строка 180: «{"message":"Некорректный запрос"}»
- Часть B › 401. Unsuccessful — Unauthorized, строка 185: «{"message":"Требуется вход"}»
- Часть B › 403. Unsuccessful — Forbidden, строка 192: «{"message":"Карта не найдена"}»

**Проблема.** result в таблице ответа (строка 155) задан без условия, но в примерах ошибок (строка 180, строка 185, строка 197) его нет. Для result=ERROR не определено, как возвращается прежнее состояние, а amount есть только при успехе.  
**Сценарий.** Ответ 500 {"message":"Ошибка сервиса"}: клиент ждёт result; при ERROR прежний порог не возвращается.  
**Последствия.** Клиент не может единообразно разобрать ответ.  
**Что исправить.** Сделать result условным (только 200) либо добавить во все тела; уточнить поля прежнего состояния.  
**Было → стало.** Строка 155: «result | string | OK / ERROR | Исход сохранения | —» → «result | string | OK/ERROR | только в ответе 200; в 4xx/5xx только message»

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
