#### <a id="d-01"></a>🔴 D-01. Обещано чтение настроек через API, метода чтения нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 108: «Description | Сохранение порога. Функциональные требования: чтение порога» · «Request URL | Dev: /alerts/saveLimit . Prod: —»

**Проблема.** Строка 52 обещает чтение и сохранение настроек через дочерний документ, строка 29 показывает порог, переключатель и сумму за месяц, но в части B описан только `saveLimit` (строка 103, строка 108). Операции чтения нет.  
**Сценарий.** Клиент открывает Карты → Расходы → Уведомления: приложению нечем получить порог, состояние переключателя и сумму за месяц.  
**Последствия.** Клиентский разработчик не может реализовать открытие экрана, тесты чтения не написать.  
**Как исправить.** Добавить в дочерний документ метод чтения (GET) с параметром `cardId` и ответом: порог, признак включения, сумма расходов за месяц.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/`<уточнить: путь метода чтения>; параметр `cardId` (string, 1–64, обязателен); ответ 200: {"amount":"<порог, тенге>","enabled":"0|1","spent":"<уточнить: имя поля суммы за месяц и единица>"}»

#### <a id="d-02"></a>🔴 D-02. Не определено, какое событие процессинга считается «проведённой» покупкой

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»

**Сценарий.** Покупка 1 500 ₸ при расходах 48 500 ₸ и пороге 50 000 ₸. Если брать авторизацию — push сразу; если клиринг — через дни, возможно с иной суммой или в другом месяце.  
**Последствия.** Неизвестно, какое событие принимать от процессинга; клиент получит уведомление сразу или через дни, а отменённая авторизация даст ложное уведомление.  
**Как исправить.** Назвать событие процессинга для учёта и описать сумму и судьбу отменённой авторизации; согласовать с целью и сроком в одну минуту.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки, по которым получено <уточнить: сообщение об авторизации или о проведении (клиринге)>; сумма берётся из <уточнить: какого сообщения>.»

- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»

**Проблема.** Шаг 5 требует вернуть прежнее состояние (строка 121), но amount и enabled возвращаются только при успехе (строка 156), пример ERROR содержит лишь message (строка 171).  
**Сценарий.** amount=500: клиент должен показать прежний порог, а в ответе его нет.  
**Последствия.** Клиент не знает, как показать прежнее значение и как разбирать ответ отказа.  
**Как исправить.** Задать код и тело отказа по сумме; если прежнее состояние нужно в ответе, снять условие «при успехе» у amount и enabled.

#### <a id="d-16"></a>🟠 D-16. Типы amount и enabled в запросе и ответе различаются

**Проблема.** amount и enabled — integer в запросе (строка 143, строка 144), но string в ответе (строка 156, строка 157).

#### <a id="d-17"></a>🟠 D-17. Перечень кодов ответа противоречив, неполон и открыт

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › 200. Successful — Created, строки 165 и 175: «200. Successful — Created» · «403. Ответ в случае, если на указанный ресурс доступ запрещен»
- Часть B › 403. Unsuccessful — Forbidden, строки 188 и 189: «403. Unsuccessful — Forbidden» · «Для чужой карты возвращается 404, как и для отсутствующей карты»

**Проблема.** Для чужой карты строки 175 задаёт 403, а в блоке 403 возвращается 404 (строка 189), которого нет в перечне. Код 201 назван успешным (строка 151), но не описан; 200 подписан «Created» (строка 165); «400, 401 и далее» — список открыт.  
**Сценарий.** Чужой `cardId` с валидной сессией: одна реализация вернёт 403, другая 404; сервер вернёт 201 — по перечню он не предусмотрен.

**Как исправить.** Описать код 404 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «404. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
