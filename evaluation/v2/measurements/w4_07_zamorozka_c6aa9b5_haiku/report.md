#### <a id="d-02"></a>🔴 D-02. Push «в момент покупки» не согласован с учётом проведённых покупок

- Часть A › Цели, строка 23: «в момент покупки»
- Часть A › BPMN схема процесса, строка 34: «Проведение покупки → пересчёт расходов»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Нефункциональные требования, строка 46: «в течение минуты после получения события»

**Проблема.** Строка 23 обещает push «в момент покупки», строка 46 допускает минуту после события, а строка 38 считает расходы по «проведённым покупкам». Проведение приходит через дни после авторизации.  
**Сценарий.** Покупка 10 марта 12:00 на 1 500 ₸ при расходах 48 500 ₸ и пороге 50 000 ₸: авторизация 10 марта, проведение 12 марта. По цели push 10 марта, по Ф-2 — 12 марта.  
**Последствия.** Клиент получит уведомление с задержкой на несколько дней вместо момента покупки; приёмка по цели и НФТ невыполнима, тестировщик не может подтвердить ни одно из двух правил.  
**Как исправить.** Указать, какое событие запускает учёт и push, и согласовать с целью и НФТ фактический срок реакции.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Расходы и push формируются по событию <уточнить: авторизация или проведение>; срок отправки push от события — <уточнить: значение>.»  
**Вопрос владельцу.** Учитывать ли покупку в счётчике и отправлять ли push по авторизации (быстрее, но может быть отменена) или по проведению (позже, но окончательно)? → [Q-02](#q-02) (варианты ответа)

#### <a id="d-03"></a>🔴 D-03. Критерий приёмки №2 противоречит Ф-2 для покупки 31 января

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу даты совершения, а строка 64 ожидает рост февральского счётчика для той же покупки, проведённой 1 февраля. Какое событие определяет месяц, не сказано.  
**Сценарий.** Покупка 31 января в 23:58 на 4 000 ₸, проведена 1 февраля в 00:03 по Алматы. По Ф-2 январский счётчик +4 000 ₸, февральский без изменений; по строке 64 февральский +4 000 ₸.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸, февральский без изменений», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸, февральский без изменений», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Покупка 31 января в 23:58 на 4 000 ₸» → «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Январский счётчик вырос на 4 000 ₸; февральский счётчик не изменился (покупка относится к январю по дате совершения в Алматы)»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик +4 000 ₸, февральский без изменений» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — месяц определяется по дате проведения покупки в Алматы; B — месяц определяется по дате совершения покупки в Алматы  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Месяц по Алматы, учёт покупок и возвратов"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-04"></a>🔴 D-04. Ф-3 запрещает второй push в месяц, Ф-4 требует его при новом пороге

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

- **B** Не более одного push за месяц на каждое значение порога: после смены порога push отправляется при первом переходе через новый порог в этом месяце, даже если push по прежнему порогу уже был
- **C** Не более одного push за календарный месяц; при понижении порога ниже накопленной суммы push отправляется сразу при сохранении настройки, если в этом месяце его ещё не было

Зачем: Без решения две команды по-разному реализуют повтор push в том же месяце, и тест сценария «смена порога» не может быть однозначным.

**<a id="q-05"></a>Q-05** Код ответа при неверной сумме · ⛔ блокирует · кому: Архитектор · к [D-05](#d-05), [D-16](#d-16)

Где: Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»; Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»

- **B** Для чужой карты возвращается HTTP 403 с телом «Доступ запрещён», для отсутствующей — HTTP 404 с телом «Карта не найдена»

Зачем: Тесты на чужую карту дадут разные коды; при первом варианте чужая карта не отличается от отсутствующей, при втором — возможен перебор идентификаторов карт.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
