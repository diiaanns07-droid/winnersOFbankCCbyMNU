#### <a id="d-01"></a>🔴 D-01. Обещано чтение настроек, но метода чтения в части B нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 104: «Description | Сохранение порога. Функциональные требования: чтение порога» · «REST type | GET»

**Проблема.** Строки 52 и 103 обещают чтение порога через REST API, но в части B описан только `saveLimit`, который сохраняет. Ни один метод не отдаёт переключатель, порог и сумму за месяц для экрана строки 29.  
**Сценарий.** Клиент открывает экран «Уведомления»: приложению нужны текущие переключатель, порог и сумма за месяц, а метода чтения нет. Экран нечем заполнить, тест чтения не написать.  
**Последствия.** Клиентский разработчик не может реализовать экран, тест чтения не написать.  
**Как исправить.** Описать метод чтения настроек (порог, enabled, сумма за месяц) в дочернем документе либо убрать обещание чтения.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET `/alerts/getLimit?cardId=`<идентификатор карты>; ответ 200 {"result":"OK","amount":"<порог, тенге>","enabled":"0|1","spent":"<уточнить: имя поля и единица суммы за месяц>"}»  
**Вопрос владельцу.** Какие данные должен возвращать метод чтения и откуда приложение берёт сумму за месяц? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — отдельный метод чтения (GET) возвращает порог, признак включения и сумму за месяц; B — отдельный метод чтения (GET) возвращает порог и признак; C — один метод PUT на карту для чтения и сохранения, сумма за месяц в ответе  
*Критичный, блокирует разработку и тестирование · критерий «Полнота набора» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.3) · требования [R-03](#r-03 "Экран расходов: переключатель, порог, сумма, кнопка"), [R-12](#r-12 "Настройки через REST API; идемпотентность событий"), [R-16](#r-16 "Общие параметры метода сохранения порога") · нашли: архитектор, проверка набора, правило «обещанные операции»*

#### <a id="d-02"></a>🔴 D-02. Критерий приёмки №2 противоречит правилу Ф-2 о месяце покупки

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Провести 1 февраля в 00:03 по Алматы»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу по дате совершения, а критерий приёмки (строка 64) относит ту же покупку к февралю по дате проведения.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03. По Ф-2 расходы января, по критерию приёмки февральский счётчик вырос на 4 000 ₸. Порог сработает в разных месяцах.  
**Последствия.** Разработчик и тестировщик получат разные итоги месяца, порог сработает в разных месяцах, возможны спорные push.  
**Как исправить.** Выбрать одно событие (совершение или проведение) для отнесения к месяцу и привести Ф-2 и критерий в соответствие.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц покупки определяется по <уточнить: дате совершения или дате проведения> покупки по времени Алматы (UTC+5).»  
**Вопрос владельцу.** Месяц определяется по дате совершения покупки или по дате её проведения? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — по дате совершения покупки (Алматы); B — по дате проведения (Алматы); C — по дате авторизации (Алматы), критерий и правило переписать под это событие  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Правила учёта расходов за месяц"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Ф-3 «один push в месяц» противоречит Ф-4 после смены порога

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 (строка 39) ограничивает push одним в месяц на карту, Ф-4 (строка 40) требует push при следующем достижении нового порога независимо от истории. Приоритет правил не задан.  
**Сценарий.** Порог 50 000 ₸ достигнут, push отправлен. Клиент поднял порог до 80 000 ₸, расходы дошли до 80 000 ₸ в том же месяце: по Ф-3 push нет, по Ф-4 push есть.  
**Последствия.** Реализация и тесты разойдутся: клиент либо не узнает о новом бюджете, либо получит второй push.  
**Как исправить.** Явно указать, сбрасывает ли смена порога лимит одного push в месяц.  
**Было → стало.** Строка 39: «На карту приходится максимум один такой push за календарный месяц» → «На карту приходится максимум один push за календарный месяц для каждой действующей настройки порога; при изменении порога признак отправки сбрасывается.»  
**Вопрос владельцу.** После смены порога push в том же месяце разрешён (A) или нет (B)? → [Q-03](#q-03) (варианты ответа)

*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Push при достижении порога, один в месяц"), [R-08 / Ф-4](#r-08 "При смене порога сумма сохраняется") · нашли: аналитик, тестировщик, проверка набора*

#### <a id="d-05"></a>🟠 D-05. Не определено, какое событие покупки учитывается и запускает push

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель строки 23 обещает уведомление «в момент покупки», а строки 38 и 43 опираются на «проведённую покупку»; авторизация и проведение (клиринг) — разные события с разрывом в дни. Срок строки 46 отсчитывается от получения события.  
**Сценарий.** Покупка 1 500 ₸ авторизована 30 января, клиринг 2 февраля. При опоре на авторизацию push уходит 30 января, при опоре на проведение — 2 февраля, в другом месяце.  
**Последствия.** Разработка выберет событие наугад, клиент получит уведомление с опозданием на дни или с неверной суммой, а обещание «в момент покупки» и «в течение минуты» нельзя проверить при приёмке.  
**Как исправить.** Зафиксировать этап операции, который запускает пересчёт расходов, и сообщение процессинга, которое сервис принимает; согласовать с ним цель и срок в одну минуту.

#### <a id="d-16"></a>🟠 D-16. Ответ при отклонении суммы не содержит прежнего состояния

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»

**Проблема.** Шаг 5 (строка 121) требует вернуть прежнее состояние, но amount и enabled возвращаются только при успехе (строка 156), а пример ERROR (строка 171) содержит лишь message.  
**Сценарий.** Запрос amount=500: по шагу 5 нужна прежняя настройка, в ответе её нет.  
**Последствия.** Клиент не знает, какое состояние показать после отказа.  
**Как исправить.** Определить код и тело для отклонённой суммы, включая поля прежнего состояния.  
**Предлагаемая формулировка.** «400 {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний порог>","enabled":"<прежний признак>"}»

#### <a id="d-17"></a>🟠 D-17. Типы amount и enabled различаются в запросе и ответе

- Часть B › Query-параметры, строки 143 и 144: «amount | integer» · «enabled | integer»
- Часть B › Ответ, строки 156 и 157: «amount | string» · «enabled | string»

**Проблема.** amount и enabled в запросе integer (строка 143, строка 144), в ответе string (строка 156, строка 157).  
**Сценарий.** Клиент отправляет amount как integer и получает обратно значение типа string; строгий разбор ответа или сравнение отправленного и сохранённого значения не проходит.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Порог в тенге, обязательный"), [R-28](#r-28 "Признак включения 0/1, обязательный"), [R-32](#r-32 "Порог в ответе при успехе"), [R-33](#r-33 "Признак включения в ответе") · нашли: правило «контракт API»*

#### <a id="d-18"></a>🟠 D-18. Перечень кодов ответа противоречив, неполон и открыт

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный»
- Часть B › 200. Successful — Created, строки 165 и 175: «200. Successful — Created» · «403. Ответ в случае, если на указанный ресурс доступ запрещен»
- Часть B › 403. Unsuccessful — Forbidden, строки 188 и 189: «403. Unsuccessful — Forbidden» · «Для чужой карты возвращается 404, как и для отсутствующей карты»

**Проблема.** Строка 151 называет успешным 201, которого нет в статусах, а 200 подписан «Created» (строка 165); перечень ошибок заканчивается «и далее»; для чужой карты строки 175 задаёт 403, а блок 403 даёт 404 (строка 189).  
**Сценарий.** Запрос с `cardId` чужой карты: по строке 175 ответ 403, по строке 189 — 404 «Карта не найдена».  
**Последствия.** Клиент обработает ответ как неизвестную ошибку; спор при приёмке о правильном коде; автотесты контракта нельзя написать однозначно.  
**Как исправить.** Описать код 201 в перечне статусов (когда возвращается, тело ответа) или убрать упоминание; привести заголовки разделов в соответствие с кодами.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «201. <уточнить: когда возвращается>. Тело ответа: <уточнить>.»  
**Вопрос владельцу.** Какой код для чужой карты: 403 или 404? → [Q-08](#q-08) (варианты ответа)  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-30](#r-30 "Правило успешности ответа по коду"), [R-35](#r-35 "Код 200 — успешное выполнение метода"), [R-38](#r-38 "Код 403 — доступ к ресурсу запрещён"), [R-40](#r-40 "Код 404 — чужая или отсутствующая карта, не найдена") · нашли: правило «контракт API», правило «размытые слова», проверка набора*

#### <a id="d-19"></a>🟠 D-19. Ответы 400, 401, 403 и 500 без поля result

- Часть B › Ответ, строка 155: «result | string | OK / ERROR»
- Часть B › 400. Unsuccessful — Bad request, строка 180: «{"message":"Некорректный запрос"}»
- Часть B › 401. Unsuccessful — Unauthorized, строка 185: «{"message":"Требуется вход"}»
- Часть B › 403. Unsuccessful — Forbidden, строка 192: «{"message":"Карта не найдена"}»

**Проблема.** Таблица ответа (строка 155) задаёт result как OK/ERROR без условия, но в примерах ошибок (строка 180, строка 185) поля result нет.  
**Сценарий.** Клиент читает result в ответе 401: поля нет, разбор падает.  
**Последствия.** Разные реализации обработки ошибок у клиента и сервера; тесты контракта на ошибки не написать.  
**Как исправить.** Либо добавить result во все тела ошибок, либо указать в таблице ответа, при каких кодах поле result присутствует.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «result | <уточнить: тип> | Обязательно во всех ответах | Признак результата»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-31](#r-31 "Исход сохранения OK или ERROR"), [R-40](#r-40 "Код 404 — чужая или отсутствующая карта, не найдена") · нашли: правило «контракт API»*

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
