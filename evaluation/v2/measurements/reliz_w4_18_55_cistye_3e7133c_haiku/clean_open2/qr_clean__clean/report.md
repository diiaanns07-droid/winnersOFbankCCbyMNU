### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Пример ответа возвращает сумму 5000 при QR с суммой 3000

- Часть B › Общие параметры, строка 113: «qrId":"qr-5f2a","cardId":"c-2001","amount":5000»
- Логика работы метода, п. 5, строка 125: «Если в QR-коде задана сумма, использовать её, а поле amount запроса не учитывать»
- Часть B › 200. Successful, строка 176: «{"status":"DONE","transferId":"tr-90311","amount":5000,"recipientName":"Айгерим С."}»
- Часть B › Методы сервиса QR-кодов, строка 211: «recipientName":"Айгерим С.","amount":3000»

**Проблема.** Строка 125 велит списывать сумму, заданную в QR (по строке 211 у qr-5f2a это 3000). Пример запроса строки 113 передаёт amount 5000, пример ответа строки 176 возвращает amount 5000 и перевод на 5 000 ₸.  
**Сценарий.** QR qr-5f2a на 3000 ₸: запрос с amount 5000 по строке 113. По строке 125 списывается 3000 ₸, по примеру ответа строки 176 — 5000 ₸. Тест не может выбрать ожидаемую сумму списания.  
**Последствия.** Расхождение по сумме списания и зачисления: клиент может быть списан на сумму, отличную от показанной на экране, а тест на сумму пройдёт или не пройдёт в зависимости от выбранного примера.  
**Как исправить.** Исправить пример (строка 113) и строка 176 так, чтобы они соответствовали шагу 5 (QR с суммой 3000: amount в ответе 3000), либо явно описать пример для QR без суммы; пример qr-5f2a в строке 210 использовать отдельно от строки 211.  
**Было → стало.** Строка 176: «{"status":"DONE","transferId":"tr-90311","amount":5000,"recipientName":"Айгерим С."}» → «Пример: QR qr-5f2a с суммой 3000 ₸, запрос с amount 5000 → ответ {"status":"DONE","`transferId`":"tr-90311","amount":3000,"`recipientName`":"Айгерим С."}; для QR без суммы в примере использовать отдельный `qrId`.»  
**Вопрос владельцу.** Какой `qrId` относится к примеру QR без суммы, а какой к QR с суммой 3 000 ₸? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — пример относится к QR с суммой 3000 ₸; B — пример относится к QR без суммы  
*Критичный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-25](#r-25 "Выбор суммы перевода и её проверка"), [R-40](#r-40 "Сумма перевода в тенге"), [R-51](#r-51 "Данные QR-кода, GET /qr/{qrId}") · нашли: тестировщик*

#### <a id="d-02"></a>🟠 D-02. Чужой QR-код читается по короткому `qrId` без проверки владельца

- Ф-5, строка 41: «Получатель может отменить QR-код»
- Часть B › Общие параметры, строка 113: «qrId":"qr-5f2a»
- Часть B › Методы сервиса QR-кодов, строка 211: «GET /qr/{qrId} | path: qrId (string, 1–36, обязательный)»

**Проблема.** Метод 3 (строка 211) требует только `qrId` и сессию и отдаёт имя, сумму и срок. Проверки владельца нет, в отличие от отмены (строка 212 «принадлежит другому клиенту»). Пример `qrId` короткий (строка 113).  
**Сценарий.** Клиент с валидной сессией перебирает qr-XXXX и получает имя, сумму и срок действия активных QR-кодов других клиентов.  
**Последствия.** Утечка персональных данных клиентов банка (имя и сумма платежа) и основа для социальной инженерии при оплате чужих QR-кодов.  
**Как исправить.** Задать в требовании формат `qrId` с высокой энтропией и ограничить чтение данных QR-кода.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 113: «qrId":"qr-5f2a» → «`qrId` формируется как случайный UUID v4 (128 бит, не последовательный); GET `/qr/{qrId}` возвращает данные только для отправителя, проводящего оплату по этому QR-коду в пределах срока действия; <уточнить: иной круг лиц, если нужен>.»  
**Вопрос владельцу.** Кому разрешено читать данные QR-кода через GET `/qr/{qrId}`: любому клиенту с сессией или только тому, кто его сканирует? → [Q-02](#q-02) (варианты ответа)

#### <a id="d-03"></a>🟠 D-03. Схемы вызова перевода по QR расходятся в трёх местах

- Часть A › Архитектура решения, строка 25: «Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод»
- Часть A › Sequence Diagram, строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду»
- Часть B › Схема, строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов»

**Проблема.** Архитектура (строка 25) ведёт перевод через сервис QR-кодов, последовательность (строка 45) — напрямую в сервис переводов, API (строка 136) — через контроллер и сервис QR-кодов.  
**Сценарий.** Разработчик по строке 25 строит вызов через сервис QR-кодов, по строке 45 — напрямую. Владельцы интеграции и точка проверки QR при переводе разные.  
**Последствия.** Разные интеграции, разные владельцы и разные места проверки QR при переводе.  
**Как исправить.** Привести все три схемы к одной последовательности вызовов.  
**Было → стало.** Строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов» → «Приложение отправителя вызывает QrTransferController, который обращается к сервису QR-кодов, затем к сервису переводов.»  
**Вопрос владельцу.** Проходит ли перевод по QR через сервис QR-кодов перед сервисом переводов, или приложение отправителя вызывает сервис переводов напрямую? → [Q-03](#q-03) (варианты ответа)  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-02](#r-02 "Компоненты и связи сервисов при переводе по QR"), [R-11](#r-11 "Последовательность вызовов между системами"), [R-31](#r-31 "Схема вызова метода перевода по QR") · нашли: проверка набора*

#### <a id="d-04"></a>🟠 D-04. Состояние перевода «в обработке» не хранится, но проверяется при отмене

- Часть A › Требования к данным, строка 51: «статус (активен, оплачен, отменён, истёк) и идентификаторы переводов»
- Часть B › Методы сервиса QR-кодов, строка 212: «по QR-коду есть перевод в обработке, QR-код уже отменён или срок истёк»

**Проблема.** DELETE (строка 212) возвращает 410 при переводе «в обработке», но перечень данных (строка 51) хранит статус QR и идентификаторы переводов, без состояния перевода.  
**Сценарий.** Получатель отменяет QR без суммы, перевод по нему уже принят в обработку. По данным нельзя выбрать 410 или 200 CANCELLED.  
**Последствия.** Отмена может пройти по переводу, который уже выполняется, либо будет ложно отклонена.  
**Как исправить.** Добавить в перечень хранимых данных состояние каждого перевода и описать его значения.

#### <a id="d-06"></a>🟠 D-06. Статус «оплачен» после REJECTED не снимается, шаг 6 блокирует повтор

**<a id="q-01"></a>Q-01** Какой QR относится к примеру перевода · ⛔ блокирует · кому: Аналитик · к [D-01](#d-01)  
Пример запроса перевода использует `qrId` qr-5f2a с amount 5000, а в примере данных QR этот же `qrId` имеет сумму 3000 ₸. Какой QR описывают примеры запроса и ответа: QR с суммой 3000 ₸ или QR без суммы?  
Где: Часть B › Общие параметры, строка 113: «"qrId":"qr-5f2a","cardId":"c-2001","amount":5000»; Логика работы метода, п. 5, строка 125: «Если в QR-коде задана сумма, использовать её, а поле amount запроса не учитывать»; Часть B › Методы сервиса QR-кодов, строка 211: «"recipientName":"Айгерим С.","amount":3000»

- **A** Пример относится к QR с суммой 3000 ₸: поле amount в запросе (5000) игнорируется, в ответе amount 3000 и `transferId`, списывается 3000 ₸. Пример ответа исправляется на эти значения.
- **B** Пример относится к QR без суммы: запрос с amount 5000 списывает 5000 ₸, в ответе amount 5000. Для QR с суммой 3000 ₸ добавляется отдельный пример с другим `qrId`.

Зачем: Без ответа тест не может выбрать ожидаемую сумму списания: при одном толковании списывается 3000 ₸, при другом 5000 ₸.

**<a id="q-02"></a>Q-02** Доступ к чтению данных QR-кода · можно ответить позже · кому: ИБ · к [D-02](#d-02)  
Кто может получить данные QR-кода (имя, сумму, срок) методом чтения по `qrId`: любой клиент с действующей сессией или только клиент, который сканирует QR? И каким должен быть формат `qrId`, чтобы его нельзя было перебрать?  
Где: Часть B › Методы сервиса QR-кодов, строки 211 и 212: «path: qrId (string, 1–36, обязательный)» · «404 — QR-код не найден или принадлежит другому клиенту»

- **A** Читать может любой клиент с сессией, но `qrId` генерируется случайно, не короче 36 символов и не меньше 128 бит энтропии; неизвестный или чужой для чтения `qrId` даёт 404.
- **B** Читать может только клиент, отсканировавший QR: сервис фиксирует сканирование в течение срока действия, для остальных клиентов метод чтения возвращает 404.

Зачем: Без ответа нельзя написать тест на доступ к чужим QR и нельзя задать формат `qrId`: короткий перебираемый идентификатор отдаёт имена, суммы и сроки чужих QR.

**<a id="q-03"></a>Q-03** Схема вызова перевода по QR · можно ответить позже · кому: Архитектор · к [D-03](#d-03)  
Проходит ли перевод по QR через сервис QR-кодов перед сервисом переводов, или приложение отправителя вызывает сервис переводов напрямую?

- **A** Перевод идёт через сервис QR-кодов: контроллер перевода сначала запрашивает проверку QR у сервиса QR-кодов, затем сервис переводов, антифрод и зачисление.

**<a id="q-04"></a>Q-04** Состояние перевода при отмене QR · можно ответить позже · кому: Архитектор · к [D-04](#d-04)

Зачем: Без ответа при отмене QR нельзя выбрать между 200 CANCELLED и 410, а данные для проверки состояния перевода не описаны.

**<a id="q-05"></a>Q-05** Срок действия QR-кода · можно ответить позже · кому: Владелец продукта · к [D-05](#d-05)

- **B** Срок задаётся для каждого QR полем ttl от 5 до 30 минут, значение по умолчанию 15 минут; проверка срока всегда использует это поле.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
