#### <a id="d-01"></a>🔴 D-01. Возврат премии при досрочном погашении и отказе

- Ф-4, строка 40: «премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней»
- Ф-5, строка 41: «При полном досрочном погашении кредита страхование прекращается»

**Проблема.** Ф-4 (строка 40) возвращает премию полностью при отказе, Ф-5 (строка 41) возвращает часть премии при полном погашении. Для случая погашения и последующего отказа документ не задаёт итоговую сумму и число возвратов.  
**Сценарий.** Кредит 1 000 000 ₸ на 24 мес, премия 36 000 ₸, выдан 1 марта. 5 марта погашен полностью (Ф-5: 34 500 ₸), 7 марта отказ (Ф-4: 36 000 ₸). Итог 70 500, 36 000 или 34 500 ₸ — документ не говорит.  
**Последствия.** Банк может выплатить премию дважды (клиент получает лишние деньги) либо клиент получает меньше, чем ожидал; разработка и приёмка выбирают сумму наугад.  
**Как исправить.** Добавить правило: премия возвращается не более одного раза, при полном погашении в течение 14 дней отказ не возвращает повторно сумму, уже возвращённую по Ф-5, и наоборот.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Премия возвращается не более одного раза: при отказе по Ф-4 возвращается вся премия за вычетом уже возвращённой по Ф-5 суммы; <уточнить: что считать уже возвращённой суммой>.»  
**Вопрос владельцу.** Если кредит погашен полностью в течение 14 дней, при отказе возвращается вся премия или только остаток после Ф-5? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — после отказа и после полного досрочного погашения метод возвращает статус «прекращено» с…; B — после отказа метод возвращает статус «отказано», после полного досрочного погашения…; C — после отказа или полного досрочного погашения метод возвращает 404 «полис не найден»…

#### <a id="d-08"></a>🟠 D-08. Повторный вызов для подписанной заявки: успех или 409

#### <a id="d-09"></a>🟠 D-09. Тела ответов 400 и 422 не совпадают с перечнем причин кодов

- Часть B › 400. Unsuccessful — Bad request, строка 181: «{"message":"Сумма или срок вне допустимого диапазона"}»
- Часть B › 422. Unsuccessful — Unprocessable entity, строка 201: «{"message":"Страхование недоступно по возрасту"}»

**Проблема.** Строка 166 относит к 400 и отсутствие согласия, тело строки 181 говорит только о сумме или сроке; строка 170 относит к 422 отказ партнёра, тело строки 201 говорит только о возрасте.  
**Сценарий.** Клиент не дал согласие: приходит 400 про сумму или срок. Партнёр отказал: приходит 422 про возраст. Клиенту показана неверная причина.  
**Последствия.** Приложение покажет клиенту неверную причину отказа.  
**Как исправить.** Задать отдельные тексты сообщений для каждой причины внутри кодов 400 и 422.  
**Было → стало.** Строка 181: «{"message":"Сумма или срок вне допустимого диапазона"}» → «400: {"message":"Нет согласия на передачу персональных данных"} или {"message":"Сумма или срок вне допустимого диапазона"}; 422: {"message":"Страховая компания отказала"} или {"message":"Страхование недоступно по возрасту"}.»  
*Существенный, блокирует тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-40](#r-40 "Код 400 — сумма, срок вне диапазона или нет согласия"), [R-44](#r-44 "Код 422 — возраст или отказ страховщика при проверке"), [R-25](#r-25 "Передача данных страховщику после согласия") · нашли: архитектор*

**<a id="q-01"></a>Q-01** Статус полиса после отказа и досрочного погашения · ⛔ блокирует · кому: Архитектор · к [D-02](#d-02), [D-01](#d-01)  
Какой статус и какие данные должен возвращать метод сведений о страховании после отказа от страхования в течение 14 дней и после полного досрочного погашения кредита? Сейчас в описании метода есть только статус ACTIVE для действующего полиса, а статус REMOVED относится к снятию с неподписанной заявки.  
Где: Часть B › Методы расчёта и отказа, строки 222 и 223: «{"status":"REMOVED","rate":27.0}» · «{"status":"ACTIVE","policyNumber":"LI-2026-000123","startDate":"2026-0…»; Ф-4, строка 40: «премия возвращается полностью на текущий счёт клиента в течение 7 рабочих дней»

- **A** После отказа и после полного досрочного погашения метод возвращает статус «прекращено» с новым полем `endDate` (дата прекращения); `policyNumber` сохраняется, статус ACTIVE только для действующего полиса.
- **B** После отказа метод возвращает статус «отказано», после полного досрочного погашения — статус «погашено»; `policyNumber` сохраняется в обоих случаях.
- **C** После отказа или полного досрочного погашения метод возвращает 404 «полис не найден», сведения о прекращённом полисе не отдаются.

Зачем: Без ответа тесты не могут проверить статус после отказа и погашения: разработка вернёт ACTIVE, а тестировщик ожидает другое значение, и клиент в приложении увидит неверное состояние полиса.

**<a id="q-02"></a>Q-02** Путь выпуска полиса и номера полиса от партнёра · можно ответить позже · кому: Архитектор · к [D-05](#d-05), [D-03](#d-03)  
По какому маршруту сервис страхования вызывает партнёра на выпуск полиса и как получает номер полиса: напрямую от конвейера или через API кредитов? Архитектура ведёт вызовы через API кредитов, а последовательность вызывает страхование напрямую, и в последовательности нет ответа партнёра с номером полиса.  
Где: Часть A › Архитектура решения, строка 25: «Мобильное приложение → API кредитов → кредитный конвейер»; Часть A › Sequence Diagram, строка 45: «Кредитный конвейер → сервис страхования: кредит выдан, выпустить полис»; Часть A › Требования к интеграции, строка 54: «Сервис страхования получает номер полиса от страховой компании-партнёра после выдачи…»

- **A** Конвейер вызывает сервис страхования напрямую; сервис страхования синхронно получает от партнёра номер полиса и сохраняет его; API кредитов в выпуске полиса не участвует.
- **B** Конвейер вызывает сервис страхования через API кредитов; номер полиса возвращается по той же цепочке в обратном направлении.
- **C** Партнёр присылает номер полиса асинхронно отдельным событием; до его получения метод сведений о страховании возвращает `policyNumber` = `null`.

Зачем: Без выбора маршрута архитектура и последовательность расходятся, а метод сведений и уведомление о полисе не могут получить номер полиса в согласованном месте, поэтому интеграция не реализуема однозначно.

**<a id="q-03"></a>Q-03** Снятие страхования, если кредит не выдан после подписания · можно ответить позже · кому: Владелец продукта · к [D-06](#d-06)  
Что происходит со страхованием, если заявка уже подписана, но кредит не выдан: страхование снимается автоматически без списания премии, и нужно ли уведомлять клиента? Сейчас снятие описано только до подписания заявки, а путь после подписания не описан.  
Где: Часть A › BPMN схема процесса, строка 34: «подписание договора кредита и заявления на страхование → выдача кредита и оплата премии»; Часть B › Методы расчёта и отказа, строка 222: «только до подписания заявки»

- **A** Страхование снимается автоматически, премия не списывается, клиенту отправляется уведомление через сервис уведомлений.
- **B** Страхование снимается автоматически, премия не списывается, уведомление клиенту не отправляется.
- **C** Страхование не снимается: заявка закрывается вместе с кредитом, премия не списывается, метод снятия после подписания возвращает 409.

Зачем: Без ответа не ясно, остаётся ли полис без кредита и получает ли клиент уведомление; разработка и тестирование по-разному проверят статус страхования и отправку сообщения на этом пути.

## <a id="pe"></a>Приложение Е. Методика

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
