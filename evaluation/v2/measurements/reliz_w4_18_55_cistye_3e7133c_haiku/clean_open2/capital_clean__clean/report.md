**<a id="q-01"></a>Q-01** Состав ответа метода чтения условий · можно ответить позже · кому: Архитектор · к [D-04](#d-04), [D-14](#d-14)  
Какие поля и в каком виде возвращает метод чтения условий и процентов, чтобы экран показывал дату начала нового способа и карту для выплаты, если смены способа в следующем месяце нет?  
Где: Часть A › Дизайн процесса UI, строка 28: «После сохранения под переключателем показывается дата, с которой действует новый способ»; Часть B › Методы чтения, строка 201: «"payoutCardId":null»

- **A** Метод чтения возвращает `effectiveFrom` в формате ГГГГ-ММ-ДД, если `nextMode` отличается от `currentMode`, иначе `null`; `payoutCardId` — карта для выплаты текущего месяца (строка или `null`), с описанием в таблице полей как у метода сохранения.
- **B** `effectiveFrom` всегда возвращается как 1-е число следующего месяца, даже если `nextMode` совпадает с `currentMode`; `payoutCardId` — карта текущего месяца (строка или `null`).
- **C** Метод чтения не возвращает дату: экран после сохранения показывает дату из ответа метода сохранения и не показывает её при повторном открытии экрана.

Зачем: Без ответа нельзя написать тест на поле `effectiveFrom` и на `payoutCardId`: на один и тот же вход экран и метод чтения дают разные данные, а поле `payoutCardId` в ответе не имеет типа и смысла.

**<a id="q-02"></a>Q-02** Источник списка карт для выбора в UI · можно ответить позже · кому: Архитектор · к [D-05](#d-05)  
Откуда экран получает список карт клиента в тенге для выбора карты выплаты: из уже существующего сервиса карт или через новый метод, которого в документе сейчас нет?  
Где: Часть A › Дизайн процесса UI, строка 28: «выбор карты для выплаты (виден при выборе «На карту»)»; Часть B, строка 99: «Метод 1 — изменение способа выплаты»

- **A** Список карт клиента в тенге берётся из существующего сервиса карт клиента; в требование добавляется ссылка на этот вызов и формат его ответа.
- **B** Добавляется новый метод чтения списка карт клиента в тенге по образцу методов 2 и 3 с полями id карты и маской номера; его описание включается в дочерний документ.
- **C** Выбор карты в приложении выполняется без списка: клиент вводит идентификатор карты вручную, а проверка делается методом сохранения способа.

**<a id="q-03"></a>Q-03** Хранение карты на следующий месяц · можно ответить позже · кому: Владелец продукта · к [D-08](#d-08)  
Если клиент меняет карту для выплаты в середине месяца, на какую карту выплачиваются проценты текущего месяца: на прежнюю или на новую?  
Где: Ф-3, строка 38: «Новый способ выплаты применяется начиная со следующего календарного месяца; проценты…»; Часть A › Требования к данным, строка 50: «Хранить идентификатор счёта, способ выплаты, карту для выплаты, дату начала действия…»

- **A** Хранятся две карты: карта текущего месяца и карта следующего месяца; проценты текущего месяца выплачиваются на карту текущего месяца, а с 1-го числа следующего месяца карта следующего месяца становится текущей.
- **B** Карта меняется сразу, а проценты текущего месяца выплачиваются на новую карту, если клиент выбрал её до последнего дня месяца; отдельной карты на следующий месяц не хранится.
- **C** Карта меняется только вместе со способом с 1-го числа следующего месяца, а текущий месяц выплачивается на карту, сохранённую на 1-е число текущего месяца; новая карта, выбранная в середине месяца, сохраняется до 1-го числа.

Зачем: Одно поле карты перезаписывает карту текущего месяца, поэтому при выплате 31-го числа разработчик и тестировщик могут получить разные карты для одного и того же начисления.

**<a id="q-04"></a>Q-04** Куда уходят проценты при закрытии счёта · можно ответить позже · кому: Владелец продукта · к [D-10](#d-10)

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».
