#### <a id="d-01"></a>🔴 D-01. Чтение порога обещано, но в API есть только сохранение

- Часть A › Дизайн процесса UI, строка 29: «сумма за месяц и кнопка «Сохранить»»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строка 103: «Description | Сохранение порога. Функциональные требования: чтение порога»

**Проблема.** Строка 52: «Приложение читает и сохраняет настройки через дочерний документ»; строка 103: «Функциональные требования: чтение порога»; строка 43: «получить порог карты». В API описан только `saveLimit`, а amount и enabled обязательны (строки 143–144).  
**Сценарий.** Экран «Карты → Расходы → Уведомления» (строка 29) должен показать порог и сумму за месяц. Вызов без изменения невозможен: без amount метод не выполнится, с amount перезапишет порог.  
**Последствия.** Приложение и сервис расходов не смогут прочитать настройку без её изменения, и обещанное чтение не реализуемо по тексту.  
**Как исправить.** Описать отдельную операцию чтения настройки карты: путь, метод, параметр `cardId`, ответ с result, amount, enabled и кодами ошибок.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET <уточнить: путь операции чтения>; query: `cardId` (string, 1–64, обязательно); ответ 200 {"result":"OK","amount":"<порог, тенге>","enabled":"0|1"}; 404 при отсутствии карты или чужой карты.»  
**Вопрос владельцу.** Операция чтения должна возвращать значения по умолчанию, если настройка не сохранялась (уточнить)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — одобрение авторизации; B — проведение (клиринг)

#### <a id="d-02"></a>🔴 D-02. Месяц покупки: по дате совершения в Ф-2 и по проведению в приёмке

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Строка 38: «Месяц определяется по дате совершения покупки в Алматы»; строка 64: «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸». Одна покупка по Ф-2 — январь, по приёмке — февраль.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 по Алматы. Код по Ф-2 даст январский счётчик +4 000 ₸ и не пройдёт критерий строки 64; код под критерий нарушит Ф-2.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик +4 000 ₸, февральский не меняется», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик +4 000 ₸, февральский не меняется», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик вырос на 4 000 ₸» → «Покупка 31 января в 23:58 на 4 000 ₸ | Провести 1 февраля в 00:03 по Алматы | Февральский счётчик не изменился; январский счётчик вырос на 4 000 ₸»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик +4 000 ₸, февральский не меняется» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — нет: за календарный месяц уходит не более одного push независимо от смены порога; B — да: push уходит при каждом достижении порога, но не более одного на каждое значение…  
*Критичный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-06 / Ф-2](#r-06 "Определение месяца и состав учитываемых операций"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: тестировщик, аналитик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Ф-3 и Ф-4 дают разное число push за месяц после смены порога

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Строка 39: «На карту приходится максимум один такой push за календарный месяц»; строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки». Для одного входа число push за месяц разное.  
**Сценарий.** Порог 50 000 ₸, push отправлен. Порог повышен до 100 000 ₸ при накопленных 50 000 ₸; покупки доводят сумму до 100 000 ₸ в том же месяце. По Ф-3 второго push нет, по Ф-4 push отправляется.  
**Последствия.** Разработчик и тестировщик по-разному реализуют повтор push в одном месяце.  
**Как исправить.** Явно указать, действует ли лимит одного push в месяц после смены порога.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Ф-4. При изменении порога накопленная сумма сохраняется. **Вопрос владельцу.** Что верно: «второго push в этом месяце нет» (как в Ф-3) или «push отправляется при достижении нового порога» (как в Ф-4)? → [Q-03](#q-03) (варианты ответа)

Где: Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»; Часть A › Дизайн процесса UI, строка 29: «сумма за месяц и кнопка «Сохранить»»; Особые правила, п. 2, строка 125: «Повторное сохранение заменяет действующую настройку»

- **A** Отдельный метод чтения по `cardId`: возвращает amount в тенге, enabled, сумму за текущий месяц в тенге; если настройки нет, возвращает enabled «0» и без amount
- **B** Отдельный метод чтения по `cardId`: возвращает только amount и enabled; сумма за месяц на экран не выводится, пункт экрана удаляется

Зачем: Без метода чтения экран не покажет текущее состояние, а разработка не знает, что возвращать при отсутствии сохранённой настройки.

**<a id="q-05"></a>Q-05** Код ответа при сумме вне диапазона · ⛔ блокирует · кому: Архитектор · к [D-05](#d-05)

Где: Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»; Часть B › 200. - **A** 400, тело содержит поля result со значением ERROR и message с описанием ошибки; пример с кодом 200 и ERROR удаляется
- **B** 200, тело содержит result со значением ERROR и message; код 400 для этого случая не используется

Зачем: Клиент и тест по-разному проверят неверную сумму: по коду статуса или по полю result, и приложение не сможет обработать ошибку одинаково.

- **B** POST с параметрами в строке адреса, как в примере curl; тип GET заменяется на POST

- **B** Нет: менять порог может только владелец карты, держатель дополнительной карты может только смотреть

Зачем: Разработка не знает, какую роль проверять в сессии, и тест доступа для дополнительной карты может дать противоположный результат.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
