### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🟠 D-01. Сохранение настроек при выключении описано двумя способами

- Ф-8, строка 41: «При выключении настройки сохраняются и показываются при повторном включении»
- Особые правила, п. 2, строка 154: «При enabled = false поля roundingStep, savingsAccountId и monthlyLimit не проверяются и не сохраняются»

**Проблема.** Ф-8: «При выключении настройки сохраняются и показываются при повторном включении». Особое правило 2 метода 1: поля «не проверяются и не сохраняются». Непонятно, записывается ли шаг из тела запроса при enabled = false.  
**Сценарий.** Сохранён шаг 100; клиент шлёт enabled=false и `roundingStep`=500. По Ф-8 может сохраниться 500, по правилу 2 остаётся 100; при повторном включении шаг разный.  
**Последствия.** Разработчик и тестировщик по-разному реализуют сохранение полей при выключении, и после повторного включения клиент получит другой шаг округления.  
**Как исправить.** Привести особое правило 2 в соответствие с Ф-8: при выключении поля не валидируются и не перезаписываются, а ранее сохранённые значения остаются и возвращаются в ответе.  
**Было → стало.** Строка 154: «При enabled = false поля roundingStep, savingsAccountId и monthlyLimit не проверяются и не сохраняются» → «2. При enabled = false поля `roundingStep`, `savingsAccountId` и `monthlyLimit` не проверяются и не перезаписываются; ранее сохранённые значения остаются и возвращаются в ответе.»  
**Вопрос владельцу.** Должны ли значения шага, счёта и предела из запроса выключения сохраняться? → [Q-01](#q-01) (варианты ответа)  
*Существенный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-12 / Ф-8](#r-12 "Поведение при выключении и смене шага"), [R-60](#r-60 "При выключении поля не проверяются и не сохраняются"), [R-58](#r-58 "Сохранение изменений и история, ответ 200") · нашли: аналитик, проверка набора*

Что происходит с шагом округления, сберегательным счётом и месячным пределом, которые клиент передаёт при выключении копилки: сохраняются ли они или сохраняется только признак выключения?  
Где: Ф-8, строка 41: «При выключении настройки сохраняются и показываются при повторном включении»; Особые правила, п. 2, строка 154: «При enabled = false поля roundingStep, savingsAccountId и monthlyLimit не проверяются и…»; Логика работы метода, п. 5, строка 150: «при enabled = false — только признак выключения»

- **A** При выключении сохраняется только признак выключения. Значения шага, счёта и предела из тела запроса не сохраняются; ответ и повторное включение показывают ранее сохранённые значения.
- **B** При выключении значения шага, счёта и предела из тела запроса сохраняются без проверки; ответ и повторное включение показывают их.
- **C** При выключении значения шага, счёта и предела из тела запроса сохраняются только если проходят проверки шага 4 логики метода; иначе ответ 422 и выключение не выполняется.

Зачем: Без решения на одном и том же запросе выключения разработка и тест дают разный итог: сохранится ли новый шаг или предел, и будет ли при этом ответ 422 или 200.

**<a id="q-02"></a>Q-02** Кто вправе настраивать копилку по карте · можно ответить позже · кому: ИБ · к [D-02](#d-02)  
Кто может включать и настраивать копилку по дополнительной карте: держатель карты, который вошёл в приложение, или только владелец сберегательного счёта и основной клиент карты?  
Где: Часть B › Общие параметры, строка 134: «Bearer, сессия клиента — держателя карты»; Логика работы метода, п. 3, строка 148: «принадлежит другому клиенту — 404»; Ф-1, строка 34: «открытый в банке на его имя»

- **A** Настраивать может держатель карты по своей сессии; выбираемый сберегательный счёт должен принадлежать этому же клиенту, иначе ответ 422 с кодом `ACCOUNT_NOT_ELIGIBLE`.
- **B** Настраивать может только основной клиент, которому принадлежит карта; для держателя дополнительной карты метод отвечает 404 с сообщением «Карта не найдена».
- **C** Настраивать может только клиент, на имя которого открыт выбираемый сберегательный счёт; держатель без своего счёта получает 422 с кодом `ACCOUNT_NOT_ELIGIBLE`.

Зачем: Без ответа неизвестно, кто проходит проверку прав и какой код возвращается держателю дополнительной карты, поэтому реализация и тест расходятся по доступу и по коду отказа.

**<a id="q-03"></a>Q-03** Повторные частичные возвраты одной покупки · можно ответить позже · кому: Владелец продукта · к [D-03](#d-03)  
Если по одной покупке было несколько частичных возвратов, исключается ли сумма округления из накопленной суммы один раз (при первом возврате) или при каждом возврате пропорционально возвращённой части покупки?  
Где: Ф-6, строка 39: «Возврат (REFUND, полный или частичный) исключает сумму округления исходной покупки из…»; Часть A › Требования к данным, строка 51: «operationId возврата при исключении»; критерий приёмки №9, строка 72: «уменьшилось на 50,00 ₸»

- **A** Сумма округления исключается один раз, при первом возврате (полном или частичном); последующие возвраты по той же покупке накопленную сумму не меняют.
- **B** Каждый возврат исключает долю суммы округления пропорционально возвращённой сумме к сумме покупки, суммарно не больше суммы округления покупки.

Зачем: Данные хранят один `operationId` возврата, поэтому второй частичный возврат либо не исключит сумму, либо исключит её повторно; при этом критерий с возвратом 250,00 из 1 250,00 ₸ уже требует уменьшения на 50,00 ₸ целиком.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
