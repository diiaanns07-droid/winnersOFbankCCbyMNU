#### <a id="d-01"></a>🔴 D-01. Обещано чтение настроек и суммы, метода чтения нет

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ»
- Часть B › Общие параметры, строки 103 и 108: «Сохранение порога. Функциональные требования: чтение порога» · «Request URL | Dev: /alerts/saveLimit . Prod: —»

**Проблема.** Часть A обещает чтение настроек через дочерний документ и показ порога и суммы за месяц, но в части B описан только `saveLimit` (сохранение); метода чтения нет.  
**Сценарий.** Клиент открывает экран «Уведомления»: приложению нечем получить порог, переключатель и сумму за месяц.  
**Последствия.** Обещанную функцию показа нельзя реализовать и протестировать; объём работ недооценён.  
**Как исправить.** Добавить в спецификацию метод чтения (GET без побочных эффектов) со всеми показываемыми полями или убрать обещание чтения из требований.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Добавить метод <уточнить: GET `/alerts/limit?cardId=...`> с ответом {amount, enabled, `monthSpent`} и кодами 200/401/404/500.»  
**Вопрос владельцу.** Какие данные приложение должно получать для экрана и каким методом? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — добавить отдельный метод чтения, возвращающий порог, признак включения и сумму за месяц; B — добавить отдельный метод чтения настроек и отдельный метод чтения суммы за месяц; C — чтение настроек и суммы возвращает сам метод сохранения при запросе без изменения

#### <a id="d-02"></a>🔴 D-02. Критерий приёмки №2 противоречит правилу Ф-2 о месяце

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»

**Проблема.** Ф-2 относит покупку к месяцу по дате совершения, а приёмка (строка 2) относит покупку от 31 января к февралю по дате проведения.  
**Сценарий.** Покупка 31 января 23:58, проведена 1 февраля 00:03, 4 000 ₸: по Ф-2 растёт январь, по приёмке — февраль.  
**Последствия.** Разработчик и тестировщик разойдутся в месячном счётчике, от которого зависит срабатывание push на границе месяцев.  
**Как исправить.** Выбрать одно событие для отнесения к месяцу и привести Ф-2 и критерий приёмки к нему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Месяц покупки определяется по дате <уточнить: совершения или проведения> операции в часовом поясе Алматы (UTC+<уточнить: смещение>).»  
**Вопрос владельцу.** Месяц определяется по дате совершения (авторизации) или по дате проведения покупки? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — по дате совершения (авторизации) покупки по времени Алматы; B — по дате проведения покупки по времени Алматы

#### <a id="d-03"></a>🔴 D-03. Ф-3 и Ф-4 по-разному задают число push за месяц

#### <a id="d-05"></a>🔴 D-05. Ошибка суммы описана и как 200 ERROR, и как 400

- Часть B › Ответ, строка 151: «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный»
- Часть B › Статусы, строка 163: «400. Ответ в случае, если параметры запроса заполнены неверно»
- Часть B › 200. Successful — Created, строки 165 и 171: «200. Successful — Created» · «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Под заголовком 200 приведён ответ result ERROR «Проверьте сумму» (п. 5 логики), а статус 400 — для неверных параметров; правило строки 151 считает 200 успехом, 400 отказом.  
**Сценарий.** amount=999: по примеру HTTP 200 с ERROR (успех по коду), по перечню HTTP 400 (отказ); клиент по коду покажет «сохранено».  
**Последствия.** Клиент сообщит о сохранении порога, которого нет.

#### <a id="d-16"></a>🟠 D-16. Адрес Prod и Swagger метода не заполнены

**Где:** Часть B › Общие параметры, строки 108 и 110: «Prod: —» · «Swagger | —»

**Проблема.** Для Request URL указано «Prod: —», Swagger — прочерк: адрес метода в промышленной среде не задан.

**Последствия.** Работа останавливается на уточнении; в промышленную среду нечего настраивать.  
**Как исправить.** Указать значения или явно написать «не применяется» с причиной.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 108: «Prod: —» → «Prod: <уточнить: значение>; Swagger: <уточнить: значение>»

#### <a id="d-18"></a>🟠 D-18. Ответ при отклонении суммы не возвращает прежнее состояние

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»
- Часть B › Ответ, строка 156: «amount | string | При успехе | Порог в тенге | limit_kzt»

**Проблема.** Шаг 5 требует вернуть прежнее состояние, но amount в ответе только «При успехе», а в примере ERROR amount и enabled нет.  
**Сценарий.** amount=500 при действующем пороге 50000: клиент не получает прежнее значение.  
**Последствия.** Клиент не может показать прежнее значение.  
**Как исправить.** Задать код и тело ответа для отклонения.  
**Предлагаемая формулировка.** «400 {"result":"ERROR","message":"Проверьте сумму","amount":"<прежний порог>","enabled":"<прежний признак>"}»

*Существенный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-21](#r-21 "При отклонении суммы вернуть прежнее состояние, ERROR"), [R-32](#r-32 "Порог в тенге при успехе") · нашли: архитектор*

#### <a id="d-19"></a>🟠 D-19. Типы amount и enabled различаются в запросе и ответе

- Часть B › Query-параметры, строки 143 и 144: «amount | integer | 32 bit | Да | 1 000–1 000 000 | Порог в тенге | limit_kzt» · «enabled | integer»
- Часть B › Ответ, строки 156 и 157: «amount | string | При успехе | Порог в тенге | limit_kzt» · «enabled | string»

**Проблема.** amount и enabled в запросе integer, в ответе string.  
**Сценарий.** Клиент отправляет amount как integer и получает обратно значение типа string; строгий разбор ответа или сравнение отправленного и сохранённого значения не проходит.  
**Последствия.** Разработчики клиента и сервера выберут разные типы; автотесты контракта упадут.  
**Как исправить.** Выбрать один тип для каждого поля и указать его в таблицах запроса и ответа.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «amount | <уточнить: один тип для запроса и ответа>; enabled | <уточнить: один тип для запроса и ответа>»  
*Существенный, блокирует разработку · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-27](#r-27 "Порог в тенге, обязательный"), [R-28](#r-28 "Признак включения 0/1, обязательный"), [R-32](#r-32 "Порог в тенге при успехе"), [R-33](#r-33 "Признак включения «0» или «1»") · нашли: архитектор, правило «контракт API»*

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
