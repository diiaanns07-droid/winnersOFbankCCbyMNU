#### <a id="d-02"></a>🔴 D-02. Отказ по сумме: HTTP 200 с ERROR или HTTP 400

- Логика работы метода, п. 5, строка 121: «5. При отклонении суммы вернуть прежнее состояние и результат ERROR»

**Проблема.** Строка 49 хранит «сумму покупки в тиынах», порог «в тенге» (строка 49, строка 143 `limit_kzt`); Ф-3 сравнивает накопленную сумму с порогом. Правила пересчёта (1 ₸ = 100 тиын) и округления нет.  
**Сценарий.** Покупка 1 500 ₸ = 150000 тиын сравнивается с порогом 50000 тенге без пересчёта: push срабатывает неверно или не срабатывает при 48 500 + 1 500.  
**Последствия.** Разные реализации дадут разные моменты push, и приёмка по критерию 48 500 ₸ + 1 500 ₸ станет спорной.  
**Как исправить.** Явно задать единицу накопленной суммы и правило сравнения с порогом (тиын или тенге, округление).  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Накопленная сумма за месяц хранится в тиынах; порог сравнивается после пересчёта 1 тенге = 100 тиын, округление <уточнить: вниз или до ближайшего>.»  
**Вопрос владельцу.** В какой единице хранить накопленную сумму и какое округление применять?  
*Существенный, блокирует разработку · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-11](#r-11 "Состав сохраняемых данных по карте и месяцу"), [R-22](#r-22 "Порог — целое число тенге, границы включены"), [R-27](#r-27 "Порог в тенге, целое число, обязательный") · нашли: архитектор, правило «единицы измерения»*

#### <a id="d-14"></a>🟠 D-14. Ключ распознавания повтора события процессинга не назван

- Часть A › Требования к данным, строка 49: «идентификатор операции»
- Часть A › Требования к интеграции, строка 52: «Повторная доставка одного события процессинга сохраняет исходный итог»

**Проблема.** Строка 52 обещает, что повторная доставка «сохраняет исходный итог», но не сказано, по какому полю распознаётся повтор; строка 49 хранит «идентификатор операции» без правила использования.  
**Сценарий.** Покупка 1 500 ₸ при 48 500 ₸ приходит дважды: без ключа сумма становится 50 000 и затем 51 500 ₸; повторный push возможен в том же месяце.  
**Последствия.** Лишняя сумма в расходах и повторный push клиенту; банк получает спор по итогу, а разработка не знает, по какому полю проверять повтор.  
**Как исправить.** Назвать ключ дедупликации и правило: повтор с уже учтённым идентификатором операции не меняет сумму и не отправляет push повторно.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Повтор события процессинга с уже учтённым идентификатором операции не меняет накопленную сумму и не отправляет push повторно; ключ — <уточнить: поле идентификатора операции>.»  
*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-11](#r-11 "Состав сохраняемых данных по карте и месяцу"), [R-12](#r-12 "Чтение и сохранение настроек через REST API") · нашли: риски*

- **B** Для чужой карты — 403 с телом {"message":"Доступ запрещён"}, для отсутствующей — 404 с телом {"message":"Карта не найдена"}.

Зачем: Разные коды для чужой карты дают возможность проверить, существует ли карта другого клиента, и тест на эту ветку не может иметь один ожидаемый результат.

**<a id="q-08"></a>Q-08** Push при понижении порога ниже накопленной суммы · можно ответить позже · кому: Владелец продукта · к [D-11](#d-11)  
Отправлять ли push, если клиент понизил порог до значения, которое уже ниже накопленной суммы? В правиле о переходе снизу вверх push при понижении не описан.  
Где: Ф-3, строка 39: «Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше»; Ф-4, строка 40: «Если она ниже нового порога, следующее достижение вызывает push»

- **A** Нет: push при понижении порога не отправляется; достижение засчитывается только при переходе суммы снизу вверх через порог.
- **B** Да: push отправляется сразу при понижении порога, если накопленная сумма уже равна новому порогу или выше и push за месяц ещё не отправлялся.

Зачем: Без ответа при понижении порога одна команда отправит push, а другая — нет, и тест на этот случай невозможно написать.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
