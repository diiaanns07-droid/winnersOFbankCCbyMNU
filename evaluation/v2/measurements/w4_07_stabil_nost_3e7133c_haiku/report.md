#### <a id="d-01"></a>🔴 D-01. Операция чтения порога и суммы за месяц не описана

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить»»
- Часть A › Требования к интеграции, строка 52: «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API»»
- Часть B › Общие параметры, строки 103 и 108: «Description | Сохранение порога. Функциональные требования: чтение порога» · «Dev: /alerts/saveLimit»
- Логика работы метода, п. 4, строка 120: «4. Заменить настройку и вернуть результат сохранения»

**Проблема.** Документ обещает чтение порога (строка 52, строка 103) и показ суммы за месяц (строка 29), но метод описан только для сохранения (строка 108). Логика шагов 1–5 (строки 117–121) не содержит чтения.  
**Сценарий.** Клиент открывает «Карты → Расходы → Уведомления». Приложению нужны порог 50 000 ₸ и сумма за месяц 48 500 ₸; единственный метод `saveLimit` заменяет настройку и не возвращает сумму за месяц.  
**Последствия.** Экран не может показать сохранённый порог и месячную сумму без записи; тест чтения не имеет операции для проверки.  
**Как исправить.** Описать операцию чтения настроек карты с полями ответа порога, признака и суммы за месяц, либо убрать обещание чтения из строки 52 и описание «чтение порога» из строки 103.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «GET <уточнить: путь операции чтения>?cardId=<уточнить: идентификатор карты> → 200 {"result":"OK","amount":"<уточнить: порог в тенге>","enabled":"0 или 1","`monthSum`":"<уточнить: имя поля суммы за месяц>"}»  
**Вопрос владельцу.** Какая операция отдаёт приложению текущий порог и сумму расходов за месяц?  
*Критичный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-12](#r-12 "Чтение и сохранение настроек через REST API"), [R-16](#r-16 "Метод сохранения порога: GET, адрес, авторизация"), [R-20](#r-20 "Замена настройки и возврат результата сохранения"), [R-03](#r-03 "Экран расходов: переключатель, порог, сумма, кнопка") · нашли: архитектор, проверка набора, правило «обещанные операции»*

#### <a id="d-02"></a>🔴 D-02. Второй push в месяце: Ф-3 запрещает, Ф-4 разрешает

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 (строка 39) допускает максимум один push за календарный месяц, а Ф-4 (строка 40) требует push при следующем достижении порога независимо от истории. Для смены порога в одном месяце правила расходятся.  
**Сценарий.** Порог 50 000, push отправлен в марте; порог повышен до 100 000, накоплено 50 000, покупка 50 000 в марте. По Ф-3 второго push нет, по Ф-4 — есть.  
**Последствия.** Разные ответы на приёмке: клиент получит второй push или нет.  
**Как исправить.** Явно указать, снимает ли Ф-4 лимит одного push за месяц.  
**Вопрос владельцу.** Что верно: «второго push в марте нет, лимит один в месяц» (как в Ф-3) или «push отправляется независимо от прошлого push» (как в Ф-4)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — нет: за календарный месяц уходит не более одного push, смена порога не даёт нового push…; B — да: при каждом переходе накопленной суммы через новый порог уходит push, даже если push в…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Push при достижении порога, раз в месяц"), [R-08 / Ф-4](#r-08 "Накопленная сумма при изменении порога") · нашли: проверка набора*

#### <a id="d-03"></a>🔴 D-03. Месяц покупки: дата совершения или дата проведения

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Ф-2 (строка 38) относит покупку к месяцу даты совершения, а критерий приёмки (строка 64) относит покупку 31 января, проведённую 1 февраля, к февралю. Одно и то же событие даёт разный месяц.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03 (Алматы). По Ф-2 январский счётчик +4 000 ₸; по критерию февральский счётчик +4 000 ₸.  
**Последствия.** Разработчик выберет одно событие, тестировщик проверит другое, и приёмка по критерию провалится на реализации по Ф-2 (или наоборот) при каждой покупке на стыке месяцев.  
**Как исправить.** Выбрать одно событие для отнесения покупки к месяцу и привести Ф-2 и критерий приёмки к нему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «Месяц определяется по дате совершения покупки в Алматы» → «Ф-2. Месяц определяется по дате <уточнить: дата совершения покупки или дата проведения покупки> в Алматы. В расходы входят проведённые покупки.»  
**Вопрос владельцу.** По какой дате покупка относится к месяцу: по дате совершения или по дате проведения (в часовом поясе Алматы)?

#### <a id="d-04"></a>🔴 D-04. «Проведённая» покупка: авторизация или клиринг не определены

#### <a id="d-16"></a>🟠 D-16. Тиыны и тенге без правила пересчёта и округления

**<a id="q-01"></a>Q-01** Повторный push в одном месяце · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)

Где: Ф-1, строка 37: «По умолчанию уведомление выключено»; Логика работы метода, п. 3, строка 119: «Проверить сумму и переключатель»

- **A** Покупки учитываются всегда; при включении push не отправляется, пока накопленная сумма не перейдёт через порог в следующей покупке
- **B** Покупки учитываются всегда; при включении, если накопленная сумма уже не ниже порога, push отправляется один раз за месяц
- **C** Покупки при выключенном переключателе не учитываются; при включении сумма начинает считаться с покупок после включения

Зачем: Клиент, включивший уведомление после превышения порога, получит push или не получит его в зависимости от реализации.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
