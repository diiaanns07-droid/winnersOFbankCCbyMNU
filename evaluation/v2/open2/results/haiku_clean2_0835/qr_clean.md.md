#### <a id="d-01"></a>🟠 D-01. Путь вызова перевода: последовательность минует сервис QR-кодов, архитектура и API требуют его

**Требования:** [R-02](#r-02 "Участники архитектуры: приложения, сервис QR-кодов, переводов, антифрод"), [R-12](#r-12 "Последовательность взаимодействий компонентов при переводе"), [R-15](#r-15 "Приложения работают с QR-кодом через дочерний REST API"), [R-32](#r-32 "Схема вызова метода: контроллер, сервисы, ответ приложению") · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие · **Блокирует:** разработку · **Нашли:** архитектор, проверка набора

- Часть A › Архитектура решения, строка 25: «Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод»
- Часть A › Sequence Diagram, строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду»
- Часть B › Схема, строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов»

**Проблема.** строка 45: «Приложение отправителя → сервис переводов: выполнить перевод по QR-коду» задаёт прямой вызов. строка 25: «Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод» и строка 136: «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов» задают вызов через сервис QR-кодов.  
**Сценарий.** Команда переводов реализует прямой вызов по строке 45, а команда QR-сервиса ждёт проверку QR в своём сервисе по строке 136. Перевод по QR-коду с истёкшим сроком проходит в сервис переводов без проверки.  
**Последствия.** Проверка QR (срок, отмена, оплата) может быть обойдена или выполнена дважды; интеграционные тесты строятся по разным маршрутам.  
**Что исправить.** Заменить строка 45 на «Приложение отправителя → QrTransferController → сервис QR-кодов → сервис переводов: выполнить перевод по QR-коду» и привести строка 25 и строка 136 к этому же маршруту.  
**Было → стало.** Строка 25: «Приложение отправителя → сервис QR-кодов → сервис переводов → антифрод» → «Приложение отправителя → QrTransferController (сервис переводов) → сервис QR-кодов (проверка QR) → сервис переводов (антифрод, списание, зачисление) — либо прямой вызов; <уточнить: какой путь выбран>.»  
**Вопрос владельцу.** Вызывает ли приложение сервис переводов напрямую или через QrTransferController и сервис QR-кодов?

#### <a id="d-02"></a>🟠 D-02. Активность и валюта карты получателя не проверяются при переводе (п. 3 логики)

**Требования:** [R-06 / Ф-1](#r-06 "Получатель с активной картой KZT, сумма от 100 до 500 000") (Получатель с активной картой KZT, сумма от 100…), [R-24](#r-24 "Поиск QR по qrId, коды 404 и 410 для карты получателя") (Поиск QR по `qrId`, коды 404 и 410 для карты…), [R-48](#r-48 "410: срок истёк, QR отменён, оплачен или карта получателя недоступна") (410: срок истёк, QR отменён, оплачен или карта…) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** неполнота · **Блокирует:** разработку · **Нашли:** риски

- Часть A › Функциональные требования, строка 37: «Получатель — клиент банка с активной картой KZT»
- Часть B › Логика работы метода, строка 123: «Если карта зачисления получателя закрыта или заблокирована, вернуть 410»
- Часть B › Статусы, строка 171: «или карта получателя недоступна»

**Проблема.** строка 37: «Получатель — клиент банка с активной картой KZT» — условие Ф-1. строка 123: «Если карта зачисления получателя закрыта или заблокирована, вернуть 410» проверяет только закрытие и блокировку. строка 171 повторяет «или карта получателя недоступна».  
**Сценарий.** QR создан на карту в тенге; затем карта переведена в неактивное состояние или сменила валюту. По строке 123 проверка проходит, перевод возвращает DONE. По строке 37 перевод должен быть отклонён.  
**Последствия.** Зачисление на неактивную или не тенговую карту либо отказ клиенту, не соответствующий Ф-1.  
**Что исправить.** В строке 123 заменить на «Если карта зачисления получателя не активна, закрыта, заблокирована или открыта не в тенге, вернуть 410»; в строке 37 уточнить, что условие проверяется на момент перевода.  
**Было → стало.** Строка 123: «Если карта зачисления получателя закрыта или заблокирована, вернуть 410» → «3. Если карта зачисления получателя не активна, закрыта, заблокирована или не в KZT на момент перевода, вернуть 410.»

#### <a id="d-03"></a>🟠 D-03. Статусная модель QR не содержит состояния «в обработке» и возврата после REJECTED

**Требования:** [R-07 / Ф-2](#r-07 "Срок QR-кода 15 минут, однократная или многократная оплата") (Срок QR-кода 15 минут, однократная или…), [R-10 / Ф-5](#r-10 "Отмена QR-кода получателем и результат после отмены") (Отмена QR-кода получателем и результат после…), [R-14](#r-14 "QR-код без реквизитов; состав хранимых данных и статусы") (QR-код без реквизитов; состав хранимых данных и…) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** отсутствует элемент · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, архитектор

- Часть A › Функциональные требования, строка 38: «если перевод отклонён (REJECTED), QR-код снова можно оплатить до конца срока действия»
- Часть A › Функциональные требования, строка 41: «по нему нет перевода в обработке»
- Часть A › Требования к данным, строка 51: «статус (активен, оплачен, отменён, истёк)»
- Часть B › Методы сервиса QR-кодов, строка 212: «по QR-коду есть перевод в обработке, QR-код уже отменён или срок истёк»

**Проблема.** строка 51 перечисляет «статус (активен, оплачен, отменён, истёк)» без состояния «в обработке», хотя строка 41 («по нему нет перевода в обработке») и строка 212 («по QR-коду есть перевод в обработке») его используют. строка 38 описывает возврат после REJECTED в «снова можно оплатить», но переход в статус не задан. Термин «считается оплаченным» (строка 38) тоже не совпадает со статусом.  
**Сценарий.** Перевод по QR с суммой отклонён антифродом (REJECTED). Статус в хранилище остаётся «оплачен», и повторная оплата блокируется. Отмена получателем при переводе в обработке проверяется по признаку, которого в модели нет.  
**Последствия.** Клиент не может повторить оплату после отказа антифрода; отмена и оплата дают разный результат при одном состоянии.  
**Что исправить.** В строке 51 заменить список на «статус (активен, в обработке, оплачен, отменён, истёк)»; описать переходы: активен → в обработке при принятии перевода; в обработке → оплачен при DONE; в обработке → активен при REJECTED (только QR с суммой). Использовать эти названия в строке 38 и строка 41.  
**Было → стало.** Строка 51: «статус (активен, оплачен, отменён, истёк)» → «Статусы QR-кода: активен, в обработке, оплачен, отменён, истёк. Переход «в обработке» → «активен» при REJECTED; «в обработке» → «оплачен» при DONE.»

#### <a id="d-04"></a>🟠 D-04. Повтор `requestId` после ответа 500 имеет два исхода; область уникальности ключа не задана

**Требования:** [R-29](#r-29 "Атомарное списание и зачисление, при сбое ответ 500"), [R-31](#r-31 "Повторный запрос с тем же requestId возвращает первый результат"), [R-37](#r-37 "Параметр requestId: UUID, ключ идемпотентности, обязательный"), [R-49](#r-49 "500: внутренняя ошибка сервера") · **Критерий:** Однозначность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · **Вид:** неоднозначность · **Блокирует:** разработку и тестирование · **Нашли:** тестировщик, риски

- Часть B › Логика работы метода, строка 128: «при сбое не проводится ни одна из них, ответ 500»
- Часть B › Особые правила, строка 132: «Повторный запрос с тем же requestId возвращает результат первого запроса»
- Часть B › Request body, строка 152: «Ключ идемпотентности»

**Проблема.** строка 132: «Повторный запрос с тем же `requestId` возвращает результат первого запроса»; строка 128: «при сбое не проводится ни одна из них, ответ 500». - Часть B › Особые правила, строка 132: «Повторный запрос с тем же requestId возвращает результат первого запроса»
- Часть B › Ответ, строка 155: «Если результат 400, 401, 404, 410 или 500 — неуспешный»

**Проблема.** Строки строки 65–69 покрывают только сценарии QR. Не покрыты: строка 122 «если нет, вернуть 400» (карта отправителя), строка 123 «вернуть 410» (закрытая карта получателя), строка 125 граница суммы без суммы в QR, строка 132 «повторный запрос с тем же `requestId`», строка 155 ответы 401 и 404.  
**Сценарий.** Сумма 99 ₸ без суммы в QR или заблокированная карта отправителя: приёмке нечем подтвердить 400, и реализация может вернуть другой код.  
**Последствия.** Ветки ошибок и идемпотентности выпадают из приёмки; дефекты в них не будут найдены.  
**Что исправить.** Добавить строки приёмки: сумма 99 ₸ без суммы в QR → 400; карта отправителя заблокирована → 400; карта получателя закрыта → 410; повтор `requestId` → тот же ответ; неизвестный `qrId` → 404; отказ антифрода → 200 REJECTED.  
**Было → стало.** Строка 123: «Если карта зачисления получателя закрыта или заблокирована, вернуть 410» → «Добавить строки: amount=99 без суммы в QR → 400; amount=500001 → 400; карта списания заблокирована → 400; карта получателя закрыта → 410; повтор `requestId` после DONE → тот же ответ без второго перевода.»

#### <a id="d-13"></a>🟠 D-13. Карта другого клиента: в методе 1 код 400, в методе 2 — 404

- Часть B › Логика работы метода, строка 122: «Проверить, что карта списания принадлежит отправителю, активна и открыта в тенге; если нет, вернуть 400»

**Проблема.** строка 122: карта списания «принадлежит отправителю, активна и открыта в тенге; если нет, вернуть 400». строка 210: «404 — карта не найдена или принадлежит другому клиенту».

- **A** Без ограничения числа оплат в пределах срока действия, общий лимит суммы не задан
- **B** Не более 10 оплат на один QR-код без суммы, общий лимит суммы не задан
- **C** Не более 10 оплат и суммарно не более 50 000 ₸ на один QR-код без суммы

Зачем: Слово «несколько» не задаёт число. Пять оплат по 5 000 ₸ либо проходят все, либо шестая отклоняется; тест на шестую оплату нельзя написать без правила.

**<a id="q-04"></a>Q-04** Срок хранения requestId для идемпотентности · не блокирует · кому: Архитектор · к [D-11](#d-11)  
Сколько времени хранится связка `requestId` и результата перевода, и что возвращается на повтор после истечения этого срока?  
Где: строка 54 «Повторный запрос перевода с тем же requestId не создаёт второй перевод»; строка 38 «QR-код действует 15 минут с момента создания»

- **A** Связка хранится 15 минут, то есть до конца срока действия QR-кода; повтор после этого срока возвращает 410
- **B** Связка хранится 48 часов с момента первого запроса; повтор после этого срока возвращает 400
- **C** Связка хранится 7 дней с момента первого запроса; повтор после этого срока выполняется как новый запрос

Зачем: Повтор через 20 минут после истечения QR сейчас может вернуть сохранённый DONE или создать второй перевод по тому же QR. Срок хранения определяет таблицу и тесты идемпотентности.

**<a id="q-05"></a>Q-05** Источник маскированного имени для push · не блокирует · кому: Архитектор · к [D-09](#d-09)  
Откуда берётся полное имя клиента для маскирования «Имя Ф.» в push и в ответе перевода, и хранится ли маскированное имя вместе с QR-кодом?  
Где: строка 42 «с суммой перевода и маскированным именем второй стороны»; строка 162 «Маскированное имя получателя»; строка 51 «Хранить идентификатор QR-кода, идентификатор клиента-получателя, карту зачисления, сумму…»

- **A** Имя берётся из профиля клиента по его идентификатору в момент перевода, маскируется по правилу «Имя Ф.» и в QR-код не сохраняется
- **B** Маскированное имя сохраняется в QR-коде при создании и используется без повторного запроса профиля

Зачем: Без источника сервис уведомлений либо получит полное ФИО без маскирования, либо отправит push без имени. Это разные исходы при одном и том же зачислении.

**<a id="q-06"></a>Q-06** Состав события «перевод зачислен» · не блокирует · кому: Архитектор · к [D-08](#d-08)  
Какие поля передаёт сервис переводов в сервис уведомлений в событии «перевод зачислен»?  
Где: строка 45 «Сервис переводов → сервис уведомлений: перевод зачислен»; строка 42 «получатель и отправитель получают push с суммой перевода»

- **A** `transferId`, `qrId`, идентификатор отправителя, идентификатор получателя, сумма в тенге, маскированные имена обеих сторон, время зачисления
- **B** `transferId`, `qrId`, идентификатор получателя, сумма в тенге, время зачисления; имена сервис уведомлений получает сам по идентификаторам

Зачем: Событие без полей не даёт сервису уведомлений ни суммы, ни идентификаторов сторон. Push с суммой и именем нельзя сформировать, а контракт между командами не совпадает.

**<a id="q-07"></a>Q-07** Код ответа при чужой карте · не блокирует · кому: Архитектор · к [D-13](#d-13)  
Какой код возвращает метод перевода и метод создания QR-кода, если карта (списания или зачисления) принадлежит другому клиенту: 400 или 404?  
Где: строка 122 «если нет, вернуть 400»; строка 210 «404 — карта не найдена или принадлежит другому клиенту»

- **A** 400 для чужой карты в обоих методах, 404 только для несуществующей карты
- **B** 404 для чужой карты в обоих методах, так как не раскрывать существование карты другого клиента

Зачем: Клиентское приложение разбирает 400 и 404 по-разному. Для одного и того же входа (чужая карта) методы дают разный код, и тесты ожидают разные значения.

**<a id="q-08"></a>Q-08** Поля тела ответа при ошибках · не блокирует · кому: Архитектор · к [D-14](#d-14)  
Содержат ли тела ошибок 400, 401, 404, 410 и 500 поле status или только message?  
Где: строка 159 «status | string | DONE / REJECTED | Результат перевода | status»; строка 196 «{"message":"QR-код недействителен"}»

- **A** Тело ошибки содержит только message; поля status, `transferId`, amount, `recipientName` есть только в ответе 200
- **B** Тело ошибки содержит status со значением ERROR и message; остальные поля есть только в ответе 200

Зачем: Клиент разбирает ответ по полю status. При 410 поля нет, и клиент не может отличить отказ от успеха. Два варианта дают разный код разбора ответа.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
