## <a id="s3"></a>3. Проверка каждого требования

### 3.1. Матрица: требование × нарушенный критерий

Столбцы: Од — однозначность; Пл — полнота требования; Ос — осуществимость; Ш — соответствие шаблону; Нб — критерии набора (раздел 4). #### <a id="d-01"></a>🔴 D-01. Выбор карты выплаты: нет операции, которая отдаёт список карт клиента

**Требования:** [R-03](#r-03 "Экран «Проценты»: ставка, проценты, переключатель, выбор карты, кнопки"), [R-14](#r-14 "Приложение получает ставку, проценты, историю и сохраняет способ выплаты"), [R-19](#r-19 "Метод 1 PUT изменения способа выплаты: адрес, авторизация, контроллер, пример"), [R-32](#r-32 "Поле cardId: 1–64 символов, обязательно для CARD, карта в тенге") · **Критерий:** Полнота набора (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.3) · **Вид:** отсутствует элемент · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, проверка набора

- Часть A › Дизайн процесса UI, строка 28: «выбор карты для выплаты (виден при выборе «На карту»)»
- Часть A › Требования к интеграции, строка 53: «Приложение получает ставку, проценты за текущий месяц и историю начислений и сохраняет способ выплаты»
- Часть B, строка 99: «Метод 1 — изменение способа выплаты; методы 2 и 3 (условия и проценты, история начислений) описаны в конце документа»
- Часть B › Методы чтения, строка 201: «payoutCardId":null»

**Проблема.** Экран обязан дать выбрать карту для выплаты (строка 28), но методы 1–3 не возвращают список карт клиента в тенге: метод 2 отдаёт только `payoutCardId` (строка 201), метод 1 не отдаёт карт (строка 172).  
**Сценарий.** Клиент открывает «Проценты», выбирает «На карту» и должен выбрать карту. Приложение не получает список карт и не знает `cardId` для PUT `/savings/{`accountId`}/payout-mode` (строка 111).  
**Последствия.** Режим «На карту» нельзя задать из приложения; основная функция Ф-1 и приёмка [R-18](#r-18) не реализуются и не тестируются.  
**Что исправить.** Добавить метод «GET `/savings/{`accountId`}/payout-cards`»: список карт клиента в тенге со статусом активна и открыта (поля `cardId`, маска номера, статус); <уточнить: состав полей и формат ответа>.  
**Было → стало.** Строка 99: «Метод 1 — изменение способа выплаты; методы 2 и 3 (условия и проценты, история начислений) описаны в конце документа» → «GET `/savings/{`accountId`}/payout-cards` — список карт клиента в тенге: массив {`cardId`: string 1–64, статус: <уточнить: набор значений статуса>}; 200 и условия ошибок — <уточнить>.»

#### <a id="d-02"></a>🔴 D-02. Время выплаты 31-го числа не задано: выплата может пройти до начисления за этот день

**Требования:** [R-04](#r-04 "Процесс начисления и выплаты процентов по BPMN") (Процесс начисления и выплаты процентов по BPMN), [R-06 / Ф-2](#r-06 "Ежедневное начисление по 14 % годовых на остаток на 23:59:59 Астаны") (Ежедневное начисление по 14 % годовых на…), [R-01](#r-01 "Клиент выбирает капитализацию или выплату на карту, видит проценты за месяц") (Клиент выбирает капитализацию или выплату на…) · **Критерий:** Однозначность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · **Вид:** неоднозначность · **Блокирует:** разработку и тестирование · **Нашли:** риски

- Часть A › BPMN схема процесса, строка 33: «Ежедневное начисление процентов → последний день месяца»
- Часть A › Функциональные требования, строка 37: «Проценты, начисленные за месяц, выплачиваются в последний календарный день месяца»
- Часть A › Критерии приемки, строка 64: «Наступило 31 марта»

**Проблема.** Выплата привязана к «последнему календарному дню месяца» без времени (строка 37, строка 33), а начисление за день завершается в 23:59:59 по Астане (строка 37); выплата раньше этого момента исключает 31-е число.  
**Сценарий.** Выплата запускается в 09:00 31 марта: начисление за 31-е не входит, сумма около 11 506,80 ₸. Выплата после 23:59:59: 11 890,36 ₸, как в критерии приёмки (строка 64). Документ допускает оба исхода.  
**Последствия.** Клиент недополучает около 383,56 ₸ при остатке 1 000 000 ₸, либо выплата расходится с критерием приёмки.  
**Что исправить.** Уточнить в Ф-2: «Выплата процентов за месяц выполняется <уточнить: время, например 00:00 следующего дня> по времени Астаны, после начисления за последний день месяца».  
**Было → стало.** Строка 37: «Проценты, начисленные за месяц, выплачиваются в последний календарный день месяца» → «Ф-2: Проценты, начисленные за месяц, выплачиваются не раньше 00:00:00 первого дня следующего месяца по UTC+5 и включают начисление за последний календарный день месяца.»

**<a id="q-02"></a>Q-02** Время выплаты процентов за месяц · ⛔ блокирует · кому: Владелец продукта · к [D-02](#d-02)

- **A** Выплата выполняется в 00:00 первого дня следующего месяца по времени Астаны, после начисления за последний день месяца; начисление за 31-е число входит в выплату

**<a id="q-03"></a>Q-03** Повтор выбора «На карту» при недоступной карте · ⛔ блокирует · кому: Владелец продукта · к [D-03](#d-03)

**<a id="q-04"></a>Q-04** Выплаты при закрытии счёта по способу · не блокирует · кому: Владелец продукта · к [D-04](#d-04), [D-05](#d-05), [D-06](#d-06)

**<a id="q-05"></a>Q-05** День закрытия счёта в периоде начисления · не блокирует · кому: Владелец продукта · к [D-08](#d-08)

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
