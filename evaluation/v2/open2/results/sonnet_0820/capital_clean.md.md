**Что исправить.** Определить «выбранный» как ожидающий способ (`nextMode`). Запрос, совпадающий с `nextMode` и `cardId`, — повтор; иной запрос заменяет `nextMode`, в том числе отменяет смену на CAPITALIZATION.  
**Вопрос владельцу.** Считать повтором совпадение с текущим способом или с ожидающим способом следующего месяца? Смена карты при том же CARD — это повтор или изменение? → [Q-06](#q-06)

- **A** Событие содержит идентификатор счёта, сумму, фактический способ, код причины замены на капитализацию и маску карты; фактический способ и код причины хранятся вместе с выплатой по месяцам
- **B** Событие содержит идентификатор счёта, сумму и фактический способ; причина замены в push не показывается, текст формирует сервис уведомлений
- **C** Событие содержит только идентификатор выплаты, остальное сервис уведомлений читает из хранилища депозитного модуля

Зачем: Без состава события сервис уведомлений не сформирует push с фактическим способом и причиной, тест push при заблокированной карте написать нельзя.

**<a id="q-06"></a>Q-06** Смысл «уже выбранного способа» при повторных запросах · ⛔ блокирует · кому: Аналитик · к [D-06](#d-06)  
С чем сравнивается запрос смены способа при определении «повторной установки»: с текущим способом месяца или с ожидающим способом следующего месяца, и считается ли смена карты при том же CARD изменением?  
Где: строка 126 «Повторная установка уже выбранного способа не считается ошибкой: возвращается 200 с…»; строка 127 «Если клиент несколько раз сменил способ в течение месяца, со следующего месяца действует…»

- **A** Сравнение с ожидающим способом (`nextMode`) и `cardId`: совпадение — повтор, 200 без изменений; иной запрос заменяет ожидающий способ, в том числе отменяет смену возвратом к CAPITALIZATION; смена карты при CARD — изменение
- **B** Сравнение с текущим способом месяца: совпадение — повтор, 200 без изменений, ожидающая смена не отменяется; отмена отложенной смены невозможна
- **C** Сравнение по полю mode с ожидающим способом без учёта `cardId`: смена карты при том же CARD считается повтором и не сохраняется

Зачем: Для последовательности CAPITALIZATION → CARD → CAPITALIZATION в одном месяце команды получат разные `nextMode`, и тест не будет однозначным.

**<a id="q-07"></a>Q-07** Учёт текущего дня в accruedInterest · не блокирует · кому: Владелец продукта · к [D-07](#d-07)  
Входят ли в поле начисленных процентов за текущий месяц проценты за день запроса, если остаток для начисления фиксируется только в 23:59:59?  
Где: строка 160 «Проценты, начисленные за текущий месяц по Ф-2 на дату запроса, ₸»; строка 37 «Остаток на конец дня — остаток счёта на 23:59:59 по времени Астаны (UTC+5).»

- **A** Входят только завершённые дни до дня запроса: запрос 15 марта при 1 000 000 ₸ даёт 14 дней, 5 369,84 ₸
- **B** Входит и текущий день по остатку на момент запроса: запрос 15 марта даёт 15 дней, 5 753,40 ₸

Зачем: Тест поля и пример ответа дадут 5 369,84 ₸ или 5 753,40 ₸, клиент увидит разные суммы на экране.

**<a id="q-08"></a>Q-08** Метод смены способа для счёта не в тенге · не блокирует · кому: Владелец продукта · к [D-08](#d-08)  
Что должен вернуть метод изменения способа выплаты, если счёт открыт и принадлежит клиенту, но ведётся не в тенге?  
Где: строка 36 «Владелец накопительного счёта в тенге выбирает способ выплаты процентов»; строка 120 «Проверить, что накопительный счёт принадлежит клиенту и открыт.»

- **A** Вернуть 400 с сообщением «Некорректный запрос»; в шаг проверки счёта добавить условие «валюта счёта — KZT»
- **B** Вернуть 404 с сообщением «Счёт или карта не найдены», как для счёта, недоступного для операции
- **C** Разрешить выбор способа для счёта в любой валюте: ограничение «в тенге» из Ф-1 убрать, выплату на карту допускать только для KZT

Зачем: Без ответа для счёта в долларах метод сохранит настройку и вернёт 200, а тест на недопустимую валюту написать нельзя.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
