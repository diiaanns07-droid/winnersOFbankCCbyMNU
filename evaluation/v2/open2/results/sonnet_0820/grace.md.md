#### <a id="d-01"></a>🔴 D-01. Включение и выключение напоминания обещано через REST API, но метода записи нет

**Требования:** [R-03](#r-03 "Блок «Льготный период» на экране кредитной карты и его состав"), [R-08 / Ф-4](#r-08 "Push-напоминание за 3 дня при включённом переключателе"), [R-13](#r-13 "Взаимодействие через дочерний REST API и одно напоминание на карту"), [R-18](#r-18 "Общие параметры метода GET получения сведений о льготном периоде"), [R-38](#r-38 "Поле reminderEnabled: признак включения напоминания") · **Критерий:** Полнота набора (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.3) · **Вид:** отсутствует элемент · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, проверка набора, риски

- Часть A › Дизайн процесса UI, строка 28: «переключатель «Напоминать о платеже»
- Часть A › Требования к интеграции, строка 52: «Приложение получает сведения о льготном периоде и включает или выключает напоминание через дочерний документ «Льготный период по кредитной карте — REST API»
- Часть B › Общие параметры, строка 104: «Description | Получение сведений о льготном периоде по кредитной карте»
- Часть B › Общие параметры, строка 105: «REST type | GET»

**Проблема.** Раздел интеграции (строка 52) обещает включение и выключение напоминания через дочерний документ, но там описан только GET чтения (строка 105). Метода изменения `reminderEnabled` нет.  
**Сценарий.** Клиент выключает переключатель «Напоминать о платеже»: приложению нечего вызывать, признак не сохраняется, push по Ф-4 приходит всё равно. Разработчик может сделать изменение через GET.

**Что исправить.** Добавить в часть B метод изменения настройки (например PUT/PATCH `/cards/{`cardId`}/grace/reminder` с телом {`reminderEnabled`}) с кодами ответов, проверкой владельца карты и описанием хранения признака.

#### <a id="d-02"></a>🔴 D-02. Некредитная карта: п. 6 логики даёт 200 `NOT_APPLICABLE`, перечень кодов — 422

**Требования:** [R-24](#r-24 "Для некредитной карты вернуть 200 с NOT_APPLICABLE"), [R-42](#r-42 "Код 422: карта не является кредитной"), [R-31](#r-31 "Код 200 успешный, коды 401, 404, 422, 500 неуспешные"), [R-20](#r-20 "Проверить принадлежность карты клиенту и её кредитность") · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, тестировщик, архитектор

- Часть B › Логика работы метода, строка 123: «Если карта не кредитная, вернуть 200 с status = NOT_APPLICABLE»
- Часть B › Ответ, строка 150: «Если результат 200 — успешный. Если результат 401, 404, 422 или 500 — неуспешный»
- Часть B › Статусы, строка 167: «422. Ответ в случае, если карта не является кредитной»

**Проблема.** Логика метода (строка 123) требует вернуть 200 со status = `NOT_APPLICABLE`, а перечень статусов (строка 167) и пример — 422. При этом строка 150 считает 200 успехом, а 422 отказом. Кроме того, п. 2 логики уже проверяет кредитность.  
**Сценарий.** GET `/cards/dc-1/grace` для дебетовой карты клиента: по п. 6 приходит 200 с `NOT_APPLICABLE`, по таблице статусов — 422 с сообщением.  
**Последствия.** Приложение и тесты ожидают разные ответы; одна из веток не будет обработана, приёмка превратится в спор.  
**Что исправить.** Оставить один вариант (например, 422 для некредитной карты), удалить п. 6 либо код 422 и значение `NOT_APPLICABLE` из status; <уточнить: какой вариант выбирает бизнес>.  
**Вопрос владельцу.** Для некредитной карты возвращать 200 `NOT_APPLICABLE` или 422? → [Q-02](#q-02)

Какая дата определяет расчётный период покупки и начало начисления процентов при неполном погашении: авторизация или проведение (отражение на счёте)?  
Где: строка 37 «Покупка относится к расчётному периоду по дате её отражения на счёте карты»; строка 38 «проценты начисляются на всю задолженность по покупкам расчётного периода с даты каждой…»

- **A** Одна дата — проведение (отражение на счёте): по ней определяется период и с неё начисляются проценты
- **B** Период определяется по проведению, а проценты начисляются с даты авторизации
- **C** Одна дата — авторизация: по ней определяется период и с неё начисляются проценты

Зачем: Покупка 28 февраля, проведённая 2 марта, попадёт в разные периоды и получит разную дату начала процентов.

**<a id="q-09"></a>Q-09** Передача напоминания в сервис уведомлений · не блокирует · кому: Архитектор · к [D-13](#d-13)  
Как и когда кредитный модуль передаёт напоминание в сервис уведомлений: что запускает передачу, формат сообщения, защита от дубля и отмена после оплаты?  
Где: строка 43 «Кредитный модуль → сервис уведомлений: передать дату окончания и оставшуюся сумму для…»; строка 52 «Кредитный модуль передаёт в сервис уведомлений одно напоминание на карту за платёжный…»

- **A** Ежедневное задание кредитного модуля в 09:00 по Астане за 3 календарных дня до окончания; сообщение содержит идентификатор карты, дату окончания, остаток в тиынах; ключ дедупликации — карта плюс платёжный период; признак отправки хранится; остаток перепроверяется перед передачей
- **B** Кредитный модуль при формировании выписки передаёт запланированное напоминание на дату окончания минус 3 дня; платёж, погашающий сумму полностью, отменяет его отдельным сообщением; ключ дедупликации — карта плюс платёжный период

Зачем: При повторе задания или оплате за час до отправки клиент получит лишний или ложный push, а тест «один push» нельзя проверить.

**<a id="q-10"></a>Q-10** Числовые нефункциональные требования · не блокирует · кому: Архитектор · к [D-14](#d-14)  
Какие числа задать для времени отклика метода, допустимого отставания данных от платежей и окна отправки push?  
Где: строка 46 «Сведения о льготном периоде отображаются быстро и всегда актуальны»

- **A** Отклик не более 2 с у 95% запросов; отставание данных не более 1 минуты от проведения платежа; push отправляется 22-го числа с 09:00 до 20:00 по Астане
- **B** Отклик не более 1 с у 99% запросов; отставание данных не более 5 минут; push отправляется 22-го числа с 10:00 до 18:00 по Астане

Зачем: Без чисел «быстро», «актуально», «своевременно» нельзя проверить нагрузочным или приёмочным тестом, а приёмка превращается в спор.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
