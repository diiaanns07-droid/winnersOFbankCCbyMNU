#### <a id="d-01"></a>🔴 D-01. Критерий приёмки 1 противоречит Ф-3: полная оплата до 25-го не даёт процентов

**Требования:** [R-14](#r-14 "Полная оплата до 25-го числа: проценты за покупки февраля не начисляются") (Полная оплата до 25-го числа: проценты за…), [R-07 / Ф-3](#r-07 "Начисление процентов при полном или частичном погашении в срок") (Начисление процентов при полном или частичном…), [R-05 / Ф-1](#r-05 "Льготный период 55 дней, расчётный период и даты выписки и платежа") (Льготный период 55 дней, расчётный период и…) · **Критерий:** Корректность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** тестировщик

- Часть A › Функциональные требования, строка 36: «платёжный период заканчивается 25-го числа того же месяца»
- Часть A › Функциональные требования, строка 38: «проценты по покупкам расчётного периода не начисляются»
- Часть A › Критерии приемки, строка 63: «Проценты за покупки февраля начислены»

**Проблема.** Ф-3 (строка 38) исключает проценты за покупки расчётного периода при полной оплате до окончания платёжного периода включительно, а критерий приёмки (строка 63) ожидает «Проценты за покупки февраля начислены» при полной оплате 120 000 ₸ 25 марта в 14:00.  
**Сценарий.** Выписка от 1 марта, задолженность по покупкам февраля 120 000 ₸, 25 марта в 14:00 внесено 120 000 ₸ (полная сумма для погашения). По Ф-3 процентов нет, по критерию приёмки они начислены.  
**Последствия.** Реализация по Ф-3 не пройдёт приёмку; реализация под критерий нарушит правило. Разработка и тестирование получают разный ожидаемый результат.  
**Что исправить.** Исправить строку строка 63 под Ф-3: «Проценты за покупки февраля не начислены, льготный период сохранён». Если владелец продукта хочет иной исход, исправить Ф-3; до решения: <уточнить: какой исход верен для платежа 25 марта в 14:00>.  
**Было → стало.** Строка 63: «Проценты за покупки февраля начислены» → «Проценты за покупки февраля не начисляются; льготный период сохранён.»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Проценты за покупки февраля не начисляются, льготный период сохранён» (по [R-07](#r-07) (Ф-3), [R-05](#r-05) (Ф-1)) или «Проценты за покупки февраля начислены» (по критерию приёмки)?

#### <a id="d-02"></a>🔴 D-02. Некредитная карта: 200 со статусом `NOT_APPLICABLE` в логике против 422 в таблице кодов

**Требования:** [R-24](#r-24 "Для некредитной карты ответ 200 со статусом NOT_APPLICABLE") (Для некредитной карты ответ 200 со статусом…), [R-42](#r-42 "Код 422 когда карта не является кредитной") (Код 422 когда карта не является кредитной), [R-20](#r-20 "Проверка принадлежности карты клиенту и её типа кредитная") (Проверка принадлежности карты клиенту и её типа…) · **Критерий:** Корректность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** тестировщик, архитектор, проверка набора, риски

- Часть B › Логика работы метода, строка 119: «Проверить, что карта принадлежит клиенту и является кредитной»
- Часть B › Логика работы метода, строка 123: «Если карта не кредитная, вернуть 200 с status = NOT_APPLICABLE»
- Часть B › Статусы, строка 167: «422. Ответ в случае, если карта не является кредитной»

**Проблема.** Логика метода п. 6 (строка 123) для некредитной карты даёт 200 со status = `NOT_APPLICABLE`, а таблица статусов (строка 167) и пример ошибки (строка 187) дают 422 с сообщением «Для этой карты льготный период не предусмотрен». Шаг 2 (строка 119) проверяет тип карты, но не задаёт исход.  
**Сценарий.** GET `/cards/{`cardId`}/grace` для дебетовой карты клиента при действующей сессии: по п. 6 логики HTTP 200, по таблице кодов HTTP 422.  
**Последствия.** Приложение и тесты получают на один запрос разный исход: успех или отказ; экран льготного периода показывается или не показывается по-разному.  
**Что исправить.** Выбрать один исход и привести п. 6 (строка 123), таблицу статусов (строка 167) и пример (строки 185–187) к нему: «Для некредитной карты возвращается HTTP <уточнить: 200 со status `NOT_APPLICABLE` или 422>».  
**Было → стало.** Строка 123: «Если карта не кредитная, вернуть 200 с status = NOT_APPLICABLE» → «Если карта не кредитная, вернуть <уточнить: 200 с status = `NOT_APPLICABLE` или 422>; второе место привести в соответствие.»  
**Вопрос владельцу.** Должен ли запрос по некредитной карте возвращать 200 `NOT_APPLICABLE` или 422? → [Q-01](#q-01)

#### <a id="d-03"></a>🔴 D-03. Операция изменения переключателя напоминания обещана, но не описана

#### <a id="d-04"></a>🟠 D-04. Частичная оплата: база процентов по Ф-3 и по особому правилу API расходится

**Требования:** [R-07 / Ф-3](#r-07 "Начисление процентов при полном или частичном погашении в срок"), [R-15](#r-15 "Частичная оплата: проценты на всю задолженность с даты каждой покупки"), [R-26](#r-26 "Прогноз процентов при частичном погашении считается на непогашенную часть"), [R-36](#r-36 "Поле interestForecast: прогноз процентов в тиынах") · **Критерий:** Корректность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** аналитик, тестировщик, риски, проверка набора

- Часть A › Функциональные требования, строка 38: «проценты начисляются на всю задолженность по покупкам расчётного периода с даты каждой покупки»
- Часть A › Критерии приемки, строка 64: «Проценты начислены на 80 000 ₸ с даты каждой покупки»
- Часть B › Особые правила, строка 127: «прогноз процентов считается только на непогашенную часть суммы для погашения»
- Часть B › Ответ, строка 158: «Прогноз процентов, если оставшаяся сумма не будет внесена до окончания платёжного периода»

**Проблема.** Ф-3 (строка 38) и критерий приёмки (строка 64) начисляют проценты на всю задолженность по покупкам, а особое правило 2 (строка 127) считает прогноз только на непогашенную часть суммы для погашения. Для одного входа два нормативных места дают разную сумму процентов.  
**Сценарий.** Задолженность по покупкам 80 000 ₸, до 25-го внесено 50 000 ₸. По Ф-3 проценты начисляются на 80 000 ₸, по особому правилу 2 прогноз считается на 30 000 ₸. Клиент видит в приложении прогноз, не совпадающий с фактическим начислением.  
**Последствия.** Тесты приёмки и поле `interestForecast` получают разные ожидаемые значения; жалобы клиентов на начисление процентов и спор о корректности прогноза.  
**Что исправить.** Выбрать одну базу и записать её в Ф-3 (строка 38) и в особом правиле 2 (строка 127): «Проценты при частичной оплате начисляются на <уточнить: всю задолженность по покупкам расчётного периода / непогашенную часть>; прогноз `interestForecast` считается на ту же базу».  
**Было → стало.** Строка 38: «проценты начисляются на всю задолженность по покупкам расчётного периода с даты каждой покупки» → «При частичном погашении проценты начисляются на <уточнить: всю задолженность по покупкам расчётного периода / непогашенную часть> с даты каждой покупки; прогноз процентов в ответе считается на ту же базу.»

**Сценарий.** Покупка 60 000 ₸ в феврале, платёж внесён не полностью, проценты начислены 26 марта. Возврат этой покупки 27 марта: по тексту он не уменьшает сумму, но не сказано, возвращаются ли начисленные проценты.  
**Последствия.** Клиент переплачивает проценты по возвращённой покупке; спор о возврате; нет правила для бухгалтерии.  
**Что исправить.** Дополнить Ф-5: «Возврат, отражённый после окончания платёжного периода, <уточнить: не меняет начисленные проценты / пересчитывает проценты с даты покупки до даты возврата>».

**Вопрос владельцу.** Возвращаются ли проценты по покупке, возвращённой после окончания платёжного периода? → [Q-06](#q-06)

#### <a id="d-16"></a>🟠 D-16. «Своевременно» для напоминаний не задано числом: срок push не проверяем

**Требования:** [R-11](#r-11 "Быстрое отображение, актуальность сведений и своевременные напоминания") (Быстрое отображение, актуальность сведений и…), [R-08 / Ф-4](#r-08 "Push-напоминание за 3 дня при включённом переключателе") (Push-напоминание за 3 дня при включённом…), [R-16](#r-16 "Напоминание за 3 дня: один push с датой и оставшейся суммой") (Напоминание за 3 дня: один push с датой и…) · **Критерий:** Проверяемость (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.6) · **Вид:** непроверяемость · **Блокирует:** тестирование · **Нашли:** аналитик, риски

- Часть A › Нефункциональные требования, строка 46: «Напоминания отправляются своевременно»
- Часть A › Критерии приемки, строка 65: «Клиент получил один push с датой 25-го числа и суммой 30 000 ₸»

**Проблема.** НФТ (строка 46) требует отправлять напоминания «своевременно»: не задано событие начала отсчёта, срок отправки и доля случаев, поэтому приёмка не может признать задержку push ошибкой.  
**Сценарий.** Напоминание за 3 дня должно уйти 22-го; если push ушёл 25-го, по НФТ требование формально выполнено, а клиент не успел внести платёж.  
**Последствия.** Требование нельзя принять или отклонить; спор при приёмке и жалобы клиентов на поздние напоминания.  
**Что исправить.** Заменить на: «Push с напоминанием отправляется не позднее <уточнить: N минут> после <уточнить: 00:00 даты напоминания>, в <уточнить: % случаев>».  
**Было → стало.** Строка 65: «Клиент получил один push с датой 25-го числа и суммой 30 000 ₸» → «Push-напоминание отправляется не позднее <уточнить: N минут> после <уточнить: момента срабатывания> в <уточнить: N%> случаев.»  
**Вопрос владельцу.** Какой допустимый срок доставки напоминания от момента его срабатывания? → [Q-09](#q-09)

**<a id="q-01"></a>Q-01** Ответ для некредитной карты: 200 или 422 · ⛔ блокирует · кому: Архитектор · к [D-02](#d-02)  
Какой HTTP-ответ получает клиент, если GET-запрос сведений о льготном периоде приходит по дебетовой карте, которая принадлежит ему и активна?  
Где: строка 123 «Если карта не кредитная, вернуть 200 с status = NOT_APPLICABLE»; строка 167 «422. Ответ в случае, если карта не является кредитной»

- **A** HTTP 200, в теле status = `NOT_APPLICABLE`; поля `paymentDueDate`, `graceAmount`, `daysLeft`, `interestForecast`, `totalDebt` возвращаются как null, `reminderEnabled` как false; пункт 6 логики и таблица статусов приводятся к этому
- **B** HTTP 422 с сообщением «Для этой карты льготный период не предусмотрен»; тело со status не возвращается; пункт 6 логики заменяется на возврат 422, статус `NOT_APPLICABLE` из ответа удаляется

Зачем: Логика метода (п. 6) и таблица статусов дают разные HTTP-коды для одного входа; приложение и тесты по одной и той же карте получат разный результат, и экран «Льготный период» для дебетовой карты будет отрисован по-разному.

**<a id="q-02"></a>Q-02** Контракт записи переключателя напоминания · ⛔ блокирует · кому: Архитектор · к [D-03](#d-03), [D-15](#d-15)

Зачем: Без описанного метода записи приложение не может выключить напоминание, а тест на выключение переключателя нельзя написать; разработчики клиента и бэкенда выберут разные методы и тела.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
