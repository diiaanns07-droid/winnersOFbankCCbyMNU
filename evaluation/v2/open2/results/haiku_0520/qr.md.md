#### <a id="d-01"></a>🔴 D-01. Создание QR-кода и получение его данных не описаны в REST API

- Часть A › Дизайн процесса UI, строка 28: «Получить по QR»
- Часть A › Дизайн процесса UI, строка 29: «экран подтверждения с маскированным именем получателя»
- Часть A › Sequence Diagram, строка 45: «Приложение получателя → сервис QR-кодов: создать QR-код. Приложение отправителя → сервис QR-кодов: получить данные QR-кода»
- Часть A › Требования к интеграции, строка 54: «Приложения создают QR-код, получают данные QR-кода перед подтверждением»
- Часть B › Общие параметры, строка 107: «Description | Выполнение перевода по QR-коду»

**Проблема.** строка 54 обещает создание QR-кода и получение его данных через дочерний REST API, но часть B (строки 99–201) описывает только POST-перевод (строка 108). Вызовы создания и получения данных есть только в последовательности строка 45.

**Последствия.** Основной сценарий нельзя реализовать по документу; разработка и тесты невозможны.  
**Что исправить.** Добавить в часть B методы «создать QR-код» (вход: `cardId`, необязательный amount; выход: `qrId`, ttl, данные QR) и «получить данные QR-кода» (вход: `qrId`; выход: `recipientName`, amount, статус) с параметрами, кодами ответа и примерами по образцу строки 107–201.

#### <a id="d-03"></a>🔴 D-03. Единица ttl: минуты в данных и секунды в проверке срока

**Требования:** [R-14](#r-14 "Состав данных QR-кода и поля хранения, включая статусы и срок ttl") (Состав данных QR-кода и поля хранения, включая…), [R-25](#r-25 "Проверка срока действия; ответ 410 при истечении или отмене") (Проверка срока действия; ответ 410 при…), [R-16](#r-16 "Перевод по QR-коду без суммы через 14 минут после создания выполнен") (Перевод по QR-коду без суммы через 14 минут…) · **Критерий:** Однозначность (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · **Вид:** расхождение единиц · **Блокирует:** разработку и тестирование · **Нашли:** аналитик, тестировщик, архитектор, риски, проверка набора

- Часть A › Требования к данным, строка 51: «срок действия ttl в минутах»
- Часть B › Логика работы метода, строка 124: «времени создания QR-кода + ttl секунд»

**Проблема.** строка 51 задаёт ttl в минутах, а строка 124 прибавляет ttl в секундах. Один и тот же ttl=15 даёт срок 15 минут или 15 секунд.

**Проблема.** строка 51 задаёт, что QR-код содержит номер карты получателя. QR показывается на экране (строка 28) и может быть сфотографирован.  
**Сценарий.** Получатель показывает QR-код в людном месте; посторонний фотографирует его и декодирует номер карты.  
**Последствия.** Утечка полного номера карты клиента; возможны мошеннические переводы и подбор реквизитов.  
**Что исправить.** Не помещать номер карты в QR-код: вместо него использовать `qrId`, по которому сервер находит карту зачисления.  
**Было → стало.** Строка 51: «QR-код содержит идентификатор QR-кода, номер карты получателя и сумму, если она задана» → «QR-код содержит только идентификатор QR-кода и, если задана, сумму; номер карты получателя в QR-код не помещается и возвращается сервисом только при запросе данных QR-кода.»

#### <a id="d-22"></a>🟠 D-22. Истёкший QR: код 410 или 400 и разные тексты сообщения

**Требования:** [R-25](#r-25 "Проверка срока действия; ответ 410 при истечении или отмене"), [R-45](#r-45 "Код 400: неверные параметры запроса или истёкший срок QR-кода"), [R-17](#r-17 "QR-код с суммой через 16 минут после создания недействителен"), [R-47](#r-47 "Код 404: QR-код не найден") · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** проверка набора, тестировщик, архитектор

- Часть A › Критерии приемки, строка 66: «Показано «QR-код недействителен»
- Часть B › Логика работы метода, строка 124: «Если срок истёк или QR-код отменён, вернуть 410»
- Часть B › Статусы, строка 168: «400. Ответ в случае, если параметры запроса заполнены неверно или срок действия QR-кода истёк»

**Проблема.** Пункт 4 логики (строка 124) отвечает 410 при истёкшем сроке, статус 400 (строка 168) и пример (строка 181) дают 400 с текстом «Срок действия QR-кода истёк». Критерий строка 66 ждёт «QR-код недействителен».  
**Сценарий.** QR с суммой создан в 10:00 с ttl 15 минут; перевод запрошен в 10:16. По строке 124 ответ 410; по строке 168 ответ 400 с сообщением «Срок действия QR-кода истёк».  
**Последствия.** Клиентское приложение и тесты ожидают разные коды для одного отказа; интеграция обрабатывает ошибку по-разному.  
**Что исправить.** Оставить один код для истёкшего QR (410 по строке 124 или 400 по строке 168) и удалить другой. Привести текст сообщения к интерфейсу «QR-код недействителен» или наоборот.

#### <a id="d-23"></a>🟠 D-23. Нарушение предусловий карты списания не имеет кода ответа

**Требования:** [R-23](#r-23 "Проверка карты списания: принадлежность, активность, открыта в тенге") (Проверка карты списания: принадлежность…), [R-46](#r-46 "Код 401: запрос без необходимой авторизации") (Код 401: запрос без необходимой авторизации) · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** отсутствует элемент · **Блокирует:** разработку · **Нашли:** архитектор

- Часть B › Логика работы метода, строка 122: «2. Проверить, что карта списания принадлежит плательщику, активна и открыта в тенге»

**Проблема.** Шаг 2 (строка 122) проверяет принадлежность, активность и валюту карты списания, но ни один код ответа (строки 167–172) не соответствует отказу по карте.  
**Сценарий.** Карта закрыта; по документу нет кода ответа, который вернуть клиенту.  
**Последствия.** Клиент получает случайный код ошибки; интеграция не может обработать отказ.  
**Что исправить.** Добавить код ответа для отказа по карте списания: <уточнить: 400 или 403> с текстом сообщения и примером.  
**Было → стало.** Строка 122: «2. Проверить, что карта списания принадлежит плательщику, активна и открыта в тенге» → «Если карта списания не принадлежит отправителю, не активна или не открыта в тенге: код <уточнить: 400 или 403>, тело {"message":"<уточнить: текст>"}.»

#### <a id="d-24"></a>🟠 D-24. Сбой после списания без описанного отката и без статуса перевода

**Требования:** [R-29](#r-29 "Списание, зачисление и возврат результата клиенту") (Списание, зачисление и возврат результата…), [R-31](#r-31 "Повторный запрос с тем же requestId возвращает результат первого запроса") (Повторный запрос с тем же `requestId` возвращает…), [R-49](#r-49 "Код 500: внутренняя ошибка сервера") (Код 500: внутренняя ошибка сервера) · **Критерий:** ИБ и операционные риски (Чек-лист ревью требований банка) · **Вид:** операционный риск · **Блокирует:** разработку · **Нашли:** риски

- Часть B › Логика работы метода, строка 128: «Выполнить списание и зачисление и вернуть результат»
- Часть B › Особые правила, строка 132: «Повторный запрос с тем же requestId возвращает результат первого запроса»
- Часть B › Статусы, строка 172: «внутренняя ошибка сервера»

**Проблема.** Списание и зачисление описаны одним шагом (строка 128). Не описано, что происходит при сбое между ними. строка 132 возвращает сохранённый результат при повторе, а строка 172 — 500 без `transferId`.  
**Сценарий.** Списание прошло, зачисление вернуло 500. Клиент повторяет запрос с тем же `requestId` и получает тот же 500 без `transferId`.  
**Последствия.** Деньги списаны без зачисления и без признака перевода; спор, ручная проверка, жалобы клиентов.  
**Что исправить.** Описать компенсацию или откат при сбое зачисления, статус перевода в таком случае и тело ответа 500 с `transfer_id`, если перевод создан.  
**Было → стало.** Строка 128: «Выполнить списание и зачисление и вернуть результат» → «Списание и зачисление выполняются в одной транзакции; при сбое зачисления списание откатывается и возвращается ошибка с признаком отмены.»

#### <a id="d-25"></a>🟠 D-25. Тела ошибок не содержат полей status, amount, `recipientName`

**Требования:** [R-39](#r-39 "Результат перевода: DONE или REJECTED"), [R-41](#r-41 "Сумма перевода в тенге в ответе"), [R-42](#r-42 "Маскированное имя получателя в формате «Имя Ф.»"), [R-38](#r-38 "Успешный ответ при коде 200, неуспешный при 400, 401, 404, 410, 500") · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** контракт API · **Блокирует:** разработку · **Нашли:** архитектор

- Часть B › Ответ, строка 159: «status | string | DONE / REJECTED | Результат перевода | status»
- Часть B › Ответ, строка 162: «recipientName | string | «Имя Ф.» | Маскированное имя получателя | —»
- Часть B › 400. Unsuccessful — Bad request, строка 181: «{"message":"Срок действия QR-кода истёк"}»

**Проблема.** Поля status, amount, `recipientName` (строки 159–162) описаны без условия применимости, тела ошибок (строка 181 и далее) содержат только message.  
**Сценарий.** Клиент получает 404 с телом {"message":"QR-код не найден"} и разбирает его как успешный перевод с пустыми status и amount.  
**Последствия.** Клиент не знает, как разбирать тело ошибки; разбор ответа зависит от реализации.  
**Что исправить.** Указать условие: status, amount, `transferId`, `recipientName` только при DONE; для ошибок описать тело с полем message и статусом ошибки.  
**Было → стало.** Строка 159: «status | string | DONE / REJECTED | Результат перевода | status» → «status, amount, `recipientName` возвращаются только при коде 200; при 400, 401, 404, 410, 500 тело содержит только message.»

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Критерии.** Отдельное требование (ISO/IEC/IEEE 29148:2018 п. 5.2.5, 5.2.7): необходимость, уместность (что, а не как), однозначность, полнота требования, единичность, осуществимость, проверяемость, корректность, соответствие шаблону, язык требований. Набор (29148 п. 5.2.6, IEEE 830-1998 п. 4.3): согласованность, полнота набора, осуществимость набора, понятность, возможность валидации, ранжирование по важности, модифицируемость, прослеживаемость. Плюс ИБ и операционные риски по чек-листу банка.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
