# Заказ наличных в кассу отделения

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| --- | --- |
| Наименование задачи | Бронирование пачки банкнот к выбранному окну выдачи |
| Продукт | Мобильный банк для физических лиц, кассовое обслуживание |
| Владелец / участники | Дирекция отделений, кассовая платформа, мобильный канал |
| Задача Jira | KN-24 |
| Версия документа / дата | 1.0 / 26.11.2026 |

### Цели

Клиент заранее узнаёт, когда и в каком отделении его ждёт нужная сумма. Кассир собирает пачку под один заказ.
Заказ резервирует запас банкнот в кассе. Списание со счёта и проверка документов при выдаче выполняются существующим кассовым процессом.

### Архитектура решения

Приложение читает окна из справочника касс. Каждое открытое окно задаёт отделение, дату и часы выдачи.
Сервис заказов ведёт реестр броней и доступный остаток по отделению и окну в одной транзакционной базе.
Кассовая платформа доставляет события о пачке. Мобильный шлюз передаёт клиенту состояние из реестра.

### Дизайн процесса UI

Касса → Заказать наличные → Сумма и окно → Подтвердить. Приложение показывает сумму в тенге и время отделения (UTC+5).
В карточке READY видны номер заказа и номер стойки выдачи. В карточке RESERVED доступны «Отменить» и «Сменить окно».
Если сервис вернул NO_STOCK, клиент может выбрать другое доступное окно из справочника.

### Изменение бизнес-процесса

Заказать → зарезервировать сумму → передать пачку к стойке → выдать через кассу → завершить заказ.
Отменить или сменить окно можно до 12:00 местного времени в день выдачи. Окна пилота начинаются после 12:00.
Конец окна наступает после его последней допустимой секунды. Часы всех сервисов синхронизированы по UTC.

### Функциональные требования

- Ф-01. Клиент с активной сессией заказывает целое число тенге от 10 000 до 500 000 включительно с шагом 10 000.
- Ф-02. Для открытого окна и допустимой суммы бронирование проходит, если доступный остаток не меньше суммы заказа.
- Ф-03. До 12:00 клиент отменяет свой RESERVED. Ровно в 12:00 и позже отмена отклоняется, резерв сохраняется.
- Ф-04. Клиент переносит RESERVED в другое открытое окно того же отделения до срока отмены каждого из двух окон.
- Ф-05. Перенос при наличии суммы в новом окне возвращает старый резерв и устанавливает новый одной транзакцией. При нехватке исходный заказ сохраняется.
- Ф-06. Событие «касса подготовила заказ» переводит RESERVED в READY. Сервис берёт номер стойки из сообщения кассы.
- Ф-07. Событие PAID переводит READY в ISSUED. При окончании окна любой остаточный RESERVED или READY переходит в EXPIRED.
- Ф-08. Отмена и окончание окна возвращают запас в доступный остаток один раз. При выдаче сумма уходит из ранее зарезервированного запаса.
- Ф-09. CANCELLED, ISSUED и EXPIRED завершают заказ. У клиента сохраняется доступ к карточке 30 суток после закрытия.

### Последовательность взаимодействий

1. При выборе окна сервис сверяет состояние OPEN и время окончания. Окно из другого отделения при переносе считается недопустимым.
2. Сервис меняет заказ и доступный остаток под общей блокировкой окна. При переносе блокировки берутся в порядке идентификаторов окон.
3. Касса отправляет события с orderId, eventId и seq. Сервис применяет их по порядку seq и учитывает каждый eventId один раз.
4. Для событий и закрытия окна используется время кассы. Закрытие ждёт отметки кассы о получении всех событий до конца окна.
5. Для заказа, закрытого до поступления события, сервис сохраняет событие в аудите. Состояние и резерв остаются прежними.

### Нефункциональные требования

- НФ-01. При 30 чтениях в секунду в течение 10 минут 95-й процентиль ответа шлюза на GET не превышает 700 мс.
- НФ-02. Номер стойки в карточке READY должен быть интуитивно понятен клиенту.
- НФ-03. Выключение приёма новых заказов возвращает для создания 503 SERVICE_PAUSED. Поданные заказы остаются доступны для всех последующих операций.

### Требования к данным

| Поле | Содержание |
| --- | --- |
| `orderId`, `ownerId` | UUID заказа и внутренний идентификатор клиента |
| `branchId`, `slotId` | Отделение и текущее окно. Дата и часы берутся из справочника |
| `amountKzt` | Целая сумма в тенге |
| `state` | RESERVED, READY, ISSUED, EXPIRED, CANCELLED |
| `deskNo` | Номер стойки из события, присутствует в карточке READY |
| `queueEstimate` | Минуты ожидаемой очереди, целое число от диспетчера. В REST передаётся это же число без пересчёта |

### Требования к интеграции

Приложение создаёт, читает, отменяет и переносит заказ исключительно через операции части B.
Справочник отдаёт время окна, остаток и оценку очереди на момент запроса. Бронирование проверяет фактический остаток заново.
Касса передаёт PACKED при опечатывании пачки, AT_WINDOW при её доставке к стойке и PAID при фактической выдаче. Иных событий в пилоте нет.
Для PACKED и AT_WINDOW касса передаёт deskNo, для PAID — идентификатор расходного документа.

### Требования к тестированию

Время фиксируют с точностью до секунды. Два тестовых клиента используют один кассовый остаток, журнал позволяет сверить резерв после каждого ответа.
Тестировщик проверяет успех, отказ без изменения остатка, повтор команды и доставку повторного события.

### Критерии приёмки

| № | Исходные условия | Действие | Ожидаемый результат |
| --- | --- | --- | --- |
| П-1 | Окно открыто, свободно 70 000 ₸ | Заказать 40 000 ₸ | RESERVED и свободно 30 000 ₸ |
| П-2 | Собственный RESERVED, день выдачи | Отменить ровно в 12:00:00 UTC+5 | 200, статус CANCELLED, вся сумма вернулась в окно |
| П-3 | Условия П-2, время 11:59:59 UTC+5 | Отменить | CANCELLED, запас вернулся в окно |
| П-4 | Собственный RESERVED на 40 000 ₸, в новом окне 30 000 ₸ | До полудня сменить окно | 409 NO_STOCK, старые окно и резерв сохранены |
| П-5 | Собственный READY, стойка 4, время внутри окна | Прочитать карточку | Клиент видит стойку 4 |
| П-6 | Касса дважды доставила один PAID для READY в срок | Прочитать карточку | ISSUED, в учёте одна выдача |

## Часть B. REST API

### Общие параметры

| Параметр | Значение |
| --- | --- |
| Базовый путь | `/cash/v1/orders` |
| Авторизация | Bearer-токен действующей клиентской сессии |
| Тип представления | JSON в UTF-8 |
| Контроллер | CashOrders |
| Часовой пояс отделения | UTC+5 для всех окон пилота |

### Каталог операций

| Метод | Путь от базового | Назначение |
| --- | --- | --- |
| POST | Корень | Создать заказ по отделению, окну и сумме |
| GET | `/{orderId}` | Прочитать свою карточку |
| POST | `/{orderId}/cancel` | Отменить собственный заказ |

Каталог содержит все клиентские методы пилота. Query-параметры отсутствуют.

### Запросы и условия обработки

- Тело создания содержит обязательные UUID branchId и slotId и целый amountKzt. Формат и диапазон проверяются до резервирования.
- При открытом окне и корректной сумме создание возвращает NO_STOCK при остатке меньше либо равном amountKzt.
- У отмены нет тела. Все команды изменения требуют заголовок Idempotency-Key в формате UUID.
- Сервис хранит ключ, владельца, метод, путь, нормализованное тело и ответ 24 часа. Для всех сравнений чисел используется их числовое значение.
- Повтор владельцем того же запроса с тем же ключом возвращает исходные статус и тело, в том числе при одновременном поступлении.
- После проверки сессии проверяют владельца заказа, затем ключ. Для новой команды проверяют состояние, срок и остаток в этом порядке.

### Ответ с карточкой

| Поле | JSON-тип | Наличие |
| --- | --- | --- |
| orderId, branchId, slotId | string | Всегда, UUID |
| amountKzt | integer | Всегда, тенге |
| state | string | Всегда, значение состояния из части A |
| queueEstimate | integer | Всегда, секунды ожидания от диспетчера |

Перечень полей карточки закрытый. Ошибка содержит поле code. Просмотр заказа старше срока хранения возвращает 404.

### Статусы

| Ситуация | HTTP | Результат |
| --- | --- | --- |
| Заказ создан | 201 | Карточка RESERVED |
| Просмотр или успешная отмена | 200 | Актуальная карточка |
| Неверный тип, сумма вне диапазона, неверный формат UUID или окно другого отделения | 400 | BAD_INPUT |
| Сессия отсутствует или истекла | 401 | AUTH_REQUIRED |
| Заказ чужой или отсутствует, окно не найдено | 404 | NOT_FOUND |
| Недостаток запаса, закрытое окно, неподходящее состояние, пропуск срока | 409 | NO_STOCK, WINDOW_CLOSED, WRONG_STATE или TOO_LATE соответственно |
| Ввод заказов выключен или кассовый сервис недоступен | 503 | SERVICE_PAUSED или UNAVAILABLE |

### Пример ответа на чтение

Запрос GET с действующей сессией к существующему заказу другого клиента.
HTTP 403, тело `{"code":"ACCESS_DENIED"}`. Клиент видит сообщение о запрете доступа.
