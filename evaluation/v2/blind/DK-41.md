# Кредитные каникулы по одному платежу

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| --- | --- |
| Наименование задачи | Перенос платежа по предложению банка |
| Продукт | Розничные кредиты, мобильный банк |
| Бизнес-процесс | Обслуживание действующего кредитного договора |
| Владелец / аналитик | Управление кредитных продуктов / аналитик мобильного банка |
| Версия / дата | 1.0 / 26.11.2026 |
| Задача Jira | DK-41 |

### Цели

Заёмщик выбирает одно доступное предложение, видит обе даты платежа и узнаёт решение без звонка в отделение.
Программа распространяется на тестовую линейку кредитов в тенге, для которой кредитная система уже рассчитала вариант графика.
Состав, сумма и порядок остальных платежей определены этим вариантом. Приложение не меняет ставки и не рассчитывает проценты.

### Архитектура решения

Приложение получает карточку предложения из действующей витрины кредитов. Команды по заявке обслуживает сервис каникул.
Кредитная система (АБС) хранит исходный график и утверждает новый. Основанием для новой даты служит идентификатор предложения.
Сервис каникул ведёт журнал заявок. Оператор поддержки может найти запись по идентификатору обращения.

### Дизайн процесса UI

Кредит → График → Каникулы → Предложение. На экране видны номер платежа, сумма, прежняя и новая даты.
После подтверждения клиент видит номер заявки. На экране отказа приложение выводит причину, переданную сервисом.
Пока заявка рассматривается, у клиента есть действие «Отозвать». После регистрации каникул доступен новый график из АБС.

### Изменение бизнес-процесса

Клиент выбирает предложение → сервис проверяет дату и владельца → АБС принимает заявку → сервис показывает состояние.
Отозванная до решения заявка больше не может изменить график. Сервис сериализует отзыв и обработку решения в порядке фиксации в журнале.

### Функциональные требования

- Ф-01. Подать заявку может единственный заёмщик действующего договора, по которому витрина вернула активное предложение.
- Ф-02. Если до платежа осталось не менее трёх календарных дней, сервис принимает заявку. Разность считают между местными датами платежа и подачи в UTC+5.
- Ф-03. По предложению этой линейки новая дата равна исходной дате платежа плюс 28 календарных дней. Переносов на рабочий день нет.
- Ф-04. Одна активная заявка на предложение исключает регистрацию второй. У отозванной или отклонённой заявки активность прекращается.
- Ф-05. Заёмщик отзывает свою заявку в состоянии PENDING через мобильный банк. После отзыва состояние равно WITHDRAWN, прежний график действует.
- Ф-06. При наступлении события «каникулы зарегистрированы» сервис переводит заявку в ACTIVE и закрывает возможность отзыва.
- Ф-07. Подтверждённый отказ АБС переводит PENDING в REJECTED и сохраняет код причины для показа клиенту.
- Ф-08. ACTIVE, WITHDRAWN и REJECTED завершают обработку заявки. Поздний ответ по закрытой заявке сохраняется только в истории.

### Последовательность взаимодействий

1. Приложение передаёт предложение и ключ запроса. Сервис проверяет владельца до выдачи сведений о договоре.
2. Сервис в одной транзакции добавляет заявку PENDING и команду для АБС. После фиксации возвращает номер заявки.
3. Адаптер АБС передаёт сервису сообщения. Сервис связывает их с заявкой по `applicationId` и игнорирует уже обработанный `eventId`.
4. Приложение перечитывает карточку при открытии экрана и после возврата из фона.

### Нефункциональные требования

- НФ-01. При 20 запросах чтения в секунду за 15 минут 95-й процентиль времени ответа шлюза не превышает 800 мс.
- НФ-02. Экран принятого решения должен вызывать у заёмщика ощущение уверенности в результате.
- НФ-03. Журнал аудита хранит идентификаторы, коды и время перехода 90 суток. Операторы продукта имеют доступ только на чтение.

### Требования к данным

| Поле | Содержание |
| --- | --- |
| `applicationId`, `offerId` | UUID заявки и действующего предложения |
| `loanId`, `ownerId` | Внутренние идентификаторы договора и заёмщика |
| `oldDate`, `newDate` | Календарные даты, формат YYYY-MM-DD |
| `state` | PENDING, ACTIVE, REJECTED или WITHDRAWN |
| `reason` | Код АБС для отказа, словарь LIMIT_USED или LOAN_CLOSED |
| `reviewAge` | Целое число минут между подачей и решением, с округлением вниз. В карточку REST уходит сохранённое число без пересчёта |

### Требования к интеграции

Создание, просмотр и отзыв заявки из приложения выполняются через дочернюю спецификацию в части B.
Адаптер АБС поставляет следующий полный перечень сообщений для этой линейки.

| Сообщение | Смысл в АБС |
| --- | --- |
| `DOSSIER_ACCEPTED` | Досье принято и получило регистрационный номер |
| `SCHEDULE_POSTED` | Версия графика записана в кредитном модуле |
| `DECISION_DENIED` | Решение об отказе, в сообщении есть код причины |

### Требования к тестированию

Проверку дат проводят на фиксированных часах UTC+5. Набор данных содержит свои и чужие договоры с отдельными предложениями.
Адаптер стенда повторно отправляет одно сообщение с прежним eventId. В журнале ожидается один переход.
При выключении функции новые заявки закрываются для ввода. Просмотр, отзыв и обработка поданных сохраняются.

### Критерии приёмки

| № | Исходные условия | Действие | Ожидаемый результат |
| --- | --- | --- | --- |
| П-1 | До платежа пять дней, предложение активно | Подать заявку | Одна запись PENDING, виден её номер |
| П-2 | Платёж приходится на 10.04.2027, предложение доступно | Открыть предложение каникул | На экране новая дата 10.05.2027 |
| П-3 | Клиент подал заявку и видит PENDING | Отозвать до решения | Карточка WITHDRAWN, исходная дата платежа сохранена |
| П-4 | АБС отказала с причиной LOAN_CLOSED | Открыть карточку | Текст «Договор закрыт» |
| П-5 | Клиент уже отозвал заявку | Доставить запоздавшее решение | Состояние WITHDRAWN сохраняется |

## Часть B. REST API

### Общие параметры

| Параметр | Значение |
| --- | --- |
| Назначение | Клиентские операции с заявками на каникулы |
| Базовый путь | `/mobile/v1/holidays` |
| Авторизация | Bearer-токен заёмщика, проверяется по ownerId |
| Представление | JSON в UTF-8, даты без времени |
| Владелец контракта | Команда кредитного сервиса |

### Каталог операций версии 1

| Метод | Путь относительно базового | Результат |
| --- | --- | --- |
| POST | `/applications` | Подать заявку |
| GET | `/applications/{applicationId}` | Прочитать карточку заявки |

Каталог исчерпывает публичные операции приложения для заявок этой версии.

### Запрос на подачу

| Поле | Расположение | Формат и обязательность |
| --- | --- | --- |
| `Idempotency-Key` | Заголовок | Обязательный UUID для POST |
| `loanId` | Тело | Обязательный UUID договора |
| `offerId` | Тело | Обязательный UUID предложения этого договора |

Повтор той же команды с тем же ключом в течение суток возвращает исходный ответ. Иное тело с тем же ключом даёт 409 KEY_REUSED.
Для действующего предложения своего договора шлюз возвращает 422 TOO_LATE, если разность местных дат платежа и подачи меньше либо равна трём дням.
При успешной подаче ответ 201 содержит applicationId и state=PENDING. Недоступность АБС после приёма команды сохраняет PENDING до доставки.

### Представление карточки

| Поле | Тип | Правило возврата GET |
| --- | --- | --- |
| `applicationId`, `offerId` | string | Обязательны во всех состояниях |
| `state` | string | Значение из справочника состояний части A |
| `oldDate`, `newDate` | string | Даты выбранного предложения во всех состояниях |
| `reason` | string | Необязательное поле, в том числе в карточке REJECTED |
| `reviewAge` | integer | Секунды от подачи до решения, указывается для ACTIVE и REJECTED |

### Статусы и примеры

| Ситуация | HTTP | Тело или код |
| --- | --- | --- |
| Чтение своей существующей заявки в любом состоянии, включая REJECTED | 200 | Карточка |
| Некорректный JSON или UUID | 400 | BAD_INPUT |
| Нет действующей сессии | 401 | AUTH_REQUIRED |
| Чужая или отсутствующая запись | 404 | NOT_FOUND |
| Вторая активная заявка | 409 | ALREADY_PENDING |
| Предложение утратило силу до подачи | 422 | OFFER_EXPIRED |
| Шлюз недоступен до регистрации команды | 503 | RETRY_LATER |

Пример чтения своей существующей заявки, которая находится в REJECTED из-за LOAN_CLOSED.
HTTP 422. Тело `{"state":"REJECTED","reason":"LOAN_CLOSED","code":"APPLICATION_REJECTED"}`.
Для всех ошибок поле `code` содержит машинный код. Технические сообщения АБС клиенту не передаются.
