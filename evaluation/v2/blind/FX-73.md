# Обмен валюты по индивидуальной котировке

## Часть A. Новый функционал

### Общие сведения

| Поле | Значение |
| --- | --- |
| Наименование задачи | Покупка долларов США за тенге по курсу, предложенному в приложении |
| Продукт | Текущие счета физического лица |
| Процесс | Обмен между двумя собственными счетами |
| Владелец / аналитик | Казначейство розницы / аналитик цифровых каналов |
| Задача Jira | FX-73 |
| Версия / дата | 1.0 / 26.11.2026 |

### Цели

Клиент видит точную сумму списания до подтверждения и может установить судьбу обмена после потери связи.
В пилоте рассматривается одно направление покупки, KZT → USD. Оба счёта принадлежат одному клиенту. Комиссия равна нулю.

### Архитектура решения

Казначейство выдаёт цену для конкретной пары счетов и объёма в долларах. Сервис котировок сохраняет цену и обе суммы.
После подтверждения расчётный модуль проводит обмен по зафиксированным суммам. Проводки связаны общим exchangeId.
Клиентский шлюз передаёт приложению карточку обмена. Журнал доступен дежурному подразделению валютных операций.

### Дизайн процесса UI

Курсы → Купить USD → Счета → Сумма → Получить курс. На экране предложения видны сумма покупки, курс и сумма списания.
После подтверждения экран показывает номер обмена. Кнопка «Проверить результат» повторно читает состояние по этому номеру.
При недостатке средств приложение предлагает поменять сумму, при запрете операций по счёту — обратиться в отделение.

### Изменение бизнес-процесса

Получить котировку → показать зафиксированную сумму → принять подтверждение → передать распоряжение → показать итог.
Получение котировки не меняет доступный остаток. Между выдачей цены и подтверждением банк может запретить операции по одному из счетов.

### Функциональные требования

- Ф-01. Клиент указывает от 1,00 до 5 000,00 USD включительно с точностью до цента. Оба счёта должны быть открыты, валюты должны соответствовать направлению.
- Ф-02. Сумма списания в KZT равна сумме в USD, умноженной на курс из предложения. Результат округляется один раз до тиына, ровно половина округляется вверх.
- Ф-03. Подтверждение действительно, если время получения шлюзом строго раньше expiresAt. При равенстве котировка просрочена, распоряжение не создаётся.
- Ф-04. Подтверждение расходует котировку один раз. Повтор команды после приёма возвращает тот же exchangeId и исходную сумму.
- Ф-05. С момента передачи в расчётный модуль обмен имеет состояние PROCESSING. При наступлении события «обмен рассчитан» клиентская карточка переходит в DONE.
- Ф-06. По exchangeId клиент получает последнее состояние как после возврата в приложение, так и после разрыва связи. История чтения доступна 30 дней.
- Ф-07. Отказ расчётного модуля завершает обмен в DECLINED. Клиентский экран различает недостаток средств и запрет операций по счёту.
- Ф-08. Расчётный модуль проводит обе суммы одной бухгалтерской операцией. При отказе обе суммы остаются на исходных счетах без изменений.

### Последовательность взаимодействий

1. Шлюз проверяет сессию и принадлежность обоих счетов. Запрос казначейству включает сумму USD и запрошенное направление.
2. Клиент подтверждает quoteId. Сервис фиксирует exchangeId перед передачей команды с этим же идентификатором в расчётный модуль.
3. Адаптер принимает сообщения расчётного модуля с exchangeId и уникальным eventId. Повторное сообщение обновляет только отметку о доставке.
4. При недоступности расчётного модуля принятая команда остаётся в очереди, повтор использует тот же exchangeId.

### Нефункциональные требования

- НФ-01. При 15 запросах в секунду в течение 20 минут 95-й процентиль выдачи котировки на шлюзе не превышает 1200 мс.
- НФ-02. Представление курса и суммы списания должно выглядеть для клиента естественно и внушать доверие.
- НФ-03. В операционном журнале все номера счетов маскируются. Разрешено сохранять только последние четыре символа каждого IBAN.

### Требования к данным

| Поле | Содержание |
| --- | --- |
| quoteId, exchangeId | UUID предложения и операции обмена |
| usdAmount, debitKzt | Десятичные строки с двумя знаками, покупка и списание |
| rate | Цена одного USD в KZT, десятичная строка с четырьмя знаками |
| expiresAt | Время окончания котировки UTC с точностью до миллисекунды |
| indicativeSpread | Справочная надбавка в базисных пунктах. В ответ на запрос котировки копируется сохранённое число без пересчёта |
| state | PROCESSING, DONE или DECLINED |

### Требования к интеграции

Выдача котировки, подтверждение и повторное чтение состояния выполняются через клиентский REST API части B.
Расчётный модуль присылает полный набор сообщений, перечисленный ниже. Порядок доставки не гарантирован.

| Сообщение | Значение у источника |
| --- | --- |
| ENTRY_BOOKED | Сформирована парная бухгалтерская запись |
| VALUE_APPLIED | Обе суммы отражены в доступных остатках |
| ENTRY_DECLINED | В проведении отказано, передан код FUNDS_LOW или ACCOUNT_FROZEN |

### Требования к тестированию

На стенде часы шлюза фиксируются в UTC. Казначейство возвращает заданный четырёхзначный курс без изменения при повторе.
Для проверки журналирования используется синтетический номер счёта. Дежурный сверяет строку журнала после успешного завершения.
При отключении выдачи новых котировок действующие предложения можно подтвердить до expiresAt, принятые распоряжения продолжают обрабатываться.

### Критерии приёмки

| № | Исходные условия | Действие | Ожидаемый результат |
| --- | --- | --- | --- |
| П-1 | Покупка 3,00 USD, курс 490,3350 KZT за USD | Получить котировку | К списанию показано 1 471,00 KZT |
| П-2 | Покупка 10,00 USD, курс 490,1000 | Подтвердить за секунду до срока | Одна команда на 4 901,00 KZT |
| П-3 | Подтверждение принято, ответ потерян | Повторить подтверждение с тем же ключом | Прежний exchangeId, второе списание отсутствует |
| П-4 | Клиент вновь открыл приложение и знает exchangeId | Нажать «Проверить результат» | Состояние операции, найденной по этому номеру |
| П-5 | Казначейство отказало до выдачи цены | Открыть экран | Кнопка подтверждения недоступна |

### Чек-лист ревью

| Проверка | Материал | Ответственный |
| --- | --- | --- |
| Требование покрывает цель | Клиент знает сумму до подтверждения | Владелец продукта |

| Определены доступ и откат | Маскирование журнала и обработка действующих предложений | ИБ и эксплуатация |

## Часть B. REST API

### Общие параметры

| Поле | Значение |
| --- | --- |
| Базовый путь | `/fx/mobile/v1` |
| Представление | JSON в UTF-8 |
| Авторизация | Bearer-токен владельца счетов |
| Контроллер | ExchangeDesk |
| Аудитория | Мобильное приложение розничного банка |

### Полный каталог клиентских операций

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/quotes` | Получить цену и срок действия |
| POST | `/quotes/{quoteId}/confirm` | Подтвердить зафиксированные суммы |

### Параметры запроса котировки

| Поле | Обязательность | Формат |
| --- | --- | --- |
| debitAccountId | Да | UUID счёта KZT |
| creditAccountId | Да | UUID счёта USD |
| usdAmount | Да | Десятичная строка с двумя знаками и точкой |

Цена применяется только к запросившему её владельцу и указанным счетам. Изменение суммы требует новой котировки.
Ответ 201 содержит quoteId, usdAmount, debitKzt, rate, expiresAt и indicativeSpread.
В поле indicativeSpread передаётся число процентов надбавки к курсу. Поле справочное и не участвует в расчёте списания.

### Логика подтверждения

1. Проверить владельца и найти quoteId. При недоступности чужого ресурса вернуть ту же ошибку, что и для неизвестного quoteId.
2. Вернуть сохранённый результат для принятой ранее команды. Ключ команды обязателен в заголовке Idempotency-Key и действует 30 дней в рамках владельца.
3. Для новой команды сравнить время получения шлюзом с expiresAt. Если значения равны с точностью до миллисекунды, принять подтверждение и создать распоряжение.
4. При времени позже expiresAt вернуть ошибку QUOTE_EXPIRED. Если котировка уже принята с другим ключом, вернуть прежний exchangeId.
5. Вернуть 202 с exchangeId и state=PROCESSING. Ответ с уже занятым ключом для другого quoteId имеет код 409 KEY_REUSED.

### Ответы и ошибки

| Ситуация | HTTP | Тело или код |
| --- | --- | --- |
| Котировка создана / подтверждение принято | 201 / 202 | Представления из описания методов |
| Синтаксически неверный запрос или сумма вне диапазона | 400 | BAD_INPUT |
| Сессия отсутствует или истекла | 401 | AUTH_REQUIRED |
| Счёт или котировка чужие либо неизвестны | 404 | NOT_FOUND |
| Подтверждение после истечения срока | 409 | QUOTE_EXPIRED |
| Ключ подтверждения занят другой котировкой | 409 | KEY_REUSED |
| Казначейство недоступно | 503 | PRICE_UNAVAILABLE |

Код причины в клиентском представлении DECLINED обязателен. Закрытый перечень клиентских значений состоит из FUNDS_LOW.
Для входящего запроса котировки с usdAmount="0.00", действующей сессией и своими открытыми счетами пример ответа приведён ниже.
HTTP 422, тело `{"code":"BAD_INPUT","field":"usdAmount"}`.

### Операционный журнал

| Момент записи | Состав полей |
| --- | --- |
| Получение котировки | quoteId, время, код результата |
| Успешное завершение обмена | exchangeId, IBAN обоих счетов полностью, время DONE |
| Отказ | exchangeId, время и код причины, переданный расчётным модулем |

Записи журнала доступны дежурному подразделению в режиме чтения в течение 30 суток.
