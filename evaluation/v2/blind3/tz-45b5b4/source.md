# Архивная копия справки об остатке

## Часть A. Новый функционал

### Назначение и участники

Клиент в мобильном банке заказывает электронную копию ранее выданной ему справки и получает её после подготовки архивом. Карточка ранее выданной справки уже существует в приложении и передаёт certificateId. Услуга бесплатна. Поиск документов и выпуск новых справок выполняются другими функциями.

**Паспорт.** Мобильный банк, раздел «Мои документы». Владелец процесса — управление клиентского сервиса. Заказ идёт в хранилище копий и через диспетчер в архив, итог архива обновляет запись, приложение читает её по запросу клиента.

### Функциональные требования

- Ф-1. Заказать и прочитать копию может только владелец справки. При неизвестном или принадлежащем другому клиенту certificateId сервис возвращает одинаковый ответ 404 ABSENT. До первого заказа чтение своей справки в этой услуге также даёт 404 ABSENT.
- Ф-2. Для справки существует не более одного бессрочного заказа на копию. При первом заказе сервис атомарно сохраняет состояние WAITING и задание на отправку в архив. Успех первого заказа означает сохранение обоих объектов. Повтор возвращает текущее состояние того же заказа без нового задания, в том числе при одновременных запросах.
- Ф-3. После итогового сообщения FILE от архива сервис показывает READY и строку contentBase64 с байтами PDF. До допустимого итогового сообщения состояние WAITING, содержимое равно null. После окончательного отказа архива состояние UNAVAILABLE и содержимое равно null. Повторный заказ после окончательного отказа возвращает то же состояние.
- Ф-4. Приложение показывает «Готовится», «Скачать PDF» или «Копия недоступна» по состоянию WAITING, READY или UNAVAILABLE соответственно. Кнопка «Обновить» перечитывает состояние. Строка base64 декодируется приложением в файл PDF без изменения байтов.

### Данные, интеграция и НФТ

- Д-1. Реестр, доступный сервису, хранит обязательные certificateId (ровно восемь цифр, включая ведущие нули) и ownerId (идентификатор владельца). Сервис копий хранит certificateId как уникальный ключ заказа, состояние, содержимое и устойчивое задание передачи. Конечный результат сохраняется весь период существования архивной справки. В рамках этой услуги справка существует бессрочно и владелец не меняется.
- И-1. Архив принимает задание с ключом certificateId. При отсутствии подтверждения доставки диспетчер повторяет передачу каждые 30 секунд до подтверждения. Архив обрабатывает один ключ один раз. При временной недоступности архива заказ остаётся WAITING, клиент может его читать.
- И-2. Архив присылает заверенный итог с ключом и ровно одним результатом — FILE (корректные байты PDF от 1 до 262144 включительно) или NO_COPY. FILE переводит WAITING в READY, NO_COPY — в UNAVAILABLE. Изменение состояния и содержимого атомарно. Применяется первый допустимый итог для существующего заказа. Последующие итоги, неизвестные ключи и сообщения вне контракта оставляют запись без изменений. Сверку отправителя и доставку выполняет действующий внутрибанковский шлюз.
- НФ-1. На приёмочном стенде при доступных реестре и хранилище не менее 95 % из 3 000 запросов чтения при 10 запросах в секунду получают ответ не дольше чем за 500 мс. Все запросы авторизованы и читают READY с файлом 262144 байта. Время измеряется на сервере от приёма запроса до окончания записи ответа.

### Критерии приёмки

| ID | До действия | Действие | Результат |
|---|---|---|---|
| КП-1 | У владельца справки 00120034 ещё нет заказа | Одновременно отправить два заказа до любого ответа архива | Один 201 и один 200, оба WAITING, одно задание |
| КП-2 | Свой заказ WAITING, архив подтвердил FILE | Прочитать копию после фиксации итога | 200 READY, декодированные байты совпадают с архивным файлом |
| КП-3 | Свой заказ WAITING, архив дал NO_COPY | Повторить заказ после фиксации итога | 200 UNAVAILABLE, contentBase64 равно null, новых заданий нет |
| КП-4 | Есть заказ другой стороны | Запросить его своей действующей сессией | 404 ABSENT без состояния или файла |
| КП-5 | Свой заказ READY | Получить ещё один итог NO_COPY, затем нажать «Обновить» | 200 READY, исходные байты сохранены |

## Часть B. Спецификация REST API

Операции клиентского API принимают действующую сессию Bearer, certificateId в пути в формате Д-1, без query и тела. Порядок общих проверок — сессия (401 SESSION), формат запроса (400 INPUT), доступ к реестру (503 REGISTRY_DOWN), наличие справки и владение (404 ABSENT), доступ к хранилищу копий (503 STORE_DOWN). При 503 STORE_DOWN фиксации нет. При потере ответа после фиксации клиент повторяет прежний запрос.

| Операция | Путь | Результат после общих проверок |
|---|---|---|
| Заказать | POST /v1/certificates/{certificateId}/archive-copy | При первом заказе 201 и снимок WAITING в момент фиксации. При существующем заказе 200 и снимок его текущего состояния. |
| Прочитать | GET /v1/certificates/{certificateId}/archive-copy | 200 и снимок текущего состояния. Для своей справки без заказа вернуть 404 ABSENT. |

Снимок JSON содержит ровно certificateId (string из Д-1), state (string из WAITING, READY, UNAVAILABLE) и contentBase64. Для READY последнее поле содержит строку стандартного Base64 RFC 4648 с обычным заполнением, без переносов. Для WAITING и UNAVAILABLE оно равно JSON null. Ошибки содержат только строковое поле code. Пример после первого заказа — `{"certificateId":"00120034","state":"WAITING","contentBase64":null}`.
