# Проверка кода трёх валидаторов

Зафиксированы BCC Review release 1933b20c и эксперимент 786366da, ERA216 4755c455, azekowka c704a9e2. Проверены функции, которые вызываются для переданного по CLI файла. Затем запущены обработчики цитат и детерминированные правила на новых текстах. Позднейшая голова release 4930e950 изменила два файла документации, дерево src/ сохранило SHA 70d38c38. Повтор использует Git-версии исходников и не требует доступа к моделям. [Сценарий](code-probes.py) · [Сырые результаты](code-probes.json)

## Что вызывается при обычном запуске

- **BCC Review.** python -m bcc_review выбирает v2. CLI передаёт путь входного файла в pipeline.review. Конвейер строит представление документа, запускает нарезку, правила и рецензентов, проверяет источники кандидатов, передаёт оставшихся судье и формирует вопросы. Открытый critical с блокируемой областью даёт запрет для этой области. Три блокирующих major дают «с условиями», один или два допускают «можно» в полном прогоне. Неполная проверка ограничивает положительный вердикт. mock выбирает ответы из тестового каталога, а offline включает предварительную проверку правилами. По коду здесь есть три разных режима работы. [Вход v2](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/__main__.py#L36) · [Загрузка и этапы](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/v2/pipeline.py#L365) · [Правило вердикта](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/v2/pipeline.py#L113) · [Выбор провайдера](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/v2/pipeline.py#L132)
- **Эксперимент BCC Review.** Восемь файлов из src/ отличаются от релизного коммита. В штатном пересмотре новый кандидат проходит duplicate_of, затем _judge_new. Судья получает полный привязанный ответ владельца. В проверке согласованности отдельная функция отбрасывает пары, для которых из двух цитат нельзя обосновать конфликт. Функции поиска цитаты у этих двух коммитов побайтно совпадают. В инструкции рецензенту рисков есть конкретный пример кэшбэка на прежнюю карту рядом с процентами, выплатами и возвратами. Это подсказка предметной области, которая способна влиять на знакомый кейс. В исследованной цепочке штатного LLM-провайдера не найдено подстановки готового официального отчёта. [Проверка дубля](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/786366da0be6fa2117028e70951c18a1a6939243/src/bcc_review/v2/stages/recheck.py#L1144) · [Вызов судьи](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/786366da0be6fa2117028e70951c18a1a6939243/src/bcc_review/v2/stages/recheck.py#L1355) · [Контекст владельца](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/786366da0be6fa2117028e70951c18a1a6939243/src/bcc_review/v2/stages/judge.py#L695) · [Проверка пары](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/786366da0be6fa2117028e70951c18a1a6939243/src/bcc_review/v2/stages/consistency.py#L710) · [Пример в рабочем промпте](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/v2/prompts/lens_risk.md#L146)
- **ERA216.** CLI загружает фактический документ, вызывает Pipeline.run и записывает отчёты. Действуют модель, правила, независимые рецензенты, сведение, проверка цитат и судья. Кэш идентифицируется содержанием системного и пользовательского сообщений, схемой и моделью. В явно выбранном replay неподходящий вход вызывает CacheMiss. Если судья недоступен, конвейер сохраняет кандидатов без слияния. Если судья оставил кандидата без решения, код возвращает его в список. Сигнал рецензента о противоречии приёмки либо пары требований первоначально получает critical, судья может изменить итоговый уровень. Это конкретные места, где тщательность калибровки влияет на число блокеров. - **Azekowka.** CLI загружает переданный файл, создаёт сессию выбранного провайдера и выдаёт отдельную ошибку при фатальном отказе LLM. Pipeline.run выполняет lint, нарезку, поэлементную проверку, проверку набора, самопроверку и вывод. Самопроверка хранит целевой ID при слиянии дублей и может изменить важность с объяснением. Один подтверждённый critical блокирует разработку, один major даёт «с условиями». На тестирование дополнительно влияет покрытие критериями приёмки. В опубликованном и проверенном пути код формирует отчёт из этих результатов. [CLI и ошибки модели](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/cli.py#L126) · [Штатная цепочка](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/pipeline.py#L101) · [Проверка и ID дублей](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/pipeline.py#L662) · [Раздельный вердикт](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/pipeline.py#L818)

В обычном CLI BCC обрабатывает --answers и --revise. ERA216 умеет пересмотреть замечания по файлу ответов, включая новые замечания. У azekowka в опубликованном парсере командной строки параметра для ответов владельца нет. ## Контроль на новых входах

Два одинаковых вхождения фразы «Срок выдачи — два рабочих дня» стояли в строках 2 и 5 разных разделов. Все системы получили подсказку «строка 5». BCC обеих версий и azekowka вернули 5. ERA216 вернул 2 и уверенность 100 из 100. Его точный поиск использует первое вхождение во всём документе. Маркер источника может вести в соседний сценарий при совершенно верных словах. [Как выбирается вхождение](https://github.com/ERA216/Hac/blob/4755c4558e1c80974b5a9c30550656f2c44e2743/revizor/verify.py#L64) · [Как учитывается близость](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/document.py#L184) · [Проверка с подсказкой](https://github.com/diiaanns07-droid/winnersOFbankCCbyMNU/blob/1933b20ca2fcde39ab59c3804a6ec4438c8ddd87/src/bcc_review/v2/quotes.py#L535)

Второй запрос содержал целиком вымышленную фразу и действительный диапазон строки 5. BCC обеих версий вернул missing. ERA216 сохранил подсказку с verified=false. Azekowka подставил настоящее содержимое строки 5, выставил verified=true со score=0.0. Это штатный резерв для основного доказательства по одному требованию. После подстановки материал можно найти точно, а связь с выводом всё ещё требует проверки. Среди 295 свидетельств 95 действующих карточек их опубликованного отчёта случаев score=0 нет. [Подстановка диапазона](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/pipeline.py#L227) · [Место фактического вызова](https://github.com/azekowka/ai-requirements-validator-task/blob/c704a9e2dffe59390c7c104a517aedfa10ae4ce8/reqvalidator/pipeline.py#L443) · [Поведение при промахе](https://github.com/ERA216/Hac/blob/4755c4558e1c80974b5a9c30550656f2c44e2743/revizor/verify.py#L76)

## Независимая сверка опубликованных цитат

Байты исходного Markdown у всех трёх совпали, SHA-256 начинается с e7dae55e5453. Для всех действующих карточек проверен указанный диапазон строк в представлении соответствующего загрузчика. Для второго сравнения применялись Unicode NFKC, нижний регистр, замена ё/е и сравнение последовательностей букв и цифр с нормализацией прочих символов. При такой проверке все три решения поместили слова цитат в заявленный диапазон. По содержанию выводов и уровней важности из этой проверки балл получить нельзя.
