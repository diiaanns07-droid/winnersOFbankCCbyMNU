# Что можно защищать по независимому испытанию

Повтор первого корпуса IE на официальном SHA `8e8e95f` выявил десять отчётов с неверным вхождением цитаты. [Результаты сравнения сборок, метрики и открытый пример](ie-release/README.md)

Для официальной сборки Max `8e8e95f` проведено отдельное испытание PV-1 с двумя банковскими политиками и перестановкой разделов. Ниже приведён более ранний корпус IE-1.0. [Результат PV-1](policy-variation/README.md)

Агент BCC версии `f91d3b6f485e883d316c94fc5e032f1a8d6c2553` создал технически проверяемый офлайн-отчёт для каждого из 24 основных Markdown-документов. Он пропустил все 24 заранее размеченных нарушения. После раскрытия эталона независимый ИИ подтвердил ещё одну способность агента — находить требования с несколькими независимо проверяемыми обязательствами. Эту способность наблюдали в трёх из четырёх синтетических банковских сюжетов. Человеческая проверка и прогон с Gemini открыты.

Четыре семьи охватывают отмену запланированного платежа, пересмотр комиссии, резервирование валюты и выдачу архивной выписки. В каждой по шесть зависимых редакций. Основной знаменатель равен 24. Две дополнительные редакции проверяют версии, ещё две — исходы решения владельца. Всего 28 содержательных документов, 31 файл с учётом повторных форматов. Измеряется только агент команды. Протокол и эталон зафиксированы до первого нового ответа агента. [Протокол](../protocol/README.md) · [Публичное обязательство по хешам](../protocol/seal.json)

## Какие выводы выдерживают проверку

Во всех 24/24 первичных отчётах оба вердикта, для разработки и для тестирования, получили значение unknown. Основание в паспорте — пропуск семантических этапов офлайн.

**Точные координаты.** Для всех 64/64 офлайн-карточек основной выборки срез текстового блока воспроизводит цитату. Корректный адрес источника позволяет быстро оспорить смысл. Например, i01/F-001 ссылается на владельца счёта, а в заголовке фигурирует владелец карты.

**Причины и переформулировки.** Четыре исходно чистые обратные пары различаются состоянием или решением. По ним агент не создал карточек вида conflict. В календарном контроле две другие карточки затронули контрольные опоры. Эта проверка относится только к правилам. Карточки реальной модели по таким входам ещё не получены. [Реестр обратных пар](../adjudication/compatible-controls.jsonl)

**Уточнённая разметка.** Для одного типа замечаний нашли 18 настоящих совпадений в трёх семьях по шесть редакций. При неизменных предсказаниях precision становится 18/58 = 31,0%, recall 18/42 = 42,9%, F1 = 36,0%. Все 24 изначально заложенные причины по-прежнему пропущены. После пересмотра на основном наборе осталось два чистых документа валютного сюжета, по одной тревоге на каждом. На панели чистых документов в новой версии разметки 0, доля тревог для этой группы не определена. Это вторичный, зависимый от выдачи разбор ИИ. [Обоснование поправки](../adjudication/README.md)

**Версии и форматы.** На четырёх A→B и одной перенумерации агент правильно проследил 0/14 ожидаемых переходов заложенных причин. При перенумерации сохранились 5/5 ранее выданных фоновых карточек. Условная доля ложных закрытий для заложенных причин не определена (0 доступных исходных карточек). Два текстовых PDF, исходный трёхстраничный и без последней страницы, вернули failed с нулём требований при наличии читаемого текста. DOCX той же версии дал partial и прошёл verify. На PDF переход с удалённой страницей остался неизмеренным. [Сопоставления редакций](../adjudication/revisions.jsonl)

**Ответы владельца.** Эталонные альтернативы по календарному сюжету задают разные результаты доступного остатка. В первичной выдаче точного вопроса о выборе времени освобождения брони не было. Через ближайший вопрос переданы два собственных текста. Родились две разные редакции. Только у одной стороны A и B согласовались (1/2). Для этой редакции проверка отчёта с решениями обнаружила ссылку на исчезнувший вопрос. Независимый повторный запуск на каждом из двух новых файлов прошёл verify. В открытом демонстрационном примере меняется реальный чек-лист агента. [Сценарий и границы демонстрации](../../defense/README.md)

## Три изменения для следующего замера

1. Сверять объект, событие, состояние и момент перед сравнением исходов. На этом участке пропущены 8/8 конфликтов одного входа, включая все 6 критичных. Проверка обратных пар нужна для контроля ложных конфликтов.
2. Сопоставлять обещанное поле ответа с исчерпывающей схемой именно этой операции. Пропущены 12/12 таких причин. На i05 агент спрашивает об отдельном методе чтения, хотя проверять нужно состав ответа операции.
3. Связывать настройки времени и количества с их единицами по обе стороны контракта. Пропущены 4/4 несовместимых единицы. Для исправления нужен тест на том же значении параметра, например на моменте истечения.

Эти числа показывают размер наблюдаемого пробела. Реальный прирост проверяют на новой закрытой выборке после фиксации следующего SHA. Результат на производственных ТЗ банка остаётся неизвестным.
