### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Ф-3 и Ф-4 дают противоположный ответ на второй push в том же месяце

**Требования:** [R-07 / Ф-3](#r-07), [R-08 / Ф-4](#r-08), [R-28](#r-28) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие · **Блокирует:** разработку и тестирование · **Нашли:** аналитик, проверка набора

- Часть A › Функциональные требования, строка 39: «На карту приходится максимум один такой push за календарный месяц.»
- Часть A › Функциональные требования, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 ограничивает карту одним push за календарный месяц, а Ф-4 требует push после смены порога «независимо от истории». Если push в этом месяце уже был, требования дают противоположные ответы.  
**Сценарий.** Порог 50 000 ₸; 10 марта расходы достигли 50 000 ₸ — push отправлен. 12 марта клиент меняет порог на 80 000 ₸ (накоплено 52 000 ₸, ниже нового порога). 20 марта расходы достигают 80 000 ₸: по Ф-3 push запрещён, по Ф-4 обязателен.  
**Последствия.** Любая реализация нарушает одно из требований: разработчик выберет правило наугад, тестировщик не сможет принять результат, клиент получит лишний push или не получит нужный.  
**Что исправить.** Выбрать приоритет: либо смена порога открывает право на ещё один push (дополнить Ф-3 исключением), либо месячный лимит действует всегда (убрать из Ф-4 «независимо от истории»). Добавить критерий приёмки на этот сценарий.  
**Было → стало.** Строка 39: «На карту приходится максимум один такой push за календарный месяц.» → «Ф-3. … На карту приходится не более одного такого push за календарный месяц, кроме случая из Ф-4: после изменения порога разрешается <уточнить: ещё один push до конца месяца или по одному на каждое изменение>.»  
**Вопрос владельцу.** Должен ли клиент получить второй push в том же месяце после изменения порога? → [Q-01](#q-01)

#### <a id="d-02"></a>🔴 D-02. Не определено, какое событие процессинга считается «проведённой покупкой»

**Требования:** [R-01](#r-01), [R-06 / Ф-2](#r-06), [R-09](#r-09), [R-10](#r-10) · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** отсутствует элемент · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, риски

- Часть A › Функциональные требования, строка 38: «В расходы входят проведённые покупки.»
- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка.»
- Часть A › Нефункциональные требования, строка 46: «в течение минуты после получения события»

**Проблема.** Не сказано, что значит «проведённая»: авторизация (холд) или клиринг, который приходит через 1–3 дня. Цель обещает уведомление «в момент покупки», а считать предписано только проведённые операции. Состав события процессинга (тип операции, сумма, валюта, дата совершения, ссылка возврата на исходную операцию) не описан.  
**Сценарий.** Клиент оплатил 15 000 ₸ в 12:00, авторизация прошла сразу, клиринг — через двое суток. Если событие — клиринг, push придёт через двое суток вопреки цели; если авторизация — отменённая авторизация уже увеличила расходы.  
**Последствия.** Нельзя спроектировать интеграцию с процессингом и посчитать расходы; требованию «в течение минуты» не к чему привязаться; тестировщик не может подготовить входное событие.  
**Что исправить.** Определить событие-источник (авторизация, клиринг или оба с правилом сверки), перечислить поля события, описать обработку отмены авторизации; согласовать цель с выбранным событием.  
**Было → стало.** Строка 43: «Процессинг → сервис расходов: проведена покупка.» → «Покупка считается проведённой при получении от процессинга события <уточнить: авторизации или клиринга>. Событие содержит идентификатор операции, идентификатор карты, тип операции, сумму в тиынах, валюту, дату и время совершения (UTC+5), для возврата — идентификатор исходной операции.»  
**Вопрос владельцу.** От какого события процессинга считать покупку проведённой: авторизация или клиринг? → [Q-02](#q-02)

#### <a id="d-04"></a>🔴 D-04. Неверная сумма в API описана двумя способами: статус 400 и ответ 200 с ERROR

**Требования:** [R-34](#r-34), [R-40](#r-40), [R-41](#r-41) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие статусов · **Блокирует:** разработку и тестирование · **Нашли:** архитектор, тестировщик

- Часть B › Статусы, строка 163: «Ответ в случае, если параметры запроса заполнены неверно.»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»
- Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Для неверной суммы документ даёт два ответа: статус 400 «параметры заполнены неверно» и статус 200 с result=ERROR и сообщением «Проверьте сумму». Заголовок «200. Successful — Created» смешивает коды 200 и 201.  
**Сценарий.** Приложение отправляет amount=500 (ниже нижней границы). По описанию статусов сервер возвращает 400 {"message":"Некорректный запрос"}, по примеру ответа 200 — 200 {"result":"ERROR","message":"Проверьте сумму"}.  
**Последствия.** Приложение не знает, по какому признаку показывать ошибку под полем; автотест не может зафиксировать ожидаемый код; бэкенд и приложение реализуют разное.  
**Что исправить.** Выбрать один способ: ошибка проверки суммы — 400 с полями result=ERROR и message; из примеров 200 убрать ответ ERROR; заголовок заменить на «200. OK».  
**Было → стало.** Строка 171: «{"result":"ERROR","message":"Проверьте сумму"}» → «400. Параметры запроса заполнены неверно, в том числе сумма вне диапазона 1 000–1 000 000: {"result":"ERROR","message":"Проверьте сумму"}.»  
**Вопрос владельцу.** Каким ответом API сообщает о неверной сумме: 400 или 200 с result=ERROR? → [Q-04](#q-04)

#### <a id="d-05"></a>🔴 D-05. Критерий приёмки №2 противоречит правилу отнесения покупки к месяцу (Ф-2)

**Требования:** [R-06 / Ф-2](#r-06), [R-14](#r-14) · **Критерий:** Согласованность (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · **Вид:** противоречие по событию · **Блокирует:** разработку и тестирование · **Нашли:** тестировщик

- Часть A › Функциональные требования, строка 38: «Месяц определяется по дате совершения покупки в Алматы.»
- Часть A › Критерии приемки, строка 64: «Покупка 31 января в 23:58 на 4 000 ₸»
- Часть A › Критерии приемки, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** По Ф-2 покупка 31 января в 23:58 относится к январю (месяц — по дате совершения), а критерий приёмки №2 ожидает рост февральского счётчика. У времени покупки не указан часовой пояс, «по Алматы» стоит только у времени проведения.  
**Сценарий.** Покупка 4 000 ₸ совершена 31.01 в 23:58, проведена 01.02 в 00:03 по Алматы. По Ф-2: январь +4 000 ₸, февраль без изменений. По критерию №2: февраль +4 000 ₸.  
**Последствия.** Реализация, верная по Ф-2, не пройдёт приёмку; исправление «под критерий» нарушит Ф-2 и сдвинет push в другой месяц.  
**Что исправить.** Привести критерий №2 в соответствие с Ф-2 (январский счётчик вырос на 4 000 ₸, февральский не изменился) либо изменить Ф-2; указать часовой пояс у обоих времён.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Покупка 31 января в 23:58 (UTC+5) на 4 000 ₸ | Провести 1 февраля в 00:03 (UTC+5) | Январский счётчик вырос на 4 000 ₸, февральский не изменился»  
**Вопрос владельцу.** К какому месяцу относится покупка, совершённая 31 января и проведённая 1 февраля? → [Q-05](#q-05)

#### <a id="d-06"></a>🟠 D-06. Метод изменения данных объявлен как GET, идентификатор карты передаётся в URL

**Требования:** [R-17](#r-17), [R-20](#r-20), [R-33](#r-33) · **Критерий:** ИБ и операционные риски (Чек-лист «Ревью требований» банка) · **Вид:** информационная безопасность · **Блокирует:** разработку · **Нашли:** архитектор, риски

- Часть B › Общие параметры, строка 109: «curl -G»

**Проблема.** Метод меняет настройку, но объявлен как GET — по RFC 9110 безопасный метод без побочных эффектов. Идентификатор карты и порог уходят в строку запроса и оседают в журналах прокси. Content-Type application/json указан, хотя тела нет.  
**Сценарий.** Прокси повторяет или кэширует GET /alerts/saveLimit?cardId=…&amount=50000&enabled=1 — настройка перезаписывается повторно, cardId попадает в журнал доступа.  
**Последствия.** Риск ИБ (идентификатор карты в журналах), непредсказуемые повторы и кэширование запроса.  
**Что исправить.** Заменить на POST или PUT с телом JSON; cardId передавать в теле или пути; убрать противоречие с Content-Type.  
**Было → стало.** Строка 148: «Тело не используется.» → «REST type: PUT. Тело (application/json): {"cardId": string, "amount": integer, "enabled": integer}.»

#### <a id="d-08"></a>🟠 D-08. Типы amount и enabled в запросе и в ответе расходятся (integer ↔ string)

**Что исправить.** Свести архитектуру, sequence и BPMN: единые имена, связь с настройками, ветви «порог не достигнут» и «push уже отправлен».

#### <a id="d-22"></a>🟠 D-22. Экран не описан полностью: выбор карты, тексты ошибок, период «суммы за месяц»

**Требования:** [R-03](#r-03), [R-05 / Ф-1](#r-05) · **Критерий:** Полнота требования (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · **Вид:** неполнота · **Блокирует:** разработку · **Нашли:** аналитик

- Часть A › Дизайн процесса UI, строка 29: «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»
- Часть A › Дизайн процесса UI, строка 29: «При ошибке ввода сообщение появляется под полем.»

**Проблема.** Не описаны выбор карты, тексты ошибок, начальное значение поля, реакция на 401, 404 и 500; не сказано, считается ли «сумма за месяц» с начала месяца или с момента включения.  
**Сценарий.** Клиент включает уведомление 20-го числа при расходах 45 000 ₸ с начала месяца: экран покажет 45 000 или 0?  
**Последствия.** Приложение и бэкенд считают по-разному; тексты ошибок придумает разработчик.  
**Что исправить.** Описать состояния экрана: выбор карты, начальное состояние, тексты ошибок для каждого кода ответа, период суммы за месяц.

#### <a id="d-24"></a>🟠 D-24. Ответы 400, 401, 404 и 500 без поля result, объявленного в таблице ответа

Вердикт считает программа: критичный дефект, блокирующий направление, — «нельзя начинать»; иначе три и более существенных — «с условиями»; иначе «можно». Подробнее — приложение Е.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон — не выше «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
