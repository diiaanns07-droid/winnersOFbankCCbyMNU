### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Ф-3 и Ф-4 дают противоположный ответ на второй push в том же месяце

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц.»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 ограничивает карту одним push за календарный месяц, а Ф-4 требует push после смены порога «независимо от истории». Если push в этом месяце уже был, требования дают противоположные ответы.  
**Сценарий.** Порог 50 000 ₸; 10 марта расходы достигли 50 000 ₸ — push отправлен. 12 марта клиент меняет порог на 80 000 ₸ (накоплено 52 000 ₸, ниже нового порога). 20 марта расходы достигают 80 000 ₸: по Ф-3 push запрещён, по Ф-4 обязателен.  
**Последствия.** Любая реализация нарушает одно из требований: разработчик выберет правило наугад, тестировщик не сможет принять результат, клиент получит лишний push или не получит нужный.  
**Как исправить.** Выбрать приоритет: либо смена порога открывает право на ещё один push (дополнить Ф-3 исключением), либо месячный лимит действует всегда (убрать из Ф-4 «независимо от истории»). Добавить критерий приёмки на этот сценарий.  
**Было → стало.** Строка 39: «На карту приходится максимум один такой push за календарный месяц.» → «Ф-3. … На карту приходится не более одного такого push за календарный месяц, кроме случая из Ф-4: после изменения порога разрешается <уточнить: ещё один push до конца месяца или по одному на каждое изменение>.»

#### <a id="d-02"></a>🔴 D-02. Не определено, какое событие процессинга считается «проведённой покупкой»

- Ф-2, строка 38: «В расходы входят проведённые покупки.»
- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка.»
- Часть A › Нефункциональные требования, строка 46: «в течение минуты после получения события»

**Проблема.** Не сказано, что значит «проведённая»: авторизация (холд) или клиринг, который приходит через 1–3 дня. Цель обещает уведомление «в момент покупки», а считать предписано только проведённые операции. **Сценарий.** Клиент оплатил 15 000 ₸ в 12:00, авторизация прошла сразу, клиринг — через двое суток. Если событие — клиринг, push придёт через двое суток вопреки цели; если авторизация — отменённая авторизация уже увеличила расходы.  
**Последствия.** Нельзя спроектировать интеграцию с процессингом и посчитать расходы; требованию «в течение минуты» не к чему привязаться; тестировщик не может подготовить входное событие.  
**Как исправить.** Определить событие-источник (авторизация, клиринг или оба с правилом сверки), перечислить поля события, описать обработку отмены авторизации; согласовать цель с выбранным событием.

#### <a id="d-04"></a>🔴 D-04. Неверная сумма в API описана двумя способами: статус 400 и ответ 200 с ERROR

- Часть B › Статусы, строка 163: «Ответ в случае, если параметры запроса заполнены неверно.»
- Часть B › 200. Successful — Created, строка 165: «200. Successful — Created»
- Часть B › 200. Successful — Created, строка 171: «{"result":"ERROR","message":"Проверьте сумму"}»

**Проблема.** Для неверной суммы документ даёт два ответа: статус 400 «параметры заполнены неверно» и статус 200 с result=ERROR и сообщением «Проверьте сумму». Заголовок «200. Successful — Created» смешивает коды 200 и 201.  
**Сценарий.** Приложение отправляет amount=500 (ниже нижней границы). По описанию статусов сервер возвращает 400 {"message":"Некорректный запрос"}, по примеру ответа 200 — 200 {"result":"ERROR","message":"Проверьте сумму"}.  
**Последствия.** Приложение не знает, по какому признаку показывать ошибку под полем; автотест не может зафиксировать ожидаемый код; бэкенд и приложение реализуют разное.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

| Критерий | Стандарт | Уровень | Что проверяется |
| :--- | :--- | :--- | :--- |
| Необходимость | ISO/IEC/IEEE 29148:2018 п. 5.2.5 | требование | без требования продукт неполон; это не дубль другого пункта |

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
