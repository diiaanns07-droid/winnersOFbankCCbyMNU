## 0. Коротко

1. Нужна **программа** (не ответ из чата), которая берёт файл с требованиями (в первую очередь
   PDF) и пишет **отчёт на русском**: нарезка на требования, проверка каждого, проверка набора,
   сводка и вердикт, можно ли начинать разработку и тестирование.
2. Проверка ведётся по **ISO/IEC/IEEE 29148:2018 (5.2.5, 5.2.6)** и **IEEE 830-1998 (4.3)**.
   Каждое замечание должно указывать на конкретное место документа, общие фразы не допускаются.
3. Документ задания **специально испорчен** («текст не вычитывался и не исправлялся»), в нём
   заложены дефекты. Жюри почти наверняка сверяет найденное с этим списком. Наш эталон — в разделе 5.
4. **Главное:** в открытом доступе уже лежит очень сильное решение другого участника (форк
   `azekowka/ai-requirements-validator-task`, агент `reqvalidator`) с отчётом: 53 требования,
   95 замечаний, 5 критичных, прогон на Claude Opus 5.5. Копировать его нельзя: лицензии нет, а
   жюри увидит совпадение с публичным репозиторием конкурента. Это планка, которую надо превзойти.
   Как — в разделе 7.
5. Гарантировать победу нельзя. Шансы сильнее всего поднимают четыре вещи: точные находки без шума,
   измеренное качество (recall и precision на эталоне), надёжный прогон на бесплатном Gemini у
   жюри одной командой и встраивание в процесс банка (автозаполнение их же чек-листа ревью).

## 1. Что именно хотят

### 1.1. Продукт
ИИ-агент для **статической проверки** готового документа требований, то есть ревью текста до
разработки. Запускать и тестировать программу, которую описывает документ, не нужно. Агент ищет
дефекты формулировок: двусмысленность, непроверяемость, противоречия, пропуски, лишние проектные
решения.

### 1.2. Как проходит прогон (п. 3 ТЗ)
1. Организаторы выдают документ требований.
2. Агент получает его на вход: **PDF обязателен**, остальные форматы (DOCX, MD, HTML, TXT) идут в плюс.
3. Агент выделяет отдельные требования и проверяет каждое.
4. Агент проверяет набор требований целиком.
5. Агент записывает отчёт в файл.

### 1.3. Что сдаётся (п. 2 ТЗ)
| Что | Требование | Как не провалить |
| :--- | :--- | :--- |
| Репозиторий с агентом | код, зависимости, инструкция; **другой человек повторяет прогон** | проверить установку на чистой машине по README (Windows и macOS тоже) |
| Отчёт | сформирован **именно этим агентом** по выданному документу; ручной отчёт не принимается | отчёт руками не править; в паспорте коммит; рядом JSON и журнал обращений к модели как доказательство |
| Документ и отчёт | сдаются **рядом со ссылкой** на репозиторий, а не вместо него | — |

### 1.4. Обязательный состав отчёта (п. 6 ТЗ)
| Раздел | Что внутри |
| :--- | :--- |
| Паспорт прогона | название документа, дата, модель, версия агента (коммит или тег) |
| Нарезка | таблица «ID в отчёте — ID в документе — краткая формулировка»; если номеров нет, агент присваивает свои и сохраняет цитату |
| Проверка каждого требования | по критериям, с цитатой и местом |
| Проверка набора | согласованность, полнота, покрытие, прослеживаемость |
| Сводка | число требований, число нарушений, **список критичных дефектов** (непроверяемые, противоречивые, неполные) |
| Итог | можно ли начинать разработку и тестирование; что исправить в первую очередь |
| Сквозное правило | **никаких общих фраз**: каждое нарушение ссылается на конкретное место |

### 1.5. Требования к репозиторию (п. 7 ТЗ)
* код агента и файл зависимостей;
* README: как получить ключ LLM, куда его положить, какой командой запустить, куда ляжет отчёт;
* **одна команда**: `агент <файл требований> <файл отчёта>`;
* секретов в репозитории нет; в корне лежит `.env.example` без ключа;
* язык и каркас свободные. Обязательны чтение документа, обращение к модели и запись отчёта.
  Мультиагентность не требуется.

### 1.6. Модель (п. 4 ТЗ)
Подойдёт любая LLM; бесплатный Gemini (Google AI Studio) назван как достаточный вариант. Модель
указывается в инструкции. Платный ключ не нужен, поэтому **жюри, скорее всего, будет запускать
агента на бесплатном Gemini**. На нём агент обязан работать надёжно и быстро.

## 2. Почему банку это нужно (контекст)

* **Дефект в требованиях — самый дорогой дефект.** Ошибка, найденная на ревью, исправляется правкой
  абзаца. Та же ошибка в проде оборачивается переделкой кода, тестов, интеграций, а иногда
  инцидентом с клиентами. Принято считать, что разница составляет десятки раз.
* **Документ написан по внутреннему шаблону банка** (это наш вывод по структуре): «Общие сведения →
  Цели → Архитектура → UI → BPMN → ФТ → Sequence → НФТ → Данные → Интеграция → Тестирование →
  Критерии приёмки → **Ревью требований (чек-лист из 14 пунктов)** → Блок согласующих», а для
  API отдельный шаблон с полями `Controller`, `Gitlab project`, `Swagger`, `DB field`. Сейчас такой
  чек-лист заполняют вручную аналитики, тестировщики, архитекторы и ИБ. Агент нужен как первая
  линия ревью: он быстрее, единообразнее и ничего не забывает.
* **Почему «без общих фраз».** Главная беда LLM — вода («рекомендуется повысить качество
  требований»). Банку нужен результат, по которому аналитик сразу правит текст: цитата, место,
  какой критерий нарушен, как переписать.
* **Почему «отчёт сформирован агентом» и «повторяемый прогон».** Оценивают инструмент, который
  можно внедрить, а не разовую работу промпт-инженера.
* **Почему бесплатная модель и свобода выбора.** Решение должно быть дешёвым и воспроизводимым. Для
  банка важен и закрытый контур (документы нельзя отправлять во внешние API), поэтому поддержка
  локальной модели (Ollama или vLLM) даёт сильный плюс на защите, даже если основной прогон идёт на
  Gemini.
* **Почему кейс про push и REST API.** Это типичная банковская доработка: карточный процессинг,
  клиринг, возвраты, часовые пояса, идемпотентность событий, API мобильного банка. В таких местах
  ловушки находит только тот, кто разбирается в предметной области.

## 3. Критерии качества, по которым проверяет агент

### 3.1. Отдельное требование: ISO/IEC/IEEE 29148:2018, п. 5.2.5
| Код | Свойство | Вопрос к требованию |
| :--- | :--- | :--- |
| И1 | Necessary (необходимое) | без него будет пробел? не дубль? |
| И2 | Appropriate (уместное) | говорит «что», а не «как»? нет лишних решений реализации? |
| И3 | Unambiguous (однозначное) | одно толкование? термины, единицы и часовые пояса определены? |
| И4 | Complete (полное) | есть субъект, условие, действие, ограничения, ошибки, границы? |
| И5 | Singular (единичное) | одно обязательство, а не четыре в одном пункте? |
| И6 | Feasible (осуществимое) | реализуемо при описанной архитектуре и данных? |
| И7 | Verifiable (проверяемое) | можно объективно доказать выполнение (тест, анализ, инспекция)? |
| И8 | Correct (корректное) | соответствует предметной области, не противоречит другим пунктам и критериям приёмки? |
| И9 | Conforming (по шаблону) | ID, модальность («система должна…»), единая терминология |

**П. 5.2.7 (язык требований)** даёт словарь для детерминированного линтера: размытые и
субъективные слова («быстро», «удобно», «в момент», «своевременно», «оптимально»), лазейки («по
возможности», «при необходимости»), открытые перечни («и т. д.», «и далее»), неопределённые
местоимения, отрицания, пассив без субъекта.

### 3.2. Набор требований: ISO/IEC/IEEE 29148, п. 5.2.6
Полнота · Согласованность · Осуществимость набора · Понятность · Возможность валидации.

### 3.3. Спецификация: IEEE 830-1998, п. 4.3
4.3.1 корректность · 4.3.2 однозначность · 4.3.3 полнота · 4.3.4 согласованность ·
**4.3.5 ранжирование по важности и стабильности** · 4.3.6 проверяемость · 4.3.7 модифицируемость ·
4.3.8 прослеживаемость.

### 3.4. Шкала серьёзности (предлагаем)
* 🔴 **критичный** — блокирует разработку или тестирование: противоречие, непроверяемое или
  неполное ключевое правило, нереализуемость;
* 🟠 **существенный** — высокий риск неверной реализации;
* 🟡 **незначительный** — оформление, стиль.

> Калибровка важнее количества. Если «существенным» помечено почти всё, жюри перестаёт доверять отчёту.

## 4. Устройство выданного документа

`docs/requirements.md`, 198 строк, две части:

* **Часть A** (строки 8–91): функционал «Месячный порог расходов по карте». Клиент задаёт порог
  от 1 000 до 1 000 000 ₸ и получает push, когда расходы за месяц достигают порога. Здесь же 4 ФТ
  (Ф-1…Ф-4), архитектура, UI, BPMN, sequence, НФТ, данные, интеграция, 3 критерия приёмки,
  **незаполненный банковский чек-лист ревью** (строки 70–85) и пустой блок согласующих.
* **Часть B** (строки 95–198): дочерняя спецификация REST API `saveLimit`.

Номера есть только у Ф-1…Ф-4, остальное агенту нужно нарезать самому. Отсюда требование ТЗ:
«если номеров не было, агент присваивает свои и сохраняет цитату».

Ловушки для нарезки:
* чек-лист ревью и блок согласующих — **не требования**: это шаблон. Их нужно исключить из
  нарезки, но отметить как незаполненные;
* таблицы API — это контракт. Не стоит делать требование из каждой ячейки вроде «Path-параметры:
  не используются»: получится шум;
* в разделе «Статусы» (строки 160–198) заголовки и тела ответов перепутаны местами.

### 5.3. 🟡 Незначительные и оформление
* «личный бюджет» (23) ↔ «порог» ↔ `saveLimit` / `limit_kzt`: терминология не едина, глоссария нет;
* заглушки: «заполняются тестировщиками» (57), версия и дата не заполнены (68), чек-лист без
  отметок (72–85), согласующие пусты (91), задачи в Jira нет (20), так что источник требований не
  прослеживается;
* нет ID у НФТ, данных и интеграции; нет приоритетов (IEEE 830, 4.3.5);
* дубль: Ф-4 (40) ↔ Особые правила, п. 3 (126); в п. 1 Особых правил (124) границы не названы;
* неатомарность: в Ф-2 четыре правила в одном пункте, в Ф-1 и Ф-3 по два-три;
* Description «Сохранение порога. Функциональные требования: чтение порога» (103) бессвязен;
* схема отката (чек-лист, строка 76) не описана: нужен feature flag;
* «в Алматы» лучше заменить на «UTC+5 (Asia/Almaty)»: с 1 марта 2024 года в Казахстане единый
  часовой пояс UTC+5.

**Ожидаемый вердикт:** начинать разработку и тестирование **нельзя**. Исправлять в таком порядке:
К2 → К5 → К4 и К3 (API) → К1 и критерии приёмки → данные и роли.

## 6. Публичное решение конкурента (форк azekowka)

В официальном репозитории BCC-HUB лежат только ТЗ, документ и `.env.example`. В публичном форке
`azekowka/ai-requirements-validator-task` другой участник выложил полное решение `reqvalidator`
(Python): 9 тысяч строк кода,
тесты, CI, 7 провайдеров LLM, PDF/DOCX/MD/HTML, кэш, самопроверка. Там же лежит отчёт
`reports/requirements-report.md`.

| Показатель | Значение |
| :--- | :--- |
| Модель | Claude Opus 5.5 через Claude Code CLI |
| Время и обращения | 12 мин, 16 запросов, около 440 тыс. токенов |
| Нарезка | 53 «требования», ID в документе есть у 16 |
| Замечания | 95: 🔴 5, 🟠 69, 🟡 21; ещё 85 отклонено при самопроверке |
| Требований без замечаний | 2 из 53 |
| Отчёт | 2 474 строки Markdown и JSON на 11 тыс. строк |
| Gemini free | 10–20 мин; в часы пик падал на 503 |

Его 5 критичных дефектов совпадают с нашими К1–К5. Почти всё из раздела 5 там тоже найдено.
Значит, «найти больше» почти не выйдет. **Выигрывать придётся качеством, удобством и доказательностью.**

### Слабые места эталона = наши точки роста
1. **Шум и раздутость.** 95 замечаний на 198 строк, 69 «существенных», 2 474 строки отчёта.
   Человек из банка столько не прочитает. Одна проблема (нет метода чтения) размазана по Д-37,
   Д-38, Д-47, Д-39.
2. **Слишком мелкая нарезка.** Каждая ячейка API-таблицы стала требованием («Path-параметры:
   не используются», «Content-Type»). Цитаты статусов растянуты на 20 строк (строки 176–198).
3. **Медленно на бесплатной модели**: 10–20 мин и около 17 запросов, а жюри будет запускать на Gemini.
4. **Банковский чек-лист ревью только помечен как «не заполнен»**, хотя его можно заполнить.
5. **Раздел «Требования к тестированию: заполняются тестировщиками»** остался пустым. Агент мог бы
   предложить черновик тест-кейсов.
6. **Нет измеренного качества**: recall и precision на размеченных документах не посчитаны.
7. **Нет UI и экспорта** в рабочие инструменты (Jira, Confluence, DOCX).

> ⚠️ **Не копируйте код `reqvalidator`.** Лицензии нет, репозиторий публичный, совпадение с
> конкурентом видно сразу. Читать его как образец архитектуры можно, писать нужно своё.

## 7. Как выиграть: что сделать (по убыванию отдачи)

### 7.1. Обязательный фундамент (без него не победить)
* одна команда `python -m <agent> docs/requirements.md reports/report.md`;
* `.env.example`, README по пунктам ТЗ, работа на **бесплатном Gemini** из коробки;
* PDF с таблицами читается корректно: проверить на PDF-версии выданного документа;
* в отчёте все 6 разделов п. 6 ТЗ; у каждого замечания ID, критерий (с номером пункта стандарта),
  серьёзность, **дословная цитата, номер строки или страницы**, рекомендация и переписанная формулировка;
* отчёт сгенерирован агентом и не правился руками; коммит в паспорте совпадает с коммитом в репозитории.

### 7.2. Точность важнее количества: главный дифференциатор
* цель: **30–45 сгруппированных замечаний** в основном отчёте вместо 95; мелочи — в приложение;
* **кластеризация дублей**: одна проблема даёт одно замечание с несколькими местами
  («нет метода чтения: строки 29, 52, 103»);
* **проверка цитат кодом**: каждая цитата ищется в тексте (точно, затем нечётко); номер строки
  вычисляет программа, а не LLM; замечание без найденной цитаты выбрасывается. Так уходят
  галлюцинации;
* **критик-проход**: вторая модель или второй запрос отсеивает ложные срабатывания и общие фразы,
  калибрует серьёзность;
* фильтр «общих фраз»: если в рекомендации нет ни одного слова из цитаты или документа, замечание
  отбрасывается или переписывается;
* **стабильность**: прогнать 2–3 раза (или двумя моделями) и оставить находки, которые повторились.
  Это ответ на вопрос жюри «а если запустить ещё раз?».

### 7.3. Сильные приёмы поиска противоречий (обобщаются на любой документ)
* **«Исполнение» критериев приёмки**: для каждой строки таблицы приёмки модель вычисляет ожидаемый
  результат **только по правилам Ф-x** и сравнивает его с заявленным. Так надёжно находится К1, и
  этот приём работает на любом документе;
* **матрица конфликтов правил**: попарная проверка ФТ и «особых правил» на противоречие, сценарием
  «а если…» (так находится К2);
* **детерминированные проверки API-контракта** (код, без LLM): метод HTTP ↔ глагол в URL
  (`GET …/save…`); список статусов ↔ заголовки ↔ примеры (201, 403/404); типы в таблице запроса ↔
  типы в таблице ответа; `Content-Type` ↔ «тело не используется»; единицы (тиын/тенге); прочерки
  `—`, `TBD`, «заполняются», «Да / Нет»;
* **CRUD-полнота**: если что-то «читается», должен быть метод чтения (К4); если что-то «хранится»,
  должно быть поле в модели данных (С7);
* **словарь терминов**: агент строит глоссарий (держатель, владелец, клиент; бюджет, порог, лимит)
  и показывает синонимы-конфликты (С5, С16).

### 7.4. Встраивание в процесс банка (вау-эффект на защите)
* **Автозаполнение их же чек-листа «Ревью требований»** (14 пунктов, строки 70–85): Да / Нет /
  Не требуется, обоснование и ссылки на ID замечаний. Это прямое попадание в их процесс, у эталона
  этого нет;
* **черновик тест-кейсов** для пустого раздела «Требования к тестированию»: граничные значения
  999 / 1 000 / 1 000 000 / 1 000 001, стык месяцев, возврат, Ф-4, дубль события, ошибки API.
  Формат «Дано / Когда / Тогда», с пометкой «черновик для тестировщика»;
* **переписанные требования** («было → стало») с маркерами `<уточнить: …>` вместо выдуманных значений;
* **экспорт**: CSV для импорта в Jira (одно замечание — одна задача), DOCX или HTML для Confluence.

### 7.5. Доказательство качества цифрами (жюри любит метрики)
* сделать мини-бенчмарк: выданный документ плюс 2–3 своих документа в том же банковском шаблоне с
  **заранее засеянными** дефектами, в форматах MD, PDF и DOCX;
* посчитать **recall** (сколько засеянных найдено) и **precision** (доля подтверждённых находок);
  таблицу положить в README и на слайд;
* сравнить модели (Gemini Flash, Gemini Pro, локальная) по качеству, времени и стоимости.

### 7.6. Скорость и надёжность у жюри
* документ целиком помещается в контекст, поэтому запросов нужно мало: нарезка (1), проверка
  требований пакетами (3–4), набор (2–3), критик (1), итог (1). Всего **около 10 запросов и 2–5
  минут** на Gemini Flash;
* structured output (JSON-схема в Gemini `response_schema` или Pydantic), `temperature=0`;
* **не берите модель из официального `.env.example`** (`gemini-1.5-flash`): семейство Gemini 1.5,
  скорее всего, уже снято с API. Список доступных ключу моделей смотрите через `models.list` и
  укажите в README актуальную Flash-модель (и резервную);
* повторы при 429 и 503 с паузой, резервная модель, кэш ответов (повторный прогон мгновенный);
* понятная ошибка, если нет ключа, вместо трейсбэка; никогда не писать «замечаний нет», если
  модель не ответила.

### 7.7. Подача
* **Демо**: простой веб-интерфейс (Streamlit или Gradio): загрузил PDF и через пару минут видишь
  отчёт. CLI одной командой остаётся основным способом запуска по ТЗ;
* Docker-образ и GitHub Actions workflow «Generate report» на ключе из Secrets;
* **закрытый контур**: работа с Ollama или vLLM, документы банка не уходят наружу;
* **питч на 3–5 минут**: боль (ручное ревью, дефекты всплывают в проде) → живое демо на PDF →
  5 критичных дефектов на экране → метрики → чек-лист банка заполнен → план внедрения
  (Confluence, Jira).

## 8. Рекомендуемая архитектура

```text
файл (PDF/DOCX/MD/HTML/TXT)
  └─► загрузчик: текст + адреса (строка / страница / ячейка таблицы)
        └─► линтер без LLM (п. 5.2.7, заглушки, единицы, API-контракт)
        └─► LLM: нарезка (цитаты, ID документа, тип; шаблоны исключаются)
              └─► код: сверка цитат, поиск пропущенных строк → LLM дорезает
        └─► LLM: проверка каждого требования по И1–И9 (пакетами, весь документ в контексте)
        └─► LLM: набор — противоречия (матрица и «исполнение» критериев приёмки),
                 полнота (CRUD, данные, ошибки), прослеживаемость (требование ↔ критерий)
        └─► код: сверка цитат и вычисление мест; кластеризация дублей
        └─► LLM-критик: ложные срабатывания, общие фразы, калибровка серьёзности
        └─► правила вердикта (код) + LLM: обоснование и приоритеты
        └─► отчёт .md (+ .json, + чек-лист банка, + тест-кейсы, + Jira CSV)
```

Стек: Python 3.11+, `google-genai` (Gemini), `pdfplumber` или `PyMuPDF`, `python-docx`, `pydantic`,
`jinja2`, `typer` или `argparse`, `pytest` с фиктивной LLM для тестов без ключа.

### Структура отчёта (предлагаем)
1. **Итог на первом экране**: вердикт, 5 критичных дефектов одной строкой каждый, «что исправить первым».
2. Паспорт прогона: документ, SHA-256 файла, дата и время, модель, коммит, число запросов, время.
3. Методика и критерии (таблица кодов И/Н с пунктами стандартов).
4. Нарезка: ID в отчёте — ID в документе — краткая формулировка — цитата — строка; исключённые фрагменты с причиной.
5. Проверка каждого требования: матрица «требование × критерий» и карточки замечаний.
6. Проверка набора: Н1–Н8, противоречия, покрытие критериями приёмки (матрица), глоссарий.
7. Сводка: числа, таблица критичных (противоречивые / непроверяемые / неполные).
8. Итог и приоритеты исправлений со ссылками на ID.
9. Приложения: заполненный чек-лист банка, черновик тест-кейсов, сигналы линтера, отклонённое
   критиком, журнал обращений к модели.

## 9. Риски дисквалификации и потери баллов

| Риск | Как избежать |
| :--- | :--- |
| Отчёт выглядит написанным или исправленным вручную | не править; генерировать с тега; паспорт с коммитом; JSON и журнал запросов рядом |
| Ключ попал в git, в том числе в историю | `.env` в `.gitignore`; проверить `git log -p` и secret scanning до сдачи |
| Похожесть на публичный `reqvalidator` конкурента | писать своё; другое название, архитектура, формат отчёта |
| Выдуманные цитаты и номера строк | сверка цитат кодом, места вычисляет программа |
| Общие фразы | фильтр и критик; правило «каждая рекомендация конкретна» в промпте |
| У жюри не запускается | проверить на чистом venv и чистом клоне, Windows/macOS/Linux, зафиксированные версии зависимостей |
| На финале выдадут **другой** документ или PDF | не подгонять промпты под этот документ; гонять на своём бенчмарке |
| Лимиты бесплатного Gemini | мало запросов, ретраи, резервная модель, кэш |
| Части отчёта на английском | все тексты и промпты на русском, проверка языка |
