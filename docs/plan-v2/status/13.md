  1–6, приложения А–Е; при превышении 900 строк сжимает вспомогательные таблицы (уровни 1–3), дефекты не теряются.
* `src/bcc_review/v2/render/console.py` — `summary(report, md_path=, json_path=)`: 4–8 строк в терминал.
* `src/bcc_review/v2/verify.py` — `verify_report(report, source)` и `main(argv)`; код 0 / 4.
* `tests/v2/fixtures/13_report_sample.json` — отчёт по эталону (К1–К5 критичные, С1–С20 существенные, 7 незначительных,
  67 цитат, все сверены); сборщик `13_build_sample.py`, отрисовка `13_report_sample.md` (810 строк).
* Тесты `tests/v2/test_13_report.py`, `tests/v2/test_13_verify.py` — 39 зелёных.

## API для конвейера (№01)

```python
from bcc_review.v2.render import jsonout, markdown, console
jsonout.finalize(report)                      # summary; verdict — если конвейер его не поставил
jsonout.write(report, out.with_suffix(".json"))
```

## Просьбы

* **№01**: в `src/bcc_review/__main__.py` / `cli.py` направить `python -m bcc_review verify ОТЧЁТ.json ИСХОДНИК`
  в `bcc_review.v2.verify.main`, если в JSON `"schema": "bcc-review/2"` (иначе — v1). В `run` записывать
  `stage_stats{этап: {calls, seconds, candidates}}` — по нему строится приложение Д. Имена этапов — как в
  `run.stages`; рендер понимает `docview, rules, segment, analyst|lens:analyst|lens_analyst, qa, architect, risk,
  consistency, quotes, judge, clarify, recheck, revise, render`.
* **№10**: в `rejected` — `{"id": "C-012", "source": "lens:qa", "title": "…", "reason": "…", "duplicate_of": "D-03"?}`;
  `verdict.summary` — 2–3 предложения без общих фраз; `fix_first` — 3–7 ID. Если `rewrite` относится к одной из
  цитат, а не к первой — можно добавить в дефект `rewrite_line` (номер строки «было»), рендер его учтёт.
* **№11**: для «до/после» положите в report.json блок `recheck`:
  `{"answers": [{"question_id", "answer"}], "before": {"verdict": {...}, "findings": {"critical", "major", "minor"}},
  "resolved": [...], "changed": [...], "added": [...]}`, а у дефектов — `status`. Снятые (`resolved`) в счётчики и
  карточки не попадают. `revise` → `rewrites: [{"finding_id", "line_start", "line_end", "before", "after"}]` и
  `revised_file` (путь к исправленному ТЗ) — пойдут в приложение Г.
* **№12**: офлайн-отчёт уже рисуется: при `provider = "offline"` (или пустом `models_used`) в шапке — пометка
  «Режим без модели», пустые разделы объясняют, почему пусты.
* **№03**: `verify` берёт `docview.load(path)["lines"][i]["text"]`, если модуль есть; иначе читает MD/TXT сам по
  правилам CONTRACT 2.1. Нормализация цитат в `verify.normalize` — по CONTRACT 7.
* **№14**: структура разделов и подписи — в `markdown.py` (словари `READINESS`, `CRITERIA`, `KIND_NAME`, `STAGES`),
  можно импортировать, чтобы HTML совпадал с MD.

## Решения

* Вердикт в `finalize` не перезаписывается, если уже есть; `verify` сверяет его с правилом кода (расхождение — код 4).
* Цитаты нарезки (`requirements[].quote`) `verify` проверяет мягко — предупреждение, не ошибка; цитаты дефектов —
  строго, на указанных строках (`fuzzy` ≥ 0,92 допускается только для помеченных `fuzzy`).
* Номер строки документа для MD/TXT = номер строки файла (`splitlines`), как на GitHub.
* Схема грузится из `contracts/v2.json` (ищется вверх от пакета). Для установки не в режиме `-e` файл нужно положить в
  пакет — решим с №16.
