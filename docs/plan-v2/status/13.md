## Сделано

* `contracts/v2.json` — JSON Schema report.json (CONTRACT 2.6): обязательные поля, перечисления severity/blocks/
  verified/статусов, `critical ⇒ blocks ≠ none`; необязательные `run.stage_stats`, `clarification` (№11), `rewrites`,
  `revised_file`, `title`/`signals`/`not_checked` (офлайн №12), `checklist_source` (№10), `topic`/`evidence` вопросов,
  `finding.status_after_answers`, `rule_conflict`; вердикт `no|conditional|yes|undetermined|none`. Лишние поля разрешены.
* `src/bcc_review/v2/render/jsonout.py` — `finalize(report)` (summary и вердикт считает код), `compute_summary`,
  `rule_verdict` (правило CONTRACT 5; для `provider=offline` — `no` только при блокирующем critical или `rule_conflict`,
  иначе `undetermined`), `validate`, `write(report, path, strict=False)` — схема проверяется при записи.
* `src/bcc_review/v2/render/markdown.py` — `render(report, max_lines=900)` / `write(report, path)`: «Кратко» (вердикт,
  числа, блокеры, «исправить первым», «до/после ответов», навигация), разделы 1–6, приложения А–Е; сжатие при > 900
  строк; рендер не падает на неполных данных (очистка типов, изоляция разделов, фазз-тест); в тексте нет английских
  слов вне `кода` и «кавычек» — проверено счётчиком №15.
* `src/bcc_review/v2/render/console.py` — `summary(report, md_path=, json_path=)`: 4–8 строк в терминал.
* `src/bcc_review/v2/verify.py` — `verify_report(report, source)` и `main(argv)`; код 0 / 4; цитаты на своих строках,
  страница PDF, SHA, счётчики, ссылки D-/R-/Q-, вердикт по правилу, коммит.
* `tests/v2/fixtures/13_report_sample.json` — отчёт по эталону (К1–К5, С1–С20, 7 незначительных, 67 цитат); сборщик
  `13_build_sample.py`, отрисовка `13_report_sample.md`.
* Тесты `tests/v2/test_13_report.py`, `tests/v2/test_13_verify.py` — 46 зелёных (PDF-тест идёт с `docview` №03).
* Каркас `bcc/v2` влит (`09f0dfb`): mock-прогон → отчёт рисуется, `python -m bcc_review verify` → OK.
* По живому прогону: предупреждения этапов по-русски (critical → критичный, «clarify:» → «Вопросы:»), ссылки на

## API для конвейера (№01)

```python
from bcc_review.v2.render import jsonout, markdown, console
jsonout.finalize(report)                      # summary; verdict — если конвейер его не поставил
jsonout.write(report, out.with_suffix(".json"))
markdown.write(report, out)                   # out — путь .md из командной строки
print(console.summary(report, md_path=str(out), json_path=str(out.with_suffix(".json"))))
```

`verify`: `bcc_review.v2.verify.main(argv) -> int`.

## Просьбы

* **№01 (сделано на моей стороне, к сведению):** в режиме `--answers` конвейер кладёт в `findings` только оставшиеся
  дефекты и оставляет вердикт «до» — `verify` давал 18 расхождений (ссылки вопросов/чек-листа/`fix_first` на снятые D-…,
  вердикт ≠ правилу). Теперь `jsonout.finalize` (его вызывает `write_outputs`) возвращает снятые дефекты из
  `findings_before` со `status_after_answers=resolved`, ставит вердикт по правилу кода и пересчитывает обоснование —
  живой прогон с `examples/v2/answers.md --revise`: verify OK 95/95. Ничего менять не нужно, кроме пункта ниже.
* **№01 (к сведению, haiku 04:09):** при исчерпании бюджета судья/вопросы помечены в `run.stages` как `ok` при 0
  вызовах (судья собрал реестр кодом) — лучше `partial`, иначе приложение Д пишет «✅ выполнен». На haiku линзы делятся
  по 3 раза и съедают бюджет до судьи; возможно, судье стоит резервировать 2 вызова.
* **№01 (важно):** в `pipeline.write_outputs` не дописывать `report["extra_markdown"]` к отчёту №13 — рендер сам
  рисует и `clarification` (таблица «до/после» на первом экране, ответы под вопросами, «Что изменили ответы»), и
  `rewrites` (было → стало в карточках и в приложении Г по `edits` режима `--revise`). Сейчас эти разделы №11
  окажутся в конце отчёта вторым экземпляром. Дописывать их стоит только в `fallback_markdown`.
* **№01:** `verify` подключён (спасибо). `stage_stats` и `checklist_source` уже используются в приложениях Д и В.
* **№10**: `rejected` в вашем формате (`candidate_id`, `reason_code`, `line`) рендер понимает; строку показывает.
* **№11**: `clarification`, `rewrites[].edits` (`applied`, `was`, `became`, `action=insert`), `revise_stats`,
  `revised_file` рисуются. Буквы вариантов — A–D.
* **№03 (волна 2, Word для жюри):** `report_docx(…, markdown=md)` переносит в Word сырые `<a id="…"></a>` (на живом
  отчёте — 42 заголовка и абзаца, 86 ячеек) и экранирование `\|`. Готово на моей стороне: `markdown.export_text(md)` —
  тот же отчёт без якорей и экранирования (`|` в ячейке → «∣»); проверено тестом через ваш `report_docx`: 0 «сырых»
  ячеек, заголовки чистые. Прошу в `report_docx` (или №01 в `write_outputs`): `from .markdown import export_text;
  markdown = export_text(markdown)`. И, если успеете, оглавление в начале документа — поле Word
  `TOC \o "1-3" \h \z \u` + `w:updateFields` в настройках, чтобы Word обновил его при открытии; сообщение
  экспорта — «дефектов», а не «замечаний».
* **№14 (волна 2, единый вид MD и HTML):** числа совпадают (живой sonnet: 30 = 4/15/11, 40 требований, 8 без
  замечаний, 93/93 цитат). Расходятся слова — прошу привести HTML к MD (подписи можно импортировать из
  `render/markdown.py`): **«дефекты»** вместо «замечания» (так в ТЗ: «список критичных дефектов», в MD и JSON);
  вердикт — `markdown.READINESS_PLAIN` («нельзя начинать», «можно с условиями», «можно начинать», «не определено»;
  сейчас в HTML «Не определён»); время — `markdown.run_stamp(run)` → «27.11.2026 02:50–02:54 (UTC+5)» (сейчас
  ISO `2026-11-27 02:54` по времени окончания); «Исправить первым» — та же семёрка, что в `verdict.fix_first`.
* **№14**: новые поля в отчёте: `clarification`, `finding.status_after_answers`, `signals`, `not_checked`, `title`,
  `checklist_source`, `rewrites[].edits`; подписи и словари — в `markdown.py` (`READINESS`, `CRITERIA`, `KIND_NAME`,
  `STAGES`).
* **№16**: файлы читаю и пишу с `encoding="utf-8"`, `verify` переключает вывод в `errors="replace"`;
  `contracts/v2.json` грузится по пути от пакета — для установки не в режиме `-e` нужен `package-data` или копия в
  пакете (скажите — сделаю копию в `render/`).

## Решения

* Вердикт в `finalize` не перезаписывается, если уже есть; `verify` сверяет его с правилом кода (расхождение — код 4).
* Цитаты нарезки (`requirements[].quote`) `verify` проверяет мягко — предупреждение, не ошибка; цитаты дефектов —
  строго, на указанных строках (`fuzzy` ≥ 0,92 допускается только для помеченных `fuzzy`).
* Номер строки документа для MD/TXT = номер строки файла (`splitlines`), как на GitHub.
* Схема грузится из `contracts/v2.json` (ищется вверх от пакета). Для установки не в режиме `-e` файл нужно положить в
  пакет — решим с №16.
