## Политика нарезки (решения №04)

* Одно требование — один пункт, одна строка таблицы параметров/статусов/критериев или один абзац с обязательством;
  пункт с несколькими обязательствами не дробится (атомарность — линзы).
* Таблица общих параметров метода (назначение, тип, URL, авторизация, CURL, Swagger, автор…) — **одно** требование
  на метод: так у официального документа 40, а не 44 требования, и замечания про GET/URL/Swagger ссылаются на одно R.
* Код ответа — одно требование; если код описан в перечне и в отдельном блоке с примером, требование — на строке
  перечня, блок с примером — в `excluded` («пример тела к коду N»). Пример, который единственное описание
  ответа метода, — требование.
* Термины глоссария — по одному требованию на термин (`kind = other`).
* `source_id`: собственный ID пункта; «<раздел>, п. N»; «<таблица>: <параметр>»; «<таблица>, строка N»;
  «Статус <код>»; для таблицы общих параметров — название раздела; у абзаца без номера — пусто.

## Просьбы

* **№03 и №01 — важно: `quotes.verify_requirements` портит нарезку.** `pipeline._segment` после `segment.run`
  вызывает `quotes.verify_requirements`, а она сужает диапазон требования длиннее 6 строк до строки цитаты:
  `R-16 «Общие параметры» 103–114 → 103` (в PDF `67–78 → 67`). Строки 104–114 (GET, URL, CURL, Swagger, Prod «—»)
  после этого не принадлежат ни одному требованию, и замечания С1, С20 не к чему привязать. Этап `segment`
  уже сам сверяет каждую цитату и чинит диапазоны (`normalize_requirement`), поэтому вызов лишний.
  Варианты (любой): №01 — убрать вызов `verify_requirements` из `pipeline._segment` (или вызывать только для
  требований без `coverage`); №03 — в `verify_requirements` не сужать диапазон, если найденная цитата лежит внутри
  него (убрать условие `old_e - old_s <= 6`). Проверка:
  `python -m bcc_review stage segment --doc release/input/requirements.md --from runs/<id> --provider mock` →
  в `runs/<новый>/stages/segment.json` у «Общие параметры» должно быть 103–114.
* №06: тест `test_clean_bases_have_no_conflicts[autopay.base, cardblock.base]` падает, потому что записанные ответы
  `06_qa/*.haiku.json` сделаны на старой нарезке №01. Фикстуры баз от №04 стабильны (3/3 прогона 1:1) и меняться
  больше не будут — можно перезаписать ответы один раз.
* Сделано на стороне №01 (снято): лишние поля ответа mock убираются по схеме; `ctx.warn`, `ctx.prompt`, `ask_split`
  со списком в `merge` — как в CONTRACT §9; `docview` даёт `kind = heading` — этап это использует.
