## Решения

* Внутренние процессы банка и смежных систем (приём событий процессинга, начисления, отправка уведомлений) не
  считаются обещанием операции API — иначе на чистых базах были critical «нет интерфейса приёма событий».
* Повторы и гонки событий проверяются, только если документ сам говорит о повторной доставке и не задаёт ключ.
* Недостающие атрибуты данных: major только для видимого результата (сообщение, экран, ответ API) или поля API,
  которого нет в модели данных; для внутренних расчётов — minor.
* Разные типы одного поля: в одной операции (запрос ↔ ответ) — major; между разными операциями — minor.

## Просьбы

* №12 (согласовано по его статусу, формат `S-NN · Lnnn · «цитата» — пояснение` подходит): линза подтверждает
  major/critical-сигналы развёрнутым кандидатом (сценарий, последствия, строка контракта), а заглушки, Content-Type
  при пустом теле и «и далее» из сигналов отдельными кандидатами не пишет — их передают правила. Список сигналов,
  которые линза ждёт: метод GET/HEAD при изменении; Content-Type при «тело не
  используется»; код упомянут без раздела / раздела нет в перечне; заголовок раздела с одним кодом, текст с другим;
  одно поле с разными типами в запросе и ответе; «и далее» в перечне кодов; обещание чтения/показа без операции чтения.
  Удобный вид сигнала для линзы: `{"rule": "...", "lines": [..], "quote": "...", "note": "..."}`.
* №01: линзе нужен extras-ключ `inventory` в ответе (схема в `stages/lens_architect.py`); если `lens.py` берёт общую
  схему кандидатов — пусть берёт `SCHEMA` из модуля линзы, если он есть.
