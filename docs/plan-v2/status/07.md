## Решения

* 04:00 — после правки №01 (`f589f86`: обрезка → `ask_split` делит до 3 уровней) линза **не делит** пакет
  требований: один запрос на весь документ (`llm.ask`, при обрезке №01 сам повторяет с удвоенным лимитом), при
  повторной обрезке — две части (контракт/данные/интеграция и остальное). Причина: линза сверяет места по всему
  документу, а у haiku лимит съедает рассуждение — половины переполняются так же, деление дало бы до 8 вызовов.
* 04:00 — для `claude_cli`, `gemini`, `anthropic` линза сразу просит 32 000 токенов ответа (их собственный
  лимит по умолчанию у №02 — тоже 32 000; у sonnet это только потолок: вывод ~9 тыс.). Для `openai` (локальные
  модели) — общий лимит линз 16 000. Замер haiku на официальном: 1 вызов, 205 с, 11/15 своих пунктов (было:
  16 000 → падение через 294 с, затем повтор 32 000 — всего 428 с).
* 04:00 — лимит снова 12 кандидатов (minor ≤ 3) по просьбе №01; «рассуждай коротко, опись — черновик».

* 03:40 — запасной путь не тратит вторую попытку, если и первая половина переполнилась (рассуждение модели, а не
  объём проверки).
* 03:15 — запасной путь в `run(ctx)`: если ответ не уместился в лимит вывода (`truncated` или текст ошибки про
  лимит вывода), линза повторяет запрос двумя частями — требования контракта/данных/интеграции и остальные
  (документ виден целиком, кандидаты только по своей части), затем слияние и та же постобработка.
* 03:05 — лимиты длины текстов кандидата (problem ≤ 350, scenario ≤ 300 символов и т. д.): судья всё равно режет
  до 420/320, а линза была самым медленным этапом (150 с против 52–78 с у остальных в полном прогоне).
* 03:05 — ветка логики «вернуть прежнее значение» — отдельное замечание с цитатой шага (в полном прогоне С15
  слился с «нет `result` в телах ошибок» и потерялся).

* Внутренние процессы банка и смежных систем (приём событий процессинга, начисления, отправка уведомлений) не
  считаются обещанием операции API — иначе на чистых базах были critical «нет интерфейса приёма событий».
* critical для кодов ответа — только «успех в одном месте, ошибка в другом» (клиент покажет успех при отказе) и код,
  который логика метода явно возвращает, но он нигде не описан; два разных кода ошибки (403/404, 400/422) — major.
* Повторы и гонки событий — только если документ сам говорит о повторной доставке и не задаёт ключ.
* Атрибуты данных: два замечания — для видимого пользователю значения (сообщение, экран, ответ) и для внутренних
  правил/поля API вне модели данных; атрибут для внутреннего расчёта по умолчанию minor.
* Разные типы одного поля: в одной операции (запрос ↔ ответ) — major; между разными операциями — minor.
* Сигналы №12: major/critical-сигналы линза подтверждает развёрнутым кандидатом (сценарий, последствия, строка
  контракта); заглушки, Content-Type при пустом теле и «и далее» из сигналов не дублирует — их передают правила.
