## Решения

* 03:15 — запасной путь в `run(ctx)`: если ответ не уместился в лимит вывода (`truncated` или текст ошибки про
  лимит вывода), линза повторяет запрос двумя частями — требования контракта/данных/интеграции и остальные
  (документ виден целиком, кандидаты только по своей части), затем слияние и та же постобработка.
* 03:05 — лимиты длины текстов кандидата (problem ≤ 350, scenario ≤ 300 символов и т. д.): судья всё равно режет
  до 420/320, а линза была самым медленным этапом (150 с против 52–78 с у остальных в полном прогоне).
* 03:05 — ветка логики «вернуть прежнее значение» — отдельное замечание с цитатой шага (в полном прогоне С15
  слился с «нет `result` в телах ошибок» и потерялся).

* Внутренние процессы банка и смежных систем (приём событий процессинга, начисления, отправка уведомлений) не
  считаются обещанием операции API — иначе на чистых базах были critical «нет интерфейса приёма событий».
* critical для кодов ответа — только «успех в одном месте, ошибка в другом» (клиент покажет успех при отказе) и код,
  который логика метода явно возвращает, но он нигде не описан; два разных кода ошибки (403/404, 400/422) — major.
* Повторы и гонки событий — только если документ сам говорит о повторной доставке и не задаёт ключ.
* Атрибуты данных: два замечания — для видимого пользователю значения (сообщение, экран, ответ) и для внутренних
  правил/поля API вне модели данных; атрибут для внутреннего расчёта по умолчанию minor.
* Разные типы одного поля: в одной операции (запрос ↔ ответ) — major; между разными операциями — minor.
* Сигналы №12: major/critical-сигналы линза подтверждает развёрнутым кандидатом (сценарий, последствия, строка
  контракта); заглушки, Content-Type при пустом теле и «и далее» из сигналов не дублирует — их передают правила.
* Лимит поднят с 12 до 14 кандидатов (minor ≤ 4): на 12 стабильно отрезались С16/С19/С20. Вывод ≈ 7–8 тыс.
  токенов, опись ≈ 1 тыс. — до лимита 16 тыс. запас есть.

## Просьбы

* **№02 (срочно):** `claude -p` на haiku вернул «API Error: Claude's response exceeded the 16000 output token
  maximum…» — `providers/claude_cli.py` классифицирует это как `unknown` (ищет только «max_tokens» / «max output
  tokens»), поэтому `ask_split` не включается и этап падает через 290 с. Нужен шаблон «output token maximum» →
  `truncated`. Плюс: у haiku в лимит 16 000 входят токены рассуждения (в прогонах без лимита — 30–47 тыс.), стоит
  задать `MAX_THINKING_TOKENS` или поднять `CLAUDE_CODE_MAX_OUTPUT_TOKENS` для `claude_cli`; у Gemini проверить,
  что `thinkingBudget` не съедает `maxOutputTokens`. У себя я поставил запасной путь (см. «Решения»).

* №01: этапу линзы нужна своя схема ответа: если в модуле `stages/lens_<имя>.py` есть `SCHEMA`, пусть `lens.run`
  берёт её (у меня `inventory` + `candidates`), иначе общую схему кандидатов. Extras `inventory` — в
  `runs/<id>/stages/architect.json`. Mock-ответ: `tests/v2/fixtures/07_official/official_architect_sonnet.json`.
* №12: формат сигналов `S-NN · Lnnn · «цитата» — пояснение` подходит. Используемые сигналы: изменение через GET/HEAD;
  Content-Type при пустом теле; код упомянут без описания / нет в перечне; в разделе одного кода описан другой;
  одно поле с разными типами в запросе и ответе; «и далее»; обещан показ/чтение без операции чтения; 200 с ошибкой
  в теле при описанном 4xx; разные единицы одной величины.
* №15: (1) строка 52 официального документа содержит два предложения (обещание чтения — К4 и повторная доставка —
  С14); замечание линзы об идемпотентности с цитатой «Повторная доставка одного события процессинга сохраняет
  исходный итог» засчитывается дублем К4 — стоит сопоставлять по цитате, а не только по номеру строки;
  (2) ключевые слова С15 не ловят «прежний порог», С16 — «нет в архитектуре» / «отсутствует в архитектуре».
* №10: линза пишет «201 упомянут без описания; 200 назван Created» отдельно от К3 (по эталону это часть К3 и С2) —
  объединяй в кластер с К3.
