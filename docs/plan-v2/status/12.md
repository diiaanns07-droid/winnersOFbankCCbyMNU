# №12 — правила v2 и офлайн-режим

Ветка: `v2/12-rules` (работаю в `claude/blissful-galileo-ip4h2p`, каждый push дублирую в `v2/12-rules`).

## Сделано

* `src/bcc_review/v2/rules/` — детерминированные правила, интерфейс CONTRACT 3:
  `rules.run(view, requirements=None) -> {"signals": [...], "candidates": [...]}`;
  `requirements` — список требований или весь выход `segment` (`{"requirements", "excluded"}`).
  * `api.py` — изменение через GET/HEAD (имя, путь, описание метода); Content-Type при «тело не
    используется»; код ответа упомянут, но не описан в перечне статусов; код в разделе другого кода;
    фраза причины в заголовке не совпадает с кодом (`200. … Created`); успешный код с ошибкой в теле при
    описанном 4xx; одно поле с разными типами в запросе и ответе одного метода; сводки «методы API» и
    «перечень статусов» для линз.
  * `units.py` — денежные величины в основной и минорной единицах без правила пересчёта (тенге/тиын,
    рубль/копейка, доллар/евро/цент; пара по одной величине, если есть); минорная единица с дробной
    частью; одно поле «по UTC» и «по UTC+N»; лимиты за разные периоды (сигнал).
  * `promises.py` — метод назван по имени, но не описан; обещано чтение/показ, а операций чтения нет.
  * `placeholders.py` — прочерки в полях, заглушки («TBD», «заполняются …»), пустые поля, неотмеченный
    чек-лист «Да / Нет», пустой блок согласующих, нет версии/даты — по одному minor на вид.
  * `language.py` — словари 29148 п. 5.2.7 (размытые сроки, субъективные оценки, лазейки, открытые
    перечни, неизмеримые сравнения, неопределённость) — только сигналы, только строки-обязательства
    (в диапазонах требований, если нарезка есть). Кандидат — только открытый перечень после перечисления.
  * `_view.py` — загрузка через `docview` №03, а пока его нет — запасной читатель MD (как `try_prompt`).
  * `python -m bcc_review.v2.rules ФАЙЛ [--segment segment.json] [--signals] [--json]` — отладка.
* `tests/v2/test_12_rules.py` — 26 тестов: официальный документ, сверка цитат, схема, чистые, мутанты,
  сырой и очищенный view, слова документа в коде правил.

**Чистые документы корпуса (8): 0 кандидатов на каждом** (`*.base`, `*.paraphrase*`), сигналов по 3 —

**Мутанты корпуса: найдено 13 из 28 заложенных дефектов, ложных — 0:**
409 не описан (2 кейса), 422 не описан, `blockedAt` UTC ↔ UTC+5 (2), `getCashback` не описан,

Не ловятся правилами (это работа линз): конфликты событий и границ, «за час ↔ за сутки» (есть только сигнал),
«нет последних цифр карты в данных», «200 без изменений ↔ 409».

## Решения

* Кандидаты правил несут поле `rule_conflict` (true — конфликт двух цитат об одном предмете), нужно для
  офлайн-вердикта. Если №01 валидирует кандидатов строго по схеме модели — поле можно отбрасывать после
  офлайн-вердикта.
* Цитата кандидата — подстрока очищенного текста строки (для таблиц — ячейки через « | »), поэтому
  находится и в сыром Markdown, и в view №03.
* Сигнал: `{"id": "S-01", "rule", "kind", "line", "quote", "message", "audience"}`.
  `rules.format_signals(signals, audience="architect")` — готовый текст блока `<сигналы>`.

## Просьбы

* **№01:** в pipeline после `docview` вызвать `rules.run(ctx.view, segment_out)`; в блок `<сигналы>` линзы
  `X` класть `rules.format_signals(ctx.signals, audience=X)` (`analyst`, `qa`, `architect`, `risk`,
  `consistency`); кандидатов правил — сразу к судье вместе с кандидатами линз.
* **№05, №07:** формат сигналов выше; скажите в своём статусе, если нужен другой вид или другие сигналы.
