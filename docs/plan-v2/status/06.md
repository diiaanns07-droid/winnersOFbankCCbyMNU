**Как устроено.** Модель отвечает тремя списками в порядке рассуждения: `acceptance_checks` → `candidates` → `test_cases`
(`lens_qa.SCHEMA`). В записи `acceptance_checks` поля идут так: `row_facts` (каждый момент операции отдельно) →
`assumptions` → `rule_requirement_ids` + `rule_evidence` (цитаты правил) → `expected_by_rules` (вычисление) → `stated`
(дословно) → `verdict` → `conflict_kind` → `explanation` → `fix`. Код (`lens_qa.postprocess`):
* `conflict` → **critical**-кандидат (`kind` = `conflict_kind`, `criterion=set_consistent`, `blocks=both`) с цитатами
  правила и строки приёмки, `scenario` = факты + исход по правилу + исход по критерию, `question`, `rewrite` = `fix`;
* `conflict` без цитаты правила → `undefined`; `undefined` → **major** (`incomplete`, `blocks=testing`);
* строка приёмки сопоставляется по номеру строки (без таблицы модель даёт всем строкам один «ID»), дубли строк
  отбрасываются, пропущенные строки `kind=acceptance` → предупреждение; `run(ctx)` делает **один** повторный вызов
  только по пропущенным строкам;
* кандидат модели о той же строке приёмки, что уже даёт `conflict`, удаляется (дубль);
* critical от модели, не являющийся противоречием (`unverifiable`, `missing_element`…), понижается до major —
  на чистых базах haiku давал ложные critical; судья может поднять;
* тест-кейсы: `T-01…`, не больше 15, «Не определено требованиями: …» ⇔ `expected_defined=false`;
* `conflict`, у которого выведенный результат дословно равен заявленному, → `match`;
* больше 10 строк приёмки → первый вызов исполняет 10, каждые следующие 10 — отдельный вызов только с
  `acceptance_checks` (ответ ~1 200 символов на строку, так линза не упирается в лимит вывода на слабой модели);
  сбой дополнительного вызова — предупреждение, а не падение этапа.

## Просьбы

* **№01 (pipeline, колонка «Дефект» в разделе 4.3 отчёта):** отчёт №13 берёт `acceptance_checks[i].finding_ids`, но
  их никто не заполняет — колонка пустая и в полном прогоне. У кандидатов линзы из приёмки есть
  `acceptance_row` (= `row_requirement_id` строки). После судьи достаточно:
  `for f in findings: for cid in f["candidate_ids"]: row = cand_by_id[cid].get("acceptance_row") → check[row]["finding_ids"].append(f["id"])`.
* **№02 (claude_cli):** `claude -p` сообщает обрезку как ошибку «API Error: Claude's response exceeded the 16000 output
  token maximum» (видел на haiku: 16 000 включают ~12–22 тыс. токенов размышлений). Прошу: (1) отображать её в
  `ProviderError("truncated")` → `llm.Truncated` (тогда сработает и `ask_split` у других линз); (2) передавать
  `max_output_tokens` в `CLAUDE_CODE_MAX_OUTPUT_TOKENS` процесса `claude -p`. Линза №06 уже распознаёт эту ошибку сама.
* **№01 (mock):** в `tests/v2/fixtures/official/` нет `lens_qa.json`, поэтому mock-прогон пишет «строка критериев приёмки
  R-13…R-15 не исполнена моделью». Прошу положить туда записанный ответ `tests/v2/fixtures/06_qa/official.sonnet.json`
  (сырой ответ модели по схеме `lens_qa.SCHEMA`).
* **№15:** записанные ответы линзы — `tests/v2/fixtures/06_qa/official.{sonnet,haiku}.json` (сырые) и
  `tests/v2/fixtures/06_qa/stage/official.*.json` (выход этапа).
* **№02 (Gemini):** Gemini по умолчанию выдаёт поля объекта в алфавитном порядке. Для линзы это ломает порядок
  рассуждения (`conflict_kind` и `explanation` окажутся раньше `derivation`, `verdict` — раньше `row_facts`).
  Прошу в адаптере Gemini для каждого объекта схемы проставлять `propertyOrdering = list(properties)` (или
  отправлять `responseJsonSchema`, который сохраняет порядок) — это нужно всем этапам, не только №06.
* **№01 (lens.py / pipeline):** для линзы `qa` вызывать `stages/lens_qa.run(ctx)` (или `lens_qa.postprocess(data, ctx.requirements)`
  после общего вызова со схемой `lens_qa.SCHEMA`); результат — `candidates`, `acceptance_checks`, `test_cases`, `warnings`.
  В `acceptance_checks` есть поля сверх CONTRACT 2.5 (`row_quote`, `row_line`, `assumptions`, `rule_evidence`,
  `derivation`, `stated_line`, `conflict_kind`, `explanation`, `fix`) — прошу зафиксировать в контракте. `id` (C-…) кандидатам
  линза не ставит — это общий код; у кандидатов из приёмки есть `origin: "acceptance_check"`.
* **№13 (отчёт):** тест-кейсы готовы для приложения «черновик раздела «Тестирование требований»»: `T-NN`, Дано/Когда/Тогда,
  `gap`, `expected_defined`; таблица `acceptance_checks` (строка → правило → ожидаемое → заявленное → вердикт) —
  наглядное доказательство К1.
* **№10 (судья):** кандидаты `origin=acceptance_check` с `verdict=conflict` — самые надёжные critical (две сверенные
  цитаты, вычисление). Линза также даёт кандидатов по контракту API (403/404, 400/200) — это пересечение с №07, кластеризуй.
