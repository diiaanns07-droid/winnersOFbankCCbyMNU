**Как устроено.** Модель отвечает тремя списками в порядке рассуждения: `acceptance_checks` → `candidates` → `test_cases`
(`lens_qa.SCHEMA`). В записи `acceptance_checks` поля идут так: `row_facts` (каждый момент операции отдельно) →
`assumptions` → `rule_requirement_ids` + `rule_evidence` (цитаты правил) → `expected_by_rules` (вычисление) → `stated`
(дословно) → `verdict` → `conflict_kind` → `explanation` → `fix`. Код (`lens_qa.postprocess`):
* `conflict` → **critical**-кандидат (`kind` = `conflict_kind`, `criterion=set_consistent`, `blocks=both`) с цитатами
  правила и строки приёмки, `scenario` = факты + исход по правилу + исход по критерию, `question`, `rewrite` = `fix`;
* `conflict` без цитаты правила → `undefined`; `undefined` → **major** (`incomplete`, `blocks=testing`);
* строка приёмки сопоставляется по номеру строки (без таблицы модель даёт всем строкам один «ID»), дубли строк
  отбрасываются, пропущенные строки `kind=acceptance` → предупреждение; `run(ctx)` делает **один** повторный вызов
  только по пропущенным строкам;
* кандидат модели о той же строке приёмки, что уже даёт `conflict`, удаляется (дубль);
* critical от модели, не являющийся противоречием (`unverifiable`, `missing_element`…), понижается до major —
  на чистых базах haiku давал ложные critical; судья может поднять;
* тест-кейсы: `T-01…`, не больше 15, «Не определено требованиями: …» ⇔ `expected_defined=false`;
