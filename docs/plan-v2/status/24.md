### (а) Запас выходных токенов по этапам

У Gemini 2.5/3.x рассуждение входит в тот же лимит ответа. Провайдер шлёт лимит `max(лимит этапа, потолок
модели)` = **65 536** на всех этапах (`GeminiProvider.output_limit`): поднять выше нельзя — это потолок модели.
Рассуждение Flash на `medium` до живого замера неизвестно, поэтому оценка пессимистичная — худший записанный
вывод слабой модели с рассуждением (haiku, `status/02.md`, `profiles.py`, `segment.py`):

| Этап | Рассуждение Gemini | Худший замер вывода с рассуждением | Запас до 65 536 | При обрезке |
| :--- | :---: | :--- | :---: | :--- |
| судья | `medium` | 39 тыс. (из них 28 тыс. рассуждения даже при `low`) | **1,7×** | повтор с `low` (провайдер, `b1497569`); деление кластеров пополам (`_call_judge`) |
| набор (`consistency`) | `medium` | 34,6 тыс. | **1,9×** | повтор с `low` (`b1497569`); краткий режим этапа |
| линзы | `medium` | 31,2 тыс. (21,8 тыс. рассуждения; при `low` — 17,1 тыс.) | 2,1× | повтор с `low`; деление пакета (`ask_split`) |
| нарезка | `low` | ≈ 20–30 тыс. (JSON ≈ 5 тыс. + рассуждение 15–25 тыс.) | 2,2–3,3× | спасение целых элементов (с патчем №22) |
| вопросы | `low` | JSON ≈ 3,4 тыс. (записанный ответ) | > 5× | — |

Меньше 2× — судья и набор. У обоих вывод на 70 % — рассуждение, поэтому провайдер при `MAX_TOKENS`, если
рассуждение заняло ≥ 25 % вывода, один раз повторяет запрос на той же модели с `low` (`b1497569`; было: сразу
наверх, этап делил пакет — лишние запросы из 20 суточных и время). Проверено на поддельном сервере: судья,
`MAX_TOKENS` при 60 тыс. рассуждения → второй запрос с `LOW` → complete, «нельзя» (`test_24_jury_gemini`).
Если обрезан сам JSON (рассуждения мало) — повтор не поможет, провайдер не тратит запрос, решает этап.
На живом прогоне смотреть `thoughts_token_count` по этапам в `trace.jsonl` — заменит оценку замером.

### (в) `--runs N` на бесплатном ключе

Каждый проход `--runs N` — новый конвейер и новый провайдер; раньше окно 5 запросов в минуту и память об
исчерпанной квоте начинались заново, и на стыке проходов шли 429. Теперь окно, «остывающие» и отключённые модели —
общие для ключа в процессе (`b1497569`, `d1a2de11`; хранится отпечаток ключа, не ключ).

**Суточная квота:** у `gemini-3.8-flash` 20 запросов в сутки на проект; проход — 9 запросов (+ повторы).
`--runs 2` укладывается (≈ 18); `--runs 3` — квота кончается посреди третьего прохода: после одного 429 остаток
идёт на `gemini-3.7-flash` (дальше отключённую модель не трогает до сброса квоты в полночь по Тихоокеанскому времени — 13:00 Астаны). Значит,
проходы с N ≥ 3 на бесплатном ключе — разные модели; сравнивать их как «устойчивость одной модели» нельзя
(просьба №22 ниже). `doctor --live` тоже тратит 1 запрос основной модели. Для живого замера этапа 2:
официальный ×2 — на `gemini-3.8-flash`, 4 чистых — на `gemini-3.7-flash` (`--model`), с пометкой модели.
