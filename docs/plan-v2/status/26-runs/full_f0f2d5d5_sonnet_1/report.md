#### <a id="d-01"></a>🔴 D-01. Критерий приёмки №2 противоречит правилу Ф-2 о месяце

- Ф-2, строка 38: «Месяц определяется по дате совершения покупки в Алматы»
- критерий приёмки №2, строка 64: «Февральский счётчик вырос на 4 000 ₸»

**Проблема.** Ф-2 относит покупку к месяцу даты совершения, а строка приёмки №2 при той же покупке ожидает рост февральского счётчика по дате проведения.  
**Сценарий.** Покупка 31 января 23:58 на 4 000 ₸, проведена 1 февраля 00:03. По Ф-2 растёт январь, по критерию №2 — февраль.  
**Последствия.** Разработчик, реализовав правило Ф-2, получит «Январский счётчик вырос на 4 000 ₸, февральский не изменился», и тест по критерию приёмки №2 упадёт, хотя код верен; код, подогнанный под критерий, нарушит правило Ф-2. Приёмка остановится до решения владельца продукта.  
**Как исправить.** Исправить ожидаемый результат критерия приёмки №2 на «Январский счётчик вырос на 4 000 ₸, февральский не изменился», если верно правило Ф-2; если верен критерий — изменить правило Ф-2. Решает владелец продукта.  
**Было → стало.** Строка 64: «Февральский счётчик вырос на 4 000 ₸» → «Январский счётчик вырос на 4 000 ₸, февральский не изменился. Время 23:58 указать по Алматы.»  
**Вопрос владельцу.** Какой результат верен для этого входа: «Январский счётчик вырос на 4 000 ₸, февральский не изменился» (по правилу Ф-2) или «Февральский счётчик вырос на 4 000 ₸» (по критерию приёмки №2)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — по дате совершения в часовом поясе Алматы; B — по дате проведения в часовом поясе Алматы; C — по дате совершения для расходов, а лимит push считается по месяцу отправки в часовом…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-06 / Ф-2](#r-06 "Правила месяца и состава расходов"), [R-14 / приёмка №2](#r-14 "Февральский счётчик вырос на 4 000 ₸") · нашли: тестировщик, аналитик, проверка набора*

#### <a id="d-02"></a>🔴 D-02. Ф-3 ограничивает push одним в месяц, Ф-4 это снимает

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3: максимум один push на карту за месяц. Ф-4: следующее достижение нового порога вызывает push независимо от истории. Приоритет правил не задан.  
**Сценарий.** Порог 50 000 достигнут, push ушёл; порог поднят до 80 000, расходы дошли до 80 000 в том же месяце. По Ф-3 push нет, по Ф-4 есть.  
**Последствия.** Разная реализация и спор при приёмке; клиент получает лишний push или не получает нужный.  
**Как исправить.** Зафиксировать, лимит один push на карту в месяц или один на каждую настройку порога.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Ф-4. При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push, <уточнить: даже если в этом месяце push уже был, или не вызывает>.»  
**Вопрос владельцу.** Что верно: «второго push в месяце не будет» (как в Ф-3) или «достижение нового порога вызывает push» (как в Ф-4)? → [Q-02](#q-02) (варианты ответа)  
**Варианты ответа:** A — максимум один push в месяц на карту при любых изменениях порога; смена порога второй push…; B — один push на каждый порог: после смены порога достижение нового порога даёт push; если…; C — один push на каждый порог: если расходы уже не ниже нового порога, push уходит сразу при…

#### <a id="d-03"></a>🔴 D-03. Отклонённая сумма: ответ 200 с ERROR или код 400

#### <a id="d-04"></a>🔴 D-04. Не определено, какое событие считается «проведена покупка»

- Ф-2, строка 38: «В расходы входят проведённые покупки»

**Последствия.** Разработка выбирает событие наугад, цель «в момент покупки» при клиринге недостижима, а при авторизации не учтены отмены и расхождение сумм; клиент получает push ложно или с опозданием в дни.  
**Как исправить.** Назвать этап операции, который процессинг передаёт и который идёт в расчёт, и правила для отмены авторизации и отличающейся суммы проведения.

**Вопрос владельцу.** Что считать расходом: авторизацию или проведение (клиринг)? Если клиринг, как менять цель «в момент покупки»? → [Q-04](#q-04) (варианты ответа)  
**Варианты ответа:** A — одобренная авторизация; B — окончательное проведение (клиринг)

- **B** Только карта в статусе «действует» в KZT; настраивает только владелец счёта; иначе код 403
- **C** Любая карта в KZT, кроме закрытой и заблокированной; настраивает любой её держатель; иначе код 400

Зачем: Проверки нет в логике метода, разные команды реализуют разный доступ.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
