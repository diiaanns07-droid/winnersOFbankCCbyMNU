## Твоя роль: №06 — линза «Тестировщик». Ветка: `v2/06-qa`

Самый сильный приём конкурентов — «исполнить» каждый критерий приёмки по правилам документа и сравнить с заявленным результатом. Так надёжно ловится противоречие приёмки и функционального правила (К1 в эталоне). Плюс черновик тест-кейсов для пустого раздела «заполняются тестировщиками» — прямой вклад в процесс банка.

**Твои файлы:** `src/bcc_review/v2/prompts/lens_qa.md`, `src/bcc_review/v2/stages/lens_qa.py`, `tests/v2/test_06_*`.

Схема ответа: `candidates` (CONTRACT 2.3) + `acceptance_checks` + `test_cases` (CONTRACT 2.5).

**Что делает линза:**
1. `acceptance_checks` — по одной записи на КАЖДУЮ строку критериев приёмки, пропуски запрещены. Порядок полей важен: факты строки по событиям (что произошло, когда, на какую сумму; не смешивать даты разных событий — например, момент совершения и момент проведения) → какое правило документа проверяет строка → ожидаемый результат, выведенный ТОЛЬКО из правил (числа, период, количество уведомлений, статус) → заявленный результат → verdict `match|conflict|undefined`. Код превращает `conflict` в critical-кандидата с двумя цитатами, `undefined` — в major.
2. Проверяемость каждого требования: есть ли объективный критерий прохождения; для НФТ — метрика, точка начала и конца измерения, доля или перцентиль, нагрузка, окружение.
3. Покрытие: какие требования и ветки не покрыты приёмкой — значения на границе диапазона и за ней, негативные сценарии, повторное событие, отключённая функция, смена настроек, отмена или возврат, переход периода, ошибки API.
4. `test_cases` — до 15, формат «Дано / Когда / Тогда» с числами; ожидаемый результат только из требований; если вывести нельзя — «Не определено требованиями: …» и `expected_defined=false`.

**Задачи:**
1. **До 04:00** — промпт и постобработка в `lens_qa.py` (acceptance_checks → кандидаты; нумерация T-01…). Прогон `stage qa` на официальном документе: К1 должен находиться через acceptance_checks в 3 прогонах из 3 — на sonnet и на haiku.
2. Корпус: мутанты `*event_conflict*` и `*range_boundary*` из `evaluation/dev/corpus/cases` — найти; на 4 чистых базах — 0 `conflict` в acceptance_checks.
3. Тест-кейсы: на официальном документе вручную проверь граничные значения диапазонов — на границе и за ней результат совпадает с правилами.
4. Цикл после замеров №15, как у всех линз.

**Готово, когда:** К1 стабильно critical; на чистых базах ни одного ложного `conflict`; тест-кейсы конкретны и не противоречат документу.
