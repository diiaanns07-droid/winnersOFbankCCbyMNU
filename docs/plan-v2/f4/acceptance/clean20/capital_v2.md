#### <a id="d-01"></a>🔴 D-01. Повтор способа с неактивной картой: по правилу 200, по статусу 400

- Особые правила, п. 1, строка 129: «Повторная установка уже выбранного способа не считается ошибкой: возвращается 200 с текущими условиями»
- Часть B › Статусы, строка 168: «400. Ответ в случае, если mode неизвестен, для CARD не передан cardId или карта не активна либо открыта не в тенге»

**Проблема.** Строка 129 относит повторную установку выбранного способа к успешному ответу 200; строка 168 требует ответ 400, если карта не активна. Для повтора CARD с неактивной картой два места дают разный исход.  
**Сценарий.** Способ CARD с c-1 сохранён; 10 марта карта заблокирована; 12 марта клиент повторно отправляет CARD с c-1. По строке 129 ответ 200, по строке 168 ответ 400.  
**Последствия.** Приложение получит противоречивый ответ; тесты и клиентские сообщения разойдутся.  
**Как исправить.** Зафиксировать единый код для повтора с неактивной картой и уточнить особое правило 1.  
**Вопрос владельцу.** При повторной установке CARD с неактивной картой возвращать 400 или 200? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — проверка карты выполняется при каждом вызове с способом CARD, включая повтор; B — при повторе уже выбранного способа CARD возвращается 200 с текущими условиями без…  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-26](#r-26 "Повтор уже выбранного способа возвращает 200"), [R-41](#r-41 "Код 400 — неверный mode, нет cardId или карта не подходит") · нашли: проверка набора*

#### <a id="d-02"></a>🟠 D-02. Закрытие счёта: получатель выплаты не определён для режима «На карту»

- Ф-3, строка 38: «Проценты, выплачиваемые на карту, перечисляются на последнюю карту, указанную клиентом для способа «На карту»»

- Ф-6, строка 41: «Ф-6. При закрытии счёта проценты за неполный месяц выплачиваются в день закрытия вместе с остатком счёта»

**Проблема.** Ф-6 (строка 41) выплачивает проценты при закрытии «вместе с остатком счёта», Ф-3 (строка 38) направляет проценты на карту, Ф-5 (строка 40) капитализирует при неактивной карте. Для закрытия при «На карту» место выплаты и состав дней не определены.  
**Сценарий.** Клиент с «На карту», карта активна, закрывает счёт 15 марта с начисленными 5 000 ₸: по одному толкованию сумма уходит на карту, по другому — на закрываемый счёт; при неактивной карте решение не задано.  
**Последствия.** Разработчик и тестировщик по-разному проверят место выплаты при закрытии, и клиент может не получить деньги на карту.  
**Как исправить.** Дописать в Ф-6 получателя выплаты для каждого способа и правило для неактивной карты.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 41: «Ф-6. При закрытии счёта проценты за неполный месяц выплачиваются в день закрытия вместе с остатком счёта» → «Ф-6. **Проблема.** Ф-1 (строка 36) ограничивает способ счетами в тенге, но шаг 2 (строка 123) проверяет только принадлежность и открытость счёта; коды 400 и 404 (строка 168, строка 170) не покрывают валюту счёта.  
**Сценарий.** Клиент с накопительным счётом в другой валюте отправляет CAPITALIZATION: по шагам 1–2 запрос проходит, по Ф-1 должен быть отказ, код ответа не указан.  
**Последствия.** Сервис сохранит способ для неподходящего счёта, а тестировщик не сможет написать проверку этого отказа.  
**Как исправить.** Добавить в шаг 2 проверку валюты счёта и указать код ответа.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 123: «Проверить, что накопительный счёт принадлежит клиенту и открыт» → «2. Проверить, что накопительный счёт принадлежит клиенту, открыт и ведётся в тенге; иначе вернуть <уточнить: код 400 или 404>.»  
**Вопрос владельцу.** Какой код ответа возвращать, если накопительный счёт не в тенге? → [Q-05](#q-05) (варианты ответа)  
*Существенный, блокирует разработку · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-05 / Ф-1](#r-05 "Выбор способа выплаты, по умолчанию капитализация"), [R-22](#r-22 "Проверка принадлежности и открытости счёта") · нашли: аналитик*

#### <a id="d-06"></a>🟠 D-06. Метод 2: ответ для закрытого счёта не описан в перечне ошибок

- Часть B › Статусы, строка 170: «404. Ответ в случае, если счёт не найден или закрыт либо счёт или карта принадлежат другому клиенту»
- Часть B › Методы чтения, строка 204: «404 — счёт не найден или принадлежит другому клиенту»

**Проблема.** Метод 1 возвращает 404 для закрытого счёта (строка 170), а перечень ошибок метода 2 (строка 204) упоминает только «не найден или принадлежит другому клиенту»; ответ GET для закрытого счёта не определён.  
**Сценарий.** Приложение запрашивает GET `/savings/{accountId}/interest` для закрытого счёта: по строке 170 ожидается 404, по строке 204 ответ не определён.  
**Последствия.** Клиентское приложение и интегратор по-разному обработают экран условий закрытого счёта; тест на этот случай не написать однозначно.  
**Как исправить.** Добавить в ошибки метода 2 условие закрытого счёта и подтвердить код, либо явно указать, что для чтения закрытый счёт возвращает 200 с определённым телом.  
**Было → стало.** Строка 204: «404 — счёт не найден или принадлежит другому клиенту» → «Метод 2, Ошибки: 404 — счёт не найден, закрыт или принадлежит другому клиенту; тело {"message":"Счёт или карта не найдены"}.»  
**Вопрос владельцу.** Для закрытого счёта чтение условий должно возвращать 404 или 200 с данными? → [Q-06](#q-06) (варианты ответа)  
*Существенный, блокирует тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-43](#r-43 "Код 404 — счёт или карта не найдены либо чужие"), [R-46](#r-46 "Метод условий и процентов: GET, ответ, 404") · нашли: архитектор*

#### <a id="d-07"></a>🟠 D-07. Откат флагом: не описано, что будет с выплатами и сохранённым способом

**Где:** Часть A › Ревью требований, строка 78: «Откат — выключение функционала флагом в мобильном банке; сохранённые данные не удаляются»

**Проблема.** Чек-лист (строка 78) заявляет откат флагом с сохранением данных, но не описано, выплатит ли банк апрельские проценты и каким способом, если функция выключена после сохранения способа на следующий месяц (строка 38).  
**Сценарий.** Функция выключена флагом 15 марта после сохранения способа «На карту» на апрель: неясно, выплатится ли апрель на карту, капитализируется ли или не выплатится.  
**Последствия.** Неясно, выплатит ли банк апрельские проценты и каким способом; клиент получит расхождение.  
**Как исправить.** Добавить требование о поведении выплат при выключении и повторном включении функции.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «При выключении функции проценты выплачиваются <уточнить: прежним способом или капитализацией>; сохранённый способ не удаляется.»  
**Вопрос владельцу.** Каким способом выплачивать проценты, пока функция выключена флагом? → [Q-07](#q-07) (варианты ответа)

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
