### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Повтор после 422 с проведённой в АБС операцией: 200 или отказ

- Особые правила, п. 2, строка 139: «после 422 или 500 сервис запрашивает статус операции в АБС»
- Особые правила, п. 3, строка 140: «При ответе 422 операция получает статус REJECTED»
- Часть B › Ответ, строка 158: «При кодах 400, 401, 404, 409 и 422 погашение по этому запросу не проведено»

**Проблема.** Строка 139 при «проведена» после 422 велит вернуть 200 с результатом, а строка 140 «При ответе 422 операция получает статус REJECTED» и строка 158 «погашение по этому запросу не проведено» фиксируют отказ.  
**Сценарий.** Расчёт на 207 200 ₸; первый запрос с ключом K получает 422 `INSUFFICIENT_FUNDS` (строка 74), операция REJECTED. Повтор с тем же ключом и телом при «проведена» в АБС: по строке 139 — 200 и списание, по строке 158 — 422 и погашения нет.  
**Последствия.** Один и тот же вход даёт успех или отказ; клиент может увидеть «погашено» при нерешённом списании либо наоборот, а в споре о приёмке не определить правильный исход.  
**Как исправить.** Определить, что статус REJECTED после 422 окончателен, и сверку с АБС делать только для UNKNOWN (после 500), как в строке 48.  
**Было → стало.** Строка 140: «При ответе 422 операция получает статус REJECTED» → «После ответа 422 операция остаётся REJECTED; повтор с тем же ключом возвращает сохранённый ответ 422 без обращения к АБС. Сверка GET `/abs/prepayments/{operationId}` выполняется только для операций в статусе UNKNOWN (ответ 500).»  
**Вопрос владельцу.** Может ли АБС вернуть «проведена» для операции, которая получила 422? Если да, какой статус и ответ должны быть сохранены? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — ответ 422 окончательный; B — после 422 сервис запрашивает статус в АБС  
*Критичный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-061](#r-061 "Правила повтора запроса с тем же ключом"), [R-062](#r-062 "Последовательность запросов по кредиту и статусы"), [R-067](#r-067 "Правило успешного и неуспешного ответа") · нашли: тестировщик, архитектор*

#### <a id="d-02"></a>🟠 D-02. Повтор после 500 с истёкшим расчётом: 422 или 200 не определено

- критерий приёмки №22, строка 80: «не найдена» — погашение проводится с тем же operationId; списаний не больше одного»
- Особые правила, п. 2, строка 139: «не найдена» — запрос обрабатывается заново с тем же operationId»

**Проблема.** Строка 139: «запрос обрабатывается заново с тем же `operationId`» включает проверку расчёта по Ф-7; строка 80: «погашение проводится с тем же `operationId`» такой проверки не содержит. Истёкший расчёт при повторе не разрешён.  
**Сценарий.** Расчёт 10:00:00, 500 в 10:00:10, АБС не нашла операцию; повтор в 11:00 с тем же ключом, расчёт истёк в 10:30. По строке 139 — 422 `CALCULATION_OUTDATED`; по строке 80 — проведение с 200.  
**Последствия.** Реализация и приёмка расходятся: один и тот же повтор дает 422 или 200, клиент и банк получают разный исход.  
**Как исправить.** Зафиксировать, что повтор по «не найдена» проверяет Ф-7 и отвечает 422, либо проводит погашение без проверки срока расчёта.  
**Вопрос владельцу.** Что верно: «запрос заново по шагам метода: расчёт не действует, 422 `CALCULATION_OUTDATED`» (как в «Особые правила, п. 2») или «погашение проводится с тем же `operationId`, 200» (как в «критерий приёмки, строка 22»)? → [Q-02](#q-02) (варианты ответа)  
*Существенный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-061](#r-061 "Правила повтора запроса с тем же ключом"), [R-049 / приёмка №22](#r-049 "Сверка после 500 при повторе запроса") · нашли: проверка набора*

#### <a id="d-03"></a>🟠 D-03. Дата начала процентов для кредита без погашений не выводится из АБС

- Ф-3, строка 34: «а если погашений не было — дата выдачи кредита»
- Часть A › Требования к интеграции, строка 50: «дата предыдущего погашения, дата очередного платежа»

**Проблема.** Строка 34 берёт для кредита без погашений «дата выдачи кредита», но в строке 50 перечень полей АБС («дата предыдущего погашения, дата очередного платежа») даты выдачи не содержит.  
**Сценарий.** Кредит выдан 01.03.2027, ОД 1 200 000 ₸, ставка 21,6 %, погашение 15.03.2027, погашений не было. Дата выдачи даёт 10 080 ₸ процентов, поле АБС без значения — 7 200 ₸ или ошибка.  
**Последствия.** Разработчики получат разные суммы процентов и полного погашения для кредитов до первого платежа, а тест на такой кредит нельзя написать без знания источника даты.  
**Как исправить.** Указать в интеграции поле АБС, из которого берётся дата выдачи кредита, либо правило для кредита без погашений в ответе GET `/abs/loans/{loanId}`.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 34: «а если погашений не было — дата выдачи кредита» → «а если погашений не было — дата выдачи кредита (поле АБС «дата выдачи» из GET `/abs/loans/{loanId}`; <уточнить: добавить это поле в ответ АБС или указать другой источник даты>)»  
**Вопрос владельцу.** Должна ли АБС возвращать дату выдачи кредита в GET `/abs/loans/{loanId}`, или дата предыдущего погашения для кредита без погашений должна равняться дате выдачи? → [Q-03](#q-03) (варианты ответа)

#### <a id="d-04"></a>🟠 D-04. Источник флага доступности кнопки в интеграции не описан

**<a id="q-01"></a>Q-01** Повтор с тем же ключом после 422 · ⛔ блокирует · кому: Архитектор · к [D-01](#d-01)  
Может ли АБС вернуть «проведена» для операции, которая уже получила 422: если да, сервис возвращает 200 и переводит операцию в DONE, или ответ 422 и статус REJECTED остаются окончательными при повторе с тем же ключом?  
Где: Особые правила, п. 2, строка 139: «после 422 или 500 сервис запрашивает статус операции в АБС»; Особые правила, п. 3, строка 140: «При ответе 422 операция получает статус REJECTED»; Часть B › Ответ, строка 158: «При кодах 400, 401, 404, 409 и 422 погашение по этому запросу не проведено»

- **A** Ответ 422 окончательный: повтор с тем же ключом и телом возвращает сохранённый 422 с тем же `errorCode` без обращения к АБС; статус REJECTED не меняется
- **B** После 422 сервис запрашивает статус в АБС; при «проведена» возвращает 200 с результатом и переводит операцию в DONE, при «не найдена» возвращает сохранённый 422

Зачем: Клиент может получить 422 «не проведено» и при повторе 200 с сохранённым списанием, а тест на статус операции даст разные результаты у разных команд.

**<a id="q-02"></a>Q-02** Повтор после 500 с истёкшим расчётом · можно ответить позже · кому: Аналитик · к [D-02](#d-02)  
Что должно быть при повторе после 500, если АБС не нашла операцию и расчёт уже истёк: сервис заново проверяет срок расчёта и отвечает 422 `CALCULATION_OUTDATED`, или проводит погашение с тем же `operationId` и отвечает 200?  
Где: Особые правила, п. 2, строка 139: ««не найдена» — запрос обрабатывается заново с тем же operationId»; критерий приёмки №22, строка 80: ««не найдена» — погашение проводится с тем же operationId; списаний не больше одного»

- **A** Повтор обрабатывается заново по всем шагам метода: если расчёт истёк по Ф-7, ответ 422 `CALCULATION_OUTDATED` и погашение не проводится; если расчёт действует, погашение проводится с тем же `operationId`
- **B** Погашение проводится с тем же `operationId` и ответом 200 независимо от срока расчёта, так как ключ идемпотентности уже зафиксировал намерение клиента

Зачем: Для одного и того же входа (500, «не найдена», расчёт истёк) одно место требует отказа, другое — успешного погашения, и тесты дадут разные списания.

**<a id="q-03"></a>Q-03** Дата начала начисления без погашений · можно ответить позже · кому: Архитектор · к [D-03](#d-03)  
Откуда сервис берёт дату начала начисления процентов для кредита, по которому ещё не было погашений: ответ АБС GET `/abs/loans/{loanId}` не содержит даты выдачи, а поле «дата предыдущего погашения» для такого кредита не описано?  
Где: Ф-3, строка 34: «а если погашений не было — дата выдачи кредита»; Часть A › Требования к интеграции, строка 50: «дата предыдущего погашения, дата очередного платежа»

- **A** АБС добавляет в ответ GET `/abs/loans/{loanId}` поле дата выдачи кредита; для кредита без погашений Ф-3 берёт именно её
- **B** АБС возвращает поле дата предыдущего погашения, и для кредита без погашений в нём передаётся дата выдачи; отдельное поле даты выдачи не вводится

Зачем: Без ответа расчёт процентов для первого погашения нового кредита нельзя реализовать однозначно, и тест с кредитом без погашений даст разные суммы у разных команд.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
