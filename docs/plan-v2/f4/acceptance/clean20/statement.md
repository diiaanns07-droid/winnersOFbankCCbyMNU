#### <a id="d-01"></a>🔴 D-01. Файл и ссылка после `fileExpiresAt`: критерий строки 22 и Ф-6 расходятся

- Ф-6, строка 36: «В момент fileExpiresAt заказ переходит в EXPIRED (конечный статус), файл становится недоступен»
- критерий приёмки №22, строка 79: «В 12:14 — файл выписки; в 12:15 — ответ 410 LINK_EXPIRED»

**Проблема.** Ф-6 (строка 36) и строка 198: после `fileExpiresAt` файл недоступен, ссылка не выдаётся. Критерий строки 22 (строка 79) для `fileExpiresAt` 15.03.2026 12:00 и скачивания в 12:14 ожидает файл выписки.  
**Сценарий.** `fileExpiresAt` 15.03.2026 12:00, ссылка выдана в 12:00; скачивание в 12:14. По Ф-6 и строка 198 (`urlExpiresAt` = 12:00) ответ 410. По критерию строки 22 — файл выписки.  
**Последствия.** Тестировщик зафиксирует ожидание, противоречащее правилу; реализация выберет одно из двух поведений.  
**Как исправить.** Исправить критерий 22: при `fileExpiresAt` 12:00 скачивание в 12:14 — 410 `LINK_EXPIRED`.  
**Вопрос владельцу.** Что верно: «файл недоступен после 12:00, ссылка не выдаётся, скачивание отклоняется 410» (как в Ф-6) или «В 12:14 выдаётся файл выписки» (как в «критерий приёмки, строка 22»)? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — С момента `fileExpiresAt` файл недоступен; B — файл доступен до окончания 15-минутного срока ссылки, выданной до `fileExpiresAt`, даже…; C — файл доступен до `fileExpiresAt` включительно, скачивание в сам момент `fileExpiresAt`…  
*Критичный, блокирует разработку и тестирование · критерий «Корректность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.1) · требования [R-13 / Ф-6](#r-13 "Срок хранения файла 7 суток и ссылки"), [R-46 / приёмка №22](#r-46 "В 12:14 — файл выписки; в 12:15 — ответ 410 LINK_EXPIRED") · нашли: проверка набора*

#### <a id="d-02"></a>🟠 D-02. В ответе АБС нет признака незавершённой операции для Ф-4

- Ф-4, строка 34: «Незавершённые операции (блокировки сумм) в выписку не входят»
- Часть A › Требования к интеграции, строка 47: «операции с датой и временем проведения, описанием и суммой»

**Проблема.** Ф-4 (строка 34) требует исключать блокировки сумм, но описание ответа GET `/abs/v1/accounts/{accountId}/turnovers` (строка 47) не перечисляет поле статуса операции, по которому их можно отличить.  
**Сценарий.** АБС возвращает блокировку 5 000 на 15.02.2026 вместе с проведёнными операциями; генератор не может её исключить, исходящий остаток не сходится с АБС.  
**Последствия.** Выписка содержит незавершённые операции или не сходится с АБС, правило Ф-4 не выполнимо.  
**Как исправить.** Добавить в описание ответа АБС поле признака незавершённой операции и правило исключения её генератором PDF.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 34: «Незавершённые операции (блокировки сумм) в выписку не входят» → «Ответ АБС turnovers: для каждой операции поле <уточнить: имя поля> — признак незавершённой операции (блокировка суммы); генератор PDF исключает такие операции из выписки.»

#### <a id="d-04"></a>🟠 D-04. Экран не задан, если ответа нет после трёх запросов

#### <a id="d-05"></a>🟠 D-05. Токен скачивания в пути URL, без сессии клиента

- Ф-6, строка 36: «допускает повторное скачивание»
- Часть B › Методы сервиса выписок, строки 192 и 199: «вызывается без заголовка Authorization: доступ даёт подписанный токен в ссылке» · «GET /statements/files/{token}»

**Проблема.** Метод 5 (строка 199) отдаёт PDF с ФИО и IBAN по токену в пути URL без Authorization (строка 192). Токен допускает повторные скачивания в пределах срока и попадает в журналы шлюза и прокси.  
**Сценарий.** Клиент получил ссылку в 12:02 и переслал её; в 12:10 любой, у кого ссылка, скачивает выписку с ФИО и IBAN без сессии клиента.  
**Последствия.** Утечка персональных данных клиента и реквизитов счёта через журналы и пересланную ссылку; жалоба клиента и разбор инцидента у банка.  
**Как исправить.** Передавать токен скачивания в заголовке или теле запроса, а не в пути; привязать токен к сессии клиента, запросившего ссылку; маскировать токен в журналах.  
**Предлагаемая формулировка.** «Метод 5 принимает токен в заголовке запроса, а не в пути URL; токен действует только для сессии, в которой выдана ссылка; токен не записывается в журналы в полном виде.»  
**Вопрос владельцу.** Допускается ли скачивание по ссылке без сессии клиента, и на какой срок (<уточнить: 15 минут или меньше>)? → [Q-04](#q-04) (варианты ответа)

**<a id="q-01"></a>Q-01** Доступность файла в момент fileExpiresAt · ⛔ блокирует · кому: Владелец продукта · к [D-01](#d-01)  
Файл выписки и ссылка на скачивание доступны в момент `fileExpiresAt` или уже нет? В правиле Ф-6 сказано, что в этот момент файл становится недоступен, а в критерии приёмки для скачивания в 12:14 при окончании срока в 12:00 ожидается файл выписки.  
Где: Ф-6, строка 36: «В момент fileExpiresAt заказ переходит в EXPIRED (конечный статус), файл становится…»; критерий приёмки №22, строка 79: «В 12:14 — файл выписки; в 12:15 — ответ 410 LINK_EXPIRED»

- **A** С момента `fileExpiresAt` файл недоступен: ссылка по токену после `fileExpiresAt` отвечает 410 `LINK_EXPIRED`, новые ссылки не выдаются; критерий с 12:14 переписывается на 410 `LINK_EXPIRED`
- **B** Файл доступен до окончания 15-минутного срока ссылки, выданной до `fileExpiresAt`, даже если это время позже `fileExpiresAt`; правило Ф-6 переписывается под это исключение
- **C** Файл доступен до `fileExpiresAt` включительно, скачивание в сам момент `fileExpiresAt` допускается, после него — 410 `LINK_EXPIRED`

Зачем: Без решения нельзя написать приёмочный тест на скачивание после срока: одна команда реализует 410, другая файл, и приёмка спорит о том, какой ответ верный.

**<a id="q-02"></a>Q-02** Признак незавершённой операции в ответе АБС · можно ответить позже · кому: Архитектор · к [D-02](#d-02)  
По какому полю ответа АБС генератор PDF отличает незавершённую операцию (блокировку суммы), которую нельзя включать в выписку? В описании ответа метода АБС перечислены дата и время, описание и сумма, но признака статуса нет.  
Где: Ф-4, строка 34: «Незавершённые операции (блокировки сумм) в выписку не входят»; Часть A › Требования к интеграции, строка 47: «операции с датой и временем проведения, описанием и суммой»

- **A** Исключать операции, у которых поле статуса операции в ответе АБС указывает на блокировку суммы; имя поля и значение указываются в описании метода АБС
- **B** Исключать операции, помеченные АБС как незавершённые в отдельном поле признака незавершённости (логический признак); поле добавляется в описание метода АБС
- **C** Блокировки суммы не возвращаются методом turnovers, фильтрация не выполняется генератором PDF; описание метода АБС фиксирует это явно

Зачем: Без признака генератор либо включит блокировки в выписку и исходящий остаток разойдётся с АБС, либо исключит нужные операции; проверить это по критерию нельзя.

**<a id="q-03"></a>Q-03** Путь возврата READY/FAILED в сервис выписок · можно ответить позже · кому: Архитектор · к [D-03](#d-03), [D-08](#d-08)  
Как генератор PDF сообщает сервису выписок результат READY или FAILED: через очередь заданий или прямым вызовом? В описании архитектуры такого пути нет, хотя в схеме вызовов он есть.  
Где: Часть A › Архитектура решения, строка 20: «Сервис выписок → очередь заданий → генератор PDF (компонент сервиса выписок) → АБС.»; Часть A › Sequence Diagram, строка 40: «генератор PDF → сервис выписок: READY или FAILED»; Часть B › Схема, строка 146: «StatementOrderController → очередь заданий»

- **A** Генератор PDF публикует результат READY или FAILED в очередь заданий, сервис выписок подписан на эту очередь и обновляет статус заказа; схема в архитектуре дополняется этим путём
- **B** Генератор PDF вызывает внутренний метод сервиса выписок для обновления статуса; очередь заданий используется только для постановки задания

Зачем: Разработчики сделают разный путь обновления статуса, из-за чего статус `IN_PROGRESS` может не смениться на READY при сбое очереди и тестировать отказ будет невозможно.

**<a id="q-04"></a>Q-04** Скачивание файла без сессии и повторы по токену · можно ответить позже · кому: ИБ · к [D-05](#d-05)  
Можно ли скачивать PDF с ФИО и IBAN клиента по токену в пути URL без сессии и сколько раз? В описании метода 5 сказано, что доступ даёт токен в ссылке, а в правиле Ф-6 — что повторное скачивание допустимо.  
Где: Часть B › Методы сервиса выписок, строки 192 и 199: «вызывается без заголовка Authorization: доступ даёт подписанный токен…» · «GET /statements/files/{token}»; Ф-6, строка 36: «допускает повторное скачивание»

- **A** Токен в пути URL, срок 15 минут, повторные скачивания в срок разрешены; журналы веб-сервера и прокси не пишут путь с токеном, токен не логируется
- **B** Токен в пути URL, срок 15 минут, одно успешное скачивание: повторный запрос с тем же токеном отвечает 410 `LINK_EXPIRED`
- **C** Токен передаётся в заголовке запроса вместо пути URL, срок 15 минут, повторные скачивания разрешены; метод 5 вызывается с заголовком сессии клиента

Зачем: Без решения нельзя написать тесты на повторное скачивание и утечку токена; реализация может оставить токен в логах или допустить скачивание после смены сессии.

**<a id="q-05"></a>Q-05** Поведение при выключенном флаге statement_pdf · можно ответить позже · кому: Владелец продукта · к [D-06](#d-06)  
Что происходит с уже созданными заказами и с методами 2–5, когда флаг `statement_pdf` выключен? В документе сказано только, что пункт меню скрывается.  
Где: Часть A › Ревью требований, строка 94: «Пункт «Выписка в PDF» скрывается флагом функционала statement_pdf; остальные функции не…»

- **A** При выключении флага новые заказы не создаются (метод 1 отвечает 422... нет: отказ по флагу), а методы 2–5 продолжают работать для существующих заказов до их EXPIRED и удаления
- **B** Выключение флага останавливает все методы 1–5 и скрывает «Мои выписки»; заказы в статусах `IN_PROGRESS` и READY переводятся в FAILED

Зачем: При откате без правила заказы в READY останутся без доступа или без удаления по Ф-6 и Ф-8, и приёмка отката не сможет проверить, что клиент не теряет файл.

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
