- Ф-2, строка 38: «В расходы входят проведённые покупки»

**Проблема.** Цель (строка 23) обещает уведомление «в момент покупки», а в расходы входят «проведённые покупки» (строка 38, строка 43). Авторизация и клиринг — разные события процессинга; какое запускает пересчёт и срок минуты, не сказано.  
**Сценарий.** Покупка 1 500 ₸ при расходах 48 500 ₸ и пороге 50 000 ₸ авторизована в понедельник, проведена в среду: по цели push в понедельник, по Ф-2 — в среду.  
**Последствия.** Разработка выберет событие наугад, клиент получит push с опозданием на дни либо по отменённой покупке, приёмка превратится в спор.  
**Как исправить.** Зафиксировать, какое событие процессинга (авторизация или клиринг) учитывается, какая сумма идёт в расчёт и как обрабатывается отмена авторизации; согласовать с целью и сроком в минуту.

#### <a id="d-02"></a>🔴 D-02. Ф-3 (один push в месяц) противоречит Ф-4 («независимо от истории») после смены порога

#### <a id="d-06"></a>🟠 D-06. Метод `saveLimit` изменяет данные через GET с параметрами в адресе

- Часть B › Общие параметры, строка 103: «Сохранение порога»
- Часть B › Общие параметры, строка 104: «REST type | GET»
- Часть B › Общие параметры, строка 108: «/alerts/saveLimit»
- Часть B › Общие параметры, строка 109: «curl -G "$BASE/alerts/saveLimit" -H "Authorization: Bearer $TOKEN" --data 'cardId=demo-42&amount=50000&enabled=1»
- Часть B › Request body, строка 147: «Content-Type: application/json»

**Проблема.** Строка 104 задаёт GET для сохранения порога, `cardId`, amount, enabled идут в URL (строка 109); при этом указан Content-Type: application/json при «Тело не используется» (строки 147–148). GET кэшируют и повторяют, адрес попадает в журналы, возможна подделка запроса.  
**Сценарий.** Клиент сохраняет новое значение; при обрыве связи библиотека или прокси повторяет GET, кэширующий узел может вернуть прошлый ответ без вызова сервера — клиент видит «успех», а значение не изменилось.  
**Последствия.** Разработка реализует небезопасный контракт; риск ИБ — идентификаторы и значения в журналах; автотесты контракта и шлюз API с политикой «GET только на чтение» его отклонят.  
**Как исправить.** Заменить GET на POST или PUT (PATCH — для частичного изменения), параметры передавать в теле запроса JSON и описать его схему.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 147: «Content-Type: application/json» → «REST type: <уточнить: PUT или POST>. Параметры передаются в теле запроса (application/json).»

#### <a id="d-09"></a>🟠 D-09. Не определено поведение при выключенном уведомлении и его включении

**<a id="q-06"></a>Q-06** Ключ повтора события и единицы суммы · можно ответить позже · кому: Архитектор · к [D-15](#d-15), D-07 (снят), [D-12](#d-12)  
По какому полю распознаётся повторная доставка события, как сравниваются расходы в тиынах с порогом в тенге и откуда берутся последние четыре цифры карты для push?  
Где: Часть A › Требования к интеграции, строка 52: «Повторная доставка одного события процессинга сохраняет исходный итог»; Часть A › Требования к данным, строка 49: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах…»

- **A** Повтор по паре «идентификатор карты + идентификатор операции»: учтённая операция не меняет сумму и не вызывает второй push; порог умножается на 100; последние четыре цифры приходят в событии процессинга
- **B** Повтор по идентификатору операции; порог умножается на 100; последние четыре цифры берутся из справочника карт по идентификатору карты

**<a id="q-07"></a>Q-07** Перечень кодов ответа метода · можно ответить позже · кому: Архитектор · к [D-19](#d-19), [D-29](#d-29)

- **B** Успех только 200; неуспех: 400, 401, 403 (чужая карта), 404 (отсутствующая карта), 500; код 201 не используется
- **C** Успех 200 и 201 (201 при первом создании настройки); неуспех: 400, 401, 404, 500; код 403 не используется

**<a id="q-08"></a>Q-08** Учёт расходов при выключенном уведомлении · можно ответить позже · кому: Владелец продукта · к [D-09](#d-09)

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
