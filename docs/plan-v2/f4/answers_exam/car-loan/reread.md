#### <a id="d-01"></a>🟠 D-01. Метод чтения экрана договора с `baseRevision` не описан

- Действия клиента, п. 3, строка 68: «3. Приложение показывает действующий день и предлагает выбрать новое число»
- Обмен между системами, строка 81: «Приложение берёт baseRevision и суммы процентов «до изменения» из этого ответа»
- М-1, строка 85: «М-1. POST /loans/{loanId}/payment-day/previews принимает целое поле day и текущую редакцию baseRevision»
- О-2, строка 168: «О-2. Владелец может прочитать актуальный график через действующий экран договора сразу после подтверждения»

**Проблема.** Строка 81 говорит, что приложение берёт `baseRevision` и проценты «до» из ответа экрана договора, но метод, путь и тело этого ответа нигде не заданы. Без него М-1 (строка 85) не вызвать.  
**Сценарий.** Клиент открыл карточку договора: приложению нужны `baseRevision` и проценты «до», контракта чтения нет, разработчик приложения и сервиса реализуют по догадке.  
**Последствия.** Нельзя вызвать расчёт с корректным `baseRevision` и показать проценты «до»; интеграция и тесты невозможны.  
**Как исправить.** Описать метод чтения договора и графика: путь, поля, коды ошибок, формат сумм.  
**Было → стало.** Строка 85: «М-1. POST /loans/{loanId}/payment-day/previews принимает целое поле day и текущую редакцию baseRevision» → «GET `/loans/{`loanId`}` возвращает `currentRevision`, `paymentDay` и installments по Г-4; ошибки по таблице ответов.»

#### <a id="d-04"></a>🟠 D-04. Порядок проверок в М-2 расходится с порядком строк таблицы ошибок

- Обмен между системами › Подтверждение, строка 96: «Для первого запроса проверяются срок предложения, актуальность baseRevision, интервал Д-3 и право по Д-4»

- Ошибки и доступность, строка 139: «Истёк срок предложения | 410 PREVIEW_EXPIRED»
- Ошибки и доступность, строка 144: «При нескольких причинах отказа у новой операции порядок проверки такой же, как порядок строк таблицы сверху вниз»

**Сценарий.** Предложение истекло и до взноса четыре дня: по М-2 ответ 410 `PREVIEW_EXPIRED`, по таблице 422 `TOO_LATE`.  
**Последствия.** Разработчик и тестировщик выберут разный код отказа, на приёмке возникнет спор.  
**Как исправить.** Задать один порядок проверок и привести к нему либо М-2, либо порядок строк таблицы.  
**Было → стало.** Строка 96: «Для первого запроса проверяются срок предложения, актуальность baseRevision, интервал Д-3 и право по Д-4» → «Для первого запроса проверяются в порядке строк таблицы ошибок сверху вниз: интервал Д-3, право по Д-4, срок предложения, актуальность `baseRevision`.»  
**Вопрос владельцу.** Какой порядок верный: сначала срок предложения и редакция или сначала Д-3 и Д-4? → [Q-05](#q-05) (варианты ответа)

#### <a id="d-05"></a>🟠 D-05. Подпись клиента в М-2 не передаётся и не проверяется

- Действия клиента, п. 7, строка 72: «7. При подтверждении клиент подписывает показанную редакцию способом авторизации приложения»
- М-2, строка 94: «М-2. POST /loans/{loanId}/payment-day/changes принимает previewId и идентификатор подтверждения requestId»

**Проблема.** Шаг 7 (строка 72) требует подпись редакции, но М-2 (строка 94) принимает только `previewId` и `requestId`; нет поля подписи и кода отказа за неверную подпись.  
**Сценарий.** Приложение шлёт `previewId` и `requestId`, сервис не может проверить подпись и принимает заявку без неё.  
**Последствия.** Подтверждение без проверки авторизации; приёмка шага 7 невозможна.  
**Как исправить.** Добавить в М-2 поле подписи, правило проверки и код отказа при ошибке подписи.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 94: «М-2. #### <a id="d-06"></a>🟠 D-06. Размер платы за перенос Д-6 не задан

**Проблема.** Д-6 (строка 43) содержит только заглушку, но М-2 (строка 98) списывает плату, а `BALANCE_LOW` зависит от её суммы.

**Последствия.** Раздел не выполняет своей роли; при приёмке нечем подтвердить требования.  
**Как исправить.** Заполнить раздел до передачи в разработку или указать срок и ответственного.  
*Существенный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требование [R-16 / Д-6](#r-16 "Плата за перенос при подтверждении") · нашли: правило «заглушки и шаблон»*

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
