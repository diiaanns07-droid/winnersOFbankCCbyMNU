### 3.2. Критичные и существенные дефекты

#### <a id="d-01"></a>🔴 D-01. Не определено событие процессинга: авторизация или проведение

- Часть A › Цели, строка 23: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки»
- Ф-2, строка 38: «В расходы входят проведённые покупки»
- Часть A › Sequence Diagram, строка 43: «Процессинг → сервис расходов: проведена покупка»
- Часть A › Нефункциональные требования, строка 46: «Сервис передаёт push на отправку в течение минуты после получения события»

**Проблема.** Цель (строка 23) обещает уведомление «в момент покупки», а в расходы входят только «проведённые» покупки (строка 38); какое событие процессинга считать, не сказано. Авторизация и проведение расходятся на дни.  
**Сценарий.** Порог 50 000, расходы 48 500, покупка 1 500 авторизована 10-го, проведена 12-го: по толкованию «авторизация» push 10-го, по «проведение» — 12-го.  
**Последствия.** Цель «в момент покупки» и срок «в течение минуты» несовместимы с учётом только проведённых покупок; разработка принимает событие наугад, клиент получает запоздалое или ложное уведомление, приёмка превращается в спор.  
**Как исправить.** Зафиксировать, какое событие процессинга (авторизация или проведение) увеличивает расходы, какая сумма идёт в расчёт, и привести цель и срок в соответствие.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 38: «В расходы входят проведённые покупки» → «В расходы входят покупки в статусе <уточнить: авторизована или проведена (клиринг)>; учитывается <уточнить: авторизованная или проведённая> сумма; при отмене авторизации расходы не меняются.»  
**Вопрос владельцу.** Расходы растут при авторизации или при проведении (клиринге) покупки? → [Q-01](#q-01) (варианты ответа)  
**Варианты ответа:** A — расходы растут при авторизации покупки; B — расходы растут только при окончательном проведении (клиринге); C — расходы растут при авторизации, при проведении сумма лишь уточняется без повторного push  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-01](#r-01 "Уведомить клиента о достижении личного бюджета"), [R-06 / Ф-2](#r-06 "Правила учёта расходов и определения месяца"), [R-09](#r-09 "Последовательность взаимодействия процессинга, расходов, настроек, push"), [R-10](#r-10 "Передача push в течение минуты") · нашли: риски, аналитик, проверка набора*

#### <a id="d-03"></a>🔴 D-03. Ф-3 и Ф-4 по-разному задают число push в месяц

- Ф-3, строка 39: «На карту приходится максимум один такой push за календарный месяц»
- Ф-4, строка 40: «следующее достижение вызывает push независимо от истории предыдущей настройки»

**Проблема.** Ф-3 разрешает максимум один push на карту в месяц, Ф-4 требует push при следующем достижении порога независимо от истории.  
**Сценарий.** Порог 50 000 достигнут, push №1; порог изменён на 60 000, расходы достигли 60 000: по Ф-3 push нет, по Ф-4 есть.  
**Последствия.** Тест не может быть написан однозначно; клиент либо получает лишний push, либо пропускает уведомление о новом бюджете.  
**Как исправить.** Определить, лимит один на карту в месяц или один на каждую настройку порога, и привести Ф-3 и Ф-4 в соответствие.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Ф-4. После изменения порога счётчик push сбрасывается: <уточнить: допускается ли второй push в месяц после смены порога>.»  
**Вопрос владельцу.** Сколько push максимум получит клиент за месяц, если сменит порог после первого push? → [Q-03](#q-03) (варианты ответа)  
**Варианты ответа:** A — не более одного push на карту в месяц при любых сменах порога; B — один push на каждое значение порога в месяце; C — один push на карту в месяц, но смена порога выше текущих расходов сбрасывает право на…

#### <a id="d-07"></a>🟠 D-07. Архитектура и последовательность расходятся, компоненты названы по-разному

- Часть A › Архитектура решения, строка 26: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push»
- Часть A › BPMN схема процесса, строка 34: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение»
- Часть A › Sequence Diagram, строка 43: «Сервис расходов → настройки: получить порог карты»

- **B** Сумма покупки, вызвавшей достижение порога

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».
