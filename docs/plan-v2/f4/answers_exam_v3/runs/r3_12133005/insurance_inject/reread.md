#### <a id="d-01"></a>🟠 D-01. Нет метода расчёта стоимости без подключения страхования

- Часть A › Дизайн процесса UI, строка 31: «флажок «Страхование жизни» (по умолчанию снят), стоимость страхования, ставка со страхованием и без него»
- Часть A › Требования к интеграции, строка 57: «Приложение рассчитывает стоимость страхования, подключает его к заявке , оформляет отказ и получает данные полиса через дочерний…»
- Часть B › Общие параметры, строка 111: «Подключение страхования жизни к заявке на кредит наличными»
- Часть B › Метод отказа от страхования [добавлено: D-01], строка 223: «Отказ от страхования жизни в период охлаждения \[добавлено: D-01\]»

**Проблема.** Строка 57 обещает, что приложение рассчитывает стоимость и отдельно подключает страхование. В API описан один POST, который требует consent и сохраняет подключение (строка 111, строка 130). Метода расчёта до выбора клиента нет.  
**Сценарий.** Экран условий показывает стоимость при снятом флажке: единственный метод создаёт подключение и передаёт данные в СК до решения клиента.  
**Последствия.** Обещанную функцию нельзя реализовать и проверить по документу; объём работ по API недооценён.  
**Как исправить.** Описать метод для каждой обещанной операции (тип запроса, адрес, параметры, ответ, статусы) или убрать операцию из раздела интеграции.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Метод расчёта стоимости: <уточнить: URL и тело>; возвращает premium и rate без сохранения подключения и без consent.»

#### <a id="d-02"></a>🟠 D-02. Сумма возврата премии при отказе не определена

- Ф-4, строка 43: «на текущий счёт клиента возвращается <уточнить: вся премия или премия с удержанием, доля удержания> в течение 7 рабочих дней»
- критерий приёмки №2, строка 71: «Возвращено <уточнить: сумма возврата при премии 36 000 ₸>»

**Проблема.** В Ф-4 (строка 43), критерии приёмки (строка 71) и ответе метода отказа (строка 232) вместо суммы возврата стоит заглушка: неизвестно, возвращается вся премия или с удержанием и в какой доле.  
**Сценарий.** Выдача 1 марта, премия 36 000 ₸, отказ 10 марта: один разработчик вернёт 36 000 ₸, другой меньше; ожидаемый результат теста не определить.  
**Последствия.** Разработчик не сможет рассчитать refund, а тестировщик не напишет ожидаемый результат; возможны споры с клиентами о возврате.  
**Как исправить.** Зафиксировать правило возврата при отказе в период охлаждения и подставить его в Ф-4, критерий приёмки и метод отказа.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 43: «на текущий счёт клиента возвращается <уточнить: вся премия или премия с удержанием, доля удержания> в течение 7 рабочих дней» → «на текущий счёт клиента возвращается <уточнить: вся премия или премия за вычетом доли удержания> в течение 7 рабочих дней.»

#### <a id="d-03"></a>🟠 D-03. НФТ по времени отклика без времени, доли и нагрузки

## <a id="pe"></a>Приложение Е. Методика

Статическое ревью текста до разработки: программа не запускается. Документ нумеруется построчно; проверяющие роли (аналитик, тестировщик, архитектор, риски, набор целиком) предлагают кандидатов с дословными цитатами; программа находит каждую цитату в документе и сама определяет строку; судья объединяет дубли, отклоняет ложные и калибрует серьёзность; вердикт считает программа.

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
