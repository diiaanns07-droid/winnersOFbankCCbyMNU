### 3.2. Критичные и существенные дефекты

#### <a id="d-04"></a>🔴 D-04. Особое правило прогноза процентов расходится с Ф-3

- Ф-3, строка 38: «проценты начисляются на всю задолженность по покупкам расчётного периода с даты каждой покупки»
- Особые правила, п. 2, строка 127: «При частичном погашении прогноз процентов считается только на непогашенную часть суммы для погашения»

**Проблема.** Ф-3 (строка 38) и критерий строки 64 начисляют проценты на всю задолженность, а особое правило 2 (строка 127) считает прогноз только на непогашенную часть.  
**Сценарий.** Долг 80 000 ₸, внесено 50 000 ₸: по Ф-3 проценты на 80 000 ₸, `interestForecast` по методу — на 30 000 ₸.  
**Последствия.** Клиент занижает ожидание процентов и не может проверить прогноз. Тестировщик не может написать ожидаемое значение `interestForecast`.  
**Как исправить.** Привести особое правило 2 к Ф-3: база прогноза равна всей задолженности по покупкам расчётного периода.  
**Было → стало.** Строка 127: «При частичном погашении прогноз процентов считается только на непогашенную часть суммы для погашения» → «При частичном погашении прогноз процентов считается на всю задолженность по покупкам расчётного периода с даты каждой покупки, как в Ф-3.»  
**Вопрос владельцу.** Прогноз должен считаться на всю задолженность или только на остаток? → [Q-04](#q-04) (варианты ответа)  
**Варианты ответа:** A — на всю задолженность по покупкам расчётного периода с даты каждой покупки; B — только на непогашенную часть суммы для погашения с даты каждой покупки  
*Критичный, блокирует разработку и тестирование · критерий «Согласованность» (ISO/IEC/IEEE 29148:2018 п. 5.2.6; IEEE 830-1998 п. 4.3.4) · требования [R-07 / Ф-3](#r-07 "Начисление процентов при полном или частичном платеже"), [R-26](#r-26 "Прогноз процентов на непогашенную часть"), [R-15 / приёмка №2](#r-15 "Проценты начислены на 80 000 ₸ с даты каждой покупки"), [R-36](#r-36 "Прогноз процентов при непогашении") · нашли: тестировщик, архитектор, проверка набора*

#### <a id="d-05"></a>🔴 D-05. Не определено, какое событие считается «внесением» платежа

- Ф-3, строка 38: «Если клиент внёс сумму для погашения полностью до окончания платёжного периода включительно, проценты по покупкам расчётного…»
- Ф-5, строка 40: «Внесённый платёж уменьшает оставшуюся сумму для погашения»
- критерий приёмки №1, строка 63: «Внести 120 000 ₸ 25 марта в 14:00»

**Проблема.** Ф-3 (строка 38) и Ф-5 (строка 40) не задают, что значит «внёс»: инициирование клиентом, приём поручения или зачисление на счёт карты. Момент окончания 25-го (конец суток, пояс) тоже не задан.  
**Сценарий.** Клиент 25 марта 23:50 отправил 120 000 ₸, зачисление 26 марта: при одном толковании льгота сохранена, при другом утрачена, проценты с даты каждой покупки.  
**Последствия.** Клиент может потерять льготу или получить проценты по спорному платежу, а банк — жалобы; разработка не знает, какое событие принимать из процессинга, тестирование не может определить ожидаемый результат.  
**Как исправить.** Зафиксировать событие, по которому платёж считается внесённым (например, зачисление на счёт карты), и пояс с часом окончания 25-го числа; согласовать с критерием приёмки.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «Платёж считается внесённым в момент зачисления на счёт кредитной карты. Платёж, зачисленный не позднее <уточнить: час> 25-го числа по <уточнить: пояс, например UTC+5>, учитывается в льготном периоде.»  
**Вопрос владельцу.** Платёж считается внесённым при создании клиентом или при зачислении на счёт карты? Какой час 25-го числа и какой пояс — граница? → [Q-05](#q-05) (варианты ответа)  
**Варианты ответа:** A — не переносится; B — переносится на ближайший следующий рабочий день  
*Критичный, блокирует разработку и тестирование · критерий «Однозначность» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.2) · требования [R-07 / Ф-3](#r-07 "Начисление процентов при полном или частичном платеже"), [R-09 / Ф-5](#r-09 "Влияние платежей, возвратов и новых покупок"), [R-14 / приёмка №1](#r-14 "Проценты за покупки февраля начислены") · нашли: риски, аналитик*

#### <a id="d-08"></a>🟠 D-08. Перечень операций вне льготы неполон, «покупка» не определена

- Ф-1, строка 36: «Льготный период действует для покупок по кредитной карте»
- Ф-2, строка 37: «Снятие наличных и переводы с кредитной карты в льготный период не входят»

**Проблема.** Ф-2 (строка 37) исключает только снятие наличных и переводы; пополнение кошельков, платежи за услуги, комиссии не отнесены ни к покупкам, ни к исключениям.  
**Сценарий.** Пополнение электронного кошелька с карты на 10 000 ₸: входит в сумму для погашения или проценты с даты операции — документ молчит.  
**Последствия.** Неверная сумма для погашения и проценты клиенту, споры при приёмке и расхождение расчёта с процессингом.  
**Как исправить.** Дать закрытый перечень типов операций, входящих и не входящих в сумму для погашения, включая квази-кэш, платежи за услуги и комиссии.  
**Предлагаемая формулировка (места «<уточнить>» заполнит ответ владельца).** «В сумму для погашения входят покупки в торговых точках и в интернете. Не входят: снятие наличных, переводы, операции, приравненные к снятию наличных (квази-кэш), <уточнить: платежи за услуги, комиссии банка>.»  
**Вопрос владельцу.** Входят ли в льготный период платежи за услуги, пополнение кошельков и комиссии банка?  
*Существенный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-05 / Ф-1](#r-05 "Длительность льготного периода и даты периодов"), [R-06 / Ф-2](#r-06 "Расчёт суммы для погашения, исключения операций") · нашли: риски*

#### <a id="d-09"></a>🟠 D-09. Шаг 3 метода не получает возвраты покупок, нужные по Ф-5

- Ф-5, строка 40: «Возврат покупки, отражённый до окончания платёжного периода, тоже уменьшает оставшуюся сумму»
- Логика работы метода, п. 3, строка 120: «3. Получить из кредитного модуля последнюю выписку и платежи после даты выписки»

**Проблема.** Ф-5 (строка 40) требует уменьшать остаток на возврат покупки, а шаг 3 (строка 120) запрашивает только выписку и платежи.  
**Сценарий.** Выписка 80 000 ₸, возврат 10 000 ₸ 20 марта, платежей нет: по Ф-5 остаток 70 000 ₸, метод вернёт 80 000 ₸.  
**Последствия.** Клиент платит лишнее или видит неверный остаток, тест возврата не пройдёт.  
**Как исправить.** Добавить возвраты в шаг 3 и формулу шага 4.  
**Было → стало.** Строка 40: «Возврат покупки, отражённый до окончания платёжного периода, тоже уменьшает оставшуюся сумму» → «3. Получить выписку, платежи и возвраты покупок, отражённые после даты выписки и до конца платёжного периода. 4. Остаток = сумма выписки минус платежи минус возвраты, не менее 0.»  
**Вопрос владельцу.** Откуда метод берёт возвраты?  
*Существенный, блокирует разработку и тестирование · критерий «Полнота требования» (ISO/IEC/IEEE 29148:2018 п. 5.2.5; IEEE 830-1998 п. 4.3.3) · требования [R-09 / Ф-5](#r-09 "Влияние платежей, возвратов и новых покупок"), [R-21](#r-21 "Получение выписки и платежей из модуля"), [R-22](#r-22 "Расчёт остатка суммы и дней") · нашли: тестировщик*

#### <a id="d-10"></a>🟠 D-10. Нефункциональные требования без измеримых значений

**Где:** Часть A › Нефункциональные требования, строка 46: «Сведения о льготном периоде отображаются быстро и всегда актуальны»

**Проблема.** Строка 46: «быстро», «всегда актуальны», «своевременно» без времени отклика, допустимой задержки данных, перцентиля и момента отправки push.  
**Сценарий.** Ответ за 3 с на 95-м перцентиле и 9 с на 99-м: одна сторона считает «быстро», другая нет; push в 23:50 накануне — «своевременно» или нет.  
**Последствия.** Тестировщик не напишет нагрузочный тест с критерием прохождения, приёмка требования превратится в спор, а деградацию под нагрузкой банк увидит только в эксплуатации.  
**Как исправить.** Записать норматив измеримо: значение с единицей, точку начала и конца замера, долю событий (перцентиль) и нагрузку, при которой он выполняется.  
**Было → стало (места «<уточнить>» заполнит ответ владельца).** Строка 46: «Сведения о льготном периоде отображаются быстро и всегда актуальны» → «Сведения о льготном периоде отображаются не позднее <уточнить: N> с после открытия блока у <уточнить: 95> % запросов при нагрузке <уточнить: RPS>; данные отстают от кредитного модуля не более чем на <уточнить: N> минут. Push отправляется в течение <уточнить: N> минут после <уточнить: время суток> 22-го числа.»  
**Вопрос владельцу.** Каковы допустимое время отклика, задержка данных о платежах и время отправки напоминания?

#### <a id="d-11"></a>🟠 D-11. Источник данных для `totalDebt` и `interestForecast` не задан

- Часть A › Требования к данным, строка 49: «Хранить идентификатор карты, расчётный период, дату выписки, сумму для погашения в тиынах, сумму внесённых платежей в тиынах…»
- Логика работы метода, п. 3, строка 120: «3. Получить из кредитного модуля последнюю выписку и платежи после даты выписки»
- Часть B › Ответ, строка 159: «totalDebt | integer | ≥ 0 | Общая задолженность по карте на дату запроса, тиыны | total_debt»

**Проблема.** Шаг 3 (строка 120) получает выписку и платежи, а `totalDebt` (строка 159) и `interestForecast` нужны данные о покупках после выписки; в перечне данных (строка 49) их нет, `due_date` и `grace_status` тоже.  
**Сценарий.** При status = LOST приложение должно показать общую задолженность, но шаг 3 получает только выписку и платежи после неё, покупок после выписки не видно — `totalDebt` не собрать.  
**Последствия.** Разработчик вынужден гадать об источнике значений `totalDebt` и `interestForecast`.  
**Как исправить.** Указать источник `totalDebt` и данных прогноза (запрос в кредитный модуль) и дополнить перечень данных полями `due_date`, `grace_status`, `total_debt`.  
**Было → стало.** Строка 120: «3. Получить из кредитного модуля последнюю выписку и платежи после даты выписки» → «3. Получить из кредитного модуля последнюю выписку, платежи после даты выписки, общую задолженность на дату запроса и покупки расчётного периода с датами. Хранить также дату окончания платёжного периода и состояние льготного периода.»  
**Вопрос владельцу.** Из какого запроса приходит общая задолженность на дату запроса? → [Q-08](#q-08) (варианты ответа)

**Шкала серьёзности**

- 🔴 **Критичный** — два места документа дают несовместимый результат для одного входа; ключевое правило нельзя однозначно реализовать или проверить; нет информации, без которой основную функцию не реализовать.
- 🟠 **Существенный** — неоднозначность или неполнота, ведущая к неверной реализации или спору при приёмке; непокрытая ветка (ошибки, повторы, отмены, границы); риск ИБ; расхождение типов, единиц, терминов.
- 🟡 **Незначительный** — оформление, незаполненный шаблон, версия и согласования, отсутствие ID и приоритетов, стиль.

**Вердикт.** Критичный дефект, блокирующий разработку, — разработку начинать нельзя; то же для тестирования. Иначе при трёх и более существенных дефектах по направлению — «можно с условиями»: начинать части, не затронутые дефектами, и исправлять их параллельно. Иначе — «можно». Частичный прогон не даёт «можно»: в лучшем случае «с условиями».

**Сверка цитат.** Сравнение без учёта регистра, вида кавычек и тире, лишних пробелов и разметки; цитата ищется у указанной строки, затем во всём документе, ближе к требованию. Нечёткое совпадение (не ниже 92 %) допускается только рядом с указанной строкой.
