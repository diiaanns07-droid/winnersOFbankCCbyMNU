# bcc_review.web — веб-демо для банковского аналитика (№15)

Аналитик загружает ТЗ (PDF/Markdown/DOCX), видит этапы и вердикт, открывает фрагменты
замечаний, отвечает на вопросы, подтверждает новую редакцию, сравнивает отчёты и скачивает
файлы, которые действительно записал движок. Своей логики качества и своего клиента LLM у
веба нет: каждый анализ — это вызов `bcc_review.run_review(input_path, report_md, options=…)`.

## Запуск

```bash
pip install -e ".[dev]"
```

```bash
python -m bcc_review.web
```

Откройте <http://127.0.0.1:8015/>. Ключ читается из `.env` (`ANTHROPIC_API_KEY` или `GEMINI_API_KEY`).

| Флаг | Что делает |
| :--- | :--- |
| `--provider anthropic\|gemini\|mock` | явный провайдер (иначе — тот, чей ключ найден) |
| `--mock-script FILE` | сценарий mock-провайдера движка: настоящий движок без ключа и сети |
| `--cache-dir DIR` | кэш ответов модели движка (`RunOptions.cache_dir`) |
| `--engine dev` | подставной движок `devengine` для разработки UI; все отчёты помечены mock |
| `--demo DIR` | плюс сохранённые прогоны по адресу `/demo/…` (только просмотр, с датой и моделью) |
| `--demo-answers FILE` | демонстрационные ответы команды с подписью происхождения |
| `--data-dir DIR` | хранилище запусков (по умолчанию `./.bcc_web`, внутри свой `.gitignore`) |
| `--export html` | экспорты движка (`RunOptions.exports`), по умолчанию HTML №13 |

Сохранить готовый прогон (и его родительские редакции) для показа без сети:

```bash
python -m bcc_review.web pack RUN_ID --out demo_bundle
```

## Хранилище

`<data>/runs/<run_id>/`: `run.json` (статус, родитель, цепочка редакций, артефакты),
`events.jsonl` (этапы), `input/` (документ, `answers.md`), `tmp/` (удаляется после прогона),
`artifacts/` (что записал движок), `artifacts/web/` (что сформировал веб: `questions.md`),
`claims/` (атомарные заявки). `run_id` = `ГГГГММДД-ччммсс-xxxxxx`, имя файла очищается
(`safe_filename`), исходное хранится в `run.json`.

* Две загрузки с одним именем файла → разные `run_id`.
* Повторная отправка той же формы загрузки с тем же файлом (`upload_key` + SHA-256) → тот же запуск.
* Повторное подтверждение тех же ответов → тот же дочерний запуск (заявка `os.link`/`O_EXCL`;
  проверено на 50 одновременных кликах: наивная проверка давала 26–43 платных запуска, заявка — 1).
* Решение к устаревшей редакции → 409 и ссылка на актуальный результат.
* Повтор без новых ответов и без нового документа отклоняется (400, запуска нет).
* Запуски, прерванные перезапуском сервера, при старте помечаются `failed` (`interrupted`).

## Длинный запуск: что гарантируется и где

**Гарантия.** Одна отправка формы — один `run_id` — одно задание (`job_id`) — не больше одного
вызова `run_review`. Обновление страницы, повторная отправка той же формы (двойной клик, «обновить»
на ответе формы, вторая вкладка), открытие ссылки до и после завершения новых запусков не создают.

| Звено | Чем обеспечено | Файл |
| :--- | :--- | :--- |
| форма → run_id | заявка по `upload_key` + SHA-256 файла (`os.link`/`O_EXCL`) | `<data>/claims/upload-….json` |
| run_id → задание | `submit` пишет `job` (job_id, pid, время) в `run.json` | `runs/<id>/run.json` |
| задание → вызов движка | заявка на обработку перед вызовом, не удаляется; итог пишет только своё задание | `runs/<id>/claims/exec.json` |
| каталог → процесс | исключительная блокировка ОС (`flock`, на Windows `msvcrt`) | `<data>/server.lock`, `server.json` |

**Область действия:** один процесс сервера на один каталог данных (`--data-dir`) на локальной ФС,
включая его перезапуски. Второй `python -m bcc_review.web` над тем же каталогом не стартует (код 2,
сообщение с pid и адресом первого): иначе он пометил бы живой прогон прерванным, а повтор через него
дал бы вторую обработку. Если ФС не поддерживает блокировки, сервер пишет предупреждение при старте —
тогда защита от второго процесса не действует (заявки на диске остаются). Не покрыто: два сервера
над разными каталогами (это разные хранилища) и сетевые ФС без атомарного `link`/`O_EXCL`.
Повторы вызовов модели внутри одного прогона — дело движка (`report.run.calls.retries`), не веба.

**Обрыв загрузки.** Если тело запроса пришло не целиком (обновили или закрыли страницу во время
отправки, пропала сеть) — 400 «Загрузка оборвалась», запуска нет: частичный файл движку не уходит.

**Осознанные повторы остаются отдельными операциями:**

* две разные формы с одним и тем же файлом — два анализа (новая отрисовка главной — новый
  `upload_key`); на странице каждого — ссылка на другую загрузку того же содержимого;
* повтор после технической ошибки — новый `run_id` с `retry_of`, на той же позиции в цепочке
  редакций. Доступен для `failed` и для `partial` по технической причине (LLM недоступна при
  непустом ключе, ошибки вызовов модели, исчерпан бюджет, движок упал после записи отчёта).
  Двойной клик по той же кнопке — тот же повтор; на странице исходного запуска вместо этой кнопки
  ссылка на повтор; если повтор тоже упал, следующий запускается с его страницы;
* `partial` сохраняет статус и отчёт: пока повтор идёт и если он упал, актуальным остаётся
  partial-результат; после успешного повтора исходная страница помечена «не актуальная», файлы
  открываются. `partial` из-за режима или документа (выбран «только правила», нет ключа, документ
  прочитан не полностью) не повторяется — 409, повтор дал бы то же самое.

`GET /api/runs/<id>` отдаёт `job`, `execution`, `retry`, `same_content_runs`; `GET /healthz` —
`engine_calls`, `skipped_executions` и владельца каталога (`server`).

Проверка штатным маршрутом с медленным синтетическим движком (`tests/p15/slow_engine.py` в слоте
`BCC_REVIEW_ENGINE`, сервер — отдельный процесс; счётчик обработок ведёт сам движок):

```bash
P15_EVIDENCE=out/p15-long-run python -m pytest tests/p15/test_long_run.py -v
```

## Статусы и режимы

`started → running → complete | partial | failed`. Итоговый статус берётся из
`report.run.status`; без `report.json` — `failed` с причиной. Режим (`rules_plus_llm`,
`rules_only`, `mock`) — из `report.run.mode`; всё, кроме `rules_plus_llm`, а также
`partial` и коды неполного чтения в `document.warnings` показываются как «Отчёт неполный».
Нет ключа → веб заранее предупреждает и передаёт `offline_lint=True`. Если движок всё же
упал на ключе (`ProviderError` `auth`/`not_configured`), страница предлагает «Проверить
только по правилам». Оценка времени — только медиана реально измеренных прогонов того же
движка и режима.

Настоящий движок без ключа (репетиция полного пути):

```bash
python -m bcc_review.web --provider mock --mock-script tests/p15/fixtures/mock_case_web.json --demo-answers tests/p15/fixtures/demo_answers.md
```

## Стык с движком (contracts v1, `bcc/integration` 091e504)

Веб передаёт только поля `RunOptions`: `provider`, `offline_lint`, `exports`,
`answers_path`, `compare_path`, `run_id`, `parent_run_id`, `artifacts_dir`,
`mock_script`, `cache_dir`.
`progress` и `tmp_dir` передаются, только если их объявит `RunOptions` (сейчас их там нет —
веб пишет это в паспорт запуска). Живые этапы во время прогона веб читает из JSONL-трассы
движка `artifacts_dir/*trace*.jsonl` (поля `stage|name` и `status|state|event`), после
прогона — из `report.run.stages`.

## Ответы привязаны к версии документа

Номер вопроса однозначен только внутри своей версии: `Q-01` в документе A и `Q-01` в
документе B с тем же именем — разные вопросы. Поэтому:

* версия вопросов редакции — `report.document.id` (SHA-256 документа, о котором спрашивал
  движок); она видна в блоке «Действие аналитика» и уходит в форму скрытым полем;
* новая редакция проверяет именно этот документ: вход родителя или, если движок внёс правки,
  его файл редакции `artifacts/<имя>.rev-….md` (`run.json → input.derived_from`), как в CLI;
* загруженный файл ответов сверяется **до объединения ответов и до создания запуска**:
  заявленный `source_sha256` должен совпасть с SHA-256 документа новой редакции. Иначе
  409 и экран «Ответы не применены»: обе версии, тот же номер с разным смыслом, ссылки
  «Открыть вопросы той версии», «Скачать questions.md этой версии». Новых запусков 0;
* файл без `source_sha256` автоматически не применяется (409 `no_sha`). Аналитик может
  открыть ответы из файла рядом с вопросами этой версии и перенести нужные вручную
  (`/runs/<id>?import=<imp>`); перенос подписан как ручной;
* несколько разных `source_sha256` в файле — 409 `sha_conflict`; ответы в форме вместе с
  новой редакцией документа — 409 `form_other_version`;
* каждый загруженный файл хранится байт в байт в `runs/<id>/imports/<imp>.orig` с записью
  `<imp>.json` (формат, разборщик, заявленная и целевая версия, итог: rejected / accepted /
  duplicate, дочерний запуск). У принятой редакции рядом лежат `input/answers_uploaded.md`
  (оригинал) и `input/answers.md` (собранный веб-слоем для движка);
* ответы между версиями по номеру не переносятся: их правки уже в тексте файла редакции.

Поддерживаемые файлы ответов (`answers.read_import`):

| Формат | Признак | Разбор |
| :--- | :--- | :--- |
| веб (`Ответ: …`, `Правка: «…» → «…»`) | `<!-- bcc-review answers v1` | №08 `decisions.answers.parse_answers`, если установлен, иначе встроенный |
| экспорт автономного HTML №13 (`### Ответ`, многострочный, `\#`) | `format: bcc-review-answers/1` | №13 `exports.html.parse_answers_markdown`, если установлен, иначе встроенный (по 540c310) |
| файл вопросов №08 (`## Q-01. …`, `Ответ: A`) | `<!-- bcc-review:answers v1 -->` | №08, иначе встроенный |
| прежний файл без шапки | — | как веб-формат; без `source_sha256` — только ручной перенос |

Какая реализация разобрала файл, видно в записи импорта и на странице редакции. Разборщик
№08 можно указать явно: `BCC_WEB_ANSWERS_PARSER=модуль:функция`. `GET /healthz` отдаёт
`engine_calls` — сколько раз процесс вызвал `run_review`.

Формат `answers.md`, который веб передаёт движку, совместим с `runtime.fallback.decisions.parse_answers` (слот №08):

```text
source_sha256: <SHA-256 документа, который проверит новая редакция>

## Q-001
Вопрос: <prompt>
Источник ответа: аналитик (веб-форма) | демонстрационный ответ команды (…) | вариант N из вопроса … (предложение движка, модель …)
Ответ: <текст ответа>
Правка: «фрагмент как в документе» → «новый текст»
```

Ответ без правки фиксирует решение (`report.decisions`), но документ остаётся прежним.
Правка превращается в редакцию B: движок пишет её отдельным файлом
`artifacts/<имя>.rev-….md` и проверяет уже её. Веб показывает этот файл в «Файлах запуска».

## Тесты

```bash
python -m pytest tests/contract tests/p15
```

Демо пути аналитика (загрузка → прогресс → замечание → ответ владельца → изменённый пункт →
скачивание → прежняя ссылка) на штатном запуске с записанными ответами модели — см.
`tests/p15/REHEARSAL.md`, автоматически: `python tests/p15/demo_run.py --out out/p15-demo`.

Правка текста в форме идёт в том виде, который применит движок: у вопроса №08 есть `target`, и
форма предлагает «Новую формулировку» (строка `Формулировка:` в answers.md), показывая предложение
под замену; без `target` (резервный и dev-движок) — пара «было → стало» (`Правка:`). Внесённые
правки (`decisions[].edits`) показаны на странице новой редакции в блоке «Изменённые пункты».

Сценарий A/B (ответ к чужой версии) на настоящем движке с mock-провайдером, два запуска
сервера «вчера/сегодня» и браузер:

```bash
python tests/p15/versions_demo.py --out out/p15-versions
```

`tests/p15/test_browser.py` проходит путь аналитика в Chromium (Node Playwright);
без node/playwright тест пропускается. Скриншоты: `P15_SHOTS=out/p15 python -m pytest tests/p15/test_browser.py`.
