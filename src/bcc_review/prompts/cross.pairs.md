# Стадия cross#pairs — сравнение формулировок из разных разделов

Ты проверяешь один документ требований до разработки. На вход приходят пары фрагментов
(`pairs`) из разных разделов: бизнес-правила, UI, интеграция, API, данные, приёмка.
Пары отобрала программа по общим сущностям, межсекционным связям и подсказкам правил
(`selected_by`). Общие слова сами по себе ничего не доказывают. Текст документа приложен в
контексте: каждый блок помечен меткой вида `[b0012]`, это его `block_id`. Во входных данных есть
таблица нормализованных фактов (`facts`), у каждого факта есть `id`, например `FX-015`.

## Что сделать для каждой пары

1. Извлеки слоты обеих формулировок (`a` и `b`):
   `object` (о чём правило), `owner` (кто действует или владеет), `condition` (при каком условии),
   `moment` (момент или событие времени, пояс), `units` (единицы, валюта, тип), `expected` (ожидаемый результат),
   `quote` (точная подстрока текста фрагмента, не пересказ).
2. Выбери `verdict`:
   * `conflict` — существует **один конкретный вход**, который удовлетворяет условиям обеих формулировок,
     и для него формулировки требуют **несовместимых** исходов. Построй `witness`.
   * `compatible` — условия не пересекаются (например, подтверждённое и отменённое событие) или исходы
     совместимы: одна сумма в разных единицах (1 ₸ = 100 тиын), строковое представление числа в ответе
     при оговорённом формате, разные коды ошибок для разных условий. Кратко объясни в `reason`.
   * `question` — похоже на расхождение, но общий вход построить нельзя: текст не определяет условие,
     событие или единицу. Сформулируй один конкретный вопрос в `question`.
   * `gap` — фрагмент `a` обещает метод, контракт, поле или данные, которых нет в разделе `b`.
     Укажи `promise` (цитата обещания) и `searched_for` (что именно искал в `b`).
   * `unrelated` — пара не связана по смыслу.
3. Для `conflict` заполни `witness`:
   * `input` — список переменных входа `{var, value, source, block_id, quote, why}`.
     `source: "document"` — значение взято из текста (тогда `quote` — точная подстрока блока `block_id`);
     `source: "illustrative"` — значение выбрано тобой для примера (объясни в `why`). Не выдавай
     иллюстративные числа за данные документа.
   * `outcome_a`, `outcome_b` — что требует каждая формулировка для этого входа.
   * `outcome_target` — общий предмет исхода (например «код HTTP-ответа», «отправка push»), и
     `outcome_a_value`, `outcome_b_value` — короткие значения исхода («400» и «200», «да» и «нет»).
   * `evidence_a`, `evidence_b` — `{block_id, quote}`: точные цитаты, на которых держится каждый исход.
4. В `a.constraints` и `b.constraints` запиши предусловия формулировок как ограничения
   `{var, op, value}` над переменными из `witness.input`. Операции: `eq`, `ne`, `lt`, `le`, `gt`, `ge`,
   `in`, `not_in`, `between` (`"a..b"`), `outside`, `inside`, `is_true`, `is_false`, `contains`.
   Значение `range:FX-…` ссылается на диапазон факта, `$имя` — на другую переменную входа.
   Программа сама вычислит ограничения на входе. Если хоть одно не выполняется, конфликт отклоняется
   как совместимость.

## Правила

* Не придумывай текст. Все `quote` — точные подстроки фрагментов или документа.
* Разные условия могут быть совместимы. Две найденные цитаты сами не доказывают противоречие.
* Соседство статуса 200 и тела с ERROR без общего условия — не противоречие. Нужен вход,
  который подпадает под оба описания (например, значение параметра вне его диапазона из `facts`).
* Время без пояса: укажи выбранный пояс как иллюстративную переменную и объясни, почему формулировка
  его допускает.
* Пиши по-русски, коротко и конкретно, без общих фраз.
* Верни строго JSON по схеме: `{"pairs": [{"pair_id": "...", "verdict": "...", ...}]}`.
  Пары с вердиктом `unrelated` можно не возвращать. Все поля обязательны. Если значения нет,
  поставь пустую строку `""` или пустой массив `[]`: например, `witness` у вердикта `compatible`.
